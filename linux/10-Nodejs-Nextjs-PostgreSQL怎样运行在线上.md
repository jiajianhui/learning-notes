# 10. 网站真的上线了：Next.js、Express 与 PostgreSQL 在线上碰头

前面捡到的东西看起来很散：Linux、SSH、端口、Docker、域名、证书。现在把它们全部摆上桌，拼成一个从浏览器真的能打开的网站：

```text
浏览器
-> HTTPS 域名
-> 反向代理
-> Next.js 页面或 Express API
-> Prisma
-> PostgreSQL
```

这一站不绑定某个项目仓库。先看懂整台机器怎样合作，之后再去 1Panel 部署 Mini CMS，就不会只剩下一连串不知道作用的点击。

## 先把所有角色请到同一张桌上

```text
互联网
├── admin.example.com:443
└── api.example.com:443
          ↓
云安全组和 UFW
          ↓
OpenResty / Caddy / Nginx
├── 127.0.0.1:3000 -> Next.js
└── 127.0.0.1:3001 -> Express
                          ↓
                 postgres:5432
                          ↓
                    数据卷与备份
```

公网只需要 80、443 和受限的管理入口。应用端口和数据库端口留在服务器内部。

---

## `npm run dev` 不能通宵值班

开发环境重视热更新和调试：

```text
npm run dev
```

生产环境需要：

```text
安装锁定依赖
-> 生成 Prisma Client
-> 构建 TypeScript / Next.js
-> 应用已提交的数据库迁移
-> 使用稳定启动命令
-> 由 Docker 或 systemd 监督
```

不能把 Next.js 开发服务器或 `tsx watch` 直接当长期生产方式。

---

## 有些变量上车前就要写好

服务器运行时读取：

- `DATABASE_URL`。
- `PORT`。
- Session、Cookie 或签名密钥。
- CORS 允许来源。
- 日志级别和运行环境。

Next.js 浏览器端公开变量常在构建时写入静态资源，例如：

```text
NEXT_PUBLIC_API_BASE_URL
```

只在容器启动时修改它，已经构建好的浏览器代码可能不会变化。部署时要明确变量是构建时还是运行时读取。

真实 `.env` 不进入 Git。`.env.example` 只保留字段名和非敏感示例。

---

## 数据库醒了，不代表表结构已经就位

```text
PostgreSQL 容器启动
-> 数据库进程可以接受连接

prisma migrate deploy
-> 按仓库中已有迁移更新生产表结构
```

生产环境不使用 `prisma migrate dev` 创建临时迁移。修改结构前先确认备份，迁移成功也不代表业务数据已经验证。

---

## 反向代理是站在 443 门口的接待员

- 监听公网 80 和 443。
- 管理 HTTPS 证书和跳转。
- 根据域名或路径选择上游服务。
- 把真实协议和客户端信息传给应用。
- 记录入口访问日志。

它不负责：

- Express 业务校验。
- 用户认证与授权。
- Prisma 迁移。
- PostgreSQL 数据备份。

---

## 1Panel 给你按钮，但运行关系仍要留在代码里

例如使用 1Panel 时，可以通过它管理：

```text
Docker Compose
OpenResty 反向代理
SSL 证书
防火墙
日志与备份任务
```

项目仍应保留 Dockerfile、Compose、环境变量示例、迁移和启动命令。换一台 Linux 服务器时，不能只有原面板中的点击记录。

---

## 上线不等于故事结束

健康检查：

```text
GET /api/health
```

日志至少回答：

- 哪个方法和路径被请求。
- 返回什么状态码。
- 花了多长时间。
- 未知错误在服务器内部是什么。

备份至少覆盖：

- PostgreSQL 逻辑备份。
- 上传文件或持久数据卷。
- Compose 和非敏感配置。
- 恢复步骤。

备份任务显示成功还不够，要把备份恢复到测试环境验证。

---

## 第一次搬家与以后换家具

首次部署：

```text
准备服务器和网络
-> 获取固定版本代码
-> 写入生产环境变量
-> 构建镜像
-> 启动数据库
-> 应用迁移
-> 启动应用
-> 配置反向代理和 HTTPS
-> 外部验证
-> 配置备份并做恢复测试
```

更新：

```text
确认版本和变更
-> 备份数据
-> 获取新代码
-> 重建镜像
-> 应用迁移
-> 替换容器
-> 检查健康、日志和业务链路
```

回滚代码不一定能回滚数据库结构。发布前要判断迁移是否向后兼容。

## 上线前的口头彩排

不看图，从浏览器开始讲一遍：

```text
HTTPS 请求怎样从 443 到达 Next.js 或 Express？
Express 为什么用 postgres:5432，而不是 localhost？
哪个变量必须在 Next.js 构建前确定？
数据库启动、迁移、备份和恢复分别发生什么？
如果页面突然打不开，去哪里看第一条线索？
```

能把这段故事讲顺，你已经不只是“会在面板里部署”，而是知道一套 Web 应用为什么能在线上活着。
