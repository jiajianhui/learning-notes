# 08. 穿过三道门：公网 IP、安全组、防火墙与 HTTPS

你在浏览器敲下域名，请求并不会一下跳进 Express。它更像一个访客，要先穿过云平台的大门，再穿过 Linux 的门，最后还要找到真正营业的柜台：

```text
互联网
-> 云安全组
-> Linux 防火墙
-> 监听地址和端口
-> 应用进程
```

阿里云控制台和 Linux 终端都能看到“端口”，正是因为它们分别看守其中一层。

## 云控制台管院子，Linux 管屋里

| 云控制台 | Linux 终端 |
|---|---|
| 创建、停止、重装实例 | 用户、文件和软件 |
| CPU、内存和磁盘规格 | 进程、服务和日志 |
| 公网 IP、私网和安全组 | 防火墙和监听端口 |
| 快照和云备份 | 应用数据和数据库备份 |

安全组位于实例外部。即使 Linux 内部防火墙关闭，安全组仍可能拦住流量。

## 先认清现在已经开着的门

第 04 章创建服务器时，只允许自己的可信公网 IP 进入 22。现在先不要增加规则，在两个位置各看一次：

```text
阿里云控制台
-> 找到实例绑定的安全组和入方向规则

Ubuntu 服务器
-> 运行 ss -lntp 查看真正监听的地址与端口
```

安全组“允许 8000”不会自动启动第 06 章的练习网页；反过来，进程监听 `127.0.0.1:8000`，也不会因为服务器有公网 IP 就突然暴露给全世界。

## 哪几扇门真的需要朝全世界打开

| 端口 | 用途 | 推荐来源 |
|---|---|---|
| 22 | SSH | 只允许自己的可信公网 IP |
| 80 | HTTP、证书验证和 HTTPS 跳转 | 公开网站可允许所有来源 |
| 443 | HTTPS | 公开网站可允许所有来源 |
| 面板端口 | 服务器管理面板 | 只允许自己的可信公网 IP |
| 3000 / 3001 / 3002 | Next.js 和 Express | 只在服务器内部，由反向代理访问 |
| 5432 | PostgreSQL | 不公开，只允许应用需要的内部连接 |

改变 SSH 默认端口可以减少部分扫描噪声，但不能替代密钥登录、来源限制、更新和最小权限。

## 80 和 443 到底是什么

端口可以先理解成一台机器上的门牌号。浏览器访问网站时，通常把两个默认门牌藏起来了：

```text
http://example.com
-> 默认寻找 80

https://example.com
-> 默认寻找 443
```

- **80 是 HTTP 的默认端口。**正式网站常用它接住旧的 `http://` 请求，再跳转到 HTTPS；某些证书签发流程也会暂时通过 80 验证域名。
- **443 是 HTTPS 的默认端口。**浏览器会先建立 TLS 加密连接，并用证书确认访问的是预期域名，再在其中传输 HTTP 请求与响应。
- **3000、3001 等是应用内部端口。**浏览器通常不直接找它们，而是由 OpenResty、Nginx 或 Caddy 从 443 反向代理过去。

**放行是允许连接通过，监听是程序正在这个地址和端口接收连接。** 安全组和 UFW 都允许 443 后，仍然需要 OpenResty 等程序监听 443。可以在服务器检查：

```bash
sudo ss -lntp | grep -E ':(80|443)[[:space:]]'
```

还没安装反向代理时没有输出很正常。第一轮只练服务器时继续只开受限的 22；等第 10 章真的准备域名、证书和公开网站时，再在安全组与 UFW 同时放行 80、443。

## 在 Ubuntu 里再设一道门

UFW 是 Ubuntu 常见的防火墙管理工具。

远程服务器启用前，先允许当前 SSH 端口：

```bash
sudo ufw allow 22/tcp
sudo ufw enable
sudo ufw status verbose
```

如果 SSH 使用其他端口，要替换 22。操作前确认云安全组、网页终端和回滚方式可用，保留现有 SSH 会话。

真正准备公开网站时再增加：

```bash
sudo ufw allow 80/tcp
sudo ufw allow 443/tcp
sudo ufw status verbose
```

同时还要在阿里云安全组增加 80、443 入方向规则。`ufw allow` 只修改 Ubuntu 屋里的门，不会替你修改云平台院子的大门。

云安全组和 UFW 都要符合预期，不能只配置其中一个就认为完成。

## 一次 HTTPS 请求怎样到达 Express

以第 20A 章的 `https://api.example.com/api/public/articles` 为例：

```text
浏览器通过 DNS 查询 api.example.com 对应的服务器 IP
-> 连接服务器的 443 端口，云安全组和主机防火墙允许通过
-> 监听 443 的 OpenResty 与浏览器建立 TLS 连接，浏览器验证网站证书
-> 浏览器在加密连接中发送 HTTP 请求：GET /api/public/articles
-> OpenResty 转发到 http://127.0.0.1:3001/api/public/articles
-> Express 查询数据库，结果经 OpenResty 返回浏览器
```

DNS 的 A 记录指向 IPv4 地址，AAAA 记录指向 IPv6 地址。第 20A 章先配置 A 记录，把管理端和 API 两个子域名都指向同一台服务器。DNS 负责找到地址，之后由端口和网站配置把请求交给对应程序。

### Nginx、OpenResty 和反向代理是什么关系

Nginx 是接收网站请求的服务程序，可以直接返回静态文件，也可以把请求转发给其他应用。**反向代理就是后一种工作方式**：接收请求、选择目标应用、转发请求，再把响应交还给调用方。

OpenResty 基于 Nginx，增加了 Lua 等扩展能力。Mini CMS 使用它处理域名、HTTPS 和请求转发，当前不需要学习 Lua。1Panel 提供管理界面，实际接收浏览器请求的是它管理的 OpenResty。

上面链路中的 `127.0.0.1` 指云服务器自身。HTTPS 在 OpenResty 这一层处理，再通过本机 HTTP 转发给 Express。具体网站配置在[后端 20A 第 8～9 步](../backend/backend-system-learning/20A-用1Panel和Docker-Compose部署MiniCMS.md#第-8-步把两个子域名分别转发到管理端和-api)完成。

### HTTPS 证书与 SSH 密钥分别证明什么

| 场景 | 验证什么 | 对应材料 |
|---|---|---|
| Mac 用 SSH 密钥登录服务器 | 服务器验证客户端能否登录指定账号 | 客户端私钥、服务器 `authorized_keys` 中的公钥 |
| SSH 客户端核对服务器身份 | 确认连接的是预期服务器 | 服务器主机密钥、本机 `known_hosts` 记录 |
| 浏览器访问 HTTPS 网站 | 浏览器验证证书是否可信、是否匹配域名，以及服务端是否持有配套私钥 | OpenResty 提供证书并用私钥参与握手；私钥留在服务端 |

HTTPS 是通过 TLS 保护的 HTTP。证书把域名与公钥等身份信息联系起来，TLS 协议负责建立加密连接并保护后续传输。面板里的“SSL 证书”通常就是这里的网站证书；它与 SSH 登录密钥用途不同，应分别配置和保管。

申请网站证书时，证书服务商还要确认你控制这个域名，通常通过 DNS 记录或 HTTP 文件验证。具体操作见[20A 第 9 步](../backend/backend-system-learning/20A-用1Panel和Docker-Compose部署MiniCMS.md#第-9-步申请证书并启用-https)；SSH 认证过程回看[第 04 章](./04-SSH-从Mac安全连接Linux.md#一次-ssh-密钥登录怎样完成)。

## 1Panel 是控制台，不是另一套魔法

1Panel 这类面板可以帮助管理：

- Docker 和 Compose。
- OpenResty 网站与反向代理。
- SSL 证书。
- 防火墙规则。
- 日志、备份和计划任务。

它仍然运行在 Linux 上，不会替代：

- 云安全组。
- SSH 救援能力。
- 应用自己的 Dockerfile 和 Compose。
- 数据库迁移、环境变量和恢复验证。

面板端口也属于管理入口，必须限制来源、使用强密码和 MFA，并保留 SSH 恢复能力。

## 安装面板和应用之前巡视一圈

```text
1. 确认当前账号仍能通过 SSH 密钥登录
2. 安全组只开放当前真正需要的端口
3. 更新软件索引并检查更新
4. 配置 UFW，先保证 SSH 可继续连接
5. 确认时间、磁盘和内存
6. 再安装 Docker、面板或应用
```

检查：

```bash
cat /etc/os-release
uname -m
timedatectl
free -h
df -h
ss -lntp
```

## 开门前的最后巡视

拿出一张纸，只画允许进入的箭头：

```text
自己的公网 IP -> 22 和面板端口
所有访客 -> 80 / 443
反向代理 -> 3000 / 3001
应用 -> 5432
```

如果你没有画出“互联网 → 5432”，也能说清安全组与 UFW 各守哪一层，这台学习服务器的门禁设计就合格了。
