# 06. 网页失踪案：沿着进程、日志和端口找到它

案发现场很普通：昨天还能打开的页面，今天只剩一句 `Connection refused`。

这次不靠想象。你会先让一个网页活起来，再亲手停掉它，最后沿着进程、端口和请求把“失踪原因”找出来。

先别重启所有东西。网页从浏览器走到应用，要经过一串可以逐个盘问的对象。你已经见过其中几个：

```text
Next.js：localhost:3000
Express：localhost:3001
PostgreSQL：localhost:5432
```

线上还会出现 SSH 22、HTTP 80 和 HTTPS 443。它们底层使用同一个端口概念，但属于不同主机、进程和网络层。接下来把它们都列为“嫌疑人”。

## 先制造一宗可以复现的案子

在 Mac 的第一个终端登录服务器：

```bash
ssh linux-learning
```

确认 Python 3 可用，然后准备一张最小网页：

```bash
python3 --version
mkdir -p ~/linux-playground/web-case
printf "<h1>the page is alive</h1>\n" > ~/linux-playground/web-case/index.html
cd ~/linux-playground/web-case
python3 -m http.server 8000 --bind 127.0.0.1
```

如果 `python3` 不存在，使用第 05 章已经学过的 APT 安装 `python3`，再重新启动。最后一条命令会一直占住当前终端，这是正常的前台进程。

在 Mac 新开第二个终端，再次登录同一台服务器：

```bash
ssh linux-learning
curl http://127.0.0.1:8000
ss -lntp | grep ':8000'
ps aux | grep '[p]ython3 -m http.server'
```

现在应该同时看到网页内容、8000 监听和 Python 进程。先别急着停网页。打开 Mac 的第三个终端，不要先登录服务器，直接把第 04 章的 SSH 隧道真正挖通：

```bash
ssh -N -L 8080:127.0.0.1:8000 linux-learning
```

这条命令没有提示符是正常的，它正在维持隧道。现在用 Mac 浏览器打开 `http://localhost:8080`，应该能看到服务器里的 `the page is alive`。数据走的是：

```text
Mac 浏览器 localhost:8080
-> SSH 隧道
-> 服务器 127.0.0.1:8000
-> Python 网页
```

回到第三个终端按 `Control-C` 关闭隧道。然后回到第一个终端按 `Control-C` 停止 Python，再在第二个终端执行：

```bash
curl http://127.0.0.1:8000
ss -lntp | grep ':8000'
```

这次 `curl` 出现 `Connection refused`、监听结果消失，案件已经完整复现：进程结束后，没有程序继续接住 8000。

## 第一位嫌疑人：进程根本没活着

- 进程是正在运行的程序实例。
- 服务是需要长期运行、可被系统管理的进程。
- `systemd` 是 Ubuntu 常见的服务管理系统。

查看：

```bash
ps aux
top
systemctl status ssh
```

`top` 按 `q` 退出；`systemctl status` 如果进入分页视图，也按 `q` 返回 Shell。

本地执行 `npm run dev` 是前台开发进程；生产 Node.js 需要由容器重启策略、systemd 或其他进程管理方式监督，不能依赖一个一直开着的 SSH 窗口。

---

## 日志是现场录像

刚才第一个终端中出现的 HTTP 请求记录，就是应用直接写到标准输出的日志。由 systemd 管理的系统服务，则可以去系统日志中查：

```bash
sudo journalctl -u ssh
sudo journalctl -u ssh -f
```

- `-u ssh` 只看 SSH 服务。
- `-f` 持续等待新日志，按 `Control-C` 结束。

第 09 章进入容器后，Compose 项目通常还会使用：

```bash
docker compose logs
docker compose logs -f api
```

这些命令要在真实 Compose 文件所在目录执行；本章还没有 Compose 项目，不要现在照着运行。

日志不应该记录密码、完整 Cookie、令牌或私钥。

## 端口只是柜台号码

| 地址 | 谁在监听 | 当前怎样理解 |
|---|---|---|
| Mac `localhost:3000` | Next.js 开发进程 | 前端开发服务器 |
| Mac `localhost:3001` | Express 开发进程 | API 开发服务器 |
| Mac `localhost:5432` | Docker 端口转发 | PostgreSQL 容器入口 |
| 服务器 `127.0.0.1:8000` | 刚才的 Python 进程 | 只供服务器本机检查的练习网页 |
| 服务器公网 IP:22 | `sshd` | SSH 远程登录 |
| 域名:443 | OpenResty / Caddy / Nginx | HTTPS 公开入口 |

Mac 使用 3000、云服务器也使用 3000，不会冲突，因为它们是不同主机。

---

## 柜台开着，但它朝哪边开

```text
127.0.0.1:8000
-> 只接受当前主机自己的连接

0.0.0.0:8000
-> 接受所有网络接口进入的连接，是否真能从公网访问还受防火墙和安全组影响
```

查看 Linux 监听：

```bash
ss -lntp
```

查看 macOS 监听：

```bash
lsof -nP -iTCP:3001 -sTCP:LISTEN
```

---

## 把请求路线画在墙上

```text
浏览器访问 https://api.example.com
-> DNS 找到公网 IP
-> 云安全组允许 443
-> Linux 防火墙允许 443
-> 反向代理监听 443
-> 转发到 127.0.0.1:3001
-> Express 接住请求
```

打开安全组不会启动 Express；Express 正在监听也不代表网络规则已经允许公网进入。

---

## 别把 CORS 抓来顶罪

浏览器用“协议 + 主机 + 端口”判断来源：

```text
http://localhost:3000
http://localhost:3001
```

端口不同，属于不同来源，浏览器会执行 CORS 检查。

- CORS：浏览器决定页面能否读取响应。
- 安全组：云平台决定流量能否进入实例。
- Linux 防火墙：操作系统决定流量能否继续。
- 进程监听：有没有程序接住地址和端口。

不要用修改 CORS 解决“TCP 端口根本连不上”的问题。

---

## 从近到远逐个排除

```text
1. 进程是否存在
2. 是否监听正确地址和端口
3. 在同一台服务器 curl 是否成功
4. Linux 防火墙是否允许
5. 云安全组是否允许
6. 反向代理是否指向正确上游
7. DNS 是否指向正确公网 IP
8. 浏览器是否遇到 CORS、Cookie 或证书问题
```

常用检查：

```bash
ps aux
ss -lntp
curl http://127.0.0.1:8000
systemctl status ssh
sudo journalctl -u ssh
```

## 结案报告

合上文档，试着口述一次：

```text
浏览器打不开网页
-> 我先在服务器上确认 ______
-> 再确认它监听 ______
-> 然后用 curl ______
-> 本机成功后才继续检查 ______ 和 ______
```

只要顺序是“进程 → 监听 → 本机请求 → 防火墙 / 安全组”，你已经有了一条比“到处重启”可靠得多的线索链。
