# 05. 网页失踪案：沿着进程、日志和端口找到它

案发现场很普通：昨天还能打开的页面，今天只剩一句 `Connection refused`。

先别重启所有东西。网页从浏览器走到应用，要经过一串可以逐个盘问的对象。你已经见过其中几个：

```text
Next.js：localhost:3000
Express：localhost:3001
PostgreSQL：localhost:5432
```

线上还会出现 SSH 22、HTTP 80 和 HTTPS 443。它们底层使用同一个端口概念，但属于不同主机、进程和网络层。接下来把它们都列为“嫌疑人”。

## 第一位嫌疑人：进程根本没活着

- 进程是正在运行的程序实例。
- 服务是需要长期运行、可被系统管理的进程。
- `systemd` 是 Ubuntu 常见的服务管理系统。

查看：

```bash
ps aux
top
systemctl status ssh
```

`top` 按 `q` 退出。

本地执行 `npm run dev` 是前台开发进程；生产 Node.js 需要由容器重启策略、systemd 或其他进程管理方式监督，不能依赖一个一直开着的 SSH 窗口。

---

## 日志是现场录像

```bash
journalctl -u ssh
journalctl -u ssh -f
```

- `-u ssh` 只看 SSH 服务。
- `-f` 持续等待新日志，按 `Control-C` 结束。

容器应用通常还会使用：

```bash
docker compose logs
docker compose logs -f api
```

日志不应该记录密码、完整 Cookie、令牌或私钥。

---

## 端口只是柜台号码

| 地址 | 谁在监听 | 当前怎样理解 |
|---|---|---|
| Mac `localhost:3000` | Next.js 开发进程 | 前端开发服务器 |
| Mac `localhost:3001` | Express 开发进程 | API 开发服务器 |
| Mac `localhost:5432` | Docker 端口转发 | PostgreSQL 容器入口 |
| 服务器公网 IP:22 | `sshd` | SSH 远程登录 |
| 域名:443 | OpenResty / Caddy / Nginx | HTTPS 公开入口 |

Mac 使用 3000、云服务器也使用 3000，不会冲突，因为它们是不同主机。

---

## 柜台开着，但它朝哪边开

```text
127.0.0.1:3001
-> 只接受当前主机自己的连接

0.0.0.0:3001
-> 接受所有网络接口进入的连接，是否真能从公网访问还受防火墙和安全组影响
```

查看 Linux 监听：

```bash
ss -lntp
```

查看 macOS 监听：

```bash
lsof -nP -iTCP:3001 -sTCP:LISTEN
```

---

## 把请求路线画在墙上

```text
浏览器访问 https://api.example.com
-> DNS 找到公网 IP
-> 云安全组允许 443
-> Linux 防火墙允许 443
-> 反向代理监听 443
-> 转发到 127.0.0.1:3001
-> Express 接住请求
```

打开安全组不会启动 Express；Express 正在监听也不代表网络规则已经允许公网进入。

---

## 别把 CORS 抓来顶罪

浏览器用“协议 + 主机 + 端口”判断来源：

```text
http://localhost:3000
http://localhost:3001
```

端口不同，属于不同来源，浏览器会执行 CORS 检查。

- CORS：浏览器决定页面能否读取响应。
- 安全组：云平台决定流量能否进入实例。
- Linux 防火墙：操作系统决定流量能否继续。
- 进程监听：有没有程序接住地址和端口。

不要用修改 CORS 解决“TCP 端口根本连不上”的问题。

---

## 从近到远逐个排除

```text
1. 进程是否存在
2. 是否监听正确地址和端口
3. 在同一台服务器 curl 是否成功
4. Linux 防火墙是否允许
5. 云安全组是否允许
6. 反向代理是否指向正确上游
7. DNS 是否指向正确公网 IP
8. 浏览器是否遇到 CORS、Cookie 或证书问题
```

常用检查：

```bash
ps aux
ss -lntp
curl http://127.0.0.1:3001/api/health
systemctl status ssh
journalctl -u ssh
```

## 结案报告

合上文档，试着口述一次：

```text
浏览器打不开网页
-> 我先在服务器上确认 ______
-> 再确认它监听 ______
-> 然后用 curl ______
-> 本机成功后才继续检查 ______ 和 ______
```

只要顺序是“进程 → 监听 → 本机请求 → 防火墙 / 安全组”，你已经有了一条比“到处重启”可靠得多的线索链。
