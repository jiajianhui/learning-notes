# 05. Linux 旅馆：文件住哪里，谁有钥匙，软件从哪来

第一次遇到这句话，很多人会觉得 Linux 在故意拦路：

```text
Permission denied
```

其实它更像旅馆前台在问：你是谁，要进哪间房，手里的钥匙允许做什么？

Linux 初学者最容易形成的坏习惯是：

```text
遇到 Permission denied
-> 在命令前加 sudo
```

这一站先逛楼层，再看工牌和门禁。等关系看清以后，`sudo` 才不会沦为万能通行证。

先从 Mac 登录上一章创建的服务器：

```bash
ssh linux-learning
```

从这里到本章结束，除非特别标明，所有命令都在远程 Ubuntu 执行。先用这三条确认位置：

```bash
hostname
whoami
pwd
```

不要继续使用第 03 章在 Mac 创建的 `~/linux-playground`。同名路径出现在不同机器上，也是两份完全不同的目录。

## 先看楼层，不背整栋大楼

| 目录 | 现在怎样理解 |
|---|---|
| `/home` | 普通用户的主目录 |
| `/root` | root 用户的主目录，不是整个文件系统根目录 |
| `/etc` | 系统和服务配置 |
| `/var` | 会持续变化的数据，例如日志 |
| `/var/log` | 常见文本日志位置 |
| `/opt` | 可选或第三方软件常用位置 |
| `/srv` | 服务提供的数据或项目可以放在这里 |
| `/tmp` | 临时文件，不能依赖长期保留 |
| `/usr` | 大量程序和共享资源 |
| `/proc` | 内核提供的进程与系统状态视图 |

这些是职责约定，不要求第一次背完整文件系统标准。

查看：

```bash
ls -ld /home /root /etc /var /opt /srv /tmp /usr /proc
df -h
```

## 你现在戴着谁的工牌

```bash
whoami
id
groups
```

- 用户表示谁在执行操作。
- 用户组让一组用户共享权限。
- `root` 是最高权限用户。
- `sudo` 让被授权的普通用户以更高权限执行一条明确命令。

例如，SSH 配置里的 `Host aliyun` 是连接别名，`User root` 才表示登录账号。连接后 `whoami` 输出 `root`，说明当前终端已经使用最高权限，执行系统管理命令时通常不必再加 `sudo`。

`sudo` 不是“重试按钮”。运行前先问：

```text
为什么普通用户没有权限？
这个文件本来应该属于谁？
当前动作真的需要系统权限吗？
```

## 三组门禁灯：`r / w / x`

```bash
mkdir -p ~/linux-playground
printf "hello from Linux\n" > ~/linux-playground/lobby.txt
ls -ld ~/linux-playground
ls -l ~/linux-playground/lobby.txt
stat ~/linux-playground/lobby.txt
```

例如：

```text
-rw-r--r--
```

可以拆成：

```text
-       普通文件
rw-     文件所有者可读写
r--     同组用户只读
r--     其他用户只读
```

目录的 `x` 表示能否进入和访问内部路径，不只是“执行目录”。

先在这块练习目录里改变权限：

```bash
chmod 700 ~/linux-playground
chmod 600 ~/linux-playground/lobby.txt
ls -ld ~/linux-playground
ls -l ~/linux-playground/lobby.txt
```

`700` 表示只有所有者能进入这个目录；`600` 表示只有所有者能读写这个文件。SSH 使用的 `~/.ssh` 和私钥也常需要严格权限，但不要拿真正的登录文件反复试验。

`chown` 改变所有者，通常需要管理员权限。例如 `chown deploy:deploy /opt/mini-cms` 表示把目录交给 `deploy` 用户和 `deploy` 用户组。`deploy` 只是示例名字，命令不会创建用户或用户组；服务器没有对应账号时不能照抄。

第 20A 章按你已有的 `root` 登录方式创建 `/opt/mini-cms`，当前用户可以直接使用它。只有要把目录交给另一个实际存在的用户管理时，才需要调整归属。`chmod` 管“允许怎么访问”，`chown` 管“文件属于谁”。

## 登录用户与应用进程用户

SSH 登录成功，只确定了当前终端使用哪个账号。还要分清应用在哪里、以谁的身份运行：

| 对象 | 用户由什么决定 |
|---|---|
| SSH 远程终端 | `ssh 用户名@地址` 或配置中的 `User` |
| 在这个终端直接启动的 Node.js 进程 | 通常继承当前用户；例如用 `root` 直接运行 `node`，进程也使用 `root` |
| Docker 容器内的应用进程 | 由镜像的 `USER` 或运行时用户配置决定，不能只看宿主机上的 `whoami` |

因此，“用 root 管理 Docker”和“应用在容器内使用哪个用户”需要分别判断。当前 20A 的 Node.js Dockerfile 尚未设置 `USER`，使用的官方基础镜像默认以 `root` 运行。镜像里虽然已有 `node` 用户，也要明确配置后才会切换，不能因为放进容器就认为已经使用普通用户。

长期运行的应用应尽量只获得必要的文件权限；安装系统软件、管理服务等操作才使用管理员权限。第一轮先看懂已有账号与目录归属。以后调整应用运行用户时，再一起确认代码、配置和写入目录的权限。

## 去 Ubuntu 的软件仓库取工具

```bash
sudo apt update
apt list --upgradable
apt search tree
sudo apt install tree
tree --version
```

主线：

```text
apt update 更新软件索引
-> apt search 查找包
-> apt install 下载并安装
-> 命令进入系统 PATH
```

`apt update` 不等于升级所有软件。正式服务器升级前要看变更、备份和维护窗口，不机械执行一串命令。

macOS 的 Homebrew 和 Ubuntu 的 APT 都能安装软件，但管理的目录、包版本和系统关系不同。

### 系统依赖与 npm 依赖分别装在哪里

以第 20A 章的后端镜像为例，安装分成两层：

| 命令 | 安装什么 | 谁使用 |
|---|---|---|
| `apt-get install openssl` | 操作系统里的 OpenSSL 工具和相关库 | Prisma 7 的迁移工具等底层程序 |
| `npm ci` | `package-lock.json` 记录的项目依赖，例如 Express、Prisma、tsx | 当前 Node.js 项目 |

OpenSSL 提供加密相关能力。本项目只需把它作为系统依赖装好，由底层工具使用，业务代码不用 `import`。`apt` 适合终端交互，Dockerfile 中通常用 `apt-get` 执行安装。

**装在哪个环境，就供哪个环境使用。** 在服务器终端执行安装，修改的是宿主机；在 Dockerfile 的 `RUN` 中安装，软件会进入镜像。宿主机装过 OpenSSL，不代表后端容器里也有。20A 把两层安装都写进后端 Dockerfile，制作镜像时一起完成。

## 亲手锁上一份“小秘密”

```bash
mkdir -p ~/linux-playground/permissions
printf "secret\n" > ~/linux-playground/permissions/private.txt
ls -l ~/linux-playground/permissions/private.txt
chmod 600 ~/linux-playground/permissions/private.txt
ls -l ~/linux-playground/permissions/private.txt
```

说清改变前后，所有者、用户组和其他用户分别能做什么。

## 再遇到 `Permission denied`

先别加 `sudo`，按这个顺序自问：

```text
我是谁？
目标是谁的？
现在的 r / w / x 是什么？
应该改权限、改所有者，还是这件事本来就不该做？
```

能走完这四问，再确认自己能区分 `/` 与 `/root`、APT 与 npm，这一站就结束了。
