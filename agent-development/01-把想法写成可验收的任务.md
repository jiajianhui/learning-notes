# 01. 把想法写成可验收的任务

## “帮我做一个聪明助手”为什么不够？

这像给装修师傅说“把房间弄舒服一点”。对方可以动工，但你们未必对“舒服”有相同理解。

任务单要把期望变成能检查的行为。它不是写得越长越好，而是让执行者知道：要改变什么、允许改哪里、怎样判断完成。

## 先写一个用户动作

本项目第一个动作是：

> 输入一个关键词，返回匹配笔记的文件名和短摘录；没有匹配时返回空结果。

这比“做一个 RAG 系统”更容易检查。RAG 是先检索资料再让模型据此生成答案的做法，后面会拆开讲；现在先做好检索这一步。

打开配套代码 `src/notes.ts` 的 `search()`，看到的真实返回结构是：

```ts
{
  matches: [{ path: 'database.md', snippet: '...' }],
  total: 1
}
```

`matches` 是准备展示的最多 5 条结果，`total` 是全部匹配数量。它们像“前五条目录”和“共找到几本书”，含义不能混用。

## 把动作写成任务单

```text
目标：验证并完善笔记关键词搜索。
范围：src/notes.ts 的搜索行为，以及对应测试。
输入：非空关键词，例如“事务”。
输出：matches 与 total；每条结果包含 path 和 snippet。
约束：只处理 notes/ 顶层普通 Markdown，不调用模型，不修改笔记。
验收：
  1. 搜索“事务”能命中 database.md。
  2. 搜索不存在的词返回空数组，total 为 0。
  3. 空关键词被拒绝。
  4. 结果超过 5 条时，matches 截断，total 保留真实数量。
交付：修改差异、运行的检查、结果及尚未验证的部分。
```

前三项已有配套测试；第四项可以作为第 02 章补充测试的练习。这里是在约定行为，不是在指定必须用哪种循环写代码。

## 正常例子之外，再写一个反例

如果只写“搜索事务有结果”，把所有文件都返回的错误实现也可能过关。

反例像试门锁时用一把错误钥匙：不仅要证明正确钥匙能开门，也要证明错误钥匙不能开。

实际测试要围绕行为：空词是否拒绝、找不到是否为空、目录外文件能否被读取。没有必要为每一行代码写一个对应测试。

## 给任务上下文，也要给边界

交给开发 Agent 时，附上：

- 项目 README：如何启动，代码在哪里。
- `package.json`：可用检查命令。
- 有关文件与现有测试：当前行为是什么。
- 不修改的范围：例如模型接口和写入流程不属于这次搜索任务。

这像把师傅带到要修的水龙头旁边，告诉他总阀在哪；不用把整栋楼的图纸都倒给他。

仓库规则和任务说明提供指导，但不能替代程序里的权限与校验。写着“不要读取目录外文件”，不代表函数已经拒绝了这种路径。

## 动手与复述

复制[任务单模板](./templates/任务单.md)，写一张“总结指定笔记”的任务单。先不让开发 Agent 实现，自己检查：文件不存在、模型超时、模型未完成时，应该发生什么？

然后用一句话解释：“任务单为什么不能只写正常结果？”如果解释不清，回看“错误钥匙”的反例，再把它换成项目里的一个输入。
