# 13. 项目与面试：怎样证明自己不只是调用了一次 API？

## 展示一条完整能力链

最有说服力的项目介绍，不需要先说“我用了很多 Agent 框架”。先说明用户原来遇到什么困难，系统怎样帮他完成任务，再展示你如何处理失败。

本系列的起点很小：从本地 Markdown 找资料并解释，在需要修改时先给出建议。你的技术贡献可以沿一条清楚的链展开：用户问题 → 模型选择工具 → 参数校验 → 查阅证据 → 回答或建议 → 确认执行 → 评估结果。

这像展示一件家具：不仅让人看成品，也让人看承重处和连接方式。面试中的失败案例、约束和改进证据，就是这些连接处。

## 写一页别人能复现的项目说明

在自己的独立练习副本中写 `PROJECT.md`，按下面顺序组织，不需要长篇包装：

1. **问题与范围**：谁用它解决什么问题？为什么第一版只处理顶层 Markdown？
2. **最小运行方式**：依赖、命令、虚构输入、预期结果，以及是否需要付费模型。
3. **执行流程**：画一张从用户输入到工具结果的图，标出程序校验与人工确认。
4. **一次失败与改进**：原始问题、失败位置、修改原因、前后逐题结果。
5. **验证与限制**：哪些实际运行过，哪些没有；生产使用还缺什么。

从前面产物取证即可，不需要再造一个庞大项目：第 03～04 章提供核心实现，第 06 章提供确认边界，第 07、12 章提供质量记录，第 11 章提供恢复与重试的取舍。

如果只完成了离线实验，直接这样写：

> 实现了本地笔记工具与 Agent 执行循环，并验证参数错误、工具失败、轮次上限和确认写入。真实模型任务效果尚未评估；目前不支持多用户与生产部署。

如果又做完了真实模型评估，再补上模型、日期、用例数量、通过标准、结果及失败例。不要把离线固定回答当成模型能力，也不要把教学数据分数包装成真实业务提升。

## 把岗位词汇翻译成项目证据

| 岗位写法 | 能展示的内容 | 还不能据此声称 |
|---|---|---|
| Tool calling / Agent | 工具 Schema、调用 ID、循环与停止原因 | 任意长任务都能自动完成 |
| RAG / 检索优化 | 候选来源、漏检分析、基线与留出结果 | 精通所有向量数据库、企业知识库已上线 |
| LangGraph / MCP | 图与普通函数对照，真实协议往返 | 已实现分布式多 Agent 或模型自动接 MCP |
| 可靠性 / 可观测性 | 去重、恢复结果、失败轨迹与状态边界 | 恰好一次外部写入或多进程容灾 |

你可以按目标职位从中选两三项深入，不必把每个实验都放进同一个运行程序。

## 用这些问题检查理解是否扎实

- “这和普通 API 包装有什么区别？”用第 03～04 章说明谁选择动作、谁执行、结果怎样进入下一轮。
- “资料没搜到为什么不让模型直接答？”区分产品是否要求基于指定资料，以及缺少证据时的行为。
- “为什么先自己写循环再学框架？”说清已经理解的机制，以及框架实际减少了什么复杂度。
- “重复请求会不会重复修改？”讲第 06 章的旧原文检查，再说明它和通用外部副作用幂等不是同一件事。
- “你怎么证明优化有效？”展示一组可比较的逐题记录，包括没有改善的例子。

练习时找一个没做过 Agent 的同事，给他三分钟看你的图和演示。如果他仍分不清模型、程序、工具和用户各自做什么，就先重写解释，而不是增加术语。

## 下一步选一个真实缺口补上

如果目标是 AI 应用岗位，可以给助手加一个简单 Web 页面和任务接口，验证真实使用、权限与部署。如果偏检索，换成自己整理且可公开的资料，建立独立评估题。如果偏平台，再深入多进程执行、队列和隔离。

这些是后续项目建议，当前仓库没有实现。选择一项完成真实闭环，比把所有方向都列在简历上更有价值。

至此，你的路线已经从“会调用模型 API”推进到“能解释并实现一个受约束的 Agent，再用证据检查它”。是否满足某个岗位，还要回到那份岗位职责与自己的实际产出逐项核对。
