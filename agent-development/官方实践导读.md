## 放到笔记助手里，真正要做的取舍

下面是结合这些资料对本项目的设计判断，不是官方要求的固定配方。

**先把任务做小。** 单篇总结用一次调用；跨篇查资料才进入工具循环。多个开发 Agent 可以一起维护代码，产品内部仍只用一个模型角色。

**让下一位开发者接得上。** 项目规则说明长期约定，任务单说明这次要做什么，交接记录说明实际做到哪里。OpenAI 的工作流示例还拆分了多类阶段文件；这个小项目用现有三份材料就够，不照搬整套目录。

**把工具做成清楚的申请表。** 参数之外还应说明用途、返回范围与失败后的可行动作。比如没找到文件时提示先搜索准确文件名，不能只甩给模型一个系统错误。

**把上下文当有限桌面。** 先看目录卡片，再取正文。历史 ID 负责衔接，不自动解决资料增长。当前的小文件和轮次限制适合教学；摘要与长期状态恢复留到实际需要时再实现。

**把检查落实到可见结果。** “已生成建议”检查建议文件；“已应用”检查原文内容。回答与实际状态矛盾时要记为失败，不能只根据回答语气评分。

**把失败变成下一次可以复现的题。** 修工具、提示词或模型配置时，一次改变一个主要因素，使用同一组样例比较，并保留未参与调试的题进行复查。

## 本轮实际补了什么？

| 改进 | 怎样亲自验证 |
|---|---|
| 任务接班 | 只给新会话任务单与交接记录，看它能否准确指出下一步和验证命令 |
| 项目审查规则 | 对“确认后才写入”分别设计违规、合规和无关变更，检查审查是否有依据 |
| 工具反馈 | 在离线测试中调用不存在的文件，检查错误是否提示先搜索，而不输出本机完整路径 |
| 失败轨迹 | `npm run demo:failure`，观察模型请求失败和轮次耗尽怎样留下记录 |
| 结果与程序结束分开 | 查看运行日志的 `status`、`verification` 与每轮 `outcome`，再人工填写评估结果 |
| 可比较的评估 | 按评估表分组；每次写入试验用新的笔记副本，分别记录程序约束与模型行为 |

代码改进可以离线测试。模型是否因此更会选词、更忠实地回答，还需要真实模型评估，当前没有这个结论。

## 阅读官方资料时也要分层

1. **工程原则**：接口清晰、按需提供资料、验证结果。这些可以迁移到不同供应商。
2. **案例条件**：任务规模、权限、模型、成本。不能把一个团队的产量直接当作你的预期收益。
3. **产品操作**：SDK 类名、控制台节点、模型推荐。使用前重新核对，不从较早的文章直接照抄。

核对时，OpenAI 的 Evaluation best practices 与 Safety in building agents 页面已带相关产品的迁移或停用提示。因此这里参考评估与数据边界的方法，不把旧 Evals 平台、Agent Builder 界面或其中的旧型号推荐作为实践依赖；配套代码仍使用 Responses API。[评估页面](https://developers.openai.com/api/docs/guides/evaluation-best-practices)、[安全页面](https://developers.openai.com/api/docs/guides/agent-builder-safety)

本轮不增加云平台、向量数据库或多 Agent 框架。只有当现有评估明确暴露能力缺口时，再讨论引入哪一项，以及怎样证明它有帮助。
