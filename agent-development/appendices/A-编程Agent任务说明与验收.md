# 附录 A. 给编程 Agent 写清任务与验收

本篇讨论怎样让编程 Agent 帮你写软件，与笔记助手内部怎样调用工具是两个主题。先完成主线 02～07，使用自己建立的 `note-agent-lab` 练习。

## 从一句愿望变成一个可检查的动作

“帮我做一个聪明助手”像让装修师傅“把房间弄舒服”。双方可能对完成标准有不同理解。

把这次工作收小：给 `searchNotes()` 补两项边界测试，证明空白词与超过 100 个字符的词会被拒绝。已有程序实现了限制，本次只增加验证证据。

把下面的说明交给一个编程 Agent 即可，不需要另找任务模板：

```text
目标：补充关键词搜索的输入边界测试。
起点：先读 package.json、search.ts、notes.ts、agent.test.ts。
范围：只新增 search-input.test.ts，不改模型请求与写入流程。
验收：
  1. searchNotes("   ") 应被拒绝。
  2. 101 个字符的关键词应被拒绝。
  3. npm run check 通过，报告实际结果。
约束：不调用真实模型，不读私人笔记，不提交或推送。
交付：说明改了什么、检查证明了什么、尚未验证什么。
```

任务单不是限定每一行怎么写，而是明确输入、范围与结果。当前代码先检查关键词再扫描文件，所以这两项失败不需要准备大量笔记。

## 为什么必须有反例？

只测试“搜索事务有结果”，一个返回所有文件的错误实现也可能通过。像检查门锁，正确钥匙能开之外，还要确认错误钥匙打不开。

任务约定也不能代替代码边界。“不要读取目录外文件”写在说明里，不代表 `readNote()` 已经校验过路径；要在程序和测试里分别核对。

## 动手与复述

照着上面的长度，自己写一次“改善总结失败提示”的任务说明。至少写清文件不存在、HTTP 失败、回答为空时的预期，禁止顺手扩大到新功能。

复述：一个任务的目标、实现范围和验收结果为什么不能混成“优化一下”？
