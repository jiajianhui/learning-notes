# 03. 服务怎样监听端口并等待请求

MiniCMS 的 `server/src/server.ts` 最后调用了 `app.listen(port, ...)`。后面已经没有业务语句，为什么终端仍然被占着，浏览器还能不断访问服务？

因为程序已经向操作系统登记了一个需要持续工作的网络入口。

## 1. 程序启动后，成为一个进程

磁盘上的源码是文件。运行它时，操作系统创建进程，为它安排内存和执行资源，给它一个进程编号 PID。

可以把源码想成菜谱，把进程想成按菜谱营业中的餐厅：同一份菜谱可以开两家店；关掉一家店，也不等于删除菜谱。

同样，执行两次启动命令，可能创建两套运行实例。它们有自己的状态和内存，不会因为读了同一份源码就自动合成一个服务。

## 2. 地址和端口共同确定入口

`http://127.0.0.1:3001/api/health` 中：

- `127.0.0.1` 指当前网络环境里的本机回环地址。
- `3001` 是目标端口。
- `/api/health` 是 HTTP 路径，连接建立后由 HTTP 服务解释。

把 IP 地址比作一栋楼的位置，端口比作楼里的接待窗口。到达这栋楼不等于进了正确窗口；到达窗口也不等于窗口能办理你的业务。

| 地址 | 在监听或访问时的含义 |
|---|---|
| `127.0.0.1` | IPv4 回环地址，只在当前网络环境内访问自己 |
| `localhost` | 通常解析到 IPv4 或 IPv6 回环地址的主机名 |
| `::1` | IPv6 回环地址 |
| `0.0.0.0` | 作为监听地址时，表示所有本地 IPv4 网络接口；不是给用户填写的远程服务地址 |

MiniCMS 当前调用 `app.listen(port)`，没有明确传 host。Node.js 省略 host 时会选择未指定地址监听，具体涉及系统的 IPv6 支持；不能据此认定只允许本机访问。下面实验明确绑定 `127.0.0.1`，让观察范围固定在本机。[Node.js listen 说明](https://nodejs.org/api/net.html#serverlistenport-host-backlog-callback)

## 3. Socket 是操作系统提供的通信端点

Socket 可以先理解为程序进行网络通信时使用的端点。服务端先建立监听 Socket，等待连接；接入客户端后，用对应的连接 Socket 收发数据。

一次 TCP 连接可以用两端的信息区分：

```text
客户端 IP + 客户端端口 ↔ 服务端 IP + 服务端端口
```

服务端常用固定端口，例如 3001；客户端通常由操作系统分配临时端口。同一个服务端监听端口可以接入多个客户端，不需要给每位用户新开一个 3002、3003。

餐厅只有一个对外门牌，但可以同时接待很多桌客人。比喻的边界是：Socket 是操作系统维护的通信资源，不是一个真的房间；一个进程也可以拥有许多 Socket。

## 4. Express 把监听交给谁

你安装的 Express 5 中，`app.listen()` 的核心逻辑可以概括为：

```js
// 原理片段：省略了 Express 对参数和错误的处理
const server = http.createServer(app);
server.listen(port);
```

Express 的 app 可以作为 Node.js HTTP 服务器收到请求后的处理函数。Node.js 负责 HTTP 与底层连接的衔接，Express 再组织路由和中间件。

因此职责是：

```text
操作系统：管理网络连接、收发数据并提供就绪通知
Node.js：把网络与 HTTP 能力交给 JavaScript 使用
Express：根据 HTTP 请求组织应用处理流程
你的路由：执行业务逻辑并返回结果
```

看到 `app.listen` 时，不需要想象 Express 自己重新实现了一套 TCP。

## 5. 为什么没有请求时程序也不退出

普通脚本执行完，没有待处理的工作或维持活动的资源时，Node.js 可以退出。监听中的服务器是一个仍然活动的资源，因此事件循环会继续等待工作。

这种等待通常由操作系统的事件通知机制协助完成，不需要 JavaScript 写一个不停检查的 `while (true)`。像店员开门营业后等待门铃，没客人时也不必绕着门跑。

有请求时，Node.js 调用注册好的处理函数；没有请求时，不代表主线程必须持续满负荷计算。第 06 章会进一步解释事件循环。

## 6. 用一个原生 Node.js 服务观察

从学习仓库根目录启动现成的[监听实验](./labs/01-listen.mjs)：

```bash
node backend/node-network-foundations/labs/01-listen.mjs
```

它默认监听 `127.0.0.1:4311`，输出 PID 和地址。核心代码是：

```js
// 核心片段；可运行的完整文件见上方链接
const server = createServer((req, res) => {
  // 每次 HTTP 请求到来，才执行这里
});

server.listen(4311, "127.0.0.1", () => {
  // 开始监听后执行一次
});
```

先预测：启动服务时，请求处理函数会执行吗？

打开第二个终端：

```bash
curl -i http://127.0.0.1:4311/api/health
```

应得到 `200` 和包含 `status`、`pid` 的 JSON。第一个终端此时才打印请求方法、路径，以及连接两端的地址和端口。重复请求，观察服务端端口仍为 4311；新的 curl 进程通常使用新的客户端临时端口。

在 Mac 上查看监听者：

```bash
lsof -nP -iTCP:4311 -sTCP:LISTEN
```

`-nP` 让地址和端口以数字显示，最后一个条件只看监听状态。对照 PID，应能确认是刚才启动的 Node.js 实验进程。Linux 上对应的排查工具可看 [Linux 第 06 章](../../linux/06-进程服务日志与端口.md)。

如果 4311 已被其他程序占用，保留它，换端口启动实验：

```bash
PORT=4411 node backend/node-network-foundations/labs/01-listen.mjs
```

后续 curl 和 lsof 的端口也要一起改成 4411。

## 7. 比较三种完全不同的失败

保持实验服务运行，访问不存在的路径：

```bash
curl -i http://127.0.0.1:4311/no-such-path
```

得到 `404`，说明已连接到 HTTP 服务，服务明确回复“没有这个路径”。

再开一个终端，尝试用相同端口启动同一实验。第二份进程应报告 `EADDRINUSE`：它还没开始接待请求，申请监听入口时就冲突了。第一个服务仍然运行。

最后在第一个终端按 `Ctrl+C`，再请求健康检查。现在通常是 `Connection refused`：目标端口已没有监听者；此时得不到 HTTP 404，因为连接没有成功到达一个可响应的 HTTP 服务。

| 现象 | 当前能判断到哪一层 |
|---|---|
| EADDRINUSE | 本地启动时申请监听地址、端口失败 |
| Connection refused | 连接被拒绝；先查目标和监听状态 |
| HTTP 404 | 已收到 HTTP 响应；继续查路径和路由 |

这些含义与程序用不用 Express 无关。实际公网故障还有防火墙、代理等因素，不能凭一条提示直接断言唯一原因。
