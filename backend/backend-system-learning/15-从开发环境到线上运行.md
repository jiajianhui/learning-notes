# 15. 运行和部署：在自己电脑能跑还不是终点

## 问题背景

开发环境中可以同时开两个终端：

```text
Next.js：localhost:3000
Express：localhost:3001
PostgreSQL：localhost:5432
```

线上环境还要考虑域名、HTTPS、构建、环境变量、数据迁移和日志。域名是用户访问服务的公开地址。

HTTPS 是加密传输的 HTTP，避免密码和 Cookie 在网络传输时直接暴露。

这一章先建立地图，不要求第一轮立刻掌握所有运维工具。

---

## 从本地运行到线上运行要补什么

### 1. 开发和生产是两套运行方式

开发环境重视：

- 热更新。
- 调试信息。
- 本地数据库。
- 快速修改。

生产环境重视：

- 稳定启动。
- HTTPS。
- 密钥安全。
- 日志和故障定位。
- 数据备份和迁移。

不能直接把开发服务器当作线上运行方式。

### 2. 后端要有明确构建和启动命令

```text
npm run dev
-> 开发时运行 TypeScript

npm run build
-> 编译并检查

npm run start
-> 运行生产构建
```

README 要写清楚 Node.js、环境变量、数据库和启动顺序。

### 3. 数据库变更要可重复

线上不能依赖“我记得自己手动建过哪些表”。

需要保存：

- `schema.prisma` 和生成的迁移文件。
- 执行顺序。
- 修改结构前的数据备份。

代码版本和数据库结构必须能够对应。

Prisma 的开发和生产命令不要混用：

```text
本地开发：prisma migrate dev
-> 根据 schema.prisma 创建迁移，并应用到开发数据库

构建阶段：prisma generate
-> 生成当前代码需要的 Prisma Client

测试、预发布和生产：prisma migrate deploy
-> 只按顺序应用已经提交的迁移
```

`migrate dev` 会使用开发流程检查结构差异，不能拿来操作生产数据库；`migrate deploy` 不会替你生成 Prisma Client，所以构建流程仍要显式执行 `prisma generate`。迁移应由部署流程执行，不要为了上线临时把生产数据库地址复制到本机。

### 4. 健康检查只回答服务是否可用

```text
GET /api/health
```

可以检查应用是否运行，必要时增加数据库连通性信息，但不要返回密码和内部配置。

### 5. 日志帮助定位线上问题

至少记录：

- 请求方法和路径。
- 响应状态码。
- 请求耗时。
- 未知错误的内部细节。

不要在日志中记录密码、完整 Cookie 和敏感密钥。

---

## 常见的线上运行关系

```text
浏览器
-> HTTPS 域名
-> Next.js 管理后台
-> HTTPS API 域名
-> Express
-> 托管 PostgreSQL
```

前端和后端可以分别部署，也可以由同一平台管理，但它们的职责和环境变量仍然分开。

---

## 第一次部署练习做到什么程度

主体完成时先保证：

- `.env.example` 完整。
- 真实 `.env` 不提交。
- `build`、`start`、`test` 命令可用。
- Prisma 迁移有记录并且能在新数据库重复执行。
- 有 `/api/health`。
- 有基础请求和错误日志。
- README 能指导新环境启动。
- 数据库知道怎样备份。

---

## 小结

```text
开发命令
-> 提供热更新和调试信息，方便在本地修改代码

构建和启动命令
-> 生成并运行要部署的代码

环境变量
-> 让数据库地址和密钥留在代码之外

迁移文件
-> 让新环境可以按相同顺序建立数据库结构

健康检查和日志
-> 确认服务是否运行，并在出错时帮助定位问题

备份
-> 数据丢失或损坏时，可以用来恢复
```

部署不是把代码上传一次，而是让系统能够安全、稳定、可重复地运行。
