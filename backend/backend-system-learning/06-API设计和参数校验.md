# 06. API 设计：让前端知道怎样请求，也知道哪里错了

## 问题背景

接口不只是一个能访问的 URL，而是前端和后端之间的约定：

```text
请求什么路径
使用什么方法
参数放在哪里
成功返回什么
失败返回什么
```

这套约定也叫 API contract。

本章只负责把接口规则说清楚，不引入具体校验库，也不搭建完整错误系统。第 05 章已经解释错误怎样传播；第 09 章先跑通真实数据库 CRUD；第 10 章再用 Zod 和错误中间件把这些约定写成正式代码。

---

## API 先约定路径、输入和输出

### 1. 路径描述资源，方法描述动作

```text
GET    /api/articles
GET    /api/articles/:id
POST   /api/articles
PATCH  /api/articles/:id
DELETE /api/articles/:id
```

这里的资源是 `articles`，HTTP 方法表示读取、创建、更新或删除。

### 2. 响应结构要稳定

单条数据：

```json
{
  "data": {
    "id": 1,
    "title": "文章标题"
  }
}
```

列表和分页：

```json
{
  "data": [],
  "pagination": {
    "page": 1,
    "pageSize": 20,
    "total": 0
  }
}
```

错误：

```json
{
  "error": {
    "code": "SLUG_ALREADY_EXISTS",
    "message": "slug 已存在",
    "details": null
  }
}
```

前端不应该每个接口猜一种完全不同的结构。

---

## 三次检查：先看数据格式，再看操作是否允许

创建文章的请求不会拿到 body 后立刻执行 SQL，而是依次经过：

```text
request.body
-> 检查字段格式
-> 判断这次操作是否符合产品规则
-> 写入数据库
-> 数据库约束再检查一次
```

### 1. 先检查数据长什么样

```text
title 是否是字符串？
page 是否是正整数？
status 是否属于 draft / published？
```

这一步只回答“客户端传来的数据能不能正常使用”。它应该在调用业务函数之前完成；当前先把它理解成一个专门检查请求数据的函数。

### 2. 再判断这次操作能不能做

```text
发布文章时正文是否完整？
发布时是否需要自动记录发布时间？
已发布文章能否重新改回草稿？
```

这一步不是检查字段是不是字符串，而是判断操作是否符合文章系统的产品规则。例如格式正常的文章数据，不代表它已经满足“可以发布”的条件。

这类判断写在文章业务函数里。第 11 章拆分项目文件时，再确定它具体放在哪一层。

### 3. 数据库最后再检查一次

```text
slug 必须唯一
title 不能为空
```

数据库约束就是数据库自身执行的防错规则，例如禁止重复、禁止 `NULL` 或限制可选值。即使后端代码已经检查过，数据库仍然要保留这些约束；第 07 章再看具体写法。

## TypeScript 类型不能代替运行时校验

```ts
type CreateArticleInput = {
  title: string;
  slug: string;
  content: string;
};
```

这个类型可以检查你自己写的 TypeScript 代码，但浏览器、Apifox 或其他客户端发送的 JSON 不会自动遵守它。

所以请求进入后端时仍要：

```text
先把外部输入当作未知数据
-> 做运行时校验
-> 通过后再交给业务代码
```

TypeScript 检查的是开发者写下的代码；校验代码检查的是服务器运行时真正收到的 JSON。

## 创建文章：先写清楚允许什么输入

请求：

```json
{
  "title": "我的第一篇文章",
  "slug": "my-first-article",
  "summary": "摘要",
  "content": "正文",
  "status": "draft"
}
```

先明确规则：

- `title` 必须是字符串，去掉首尾空格后不能为空。
- `slug` 必须是字符串，只允许小写字母、数字和连字符，并且不能重复。
- `summary` 可以不传；传了就必须是字符串。
- `content` 必须是非空字符串。
- `status` 只能是 `draft` 或 `published`。
- 未提供 `status` 时默认为 `draft`。

这些是产品允许什么数据的规则。写代码前可以先把其中一条翻译成判断条件：

```ts
const { title } = request.body;

const titleIsValid =
  typeof title === "string" && title.trim() !== "";
```

如果 `titleIsValid` 是 `false`，后端就应该拒绝这次请求。这里先关注“规则能否被准确表达”，暂时不决定用手写判断还是校验库，也不在每个 route 里编写错误响应。第 10 章会把整组字段规则集中写成 Zod Schema。

无论以后怎样组织校验代码，标题是否必填、status 允许哪些值，都要先由产品规则明确决定。

## Apifox 在这里做什么

接口完成后至少检查：

- 正常参数。
- 缺少必填字段。
- 字段类型错误。
- 不允许的状态值。
- 重复 slug。
- 不存在的文章 id。

管理后台主要验证真实操作流程，Apifox 更适合主动构造错误输入。

## 小结

```text
API 约定
-> 先写清请求方法、路径、输入字段和返回结构

数据格式校验
-> 检查必填字段、数据类型和文本长度是否正确

业务规则校验
-> 检查文章是否满足发布条件，以及当前状态是否允许这次操作

数据库约束
-> 阻止重复 slug、错误状态等数据真正写入表中

状态码和 JSON
-> 告诉客户端请求是成功、输入有误，还是目标不存在
```

读完本章后，应该能先写清楚文章 CRUD 的接口契约，再开始连接数据库。完整的运行时校验和错误处理等真实 CRUD 跑通后，到第 10 章统一实现。
