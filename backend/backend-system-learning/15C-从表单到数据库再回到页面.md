# 15C. 从表单到数据库再回到页面：看懂前后端数据流

完成第 15B 章后，用这一篇复习数据怎样在 `admin-web-antd`、Express 和 PostgreSQL 之间流动。不增加新功能，代码片段用于对照已有实现。

第 14A 章按文件追踪 CRUD，第 15A 章解释关系维护；这里关注同一份数据经过各层时，**类型、字段和含义怎样变化**。

## 1. 点击保存后，数据经过哪里

以编辑文章 42 为例：用户修改表单后点击保存，页面把表单值交给前端的 `updateArticle(id, values)`。

```text
表单中的 values：JavaScript 对象
→ features/articles/api.ts：JSON.stringify(values)，生成请求体
→ lib/api-client.ts：fetch 发送 PATCH /api/articles/42
→ Express 的 express.json()：解析请求体，得到 req.body
→ article-router.ts：Schema.parse() 校验参数和请求体，得到 id、input
→ article-repository.ts：计算发布时间，更新文章和标签关系
→ PostgreSQL：保存数据
→ router：response.json({ data: article }) 返回结果
→ 前端 response.json()：解析为 JavaScript 对象
→ 更新页面状态：列表、表单显示新数据
```

前后端都有名为 `updateArticle()` 的函数，但它们不是同一个函数：前端函数发送 HTTP 请求，后端函数通过 Prisma 操作数据库。HTTP 传递的是数据，不会把前端的函数或变量直接交给后端。

看具体问题时，沿这条线找“数据在哪一步变了”，比只看最终页面更容易定位。

## 2. 同一个 id，为什么有时是数字，有时是字符串

请求中的数据可以放在不同位置。Express 读取的位置不同，得到的值也可能不同：

| 请求内容 | 后端从哪里取 | 校验前 | 校验后 |
|---|---|---|---|
| `PATCH /api/articles/42`，路由为 `/:id` | `req.params.id` | `"42"` | 路径 Schema 用 `z.coerce.number()` 转成 `42` |
| `GET /api/articles?tagId=3&page=2` | `req.query` | `tagId` 为 `"3"`，`page` 为 `"2"` | 查询 Schema 转成数字 `3`、`2` |
| JSON 请求体 `{"tagIds":[3,7]}` | `req.body.tagIds` | 数字数组 `[3, 7]` | 仍是数字数组 |
| JSON 请求体 `{"tagIds":["3","7"]}` | `req.body.tagIds` | 字符串数组 | 本项目的 `z.number()` 拒绝它 |

**URL 里的数字先是文字，JSON 则可以直接表达数字。** `express.json()` 负责解析 JSON，不会擅自把字符串 `"3"` 改成数字 `3`。

这也解释了第 15B 章为什么要求多选 Select 的选项使用数字 id：

```ts
// 标签选项的局部写法
{ label: tag.name, value: tag.id }
```

用户看到的是标签名称，表单保存的是 `value`。使用数字 `tag.id`，选中后得到的才是后端需要的 `[3, 7]`。

## 3. Schema 是规则，parse 才执行检查和转换

定义 Schema 时还没有处理任何请求。router 调用 `.parse()`，才把这次请求的数据交给规则检查：

```ts
const input = updateArticleSchema.parse(req.body);
const article = await updateArticle(id, input);
```

第一行失败会抛出 `ZodError`，当前请求进入错误处理，不会执行第二行。通过后得到的 `input`，也不一定和原来的 `req.body` 完全一样：

| 规则 | 输入 | 校验结果 |
|---|---|---|
| 标题的 `.trim()` | `"  新标题  "` | `"新标题"` |
| 查询参数的 `z.coerce.number()` | `"2"` | 数字 `2` |
| `page` 的 `.default(1)` | 没提交 `page` | 数字 `1` |
| `tagIds` 的 `.refine()` | `[3, 3, 7]` | 校验失败，不会自动改成 `[3, 7]` |

前面三项会转换或补上值；最后一项只判断是否符合规则。repository 接收校验后的 `input`，才用得上这些结果。

前端 Form 校验帮助用户及时发现问题，后端 Zod 校验检查真正收到的请求，两者都需要。前端写 `ArticleFormValues` 之类的 TypeScript 类型，也不会自动替后端执行运行时校验。

## 4. 不传、null、空字符串和空数组分别意味着什么

以修改摘要为例，JSON 没有 `undefined`，对象里值为 `undefined` 的字段在序列化时会被省略：

```ts
JSON.stringify({ title: "新标题", summary: undefined });
// '{"title":"新标题"}'

JSON.stringify({ title: "新标题", summary: null });
// '{"title":"新标题","summary":null}'
```

后端按本项目的更新规则处理摘要：

| 提交的 summary | 校验后的 input.summary | Prisma 更新结果 | 再次回填输入框 |
|---|---|---|---|
| 不提交，或序列化前为 `undefined` | `undefined` | 不改原摘要 | 显示原摘要 |
| `null` | `null` | 保存为 SQL `NULL` | 显示空白 |
| `""` | `""` | 保存为空字符串 | 显示空白 |
| `"新摘要"` | `"新摘要"` | 保存新摘要 | 显示“新摘要” |

**`null` 不是空字符串。** 输入框看起来一样，是因为第 14 章回填时做了转换：

```ts
summary: editingArticle.summary ?? ""
```

这里的 `??` 表示：左边为 `null` 或 `undefined` 时使用 `""`，其他值保留。当前输入框清空后提交的是空字符串，不会自动变成 `null`。页面展示时的转换，也不会自行改变数据库。

如果请求整个变成 `{}`，`updateArticleSchema` 中的 `.refine()` 会拒绝空更新。上表的“不改摘要”可以与修改标题等其他字段一起使用。

“不改”和“清空”是接口对字段的约定，不能套在所有值上：

- **摘要**：更新时允许 `null` 和 `""`，两者在数据库中不同。
- **标签**：不传 `tagIds` 就保留；传 `[]` 删除旧关系；传 `null` 校验失败。
- **状态**：不传 `status` 就保留；传 `"draft"` 或 `"published"` 才指定状态，不能用 `null` 清空。

## 5. 用户只改了标题，请求可能仍然提交整个表单

第 14 章先用 `isUnchanged` 判断有没有变化；只要有变化，就把完整 `values` 交给更新接口。因此下面两件事不同：

```text
用户只改了标题
→ 当前页面仍可能提交标题、slug、摘要、正文、状态和标签

请求只提交 { "title": "新标题" }
→ 后端只更新标题，其他字段按“不提交”的规则处理
```

PATCH 允许部分更新，但不会替前端挑出“真正改过的字段”。**后端依据收到的请求处理，不能知道用户刚才在表单里点了哪里。**

例如 A 窗口打开草稿，B 窗口随后发布成功；A 再保存标题时，如果还提交 `status: "draft"`，后端就会按请求撤回文章。事务能保证本次文章和关系一起成功或回滚，不会自动判断 A 的表单是否过时。

当前先理解这个行为，不额外实现并发编辑控制。排查“只改标题却改变状态”时，先查看请求体是否带了 `status`。

## 6. 请求字段不一定是数据库列，返回字段也不一定与请求相同

第 15 章的 `tagIds` 就是这种情况。假设文章 42 最终选择标签 3、7：

```text
前端表单：tagIds: [3, 7]
→ 请求体："tagIds": [3, 7]
→ 后端拆出 tagIds，其余字段用于更新 Article
→ 中间表：保存 (42, 3)、(42, 7) 两行 ArticleTag
→ include 查询：返回 articleTags，每条关系里带 tag
→ 表单回填：再从结果中取出 [3, 7]
```

请求里的 `tagIds` 不是 `Article` 的列，所以不能把整个 `input` 直接交给 Prisma。完整的写入与事务过程回看 [15A 第 2～5 节](./15A-从单表CRUD到关系维护.md)。

同一份关系响应，前端可以取不同字段：

```ts
// 编辑时：多选框需要数字 id
article.articleTags.map((item) => item.tag.id);

// 展示时：标签块需要名称
article.articleTags.map((item) => item.tag.name);
```

`GET /api/tags` 提供全部可选标签，文章详情提供这篇文章已选的标签。选项列表和已选值是两份数据，不能互相替代。

另一个例子是 `publishedAt`：客户端不提交它，后端根据状态生成它，响应中却会返回它。**请求描述要做的修改，响应描述处理后的结果，两者不必长得一样。**

## 7. 时间从数据库返回后，为什么变成了字符串

`publishedAt` 经过各层时的形式是：

| 位置 | 数据形式 |
|---|---|
| PostgreSQL | `published_at` 时间列，类型为 `timestamptz`；草稿为 `NULL` |
| Prisma 查询结果 | JavaScript `Date` 对象，或 `null` |
| `response.json()` 发出的 JSON | ISO 时间字符串，例如 `"2026-09-10T02:00:00.000Z"`，或 `null` |
| 前端 `response.json()` 解析后 | 仍是字符串，或 `null`，不会自动变回 `Date` |

所以前端的 `Article` 类型写 `publishedAt: string | null`。需要格式化时，再转换成 `Date`：

```ts
// 显示逻辑示例：null 显示“未发布”，有值时格式化为本地时间。
const text = article.publishedAt === null
  ? "未发布"
  : new Date(article.publishedAt).toLocaleString();
```

示例中的 `Z` 表示 UTC。浏览器时区为上海时，UTC 的 `02:00` 对应本地 `10:00`；这是同一时刻的不同显示方式，不是数据库多存了 8 小时。

创建草稿时没有发布时间；发布时由后端生成当前时间；撤回时清空；更新时未提交状态就保留原时间。完整规则在[第 15 章第 6 节](./15-数据关系JOIN和事务.md)，前端不另算一份发布时间。

## 8. 数据库保存成功，为什么页面还需要更新

数据库中的文章和 React 状态中的文章是两份数据。接口保存成功，不会自动修改浏览器里的 `articles` 数组。

第 14 章直接用更新响应替换旧行；第 15B 章接入筛选分页后，保存成功还要重新请求当前列表。例如当前筛选草稿，文章发布后应从列表中消失，总数也应减少。

列表响应中的两部分要分别使用：

| 响应数据 | 后端怎样得到 | 页面怎样使用 |
|---|---|---|
| `data` | `findMany({ where, skip, take })` | Table 显示当前页的文章 |
| `pagination.total` | `count({ where })` | 分页器显示全部符合条件的数量 |

例如符合条件的文章共 23 篇，每页 10 条，第 2 页的 `data.length` 是 10，`total` 仍是 23。**当前页条数不等于总数。**

第 14 章的 `apiRequest()` 只返回响应里的 `data`。因此第 15B 章要求列表请求保留 `pagination`，否则后端虽然发了总数，前端也会在请求封装中把它丢掉。这里的具体改动见 [15B 第 3 节](./15B-标签管理与页面联调.md)。

## 9. 后端抛出的错误，怎样变成页面上的提示

后端的 `AppError` 或 `ZodError` 不会作为 JavaScript 错误对象跨网络传到浏览器。中间件先把它变成 HTTP 状态码和 JSON，前端再决定如何处理：

```text
后端操作失败
→ repository 按需转换错误，其余继续抛出
→ Express 5 交给 errorHandler
→ 返回 422、404 或 409 等状态码和错误 JSON
→ 前端 fetch 得到 Response
→ apiRequest 检查 response.ok，失败时读取错误 JSON 并 throw new Error(...)
→ 页面 catch 显示提示
```

`fetch` 收到 422 或 500 响应时，不会仅因状态码而自动抛错，所以第 14 章的请求函数写了 `if (!response.ok)`。后端错误和前端重新抛出的 `Error` 是两次不同的抛错。

例如标签 id 重复，后端响应里有：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数不正确",
    "details": [{ "field": "tagIds", "message": "标签不能重复" }]
  }
}
```

当前请求封装只读取 `error.message`，所以页面显示“请求参数不正确”。`details` 中虽然有“标签不能重复”，也不会自动出现在表单字段下面；若要展示，需要前端读取它并交给对应的 Form 字段。这里先分清已有行为，不新增字段错误展示功能。

后端四类错误的来源与错误码对照，回看[第 15 章第 10 节](./15-数据关系JOIN和事务.md)。

## 10. 联调时按这四步查数据

1. **看请求**：在浏览器 Network 中检查 URL、Query 和 Payload。字段没传，还是传了 `null`、`""`、`[]`？id 是数字还是字符串？
2. **看后端输入与保存结果**：确认传给 repository 的是 `.parse()` 返回的 `input`，再用 TablePro 查看实际记录。不要只凭输入框是否空白判断数据库值。
3. **看响应**：状态码是什么？`data` 是否包含最终标签？`pagination` 是否存在？日期是字符串还是 `null`？
4. **看前端使用**：请求封装有没有丢掉字段？页面是否重新请求并更新状态？表单回填是否做了 `?? ""` 或标签 id 提取？

能沿着“表单值 → 请求 → 校验结果 → 数据库 → 响应 → 页面”说清每一步，就回到[第 10 章](./10-MiniCMS项目总览.md)验收阶段 5，再继续第 16、16A 章的登录功能。
