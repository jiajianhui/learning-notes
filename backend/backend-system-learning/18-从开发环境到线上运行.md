# 18. 公开内容和生产运行：让个人网站读到正式文章

> Mini CMS 阶段 8：阶段 7 和并列的 shadcn/ui 管理后台完成后，用本章连通公开文章 API、个人网站列表与详情页，再准备生产运行。

## 这一章完成什么

阶段 5 已经建立草稿、发布、撤回、标签和 `publishedAt`；阶段 6 已经把管理接口放到登录保护后；阶段 7 已经能自动验证核心 API。现在还差最后一条产品链路：

```text
管理后台发布文章
-> 公开 API 只读取已发布内容
-> 个人网站显示文章列表和详情
-> content 在详情页中变成可阅读的正文
-> Mini CMS 和数据库进入生产环境
```

本章先在本地完成公开阅读链路，再建立构建、环境变量、迁移、日志和备份地图。全部本地检查通过后，使用 [18A-用 1Panel 和 Docker Compose 部署 Mini CMS](./18A-用1Panel和Docker-Compose部署MiniCMS.md) 完成真实自托管部署。本项目不使用宝塔。

## 先完成公开文章 API

管理接口要读取草稿并修改数据，所以继续受阶段 6 的登录保护。个人网站改用单独的公开路由：

```text
GET /api/public/articles
GET /api/public/articles/:slug
```

公开列表只返回展示卡片需要的字段，例如标题、slug、摘要、发布时间、封面地址和标签，不返回每篇文章的完整 `content`。公开详情使用 slug 查询单篇文章，再返回正文。

如果个人网站需要文章封面，本阶段再给 `Article` 增加可为空的字段，并同步管理表单和公开响应：

```prisma
coverImageUrl String? @map("cover_image_url")
```

它只保存图片 URL，不处理文件上传。暂时不需要封面时可以不增加，正文里的图片仍由正文格式表达。

两个接口都必须由后端固定限制：

- 只查询 `status = published` 且 `publishedAt` 不为 `null` 的文章。
- 草稿、已撤回文章和不存在的 slug 都不能通过公开接口读到。
- 默认按 `publishedAt` 从新到旧排序。
- 不直接复用会返回全部管理数据的 `/api/articles` 查询。

阶段 7 已经建立 Vitest 和 Supertest。本阶段继续补两类接口测试：已发布文章可以公开读取；草稿和撤回文章不能公开读取。

## `content` 现在仍然只是字符串

从数据库和 Express 的角度看，`content` 继续是 `String`：

```text
管理后台提交字符串
-> Zod 校验字符串
-> Prisma 把字符串保存到 PostgreSQL
-> 公开详情 API 原样返回字符串
```

阶段 5～7 不需要把数据库字段改成特殊的 Markdown 或 MDX 类型。数据库本身也没有这两种正文类型；差别发生在个人网站怎样解释这段字符串。

到本阶段真正修改个人网站前，先检查它已经练习过的 MDX 实现，再决定：

- 只需要标题、段落、列表、引用、代码块、链接和图片时，使用 Markdown 即可。
- 确实需要在正文中插入受控 React 组件时，再复用或调整现有 MDX 方案。

MDX 可以理解为“Markdown 加 JSX 组件”，不是把 Markdown 转换成 HTML 的工具。以前练过的文件型 MDX 可以作为参考，但从数据库读取字符串后怎样编译和限制组件仍要在个人网站中确认。若选择 MDX，只开放明确允许的组件，不让正文随意导入或执行代码。

无论最后选择 Markdown 还是 MDX，`content` 都可以继续保持数据库 `String`，不需要为了这个选择修改 Prisma 字段类型。

## 文章详情页怎样形成最终排版

正文格式负责表达内容结构，详情页组件和 CSS 负责视觉：

```text
公开详情 API 返回 content
-> 个人网站按选定方案解析正文
-> 标题、段落、列表、引用、代码块、链接和图片变成页面元素
-> 文章详情组件组织标题、摘要、日期、标签、封面和正文
-> CSS 决定字体、内容宽度、留白、层级、颜色和响应式样式
```

最终文章详情页的布局和正文排版参考：

- [HEY World 的 DHH 文章](https://world.hey.com/dhh/linux-as-the-new-developer-default-at-37signals-ef0823b7)：参考窄栏、克制留白、简洁元信息和专注正文的详情页布局。
- [Vercel Blog 的 `design.md` 文章](https://vercel.com/blog/how-our-agents-build-on-brand-pages-with-design-md)：参考标题层级、长文节奏、大图、链接和代码内容的正文排版。

这里只参考文章详情页，不复制对方的网站导航、品牌标识或内容存储方案。第一版至少检查：

- 标题、摘要、发布时间和标签有清楚的主次关系。
- 普通段落保持适合长时间阅读的行宽和行距。
- 多级标题、列表和引用能明显区分，但不过度装饰。
- 代码块可以横向滚动，不撑破移动端页面。
- 有封面时，封面和正文图片都保持清晰，宽度不会破坏阅读节奏。
- 手机和桌面宽度下都不需要左右拖动正文。

## 在本地验证完整发布链路

进入部署前，先完成一次真实操作：

```text
在管理后台新建草稿
-> 草稿不出现在个人网站
-> 发布后出现在公开列表
-> 点击进入文章详情页
-> 正文结构和样式正常
-> 撤回后公开列表和详情都不能继续访问
```

做到这里，才能说明 CMS 不只是“数据库里有文章”，而是真的把正式内容发布到了个人网站。

## 再从本地运行走向线上运行

开发环境中可以同时运行管理后台、Express 和 PostgreSQL，个人网站也可以在自己的项目中单独启动。线上环境还要考虑域名、HTTPS、构建、环境变量、数据迁移和日志。

HTTPS 是加密传输的 HTTP，避免密码和 Cookie 在网络传输时直接暴露。

部署对象始终是已经完成的真实 `mini-cms`：管理后台、`server` 和 PostgreSQL 各自使用生产配置，不再新建部署 demo。个人网站保留在自己的项目中，通过正式 API 域名读取内容。

## 从本地运行到线上运行还要补什么

### 1. 开发和生产是两套运行方式

开发环境重视：

- 热更新。
- 调试信息。
- 本地数据库。
- 快速修改。

生产环境重视：

- 稳定启动。
- HTTPS。
- 密钥安全。
- 日志和故障定位。
- 数据备份和迁移。

不能直接把开发服务器当作线上运行方式。

### 2. 后端要有明确构建和启动命令

```text
npm run dev
-> 开发时运行 TypeScript

npm run build
-> 编译并检查

npm run start
-> 运行生产构建
```

README 要写清楚 Node.js、环境变量、数据库和启动顺序。

### 3. 数据库变更要可重复

线上不能依赖“我记得自己手动建过哪些表”。

需要保存：

- `schema.prisma` 和生成的迁移文件。
- 执行顺序。
- 修改结构前的数据备份。

代码版本和数据库结构必须能够对应。

Prisma 的开发和生产命令不要混用：

```text
本地开发：prisma migrate dev
-> 根据 schema.prisma 创建迁移，并应用到开发数据库

构建阶段：prisma generate
-> 生成当前代码需要的 Prisma Client

测试、预发布和生产：prisma migrate deploy
-> 只按顺序应用已经提交的迁移
```

`migrate dev` 会使用开发流程检查结构差异，不能拿来操作生产数据库；`migrate deploy` 不会替你生成 Prisma Client，所以构建流程仍要显式执行 `prisma generate`。迁移应由部署流程执行，不要为了上线临时把生产数据库地址复制到本机。

### 4. 健康检查只回答服务是否可用

```text
GET /api/articles/health
```

可以检查应用是否运行，必要时增加数据库连通性信息，但不要返回密码和内部配置。

### 5. 日志帮助定位线上问题

至少记录：

- 请求方法和路径。
- 响应状态码。
- 请求耗时。
- 未知错误的内部细节。

不要在日志中记录密码、完整 Cookie 和敏感密钥。

## 常见的线上运行关系

```text
个人网站文章列表和详情页 ─┐
                          ├─> HTTPS API 域名 -> Express -> PostgreSQL
Next.js 管理后台 ─────────┘
```

托管 PostgreSQL 表示数据库运行、升级和基础维护主要由云平台负责，应用通过数据库地址连接它。第 18A 章的第一次自托管练习会把 PostgreSQL 放进同一份 Docker Compose，并通过持久卷和备份任务保存数据。

前端和后端可以分别部署，也可以由同一平台管理，但它们的职责和环境变量仍然分开。

## 进入部署实操前做到什么程度

先保证：

- 两个公开文章接口可以在本地读取已发布内容，并拒绝公开草稿和撤回文章。
- 个人网站的文章列表和详情页已经读取真实 API，不再依赖写死的临时文章。
- `content` 的 Markdown 或 MDX 解析方案已经根据个人网站现状确定。
- 文章详情页已经按两个参考链接完成第一轮布局和正文排版检查。
- 公开接口的核心规则已有自动化测试。
- `.env.example` 完整。
- 真实 `.env` 不提交。
- `build`、`start`、`test` 命令可用。
- Prisma 迁移有记录并且能在新数据库重复执行。
- 有 `/api/articles/health`。
- 有基础请求和错误日志。
- README 能指导新环境启动。
- 数据库知道怎样备份。

## 小结

```text
公开文章 API
-> 只把已经发布的内容交给个人网站

content String
-> 数据库存储正文字符串，个人网站再决定怎样解析

文章详情组件和 CSS
-> 决定最终的详情页布局和正文排版

开发命令
-> 提供热更新和调试信息，方便在本地修改代码

构建和启动命令
-> 生成并运行要部署的代码

环境变量
-> 让数据库地址和密钥留在代码之外

迁移文件
-> 让新环境可以按相同顺序建立数据库结构

健康检查和日志
-> 确认服务是否运行，并在出错时帮助定位问题

备份
-> 数据丢失或损坏时，可以用来恢复
```

部署不是把代码上传一次，而是让系统能够安全、稳定、可重复地运行。
