# 19. 文章写作、预览与内容排版

> Mini CMS 阶段 8 的第一步。完成两套后台后，用本章完善文章写作、预览和公开阅读，再进入第 20、20A 章准备上线与部署。

前面的后台能保存和发布文章，但正文只是一个文本框。现在要让它真正适合写文章：能设置小节标题、编排列表和图片，保存后继续修改，并在发布前看到网站上的排版效果。

本章先把文章新建、编辑整理成独立写作页面，再用官方 [Simple Editor 模板](https://tiptap.dev/docs/ui-components/templates/simple-editor)接通 JSON 保存、回显和预览。标题与正文组成连续的写作区，发布设置放在侧栏；工具栏沿用模板，学习重点放在完整的写作流程和数据流转。Markdown 只做简短对照。

| 步骤 | 得到什么 | 先掌握什么 |
|---|---|---|
| 独立写作页面 | 新建和编辑共用写作布局，保存后可以继续写 | 页面、表单、正文编辑器各自负责什么 |
| 模板接入与保存 | 写出带格式的文章，保存后重新打开 | 模板怎样连接表单，JSON 怎样经过 API 和数据库 |
| 公开阅读 | 个人网站读取并展示已发布文章 | 同一份 JSON 怎样变成只读正文 |
| 正文排版与预览 | 图片、代码、表格，以及统一的文章页面 | 内容结构怎样变成阅读效果 |
| 双后台写作体验 | 两套后台能继续编辑同一篇文章 | 不同表单接法下保持相同的保存与预览行为 |

先在 `admin-web-antd` 跑通，再接入 `admin-web-shadcn`。两边继续使用原来的 fetch、Axios 和同一套 Express API。

## 1. 先建立适合长文的独立写作页面

### 1.1 我们要做出的文章效果

本章参考这些真实文章的内容组织，不推测它们使用了什么编辑器或 CMS：

- [Vercel：How our agents build on-brand pages with design.md](https://vercel.com/blog/how-our-agents-build-on-brand-pages-with-design-md)：分节长文、列表、配图与图注。
- [Raycast：Raycast for iOS](https://www.raycast.com/blog/raycast-for-ios)：产品说明、分级标题和连续的功能配图。
- [OpenAI：Introducing GPT-4.5](https://openai.com/index/introducing-gpt-4-5/)：文章头部、章节组织和图文内容。

把参考变成本项目可检查的目标：文章头部有标题、摘要、日期、标签和可选封面；正文有稳定的阅读宽度和段落节奏；图片可以使用正文宽度或宽幅；代码和表格在手机上单独横向滚动。

这里的“文章模板”是公开阅读页面的布局；Simple Editor 是后台的编辑器界面，两者分别负责展示和输入。写作者选择“二级标题”“引用”“宽幅图片”等内容类型，页面负责具体字号、颜色和间距。第一版不在编辑器里开放任意字体、颜色和像素宽度，也不做参考网站里的所有互动演示。

### 1.2 Markdown 和富文本 JSON 分别保存什么

例如一段加粗文字，Markdown 可以写成：

```md
这是 **重点**。
```

Tiptap 会用对象描述“段落里面有文字，其中一段带加粗标记”：

```json
{
  "type": "doc",
  "content": [
    {
      "type": "paragraph",
      "content": [
        { "type": "text", "text": "这是 " },
        { "type": "text", "text": "重点", "marks": [{ "type": "bold" }] },
        { "type": "text", "text": "。" }
      ]
    }
  ]
}
```

`doc` 是整篇正文，`paragraph` 是段落，`text` 是文字，`marks` 表示文字上的格式。写作者不需要手写 JSON；编辑器会在输入和点击工具栏时生成它。

本章把 `Article.content` 从 Prisma `String` 改为 `Json`，保存上面的对象。标题、slug、摘要、状态、发布时间和标签仍然是独立字段。JSON 是唯一正文来源，不再同时维护可编辑的 Markdown 或 HTML 副本。

```text
Tiptap 编辑内容
→ getJSON() 得到正文对象
→ 表单把对象放进 content
→ Express 校验正文结构
→ Prisma 写入 PostgreSQL JSONB
→ 详情接口返回对象
→ 编辑器回显，或 ArticleBody 渲染文章
```

这里改变的是正文 contract。前面章节先用字符串完成 CRUD 的步骤仍然成立，不需要回头重写每一章。

### 1.3 ArticleForm 继续管理整篇文章

Tiptap 只替换 `content` 的输入控件，ArticleForm 继续管理整篇文章并统一提交。字段在数据上分开，不代表界面要排成一串带边框的输入框。标题可以是大字号、无常驻边框的输入框，与下方正文组成连续的文章画布。

Ant Design 提供表单、输入、选择等基础组件，没有直接包办写作、预览和发布的文章编辑器。这里组合已有控件和 Tiptap，分工如下：

| 字段 | Ant Design 后台 | shadcn/ui 后台 |
|---|---|---|
| title、slug、summary | 原来的 Input、TextArea 或 ProForm 对应组件 | 原来的 Input、Textarea |
| 标签 | Select 多选，放在标题下方 | 对应的标签选择控件 |
| 状态 | 由保存、发布和撤回动作决定 | 同样的操作规则 |
| content | Form.Item 内的 ArticleEditor | Controller 内的同一个 ArticleEditor |

`ArticleEditor` 是我们给模板增加表单接口后的名称。它接收 `value`，在内容变化时调用 `onChange(json)`；表单因此能像管理一个输入框一样管理它，只是字段值从字符串变成了对象。正文里的 h2/h3 是小节标题，文章标题仍来自独立的 `title` 字段。

先记住三个动作，后面会在模板原有的 `useEditor()` 中接上：

```text
输入：onUpdate → editor.getJSON() → onChange → 表单 content
保存：表单提交 → fetch / Axios → Express → Prisma
回显：详情响应 → 表单 value → editor.commands.setContent()
```

编辑器不会因为发生 `onUpdate` 就自动保存到数据库。点击保存或发布按钮，才发送创建或更新请求。

### 1.4 先迁移新建和编辑入口，跑通已有保存链路

前面的 Drawer / DrawerForm 用来练习 CRUD；长文写作需要持续输入、插图和预览，本章改用独立页面。此时先保留正文 TextArea 和字符串接口，让已有文章能在新页面中创建、修改，再进入第 2 节替换正文。这一步建立的路由、表单和保存流程会继续使用。

在 `admin-web-antd/app/admin/articles/` 中调整：

```text
page.tsx                       保留列表、筛选、分页和删除
new/page.tsx                   新建文章入口
[id]/edit/page.tsx             编辑文章入口，按 id 请求详情
_components/article-form.tsx   两个入口共用的表单与写作布局
```

如果第 16C 章已经调整文件位置，在现有组件上修改，不复制第二套表单。第 28 章的 shadcn/ui 后台已有新建、编辑页，后面只需调整布局和保存后的行为。

按下面的顺序迁移现有代码：

| 位置 | 修改动作 |
|---|---|
| 文章列表 | 新建按钮跳到 `/admin/articles/new`，编辑按钮跳到 `/admin/articles/${id}/edit`；移除文章 Drawer 和它的开关、详情状态 |
| 新建页 | 复用标签请求与默认值，挂载同一个 ArticleForm；调用 `createArticle()` |
| 编辑页 | 从路由读取 id，将原来 `openEditDrawer(id)` 内的详情请求迁到页面加载流程；加载成功后挂载表单 |
| ArticleForm | 保留字段规则、提交与错误处理，去掉对抽屉关闭的依赖；`onCancel` 改为表达实际用途的 `onBack` |
| ProComponents 版 | 将文章 DrawerForm 换成页面内 ProForm，保留字段配置；不用 `return true` 表示关闭，也不再调用列表的 `actionRef.reload()` |

编辑页可以沿用第 28 章的 `useParams<{ id: string }>()` 读取 id。请求前检查它是正整数；保留加载、失败重试、404 和登录失效处理。详情与标签加载完成后再挂载表单，继续使用 `summary ?? ""` 和 `articleTags.map(item => item.tagId)` 回填。详情请求中清理过期结果，避免快速切篇时回填到另一篇。

新建页中，替换原来“创建后关闭抽屉”的处理。下面是**局部修改片段**，放在调用过 `useRouter()` 的客户端页面内，导入沿用现有 `features/articles/api.ts` 和类型文件：

```tsx
async function handleCreate(values: ArticleFormValues) {
  const created = await createArticle(values);
  router.replace(`/admin/articles/${created.id}/edit`);
}
```

当前 fetch 封装已经解开响应的 `data`，所以这里直接读取 `created.id`。`replace` 将新建地址替换为已创建文章的编辑地址，继续保存时使用 PATCH，避免重复创建。失败时不跳转，让 ArticleForm 原有的错误处理保留输入。第 1.6 节接入离开检查后，这次保存成功的内部跳转应直接放行。

编辑页的保存函数仍调用 `updateArticle(id, values)`，成功后留在当前页。将响应按详情加载时相同的规则转成表单值，包括空摘要和标签 id，再更新表单与已保存快照；不要再关闭抽屉或跳回列表。仅修改 `initialValues` 不会更新已挂载的 Ant Design 表单，需要同一表单实例的 `setFieldsValue()`；回填要在保存成功之后。

返回列表也要保留上下文：将已有的 `title`、`status`、`tagId`、`page`、`pageSize` 同步到列表 URL，列表从 URL 初始化查询。进入写作页时通过 `returnTo` 携带该列表地址，新建成功跳到编辑页时继续携带。上面的代码只展示创建后的主跳转，接入时补上这个查询参数。返回前只接受本站 `/admin/articles` 路径及其查询参数，没有有效来源就回列表首页；不要直接跳转任意传入的 URL，也不要假设 `router.back()` 一定返回列表。回到列表后按恢复的条件重新获取数据。

**验证：** 新建一篇纯文本草稿，保存后地址变成它的编辑地址；继续修改只发 PATCH。直接刷新编辑地址能回显文章，保存失败仍保留输入；从带筛选的第 2 页进入文章再返回，筛选与分页仍在。

### 1.5 将表单排成一张连续的文章画布

页面以写作为中心：上方放操作，左侧写文章，右侧放低频设置。新建和编辑使用同一布局，只改变初始数据和保存动作：

```text
← 返回文章列表       未保存         预览  保存草稿  发布
────────────────────────────────────────────────────
                                      文章设置（可收起）
       输入文章标题                    发布状态
       已选标签   + 添加标签           访问路径（slug）
                                      摘要
       正文工具栏                      发布时间
       开始写作……
       正文和图片……
```

按以下方式重排已有字段，不新增第二套表单状态：

- **标题与正文：** 保持左对齐；标题使用大字号输入框，正文紧随其后。删除重复的可见“文章内容”“标题”“正文”标签，保留 `aria-label`、聚焦样式和字段错误。正文内部只提供 h2/h3，文章主标题继续由 `title` 保存。
- **标签：** 放在标题下方，用紧凑的多选或标签样式呈现，右侧不重复放置。沿用已有标签选择能力，“添加标签”表示选择已有标签，不在本步增加标签创建流程。
- **文章设置：** 放 slug、摘要、发布状态和发布时间；状态与发布时间用于展示，状态变化由下节的动作触发。发布时间读接口，不伪造日期。未实现封面字段时先不显示封面控件。
- **尺寸与样式：** 写作文字区先以约 720px 最大宽度为起点，设置栏约 280px，窄屏改为通过按钮打开设置面板。白底、深色文字，减少卡片边框，用留白分组；压缩顶部和工具栏高度，为正文留空间。
- **滚动：** 正文随页面滚动，工具栏可在顶栏下方吸顶；不要再把正文放进一个固定高度、独立滚动的小框。收起设置栏时保留字段值。

单个 Form / ProForm 可以同时包住顶部操作、写作区和设置区，字段不必纵向排列。将底部的重复提交按钮移到顶部；使用 ProForm 时关闭默认 submitter，再接同一表单实例的提交。标题、摘要等控件仍是 Ant Design 组件，只是布局和外观围绕写作调整。第 2 节仅将这个布局中的正文 TextArea 换为 ArticleEditor，保留其余结构。

此时不提前做空的预览按钮或假工具栏；格式工具栏在第 2 节接入，预览在第 4.3 节接入。编辑区的文字排版最终复用第 4.2 节的正文样式，预览则展示包含文章头部的完整发布效果。

**验证：** 标题、标签和正文看起来属于同一篇文章；切换或收起设置不会丢值；窄屏无需横向滚动就能填写所有必填字段。

### 1.6 保存、发布和离开分别怎样处理

第一版采用显式保存。沿用现有 `draft` / `published` 状态和创建、更新接口，不增加自动保存或文章版本表：

| 当前状态与动作 | 请求与页面结果 |
|---|---|
| 新建或草稿：保存草稿 | 校验表单，提交全部字段并指定 `status: "draft"`；新建成功进入编辑页，已有草稿留页 |
| 新建或草稿：发布 | 校验同一份表单，指定 `status: "published"`；新建成功进入编辑页，已有文章留页，显示接口返回的状态与发布时间 |
| 已发布：保存修改 | 提交当前字段，保持 `published`；提示修改会更新公开文章，成功后留页 |
| 已发布：撤回 | 确认后 PATCH `status: "draft"`，成功后更新状态；有未保存修改时先保存或明确放弃再撤回 |
| 预览 | 第 4.3 节接入，只展示当前表单内容，不调用保存或发布接口 |

将“保存草稿 / 发布”的意图交给同一个提交函数。Ant Design 可以由按钮调用同一表单实例的 `validateFields()`，再合并目标状态并调用已有保存回调；不要一边让按钮原生 submit，一边在 onClick 再发一次请求。`status` 仍是数据字段，不再同时放一个可编辑的状态下拉框。保存草稿也延续现有标题、slug、正文必填规则，空白文章不会自动落库。

保存反馈需要真实状态：加载已有文章后建立“已保存快照”；新文章以空表单为变化比较基准，显示“尚未保存”；有变化时显示“未保存”，请求中显示“保存中”，请求成功且无新变化时才显示“已保存”。失败保留输入和旧快照，并展示错误。只打开一个未填写的新建页，不应触发丢失修改的提醒。

比较时包含所有可编辑字段，标签 id 排序后再比较；第 2 节正文改为 JSON 后，比较其序列化内容，不比较对象引用。保存期间禁用会改变文章的控件和重复提交，避免响应覆盖请求期间的新输入。回填成功响应时不重建整个编辑器，不要将 `updatedAt` 或随机值作为组件 key。

离开保护跟随同一个变化状态：站内的返回、菜单和取消操作先检查未保存修改；确认离开才跳转。刷新或关闭页面时，仅在有变化时注册 `beforeunload`，保存成功后移除。它不能代替站内导航拦截，浏览器后退也要实际验证；若当前路由方案不能完整拦截后退，补按文章 id（新建使用独立键）区分的本地草稿恢复，并在恢复前让用户选择，保存或明确放弃后清除对应副本。

对已发布文章，每次输入都自动调用现有更新接口会直接改变公开内容。想保留“已发布版本之外的修改草稿”，需要额外定义版本规则，本章先不增加。

**验证：** 保存成功后继续输入，提示立即变成“未保存”；模拟失败后仍能继续修改并重试；离开确认中选择留下，所有内容仍在。重新打开草稿不会误显示为已发布；第 3 节接通公开 API 后，再验证发布与撤回后的公开状态。

## 2. 用模板跑通编辑、保存与回显

独立写作页面已经能保存纯文本文章，本节在这个页面中接入模板并改变正文 contract。结束时要能保存一篇带小标题、加粗、列表和链接的文章，重新打开后格式仍然存在。

### 2.1 安装模板，先认清改哪几个位置

在真实 `mini-cms/admin-web-antd` 目录执行官方的现有项目安装命令：

```bash
npx @tiptap/cli@latest add simple-editor
```

CLI 会把模板及它依赖的组件、Hook 和样式作为源码加入工程。它提供的是可修改的界面代码；现有 Express API、认证和数据库继续使用。先看安装产生的 Git diff，记录 CLI 版本，并保留生成源码、依赖和锁文件，后续在这份源码上修改。

按当前官方文档，入口为 `components/tiptap-templates/simple/components/simple-editor.tsx`。如果生成位置不同，按 CLI 输出查找 `SimpleEditor`，不要再新建一份同名编辑器。主要看这几处：

| 模板位置 | 本章怎样处理 |
|---|---|
| `useEditor({ extensions, content })` | 换成共享文档规则和表单传入的正文 |
| `MainToolbarContent`、移动端工具栏 | 保留现成按钮，裁剪本项目不开放的格式 |
| `EditorContext.Provider`、`EditorContent` | 保留，让工具栏操作同一个编辑器实例 |
| 示例正文与演示页面 | 取消示例正文导入，正式使用文章详情或空文档；不用的演示路由删除 |
| `simple-editor.scss` | 适配写作页主区域，保留局部布局；正文样式由第 4 节统一 |

模板的 SCSS 需要 Sass，CLI 会处理相关依赖和全局样式导入；核对生成结果即可。它原有的演示样式包含 `body`、全屏宽高和字体设置，不能直接套到整个管理后台。先移除演示字体导入、`html/body/#root/#app` 和全局滚动条规则，把其中的布局变量保留在编辑器容器内。变量文件中的 `--tt-*` 可留在 `:root`，供弹出层使用；字体、文本缩放等普通声明则限定到编辑器，避免影响后台其他页面。

将 `simple-editor.scss` 的布局改为下面的起点，工具栏组件自身的 SCSS 保留：

```scss
.article-editor.simple-editor-wrapper {
  --tt-toolbar-height: 44px;
  width: 100%;
  height: auto;
  overflow: visible;
}
.article-editor .simple-editor-content {
  width: 100%;
  max-width: none;
  margin: 0;
}
.article-editor .article-body {
  min-height: 360px;
}
```

### 2.3 后端要检查“是不是允许的正文”

前面的 `z.string().trim().min(1)` 已经不适用。一个对象即使是合法 JSON，也可能包含不存在的节点，或者把列表项放错位置。

在共享包的 `schema.ts` 新增下面的最小完整实现：

```ts
import { getSchema, type JSONContent } from "@tiptap/core";
import { z } from "zod";
import { createArticleExtensions } from "./extensions.js";

export type ArticleDocument = JSONContent & {
  type: "doc";
  content: JSONContent[];
};

export function emptyDocument(): ArticleDocument {
  return { type: "doc", content: [{ type: "paragraph" }] };
}

export function isWebUrl(value: unknown, protocols = ["https:"]) {
  if (typeof value !== "string") return false;
  try {
    return protocols.includes(new URL(value).protocol);
  } catch {
    return false;
  }
}

const editorSchema = getSchema(createArticleExtensions());

// 允许空段落，用于新文章和编辑中的预览。
export const documentSchema = z.json().transform((value, context) => {
  try {
    if (JSON.stringify(value).length > 500_000) {
      throw new Error("正文数据过大");
    }
    const doc = editorSchema.nodeFromJSON(value);
    if (doc.type.name !== "doc") throw new Error("正文必须是文档");
    doc.check();
    doc.descendants((node) => {
      if (node.type.name === "heading" && ![2, 3].includes(node.attrs.level)) {
        throw new Error("正文只允许二级和三级标题");
      }
      for (const mark of node.marks) {
        if (mark.type.name === "link" && !isWebUrl(mark.attrs.href, ["https:", "http:", "mailto:"])) {
          throw new Error("链接地址不支持");
        }
      }
    });
    if (doc.textContent.length > 100_000) {
      throw new Error("正文文字不能超过 100000 个字符");
    }
    return doc.toJSON() as ArticleDocument;
  } catch (error) {
    context.addIssue({
      code: "custom",
      message: error instanceof Error ? error.message : "正文格式不正确",
    });
    return z.NEVER;
  }
});

// 保存时延续原来的规则：正文不能只有空白。
export const contentSchema = documentSchema.refine(
  (value) => editorSchema.nodeFromJSON(value).textContent.trim().length > 0,
  { message: "正文不能为空" },
);
```

`getSchema()` 从已启用的扩展得到文档规则；`nodeFromJSON()` 读取对象；`check()` 检查节点和嵌套是否合法。这里不创建编辑器，也不需要浏览器。最后返回整理后的 JSON，后端保存校验结果，不保存未经检查的原始请求体。

在 `server/src/modules/articles/article-schema.ts` 中，用共享包导出的 `contentSchema` 替换旧的字符串 Schema。创建时使用 `contentSchema`，更新时继续使用 `contentSchema.optional()`，其余字段规则保留：

```ts
import { contentSchema } from "@mini-cms/article-content/schema";
```

同时检查 `server/src/app.ts` 的 `express.json()` 请求大小限制。这里将整个 JSON 请求限制为 `1mb`，正文的文字数量和序列化长度由上面的规则继续限制：

```ts
app.use(express.json({ limit: "1mb" }));
```

不要重复注册第二个 JSON 中间件；替换现有配置。请求体超限时沿用错误中间件，返回明确的 413，而不是包装成未知的 500。

### 2.4 转换旧文章，再改变字段类型

在 `server/prisma/schema.prisma` 中只改 `Article` 的正文属性：

```prisma

```


先打开生成的 `migration.sql`。旧文章是普通文字，不能直接执行 `content::jsonb`：普通文字不是一个 JSON 文档。也不要接受会清空旧正文的迁移或用数据库重置来绕过这个问题。

下面是本次正文列转换的 SQL。先备份，在本地数据库副本验证后，把生成文件中对应的列类型变更替换为它；迁移文件中其他有意保留的变更另行检查。

```sql
BEGIN;

ALTER TABLE "articles" ADD COLUMN "content_rich" JSONB;

UPDATE "articles" AS article
SET "content_rich" = (
  SELECT jsonb_build_object(
    'type', 'doc',
    'content', jsonb_agg(
      CASE WHEN line = '' THEN jsonb_build_object('type', 'paragraph')
      ELSE jsonb_build_object(
        'type', 'paragraph',
        'content', jsonb_build_array(jsonb_build_object('type', 'text', 'text', line))
      ) END ORDER BY position
    )
  )
  FROM regexp_split_to_table(article."content", E'\r?\n')
       WITH ORDINALITY AS lines(line, position)
);

ALTER TABLE "articles" ALTER COLUMN "content_rich" SET NOT NULL;
ALTER TABLE "articles" DROP COLUMN "content";
ALTER TABLE "articles" RENAME COLUMN "content_rich" TO "content";

COMMIT;
```

它把旧正文的每一行变成一个段落，空行保留为空段落。这里转换的是此前练习产生的纯文本，不解析 Markdown，也不编译旧网站的 `.mdx` 文件。已有 MDX 文章里的图片组等组件需要逐篇转换成新支持的内容，不能直接粘贴到 JSON 字段。

检查 SQL 后执行：

```bash

npx prisma generate
```

同步修改这些真正受影响的位置：

| 位置 | 本次变化 |
|---|---|
| `article-schema.ts` | `content` 接受文档对象；更新字段仍可省略 |
| `article-repository.ts` | 接收校验后的对象并交给 Prisma，不对正文调用 `trim()` |
| 两个后台的详情、创建、更新类型 | `content: string` 改为 `ArticleDocument` |

| 种子数据、18A 的文章测试数据 | 正文改成有效文档对象 |

Prisma 返回的 `JsonValue` 不保证一定符合文章结构。组装详情响应时，用 `documentSchema.parse(article.content)` 得到 `ArticleDocument`。如果写入处需要 Prisma 的 `InputJsonObject` 类型，只在通过 `contentSchema` 校验后进行类型衔接；类型断言本身不能替代校验。

### 2.5 给模板接上 value 和 onChange

在已经移入共享包的 `simple-editor.tsx` 中修改现有组件。下面是**局部修改片段**：新增类型和导入，替换函数参数与 `useEditor` 配置，再把两个 Effect 放在它后面；保留模板原有的工具栏、移动端逻辑与 JSX 返回值，不新建第二个编辑器。

```tsx
import { useEffect } from "react";
import { createArticleExtensions } from "@mini-cms/article-content/extensions";
import { emptyDocument, type ArticleDocument } from "@mini-cms/article-content/schema";

export type ArticleEditorProps = {
  value?: ArticleDocument;
  onChange?: (value: ArticleDocument) => void;
  onBlur?: () => void;
  disabled?: boolean;
};

// 替换原来的 SimpleEditor() 参数；下面内容放在同一个函数中。
export function SimpleEditor({
  value, onChange, onBlur, disabled = false,
}: ArticleEditorProps) {
  const editor = useEditor({
    extensions: createArticleExtensions(),
    content: value ?? emptyDocument(),
    immediatelyRender: false,
    editable: !disabled,
    editorProps: {
      attributes: { class: "article-body", "aria-label": "文章正文" },
    },
    onUpdate: ({ editor }) => onChange?.(editor.getJSON() as ArticleDocument),
    onBlur: () => onBlur?.(),
  });

  useEffect(() => {
    if (!editor) return;
    const nextValue = value ?? emptyDocument();
    if (JSON.stringify(editor.getJSON()) !== JSON.stringify(nextValue)) {
      editor.commands.setContent(nextValue, {
        emitUpdate: false,
        errorOnInvalidContent: true,
      });
    }
  }, [editor, value]);

  useEffect(() => {
    editor?.setEditable(!disabled);
  }, [editor, disabled]);

  // 原有 Hook、工具栏状态、EditorContext.Provider 和 JSX 返回值保留在这里。
}
```

合并现有的 `useEffect` 导入，不要重复声明。`useEditor`、`EditorContext` 等仍使用模板已有导入。这个片段末尾的注释代表要保留的模板代码，不能把整个函数照抄后删掉原来的返回值。

同时把模板最外层容器的 class 改为 `article-editor article-page simple-editor-wrapper`。保留内部的 `EditorContent` 和 `EditorContext.Provider value={{ editor }}`，让模板按钮和正文始终使用这里创建的同一个实例。

三条连接分别解决：

- **输入交给表单：** `onUpdate` 中的 `getJSON()` 得到正文对象，`onChange` 更新表单的 `content`。
- **表单回填编辑器：** 详情请求或表单重置改变 `value`，Effect 再用 `setContent()` 显示新正文；内容相同时不重设光标。
- **防止回填循环：** `emitUpdate: false` 表示外部回填不再触发一次 `onChange`。`immediatelyRender: false` 则用于 Next.js 的服务端渲染环境。

这里展示 `getJSON()` 与 `setContent()` 是为了理解已有模板的输入输出，不要求另做一套手写编辑器。格式按钮都使用 `type="button"`；保存期间编辑区和会改变正文的工具栏操作一起禁用，弹出的链接/图片面板也要检查 `disabled`。

在共享包 `src/editor.tsx` 中只保留客户端导出，下面路径对应附录中的目录：

```tsx
"use client";

export { SimpleEditor as ArticleEditor } from "./ui/components/tiptap-templates/simple/components/simple-editor";
export type { ArticleEditorProps } from "./ui/components/tiptap-templates/simple/components/simple-editor";
```

在第 1 节已经调整好的 ArticleForm 中，替换正文这一项。使用 ProComponents 时替换 `ProFormTextArea`；基础组件版替换 `Form.Item` 中的 `Input.TextArea`。保留页面内的单个 Form / ProForm、标题和标签布局，以及右侧设置，不再保留文章 DrawerForm：

```tsx
import { Form } from "antd";
import { ArticleEditor } from "@mini-cms/article-content/editor";
import { contentSchema, emptyDocument } from "@mini-cms/article-content/schema";

// 放在已有表单中，不新建第二层 Form。
<Form.Item
  name="content"
  rules={[{
    validator: async (_, value) => {
      const result = contentSchema.safeParse(value);
      if (!result.success) throw new Error(result.error.issues[0].message);
    },
  }]}
>
  <ArticleEditor />
</Form.Item>
```

Form.Item 会传入 `value` 和 `onChange`。新建表单的默认值中增加 `content: emptyDocument()`，编辑时由详情值覆盖；替换原来的字符串校验，不再对正文使用 `whitespace` 或字符串 `max` 规则。把已有的提交状态传给 ArticleEditor 的 `disabled`，与保存按钮使用同一个状态。

保存函数仍然提交完整表单值：fetch 对整个请求对象调用 `JSON.stringify(values)`；Axios 直接接收对象。`content` 本身始终是文档对象，不单独序列化成字符串。已有创建/更新接口继续承接请求：

```text
ArticleForm 的 title、slug、content 等字段
→ 原来的 onFinish / onSubmit
→ POST /api/articles 或 PATCH /api/articles/:id
→ Express 的 contentSchema 校验
→ article-repository 将对象交给 Prisma
→ 返回文章详情，保存成功后更新已保存快照
```

Tiptap 负责正文输入，Ant Design 负责表单和提交，Express 负责校验与保存；三者各自完成原来的工作。

编辑已有文章时，先请求详情再挂载表单，并按文章 id 设置稳定的 `key`。切换文章要重建对应的编辑器，防止撤销历史串到另一篇；不要用每次都会变化的随机 key。已有的失败提示和保留输入逻辑继续使用。

把第 1.6 节已保存快照中的正文比较改为 `JSON.stringify(values.content)`。它比较内容，不比较对象引用；加载和保存成功后再更新快照，回填时不当作用户编辑。

**验证：** 新建一篇含二级标题、加粗、列表和链接的文章，确认 Network 请求中的 `content` 是对象；保存后留在编辑页，刷新或返回列表再打开，格式仍相同。再打开另一篇，确认内容和撤销历史不会串篇。制造保存失败，正文仍保留。

### 3.2 用同一个 ArticleBody 渲染 JSON

```tsx
import { renderToReactElement } from "@tiptap/static-renderer/pm/react";

export function ArticleBody({ content }: { content: unknown }) {
```


选中现有图片后，用 `updateAttributes("image", { src, alt, caption, layout })` 修改。图注由面板编辑，不假设图中已经出现可直接输入的富文本框。复制外部 HTML 图片时只承诺保留可识别的图片属性；跨后台完整回显依赖保存的 JSON。

在 `schema.ts` 的 `doc.descendants()` 回调中，保留第 2 节的标题和链接检查，再增加图片校验；`isWebUrl` 继续复用已有定义：

```ts
if (node.type.name === "image") {
  if (!isWebUrl(node.attrs.src)) throw new Error("图片需要有效的 HTTPS 地址");
  if (typeof node.attrs.alt !== "string" || typeof node.attrs.caption !== "string") {
    throw new Error("图片说明格式不正确");
  }
  if (!["normal", "wide"].includes(node.attrs.layout)) {
    throw new Error("图片宽度选项不正确");
  }
}
```

前后端使用同一校验入口，图片和链接面板从共享包的 `/schema` 入口导入 `isWebUrl`，确认属性有效后才插入正文；封面也使用相同的 HTTPS 地址规则。不要因为 JSON 没有直接写 HTML，就允许任意链接协议。保存仍要求正文含有非空文字，纯图片文章暂不纳入本轮。

模板已经处理了标题、列表、引用、代码和链接的工具栏交互。本节只增加项目需要的图片属性面板与表格操作，按钮样式沿用模板的 Toolbar/Button：

| 用户操作 | 编辑器调用 |
|---|---|
| 插入图片、修改选中图片 | 上面的 `insertContent(...)`、`updateAttributes("image", ...)` |
| 插入表格 | `insertTable({ rows: 3, cols: 3, withHeaderRow: true })` |
| 调整表格 | `addRowAfter()`、`addColumnAfter()`、`deleteRow()`、`deleteColumn()`、`deleteTable()` |

这些命令放在 `editor.chain().focus()...run()` 中。新增面板打开前记录选区位置，确认时恢复选区再插入；编辑现有图片时确认目标仍是选中的图片。取消面板不改变正文。代码高亮可以在基本代码块稳定后接入。

**验证：** 每新增一种内容，就走一遍“插入 → 保存 → 重新打开 → 网站显示”。额外尝试未知节点和不支持的 URL 协议，API 应拒绝。扩展变化后重新构建共享包，同时更新所有使用它的工程。

### 4.3 预览必须读取当前表单值

在共享包的 `renderer.tsx` 中继续增加 `ArticlePage`，让后台和网站连文章头部也共用：

```tsx
export type ArticlePageProps = {
  title: string;
  summary?: string | null;
  publishedAt?: string | null;
  tagNames: string[];
  coverImageUrl?: string | null;
  content: unknown;
};

export function ArticlePage(props: ArticlePageProps) {
  const date = props.publishedAt
    ? new Intl.DateTimeFormat("zh-CN", { timeZone: "Asia/Shanghai" })
        .format(new Date(props.publishedAt))
    : "尚未发布";

  return (
    <article className="article-page">
      <header className="article-header">
        <h1>{props.title || "未命名文章"}</h1>
        {props.summary && <p className="article-summary">{props.summary}</p>}
        <p className="article-meta">{date} · {props.tagNames.join(" / ")}</p>
        {props.coverImageUrl && <img className="article-cover" src={props.coverImageUrl} alt="" />}
      </header>
      <ArticleBody content={props.content} />
    </article>
  );
}
```

后台从表单中取标题、摘要、封面、标签和正文，映射成这些属性。Ant Design 使用同一表单实例的 `Form.useWatch`；shadcn/ui 使用 React Hook Form 的 `useWatch`。不要只读 `getFieldsValue()` 却没有订阅变化，也不要重新请求数据库里的旧正文来预览。

接通第 1.5 节顶栏的“预览”按钮，在同一个写作页面切换编辑与预览；预览时收起文章设置，按钮变为“返回编辑”。这是视图切换，不是离开文章，不触发未保存离开提醒。保留表单和编辑器实例，可以用 `hidden` 隐藏编辑区域，不要用条件分支卸载整个表单。

预览渲染当前表单快照，即使还没保存也能看。窄屏、桌面按钮分别给预览外层设置例如 `390px`、`1040px` 的最大宽度。所有预览、设置和格式按钮都不触发表单提交。校验发现必填的 slug 等设置字段有误时，展开设置面板并定位错误；字段隐藏时不能只提示“保存失败”而找不到原因。

个人网站也使用 `ArticlePage`，并提供同样的字体和 CSS。最终一致性来自同一份数据、扩展、组件、样式和相同的可用宽度，不能只凭“都装了 Tiptap”判断。

类型导入、详情回填和提交数据同步使用 `ArticleDocument`。Axios 仍然把完整表单对象放进 `data`，不单独序列化正文。

### 5.2 两套后台保持同一条写作流程

shadcn/ui 沿用第 28 章已有的新建、编辑路由，将“保存后返回列表”改为第 1.4 节的新建后进入编辑页、编辑保存后留页。复用第 1.5 节的标题、标签、正文与设置布局，以及第 1.6 节的保存、发布和离开规则；标签管理继续沿用各自已有的简单界面。

两套后台可以保留自己的按钮和设置控件。ArticleEditor、文档规则、预览组件和正文样式共用；shadcn/ui 不因为更换 UI 组件就另存一套 Plate JSON。这样同一篇文章才能在两个后台中直接继续编辑。

用两套后台分别检查以下行为：

| 体验 | 应该发生什么 |
|---|---|
| 格式工具栏 | 能恢复普通段落，按钮状态随选区变化；链接和图片用表单面板填写 |
| 中文输入和快捷键 | 输入法选字不中断；加粗、撤销、重做可用；格式按钮不触发提交 |
| 页面与保存 | 新建成功进入该文章编辑页，编辑保存后留页；反馈与请求结果一致 |
| 输入保护 | 失败保留输入；返回、刷新和后退不会无提示丢失修改 |
| 文章设置 | 可收起，窄屏可打开；字段错误能定位，收起不会丢值 |
| 预览 | 读取未保存内容，切换回来保留输入与撤销历史 |
| 返回列表 | 恢复进入文章前的筛选与分页，并重新获取列表 |

```json
}
```

上述核心文件的相对导入使用 `.js` 后缀，TypeScript 会输出可被 Node.js 加载的 ESM；`extensions.ts` 引入的 `image.ts` 也会随依赖一起编译。UI 源码不进入这个构建，保留 `"use client"`，由 Next.js 编译。模板通过包的 `/extensions`、`/schema` 入口使用编译后的规则，避免把客户端入口引入后端。

新增 `src/ui/editor-ui.scss`，引用 CLI 生成的变量与动画文件。下面路径对应 A 节目录，实际名字以生成结果为准：

```scss
@use "./styles/variables";
@use "./styles/keyframe-animations";
```

Sass 会找到 `_variables.scss` 等文件。组件自己的 SCSS 继续由组件导入，这个入口只补原先由应用全局 CSS 引入的变量与动画。

### C. 打包并让 Next.js 编译模板

源文件准备好后在包目录运行：

```bash
npm run build
npm pack
```

将生成的 `mini-cms-article-content-0.1.0.tgz` 复制到每个使用方自己的 `vendor/`：`server`、两个后台，以及个人网站。在各工程根目录运行：

```bash
npm install ./vendor/mini-cms-article-content-0.1.0.tgz
```

`server` 只导入 `/schema`，后台导入 `/editor`、`/renderer` 和样式，个人网站导入 `/renderer` 和文章样式。归档、使用方的 `package.json` 与锁文件一起纳入版本管理；编译产物 `dist/` 和 `node_modules/` 可以忽略。

两个后台都执行 `npm install -D sass`，并在已有的 `next.config.ts` 配置对象中加入下面一项，保留其余配置；已有数组时追加包名：

```ts
transpilePackages: ["@mini-cms/article-content"],
```

在后台根布局依次导入：

```tsx
import "@mini-cms/article-content/editor-ui.scss";
import "@mini-cms/article-content/styles.css";
```

模板的 TSX 和 SCSS 由 Next.js 处理，Ant Design 与 shadcn/ui 都能使用；个人网站只读编译后的 `/renderer`，不需要编辑器 UI 或 Sass。`npm run build` 只检查共享核心，两个后台的构建还要检查模板源码与样式是否完整。

**验证：** 在包目录先用 `npm pack --dry-run` 检查清单，要能看到 `dist`、`src/editor.tsx`、`src/ui` 与文章 CSS；在干净的使用方安装归档后构建，不能从原后台目录或本机绝对路径补找文件。

修改共享源码后提升包版本，重新构建、打包，并在使用方显式安装新的归档。不要用相同版本名覆盖归档后期待依赖自动更新。开发初期多一次打包动作，换来几个独立项目和 Docker 构建都使用相同的确定版本。

第 20A 章的 Dockerfile 会在 `npm ci` 前复制 `vendor/`。否则本地能安装，容器里仍会因找不到归档而失败。
