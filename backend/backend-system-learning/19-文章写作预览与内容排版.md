# 19. 文章写作、预览与内容排版

> Mini CMS 阶段 8 的第一步。先在已有的 Ant Design 后台完成文章写作、预览和公开阅读，再进入第 20、20A 章准备上线与部署。shadcn/ui 不是本章前置条件，第 6 节留到学习第二套后台时接入。

前面的后台能保存和发布文章，但正文只是一个文本框。现在要让它真正适合写文章：能设置小节标题、编排列表和图片，保存后继续修改，并在发布前看到网站上的排版效果。

本章先把文章新建、编辑整理成独立写作页面，再用官方 [Simple Editor 模板](https://tiptap.dev/docs/ui-components/templates/simple-editor)接通 JSON 保存、回显和预览。标题与正文组成连续的写作区，发布设置放在侧栏；工具栏沿用模板，学习重点放在完整的写作流程和数据流转。Markdown 只做简短对照。

完成本章后，可以继续阅读 [19A-提升写作体验](./19A-提升写作体验.md)，通过选中文字的浮动排版、空行 `+` 插入和收起固定工具栏，改进已有写作页。

| 步骤 | 得到什么 | 先掌握什么 |

| 独立写作页面 | 新建和编辑共用写作布局，保存后可以继续写 | 页面、表单、正文编辑器各自负责什么 |
| 模板接入与保存 | 写出带格式的文章，保存后重新打开 | 模板怎样连接表单，JSON 怎样经过 API 和数据库 |
| 统一展示准备 | 提取编辑器、预览和网站共用的正文扩展 | 数据来源不同，文章组件与样式共用 |
| 公开阅读 | 个人网站读取并展示已发布文章 | 同一份 JSON 怎样变成只读正文 |
| 正文排版与预览 | 图片、代码、表格，以及统一的文章页面 | 内容结构怎样变成阅读效果 |

## 1. 先建立适合长文的独立写作页面

### 1.1 我们要做出的文章效果

本章参考这些真实文章的内容组织，不推测它们使用了什么编辑器或 CMS：

- [Vercel：How our agents build on-brand pages with design.md](https://vercel.com/blog/how-our-agents-build-on-brand-pages-with-design-md)：分节长文、列表、配图与图注。
- [Raycast：Raycast for iOS](https://www.raycast.com/blog/raycast-for-ios)：产品说明、分级标题和连续的功能配图。
- [OpenAI：Introducing GPT-4.5](https://openai.com/index/introducing-gpt-4-5/)：文章头部、章节组织和图文内容。

把参考变成本项目可检查的目标：文章头部有标题、摘要、日期、标签和可选封面；正文有稳定的阅读宽度和段落节奏；图片提供正文同宽、宽幅和全宽三档；代码和表格在手机上单独横向滚动。

这里的“文章模板”是公开阅读页面的布局；Simple Editor 是后台的编辑器界面，两者分别负责展示和输入。写作者选择“二级标题”“引用”等格式、插入图片并选择宽度，页面负责统一字号、颜色和间距。第一版不开放任意字体和文字颜色，也不做参考网站里的所有互动演示。

### 1.2 Markdown 和富文本 JSON 分别保存什么

例如一段加粗文字，Markdown 可以写成：

```md
这是 **重点**。
```

Tiptap 会用对象描述“段落里面有文字，其中一段带加粗标记”：

```json
{
  "type": "doc",
  "content": [
    {
      "type": "paragraph",
      "content": [
        { "type": "text", "text": "这是 " },
        { "type": "text", "text": "重点", "marks": [{ "type": "bold" }] },
        { "type": "text", "text": "。" }
      ]
    }
  ]
}
```

`doc` 是整篇正文，`paragraph` 是段落，`text` 是文字，`marks` 表示文字上的格式。写作者不需要手写 JSON；编辑器会在输入和点击工具栏时生成它。

本章把 `Article.content` 从 Prisma `String` 改为 `Json`，保存上面的对象。标题、slug、摘要、状态、发布时间和标签仍然是独立字段。JSON 是唯一正文来源，不再同时维护可编辑的 Markdown 或 HTML 副本。

```text
Tiptap 编辑内容
→ getJSON() 得到正文对象
→ 表单把对象放进 content
→ Express 校验正文结构
→ Prisma 写入 PostgreSQL JSONB
→ 详情接口返回对象
→ 编辑器回显，或 ArticleBody 渲染文章
```

这里改变的是正文 contract。前面章节先用字符串完成 CRUD 的步骤仍然成立，不需要回头重写每一章。

### 1.3 ArticleForm 继续管理整篇文章

Tiptap 只替换 `content` 的输入控件，ArticleForm 继续管理整篇文章并统一提交。字段在数据上分开，不代表界面要排成一串带边框的输入框。标题可以是大字号、无常驻边框的输入框，与下方正文组成连续的文章画布。

Ant Design 提供表单、输入、选择等基础组件，没有直接包办写作、预览和发布的文章编辑器。这里组合已有控件和 Tiptap，分工如下：

| 字段 | Ant Design 后台 | shadcn/ui 后台 |
|---|---|---|
| title、slug、summary | 原来的 Input、TextArea 或 ProForm 对应组件 | 原来的 Input、Textarea |
| 标签 | Select 多选，放在右侧文章设置中 | 对应的标签选择控件，同样放在右侧 |
| 状态 | 沿用状态选择控件，随表单提交 | 同样的操作规则 |
| content | Form.Item 内的 ArticleEditor | Controller 内的同一个 ArticleEditor |

表中的 shadcn/ui 列只说明未来接法，本轮完成 Ant Design 列即可。

`ArticleEditor` 是我们给模板增加表单接口后的名称。它接收 `value`，在内容变化时调用 `onChange(json)`；表单因此能像管理一个输入框一样管理它，只是字段值从字符串变成了对象。正文里的 h2/h3 是小节标题，文章标题仍来自独立的 `title` 字段。

先记住三个动作，后面会在模板原有的 `useEditor()` 中接上：

```text
输入：onUpdate → editor.getJSON() → onChange → 表单 content
保存：表单提交 → fetch / Axios → Express → Prisma
回显：详情响应 → 表单 value → editor.commands.setContent()
```

编辑器不会因为发生 `onUpdate` 就自动保存到数据库。点击保存或发布按钮，才发送创建或更新请求。

### 1.4 先让“新建”和“编辑”跳到独立页面

列表的“新建”按钮跳转到新建页，“编辑”按钮携带当前文章 id，跳转到对应编辑页。页面文件位于 `admin-web-antd/app/admin/articles/`：

| 入口 | 跳转地址 | 页面文件 |
|---|---|---|
| 新建文章 | `/admin/articles/new` | `new/page.tsx` |
| 编辑某篇文章 | `/admin/articles/${id}/edit` | `[id]/edit/page.tsx` |
| 返回文章列表 | `/admin/articles` | `page.tsx`（已有） |

用 `useRouter()` 获取 router，通过 `router.push()` 跳转。编辑页用 `useParams()` 读取 id；它是字符串，查询详情时再转为数字。使用这些 Hook 的页面声明 `"use client"`。

### 1.5 将表单排成一张连续的文章画布

**核心布局**

1. **共用组件：** 新建和编辑页都使用 ArticleForm，布局统一在 `_components/article-form.tsx` 中调整。

2. **左右分区：** 左侧放标题和正文；右侧放标签、slug、摘要和状态，状态沿用原有选择控件。

3. **顶部操作：** 返回列表和“检查输入”按钮放在顶部，提交后在 Console 打印通过校验的表单值。真实标签、详情和保存请求在第 1.6 节接入。

**实现重点**

- **字段管理：** 保留原有 `name` 和 `rules`，所有字段由同一个 Form / ProForm 管理，不额外维护字段状态。编辑表单用文章 id 作为 `key`，切换文章时区分表单状态。

- **写作样式：** 标题使用大字号、无常驻边框的输入框；正文继续用 TextArea，通过 `autoSize` 随内容增高，让整页滚动。去掉重复的标题、正文标签，保留 `aria-label`、聚焦提示和校验错误。

- **尺寸适配：** 写作区最大宽度约 720px，设置区约 280px；窄屏改为上下排列，设置字段保持可见。

### 1.6 再接新建保存、编辑回显和更新

**核心流程**

1. **新建保存：** Form 收集并校验输入 → `createArticle(values)` 发 POST → 拿到新文章 id → 跳到这篇文章的编辑页。

2. **打开编辑页：** 从 URL 取 id → `useEffect` 中调用 `getArticleById(id)` 发 GET → 拿到文章详情 → 用 `initialValues` 填入表单。

3. **编辑保存：** 用户修改并点击保存 → `updateArticle(id, values)` 发 PATCH → 拿到更新后的文章 → 转成表单值 → 用 `form.setFieldsValue()` 更新当前表单，留在页面继续写。

**实现重点**

- **表单实例：** 用 `Form.useForm()` 创建实例，通过 `form` 属性连接到现有 Form。`initialValues` 用于初次显示；修改它不会重新初始化已挂载的表单。

- **`onSubmit` 返回类型：** `Promise<ArticleFormValues | void>` 描述保存函数交回 ArticleForm 的结果。新建的 `handleCreate` 只拿 id 跳转，返回 `void`；编辑的 `handleUpdate` 返回最新 `ArticleFormValues`，用于回填。

- **提交与更新状态：** 新建和编辑共用 `submitting`，请求前设为 `true`，禁用输入和提交按钮以避免重复提交，结束后在 `finally` 中恢复。失败保留输入并提示错误。

  编辑时先比较原文章与当前表单，内容未变就不发 PATCH；成功后同步 `article` 和表单值，作为下次比较的基准。

### 1.7 体验优化：保存草稿、立即发布与离开提醒（可选）

**保存草稿与立即发布**

新建页顶部放“返回”“保存草稿”“立即发布”，由按钮决定状态，不再显示状态选择框：

| 操作 | 提交流程 |
|---|---|
| 保存草稿 | 校验表单 → 指定 `status: "draft"` → `createArticle(values)` |
| 立即发布 | 校验表单 → 指定 `status: "published"` → `createArticle(values)` |

两个按钮共用同一份表单和保存逻辑，成功后都进入新文章的编辑页。保存草稿仍遵守现有必填规则。编辑页保留“返回”“保存修改”，通过右侧状态选择完成发布或撤回，再统一保存。

**离开提醒**

提取第 1.6 节的新旧数据比较逻辑，判断是否有未保存修改。编辑页与最近一次保存的数据比较，新建页与初始空表单比较；保存成功后更新比较基准，失败时保留原基准。

在 ArticleForm 中增加下面的函数，将返回（当前“取消”）按钮的 `onClick={onCancel}` 改为 `onClick={handleCancel}`。`hasUnsavedChanges()` 是从上述比较逻辑提取的自定义函数：

```tsx
function handleCancel() {
  if (
    hasUnsavedChanges() &&
    !window.confirm("修改尚未保存，确定离开？")
  ) {
    return;
  }

  onCancel();
}
```

有修改且取消离开时，`return` 阻止后续跳转；没有修改或确认离开时，执行父页面传入的 `onCancel()`，返回列表。

**这段代码只保护绑定了它的按钮。** 浏览器前进、后退，以及页面内其他菜单、`Link` 或 `router.push()` 都不会自动调用它。其他站内跳转需要共用相同的离开检查；浏览器前进、后退需另行处理。刷新或关闭页面使用 `beforeunload`，它不覆盖站内路由切换。保存成功后的新建转编辑不触发提醒。

打开模板文件，只需先认清三处：

### 2.2 让 SimpleEditor 支持表单取值与回填

`ArticleForm` 里的 `<Form>` 记录文章数据，`TextArea` 是你输入正文的地方。两者通过 `Form.Item` 连接，下面省略了校验和样式配置：

```tsx
<Form.Item name="content">
  <Input.TextArea />
</Form.Item>
```

**`name="content"` 告诉 `Form.Item`：这个输入框读写的是 Form 中名叫 `content` 的字段。** `content` 是我们起的字段名，与文章 API 的正文字段同名。

`Form.Item` 在显示输入框时，就会自动给 `TextArea` 传入两个属性：

- **`value`：当前要显示的内容。** 比如 Form 的 `content` 是“你好”，`TextArea` 收到的 `value` 就是“你好”，输入框也就显示“你好”。
- **`onChange`：处理输入的函数。** 这个函数也由 `Form.Item` 提前传好。你把文字改成“你好呀”，`TextArea` 就调用它，`Form.Item` 再把 Form 的 `content` 更新为“你好呀”。

`TextArea` 已经支持这两个属性，所以之前没有手写 `value/onChange`。官方 `SimpleEditor` 还没接收它们，本节给它补上，下一节再替换 `TextArea`。

换成编辑器后，`Form.Item` 自动做的事可以简化理解成下面这样。**这是传值过程的示意，不需要把它写进项目，也没有展示 Form 内部的校验和订阅代码：**

```tsx
<ArticleEditor
  value={表单里当前的正文}
  onChange={(最新正文) => {
    把最新正文写入表单的content字段(最新正文);
  }}
/>
```

所以，`onChange` 能更新 Form，是因为 **Form.Item 传进来的这个函数负责更新字段**。编辑器调用它时，把最新正文作为参数交进去即可。Form 记录新值后，又会把新值作为 `value` 传回来。只声明两个属性还不够，下面还要让编辑器实际读取 `value`、调用 `onChange`。

文章的 `content` 字段以前存字符串，现在改存 Tiptap 输出的 JSON 对象。因此需要定义这个对象的类型、提供新建时的空白内容，并检查用户是否真的输入了文字。在 `admin-web-antd/features/articles/article-content.ts` 中定义：

```ts
import type { JSONContent } from "@tiptap/core";

export type ArticleContent = JSONContent;

export function emptyDocument(): ArticleContent {
  return { type: "doc", content: [{ type: "paragraph" }] };
}

export function hasArticleText(node: unknown): boolean {
  if (!node || typeof node !== "object") return false;
  if ("type" in node && node.type === "text" &&
      "text" in node && typeof node.text === "string" && node.text.trim()) {
    return true;
  }
  return "content" in node &&
    Array.isArray(node.content) && node.content.some(hasArticleText);
}
```

- **`JSONContent` / `ArticleContent`：声明正文的数据类型。** `JSONContent` 描述 Tiptap 正文的 JSON 结构；`ArticleContent` 是它的别名，后面用来声明文章的 `content` 字段和编辑器的 `value` 属性。
- **`emptyDocument()`：生成空白正文。** 返回一个只有空段落的文档，新建文章还没有内容时，编辑器就用它显示空白输入区。
- **`hasArticleText()`：防止空正文提交。** 它逐层查找文字节点，找到非空文字才返回 `true`。空段落也是一个 JSON 对象，因此第 2.3 节要用这个函数判断用户是否真的写了内容。

接下来修改 `simple-editor.tsx`。先导入类型和空白内容函数，用 `ArticleEditorProps` 声明编辑器接收哪些属性；取值、校验和提交继续由原来的 Form 处理：

```tsx
import {
  emptyDocument,
  type ArticleContent,
} from "@/features/articles/article-content";

export type ArticleEditorProps = {
  value?: ArticleContent;
  onChange?: (value: ArticleContent) => void;
  onBlur?: () => void;
  disabled?: boolean;
};
```

`?` 表示写 `<ArticleEditor />` 时可以不手动传这个属性。新建和编辑都由 `Form.Item` 在运行时补上 `value/onChange`，TypeScript 检查组件调用时看不到这一步，所以这里声明为可选。新建时 `value` 可能是 `undefined`，编辑器用 `emptyDocument()` 显示空白；编辑时接收已有正文。`onChange` 在显示表单时就已传好，用户输入时才调用它。

`onBlur` 用来通知外部编辑区失去焦点，按需传入；`disabled` 控制保存期间能否编辑。

再让 `SimpleEditor` 接收这些属性。`disabled = false` 表示默认可以编辑，原有函数体继续保留：

```tsx
export function SimpleEditor({
  value, onChange, onBlur, disabled = false,
}: ArticleEditorProps) {
  // 原有函数体保留，按下面两处修改。
}
```

**第一处：显示初始正文，并把输入交回 Form。**

在已有的 `useEditor({...})` 中替换 `content`，新增 `editable`、`onUpdate`、`onBlur`。原有 `extensions`、`editorProps`、`immediatelyRender: false` 等配置保留；删除顶部的示例正文 `content.json` 导入。下面只是需要修改的选项：

```tsx
content: value ?? emptyDocument(),
editable: !disabled,
onUpdate: ({ editor }) => onChange?.(editor.getJSON()),
onBlur: () => onBlur?.(),
```

- **显示内容：** `useEditor` 的 `content` 选项用 `value` 初始化编辑区；还没有值时，用 `emptyDocument()` 显示一个空段落。
- **记录输入：** 你把“你好”改成“你好呀”，Tiptap 会显示新文字并触发 `onUpdate`。`editor.getJSON()` 读出包含“你好呀”的正文对象，编辑器再调用 `onChange`，让 Form 更新 `content` 字段。
- **禁用与失焦：** `editable: !disabled` 设置编辑器刚创建时能否输入；点到标题等其他输入框时，编辑区失去焦点，就调用外部传来的 `onBlur`。

`onChange?.(...)` 中的 `?.()` 表示“传了这个函数就调用，没传就跳过”。接入表单后，这个 `onChange` 就是 `Form.Item` 提前传好的函数。

这条方向是：**用户输入 → Tiptap 更新正文 → `onUpdate` → `onChange(正文对象)` → Form 更新 `content`。** Form 收到的是正文对象；原来 TextArea 交给 Form 的则是输入事件，Form 从事件中读取文字。

**第二处：让后续回填和禁用状态也能更新编辑器。**

`useEditor` 中的 `content` 只设置初始内容。新建保存后会跳到编辑页，获取文章详情，再通过 `initialValues` 初始化 Form 和编辑器。

**这里举的是编辑页保存修改后的情况：** `ArticleForm` 用 `form.setFieldsValue()` 更新当前 Form，`Form.Item` 再把最新的 `content` 作为 `value` 传给已有的编辑器。下面第一个 Effect 调用 `setContent()`，让编辑区显示这份内容。**它处理的是 Form → 编辑器的回填；用户打字时的实时显示由 Tiptap 自己处理。**

在 `useEditor` 后增加下面两个 Effect。模板已有 `useEffect` 导入：

```tsx
useEffect(() => {
  if (!editor) return; // 编辑器还没创建好时，先跳过。
  const nextValue = value ?? emptyDocument();
  if (JSON.stringify(editor.getJSON()) !== JSON.stringify(nextValue)) {
    editor.commands.setContent(nextValue, {
      emitUpdate: false,
      errorOnInvalidContent: true, // 内容结构不合法时，直接报错。
    });
  }
}, [editor, value]);

useEffect(() => {
  editor?.setEditable(!disabled, false);
}, [editor, disabled]);
```

第一个 Effect 先比较内容。比如你刚把“你好”改成“你好呀”，编辑器已经显示了新文字，Form 又把同一份内容作为 `value` 传回来。这时再调用 `setContent()` 就是在重新替换整篇内容，可能导致光标跳动，所以内容相同就跳过。

Form 传来的内容不同时，才调用 `setContent()` 回填。`emitUpdate: false` 让回填不触发 `onUpdate`，避免编辑器再调用 `onChange`，把同一份内容交回 Form。

第二个 Effect 处理保存期间的开关：`disabled` 为 `true` 时禁止输入，变回 `false` 后恢复编辑。第二个参数 `false` 表示切换开关时不触发 `onUpdate`。`useEditor` 中的 `editable` 设置初始状态，这个 Effect 负责更新已有编辑器。

两条数据流到这里就接通了：**输入时，编辑器把正文交给 Form；回填时，Form 把正文交给编辑器。** `disabled` 的 Effect 单独处理能否编辑，与正文回填分开。

### 2.4 让现有 API 保存 JSON，再打开文章回显

**先调整后端校验**

编辑器正常生成的 JSON 符合当前扩展的结构，但接口也可能收到 Apifox 等工具直接提交的数据，因此后端仍需校验。

根据 Tiptap 的节点结构，并对照 `editor.getJSON()` 的结果，可以把本次结构校验分成两部分：

1. **最外层的文档节点 `doc`。** 它代表整篇正文，必须有 `content` 数组，用来存放内部节点。这部分由 `documentSchema` 检查。
2. **里面的内容节点。** 段落、标题、文字等，都用 `nodeSchema` 检查。节点还可以通过自己的 `content` 数组包含子节点；无论嵌套多少层，都继续使用同一套规则。

内部节点共用几个字段：`type` 表示种类，`text` 保存文字，`attrs` 保存属性，`marks` 保存加粗等文字格式，`content` 存放子节点。不同节点使用的字段不同，所以 `nodeSchema` 要求 `type` 必填，其余字段存在时再检查。

代码先定义 `nodeSchema`，再由 `documentSchema` 使用它检查内部节点。最后，`contentSchema` 在结构检查的基础上增加本项目的业务限制：正文必须有非空文字，文字和整个 JSON 的长度不能超限。

使用工程里已有的 Zod，在 `server/src/modules/articles/article-content-schema.ts` 中写入下面的规则：

<details>
<summary>正文 JSON 的基础校验代码</summary>

```ts
import { z } from "zod";

const attrsSchema = z.record(z.string(), z.json());

type ContentNode = {
  type: string;
  text?: string;
  attrs?: z.infer<typeof attrsSchema>;
  marks?: { type: string; attrs?: z.infer<typeof attrsSchema> }[];
  content?: ContentNode[];
};

// z.lazy 让规则可以引用自身，继续检查子节点。
const nodeSchema: z.ZodType<ContentNode> = z.lazy(() => z.object({
  type: z.string().min(1),
  text: z.string().optional(),
  attrs: attrsSchema.optional(),
  marks: z.array(z.object({
    type: z.string().min(1),
    attrs: attrsSchema.optional(),
  })).optional(),
  // 子节点可以不存在；如果存在，数组里的每一项都按 nodeSchema 检查。
  content: z.array(nodeSchema).optional(),
}));

export const documentSchema = z.object({
  type: z.literal("doc"),
  content: z.array(nodeSchema),
});

function getText(node: ContentNode): string {
  return node.type === "text" ? node.text ?? "" :
    (node.content ?? []).map(getText).join("");
}

export const contentSchema = documentSchema
  .refine((value) => getText(value).trim().length > 0, {
    message: "正文不能为空",
  })
  .refine((value) => getText(value).length <= 100_000, {
    message: "正文文字不能超过 100000 个字符",
  })
  .refine((value) => JSON.stringify(value).length <= 500_000, {
    message: "正文数据过大",
  });
```

</details>

```ts
function stringifyContent(value: unknown) {
  return JSON.stringify(value, (_, node) =>
    node && typeof node === "object" && !Array.isArray(node)
      ? Object.fromEntries(
          Object.entries(node).sort(([a], [b]) => a.localeCompare(b))
        )
      : node
  );
}
```

## 3. 让后台预览与网站详情共用一套展示

第 2 节已经把正文保存成 JSON。接下来要让后台预览和网站详情把这份数据显示成文章。**核心思路是：根据 JSON 生成文章的 HTML 结构，再用 CSS 设置具体排版。**

读取 JSON 时，各个字段分别决定怎样显示：

- **`type` 决定内容种类**：例如 `paragraph` 显示为段落 `<p>`，`heading` 显示为标题。
- **`attrs` 补充具体属性**：例如标题的 `level: 2` 决定使用 `<h2>`，图片的 `src` 决定加载哪张图片。
- **`marks` 指定文字格式**：例如 `bold` 把文字包在 `<strong>` 中，`link` 根据自己的 `attrs.href` 生成链接。
- **`content` 包含子节点**：继续逐层读取，把里面的文字、段落等显示出来。

例如，一个二级标题里有加粗的“你好”，转换后就是 `<h2><strong>你好</strong></h2>`。标题多大、行距多少、段落之间留多少空白，再由 CSS 决定。JSON 保存内容和格式信息，CSS 控制具体外观。

**这些转换由 Tiptap 的扩展和渲染器完成。** 扩展定义标题、列表、加粗等格式及其 HTML 对应关系，渲染器使用这些规则把 JSON 显示为文章。我们复用已有扩展即可。

后台预览读取当前表单，网站详情读取 API；要让同一篇文章在两处显示一致，就需要共用扩展配置、文章展示组件和 CSS。第 4 节接通公开接口与只读展示，第 5 节完善内容类型、排版和预览。

**本节就是把 `useEditor` 的 `extensions` 中负责正文格式的部分提取出来，放进 `createArticleExtensions()`，让编辑器、后台预览和个人网站共用。** 标题、列表、加粗、图片等格式放进这个函数；查找替换、选区显示等编辑功能继续留在 `SimpleEditor` 中。

### 4.1 公开接口只读取已发布内容

访客打开网站时，需要直接读取已发布文章。新增两个 GET 接口，沿用已有查询、分页和错误处理：

```text
GET /api/public/articles
GET /api/public/articles/:slug
```

两者都由后端固定查询 `status = published` 且 `publishedAt` 不为空的文章。列表不带正文；详情按 slug 查询，找不到可公开的文章就返回 404。

**先增加公开查询**

在 `server/src/modules/articles/article-repository.ts` 中新增下面的内容，沿用已有的 `prisma` 和 `Prisma` 导入：

```ts
const publicWhere: Prisma.ArticleWhereInput = {
  status: "published",
  publishedAt: { not: null },
};

const publicSelect = {
  title: true,
  slug: true,
  summary: true,
  publishedAt: true,
  articleTags: { select: { tag: { select: { name: true } } } },
} satisfies Prisma.ArticleSelect;

export async function getPublicArticles(page: number, pageSize: number) {
  const [articles, total] = await Promise.all([
    prisma.article.findMany({
      where: publicWhere,
      select: publicSelect,
      orderBy: [{ publishedAt: "desc" }, { id: "desc" }],
      skip: (page - 1) * pageSize,
      take: pageSize,
    }),
    prisma.article.count({ where: publicWhere }),
  ]);
  return { articles, total };
}

export function getPublicArticleBySlug(slug: string) {
  return prisma.article.findFirstOrThrow({
    where: { ...publicWhere, slug },
    select: { ...publicSelect, content: true },
  });
}
```

列表和详情共用 `publicSelect`，详情通过 `content: true` 多取正文。标签沿用已有 `articleTags → tag → name` 结构，网站稍后从中取出名称。

`findFirstOrThrow()` 沿用现有 `getArticleById` 的错误处理：找不到符合发布条件的文章时抛出 `P2025`，由已有错误中间件返回 404，无需手写不存在判断。函数直接返回查询的 Promise，路由中 `await` 即可。

**公开展示前，限制可保存的正文格式**

第 2.4 节检查了字段的基本结构，但还没限制字段里的具体值。例如下面这个标题节点，`type` 是字符串，`attrs` 是对象，子节点也有文字，可以通过之前的基础校验：

```json
{
  "type": "heading",
  "attrs": { "level": 99 },
  "content": [{ "type": "text", "text": "示例小节" }]
}
```

但第 3 节已经约定正文只使用 h2、h3，`level: 99` 显然不符合要求。**本步就是把这些格式约定加入后端校验，让不符合要求的正文在保存前被拦住。** 即使绕过编辑器，通过 Apifox 提交，也要经过检查。

先在 `article-content-schema.ts` 的 `ContentNode` 类型后面增加下面的规则：

- **允许哪些格式**：`allowedNodeTypes` 和 `allowedMarkTypes` 是两份允许名单，按第 3 节启用的扩展填写。`Set.has()` 判断节点或文字格式的名称是否在名单里。
- **属性应该填什么**：`checkArticleNode()` 根据当前节点的种类继续检查，例如标题级别只能是 2、3；图片和链接的地址交给 `isWebUrl()` 检查格式与协议。

函数中的 `node` 是当前检查的节点，`context` 由 Zod 提供。发现不符合规则的内容时，调用 `context.addIssue()` 记录校验错误。

<details>
<summary>完整规则：允许名单、地址检查和节点检查函数</summary>

```ts
const allowedNodeTypes = new Set([
  "paragraph", "heading", "text", "hardBreak", "blockquote",
  "bulletList", "orderedList", "listItem", "codeBlock",
  "horizontalRule", "taskList", "taskItem", "image",
]);
const allowedMarkTypes = new Set([
  "bold", "italic", "strike", "underline", "code", "link",
  "highlight", "superscript", "subscript",
]);

export function isWebUrl(value: unknown, protocols = ["https:"]): boolean {
  if (typeof value !== "string") return false;
  try {
    return protocols.includes(new URL(value).protocol);
  } catch {
    return false;
  }
}

function checkArticleNode(node: ContentNode, context: z.RefinementCtx) {
  if (!allowedNodeTypes.has(node.type)) {
    context.addIssue({ code: "custom", message: "正文包含不支持的节点" });
  }
  if (node.type === "text" && !node.text) {
    context.addIssue({ code: "custom", message: "文字节点缺少内容" });
  }
  if (node.type === "heading" &&
      node.attrs?.level !== 2 && node.attrs?.level !== 3) {
    context.addIssue({ code: "custom", message: "正文只允许二级和三级标题" });
  }
  if (node.type === "image" && !isWebUrl(node.attrs?.src)) {
    context.addIssue({ code: "custom", message: "图片需要有效的 HTTPS 地址" });
  }
  for (const mark of node.marks ?? []) {
    if (!allowedMarkTypes.has(mark.type)) {
      context.addIssue({ code: "custom", message: "正文包含不支持的格式" });
    }
    if (mark.type === "link" &&
        !isWebUrl(mark.attrs?.href, ["https:", "http:", "mailto:"])) {
      context.addIssue({ code: "custom", message: "链接地址不支持" });
    }
  }
}
```

</details>

**写好函数后，还要让 Zod 在校验时调用它。** 将原来的 `nodeSchema` 替换为下面这段：字段规则保持不变，只在 `z.object({...})` 后接上 `.superRefine(checkArticleNode)`。它表示“基础结构检查通过后，再执行这个自定义检查函数”：

```ts
const nodeSchema: z.ZodType<ContentNode> = z.lazy(() => z.object({
  type: z.string().min(1),
  text: z.string().optional(),
  attrs: attrsSchema.optional(),
  marks: z.array(z.object({
    type: z.string().min(1),
    attrs: attrsSchema.optional(),
  })).optional(),
  content: z.array(nodeSchema).optional(),
}).superRefine(checkArticleNode));
```

子节点仍由 `content: z.array(nodeSchema)` 逐层检查，所以里面的每个节点也会执行 `checkArticleNode()`。例如遇到上面的标题，函数发现 `level` 为 99，就记录“正文只允许二级和三级标题”。创建或更新请求中的 Schema 校验会因此失败，由已有错误中间件返回 422，正文不会写入数据库。

**验证：** 用 Apifox 提交文章：正文标题的 `level` 为 `99` 时返回 422，改为 `2` 后保存成功。公开接口能读取已发布文章；草稿、撤回文章返回 404，列表不带正文。

在 `admin-web-antd/.env.local` 中增加 `NEXT_PUBLIC_UPLOAD_URL`，值填写你现有上传接口的完整地址，修改后重启前端开发服务。

在 `lib/tiptap-utils.ts` 中，将现有 `handleImageUpload` 整个替换为下面的函数，文件中其他工具函数和 `MAX_FILE_SIZE` 保留：

```ts
export const handleImageUpload = async (
  file: File,
  onProgress?: (event: { progress: number }) => void,
  abortSignal?: AbortSignal
): Promise<string> => {
  if (file.size > MAX_FILE_SIZE) {
    throw new Error(`图片不能超过 ${MAX_FILE_SIZE / 1024 / 1024}MB`);
  }

  const uploadUrl = process.env.NEXT_PUBLIC_UPLOAD_URL;
  if (!uploadUrl) throw new Error("未配置图片上传地址");

  const formData = new FormData();
  formData.append("file", file); // 对应后端的 upload.single("file")。

  const response = await fetch(uploadUrl, {
    method: "POST",
    body: formData,
    signal: abortSignal,
  });
  // 根据后端返回定义类型：成功有 url，失败有 error，所以两者都可选。
  const data: { url?: string; error?: string } = await response.json();

  if (!response.ok) throw new Error(data.error || "图片上传失败"); // 失败时读取 error。
  if (!data.url) throw new Error("上传接口没有返回图片地址");

  onProgress?.({ progress: 100 });
  return data.url; // 对应后端 res.json({ url: publicUrl })，模板用它显示图片。
};
```

`FormData` 用来装文件，字段名 `file` 要与后端一致。发送时让浏览器自动设置 `Content-Type`，无需手动填写。[FormData 用法](https://developer.mozilla.org/en-US/docs/Web/API/XMLHttpRequest_API/Using_FormData_Objects)

现有 `apiRequest` 固定取响应中的 `data` 字段；上传接口返回 `{ url }`，直接复用会得到 `undefined`。因此这里用 `fetch`，读取响应后返回其中的 `url`。

`onProgress` 这里只在上传成功后将进度设为 100%，上传期间不更新百分比。函数返回图片地址后，模板将占位块替换为图片。`abortSignal` 用于取消请求。**文件保存在 TOS，正文 JSON 只保存图片 URL 和图片属性。**

**扩展图片节点，保存图注和宽度**

官方 `Image` 扩展已经能保存和显示图片。为了让图注和宽度选择也能随正文保存，我们基于它创建图片扩展 `ArticleImage`，增加两个属性：

**这两个属性是本项目自定义的，官方 Image 不自带。** 它们和原有的 `src`、`alt` 一起保存在图片节点的 `attrs` 中，例如：

```json
{
  "type": "image",
  "attrs": {
    "src": "https://example.com/sunset.jpg",
    "alt": "",
    "caption": "傍晚的海边",
    "layout": "wide"
  }
}
```

下面先定义这些属性和图片的显示结构，下一步再添加菜单来修改它们。新增 `features/articles/tiptap/article-image.ts`，用 `Image.extend()` 扩展官方 Image：

```ts
import Image from "@tiptap/extension-image";

export const ArticleImage = Image.extend({
  addAttributes() {
    return {
      ...this.parent?.(), // 保留 src、alt、title 等属性；上传组件会将文件名填入 alt 和 title。
      caption: { default: "" },
      layout: { default: "normal" },
    };
  },
  renderHTML({ node }) {
    const { src, alt, title, caption, layout } = node.attrs; // 读取当前图片的属性。
    // 数组描述 HTML 结构：[标签名, HTML 属性, 子元素...]。
    return [
      "figure", // 包住图片和图注。
      { class: "article-image", "data-layout": layout }, // CSS 根据 data-layout 设置宽度。
      ["img", { src, alt, title, loading: "lazy" }], // title 保留上传文件名的悬停提示。
      ["figcaption", {}, caption], // 图注；空对象表示没有额外的 HTML 属性。
    ];
  },
}).configure({ allowBase64: false });
```

`renderHTML()` 把图片节点变成带图注的 `<figure>`，并把宽度选项写到 `data-layout`，供 CSS 设置宽度。编辑器、预览和网站都使用这个结构；正文中的节点类型仍是 `image`。

```tsx
"use client";

import type { Editor } from "@tiptap/core"; // 编辑器实例的类型，用于标注传入的 editor。
import { NodeSelection } from "@tiptap/pm/state"; // 配合 instanceof 判断是否选中了整个节点。
import { useEditorState } from "@tiptap/react"; // 跟随编辑器状态变化，读取当前图片属性并更新菜单。
import { BubbleMenu } from "@tiptap/react/menus";

import { Input } from "@/components/tiptap-ui-primitive/input";

// 接收 SimpleEditor 正在使用的 editor，菜单才能操作正文中的图片。
export function ArticleImageMenu({ editor }: { editor: Editor }) {
  // image 是读到的属性对象，菜单通过 image.layout、image.caption 显示当前值。
  const image = useEditorState({
    editor, // 编辑器状态变化时重新读取，属性变化后更新菜单。
    // 读取当前选中 image 节点的 attrs，不是查找 HTML 中的 img 标签。
    // ArticleImage 虽然渲染成 figure，继承的节点类型仍是 "image"。

  return (
    // BubbleMenu 把下面的按钮和输入框显示在选中的图片上方。
    <BubbleMenu
      editor={editor}
      pluginKey="article-image-menu"
      options={{ placement: "top", offset: 8, flip: true, shift: true }}
      shouldShow={({ state }) => {
        // 仅在可编辑且选中了整个图片节点（NodeSelection）时显示菜单。
        return editor.isEditable &&
          state.selection instanceof NodeSelection &&
          state.selection.node.type.name === "image";
      }}
      className="article-image-menu"
    >
      {/* 生成三个宽度按钮，aria-pressed 标记当前图片使用的选项。 */}
      {([
        ["normal", "正文同宽"],
        ["wide", "宽幅"],
        ["full", "全宽"],
      ] as const).map(([value, label]) => (
        <Button key={value} type="button" aria-pressed={image.layout === value}
          onClick={() => {
            // 修改选中图片的 layout；实际宽度由后面的 CSS 设置。
            editor.commands.updateAttributes("image", { layout: value });
          }}>
          {label}
        </Button>
      ))}
      {/* 显示当前图片的图注，输入时把新文字写回 caption。 */}
      <Input
        aria-label="图注"
        placeholder="添加图注（可选）"
        value={image.caption ?? ""}
        onChange={(event) => {
          editor.commands.updateAttributes("image", { caption: event.target.value });
        }}
        onKeyDown={(event) => {
          if (event.key === "Enter" && !event.nativeEvent.isComposing) {
            event.preventDefault(); // 图注中按 Enter 不提交文章。
          }
        }}
      />
    </BubbleMenu>
  );
}
```

**占位块处理完后再保存**

在前端 `article-content.ts` 增加检查函数，复用已有 `ArticleContent` 类型：

```ts
    (node?.content?.some(hasImageUpload) ?? false);
}
```

它从正文中查找上传占位块。在 `ArticleForm` 导入 `hasImageUpload`，将下面的判断放到正文 `validator` 中、原来的非空检查前：

### 5.3 增加预览按钮，查看当前文章效果

**从 Form 读取当前文章**

```tsx
const [previewing, setPreviewing] = useState(false);
```

**验证：** 修改一篇尚未保存的文章，预览立刻反映新内容；返回编辑时输入和撤销记录仍在，点击正文可以继续写。保存并发布后，在相同宽度下比较后台预览与网站；标题、正文、图片宽度、图注和代码样式一致。

## 6. 后续接入 shadcn/ui：学习第二套后台时再做

第一次阅读本章先跳到第 7 节。以后学习第 25～29 章，在第 28 章实现文章表单时配合本节使用；该章的字符串正文示例属于此前的 CRUD 基础写法，连接已经升级的 API 时，从一开始就换用这里的 JSON Schema、默认值和 ArticleEditor。不要先用字符串请求新接口，也不要把数据库改回 String。

### 6.1 第二套后台只改变表单接法

开始第二套后台时，再按官方 CLI 安装这个项目自己的模板与依赖。将 Ant Design 中已完成的 `value/onChange` 适配、格式取舍和正文辅助文件同步过去，沿用相同的 JSON 数据规则。

同步第 5.1 节的上传回调、图片菜单、扩展、`hasImageUpload` 和 CSS，并安装相同菜单依赖。第二套后台同样使用上传占位块；提交前检查上传是否完成，表单继续使用各自的 UI 组件。

在 `features/articles/article-form-schema.ts` 中，用 `z.custom` 替换原来的正文字符串校验：

```ts
import type { ArticleContent } from "./article-content";
import { hasArticleText, hasImageUpload } from "./article-content";

// 替换原来的 content 属性。
content: z.custom<ArticleContent>(hasArticleText, {
  message: "正文不能为空",
}).refine(value => !hasImageUpload(value), {
  message: "请等待图片上传完成，或删除未完成的上传占位块",
}),
```

新建默认值使用 `emptyDocument()`，表单类型继续由 Zod 推导。与 Ant Design 一样，前端先检查非空文字，API 继续校验节点和属性。

在原有 Controller 中接入适配后的编辑器：

```tsx
<ArticleEditor
  value={field.value}
  onChange={field.onChange}
  onBlur={field.onBlur}
  disabled={form.formState.isSubmitting}
/>
```

Axios 继续提交完整表单对象，不单独序列化正文。保存成功后用返回的数据回填；失败保留输入。详情加载完成后再挂载带文章 id 的表单。

此时先让两套后台编辑同一篇文章，确认格式、正文和元信息一致。共享包是否值得提取，等实际出现重复维护成本后再决定，不作为本轮前置任务。

### 6.2 两套后台保持同一条写作流程

shadcn/ui 沿用第 28 章已有的新建、编辑路由，将“保存后返回列表”改为第 1.6 节的新建后进入编辑页、编辑保存后留页。复用第 1.5 节的布局：左侧是标题和正文，右侧是标签、slug、摘要和发布信息。若 Ant Design 后台已完成第 1.7 节的体验优化，再同步相同的按钮与离开提醒。标签管理继续沿用各自已有的简单界面。

两套后台可以保留自己的按钮和设置控件，正文沿用相同的模板适配、格式规则、预览组件和 CSS。统一的是保存的数据与显示结果，不要求先建立组件包。

用两套后台分别检查以下行为：

| 体验 | 应该发生什么 |
|---|---|
| 格式工具栏 | 能恢复普通段落；图片按钮插入上传占位块，选中图片可切换宽度和填写图注 |
| 中文输入和快捷键 | 输入法选字不中断；加粗、撤销、重做可用；格式按钮不触发提交 |
| 页面与保存 | 新建成功进入该文章编辑页，编辑保存后留页；反馈与请求结果一致 |
| 输入保护 | 失败保留输入；若已接入离开提醒，返回、刷新和后退时检查未保存修改 |
| 文章设置 | 标签、slug、摘要和发布信息放在右侧；窄屏改为上下排列，字段错误可见 |
| 预览 | 读取未保存内容，切换回来保留输入与撤销历史 |
| 返回列表 | 恢复进入文章前的筛选与分页，并重新获取列表 |

## 7. 用同一篇文章验收，再进入上线

准备一篇自己的样例文章，包含：标题、摘要、标签、中文长段落、h2/h3、加粗、链接、普通列表、任务列表、引用、代码块、不同宽度的图片、图注和表格。已实现封面时再加入封面。

按顺序完成：

```text
从带筛选和分页的 Ant Design 列表进入新建页
→ 编辑并预览未保存内容
→ 保存草稿后进入该文章编辑页，继续修改并保存
→ 返回列表，检查筛选与分页，再打开这篇文章
→ 发布后查看个人网站
→ 对比相同宽度的预览与公开页面
→ 撤回后公开列表和详情不再可读
```

本轮通过 Ant Design 后台完成以上链路即可。第二套后台建好后，再补第 6 节的跨后台编辑与体验检查，不阻塞当前写作能力和上线。

沿用第 18A 章的独立测试数据库，补充有意义的接口检查：

- 有效正文保存后往返一致；仅更新标题不覆盖正文。
- 模板保留的格式都能保存并渲染；已移除的格式不会通过粘贴或快捷键进入允许的文档结构。
- 字符串正文、未知节点、错误字段类型、空白正文和不支持的 URL 得到明确错误。
- 正文超限与整个请求体超限分别返回约定的 422、413。
- 已发布内容可公开读取，草稿和撤回内容不可公开读取。

测试重点检查文字、层级、格式和图片属性没有丢失。比较 JSON 时使用第 2.4 节的字段排序方式，不依赖数据库返回的对象键顺序。本轮已按第 2.4 节清空旧文章并重建种子，验收新保存的正文和 JSON 种子即可。

最后运行当前 `admin-web-antd`、`server`、个人网站各自已有的构建和相关检查。`admin-web-shadcn` 创建并接入后再单独检查；各工程依赖与锁文件保持完整。

本章完成后，回到[第 10 章](./10-MiniCMS项目总览.md)核对阶段 8 的内容能力，再进入[第 20 章](./20-从开发环境到线上运行.md)准备生产运行。编辑器、正文格式和排版不拖到部署时才决定。

想先改善写作交互时，接着完成 [19A-提升写作体验](./19A-提升写作体验.md)，再进入第 20 章；基础保存与公开阅读链路沿用本章。
