# 15B. 标签管理与页面联调

> Mini CMS 阶段 5：完成第 15 章的后端练习，并用 15A 复习关系维护后，继续完善 `server` 和 `admin-web-antd`。

## 本章要完成什么

第 15 章结束时，后端已经能处理关系、筛选和发布规则，但标签本身还不能被管理，页面上也还没有标签相关的操作入口。本章先完成标签接口和管理页，再把标签选择、筛选和分页接入已有文章页面，最后生成测试数据联调。

标签 CRUD 继续作为独立练习；首次接入的表单数据和分页请求给出局部代码，接在第 14 章已有实现上。下面后端路径相对 `mini-cms/server`，前端路径相对 `mini-cms/admin-web-antd`。

## 1. 标签接口

新建标签模块，按下面三个文件分工：

```text
src/modules/tags/
├── tag-schema.ts       Zod 校验和推导类型
├── tag-repository.ts   Prisma 查询
└── tag-router.ts       四个路由
```

对应四个接口：

```text
GET    /api/tags
POST   /api/tags
PATCH  /api/tags/:id
DELETE /api/tags/:id
```

与文章模块的差别只有几处：

| 差别 | 说明 |
|---|---|
| 字段更少 | 只有 `name` 和 `slug`，没有状态、发布时间和正文 |
| `slug` 唯一 | 和文章一样用 `@unique`，重复时返回 409，提示应写“标签 slug 已经存在” |
| 不需要分页 | 标签数量少，列表全部返回；文章筛选下拉框也要用这份数据 |
| 删除有连带影响 | 按第 15 章第 7 节，删除标签会清掉相关关系行，但不会删掉文章 |

### 1.1 先定义标签请求的 Schema

Schema 是可以执行的输入规则。新建 `src/modules/tags/tag-schema.ts`：

```ts
import { z } from "zod";

const nameSchema = z.string().trim().min(1, "标签名称不能为空");
const slugSchema = z.string().trim().toLowerCase()
  .min(1, "slug 不能为空")
  .max(200, "slug 不能超过 200 个字符")
  .regex(/^[a-z0-9]+(?:-[a-z0-9]+)*$/, "slug 只能包含小写字母、数字和连字符");

export const createTagSchema = z.strictObject({
  name: nameSchema,
  slug: slugSchema,
});

export const updateTagSchema = z.strictObject({
  name: nameSchema.optional(),
  slug: slugSchema.optional(),
}).refine((input) => Object.keys(input).length > 0, {
  error: "至少提交一个可修改字段",
});

export const tagIdParamsSchema = z.strictObject({
  id: z.coerce.number().int().positive(),
});

export type CreateTagInput = z.infer<typeof createTagSchema>;
export type UpdateTagInput = z.infer<typeof updateTagSchema>;
```

名称去掉首尾空格后不能为空；slug 沿用文章规则。更新时没传的字段保持原值，但 `{}` 会被拒绝。`z.strictObject()` 还会拒绝额外的 `id` 等字段。

同一份 `createTagSchema` 有两个用途：Router 调用它的 `.parse(request.body)`，校验并规范化创建标签接口收到的数据；`z.infer<typeof createTagSchema>` 则推导出 `CreateTagInput` 类型，用作 Repository 中 `createTag()` 的 `input` 参数类型。下一小节把这两处接起来。

### 1.2 接好 Repository、Router 和应用入口

以创建标签为例，先看 Schema 怎样连接 Router 和 Repository。下面分别是两个文件中的局部代码：

```ts
// tag-repository.ts：从 Schema 文件导入推导出的输入类型。
import type { CreateTagInput, UpdateTagInput } from "./tag-schema";

export function createTag(input: CreateTagInput) {
  return prisma.tag.create({ data: input });
}
```

这段先展示输入类型和 Prisma 调用，创建时的错误转换按下文补齐。`prisma` 仍使用项目已有的数据库实例。

```ts
// tag-router.ts：校验本次请求，把校验后的值传给 Repository。
tagRouter.post("/", async (request, response) => {
  const input = createTagSchema.parse(request.body);
  const tag = await createTag(input);
  response.status(201).json({ data: tag });
});
```

例如请求体是 `{"name":"  后端  ","slug":" BACKEND "}`，`.parse()` 返回的 `input` 是 `{"name":"后端","slug":"backend"}`，Router 再把这个值交给 `createTag(input)`。字段不合法时，`.parse()` 抛出错误，后面的 `createTag(input)` 就不会执行。

`CreateTagInput` 让 TypeScript 检查 `createTag()` 的参数类型，类型标注本身不会检查真实请求，也不会去掉空格或转换大小写。这些运行时操作由 Router 中的 `.parse()` 完成。更新接口同理：`updateTagSchema` 校验请求体，从它推导出的 `UpdateTagInput` 作为 `updateTag()` 的 `input` 参数类型。

参照文章 Repository，独立实现下面四个函数。输入类型从 `./tag-schema` 用 `import type` 导入：

| 函数 | Prisma 操作 |
|---|---|
| `getTags()` | `prisma.tag.findMany()`，返回 `id、name、slug`，可按 id 升序排列 |
| `createTag(input: CreateTagInput)` | `prisma.tag.create({ data: input })` |
| `updateTag(id: number, input: UpdateTagInput)` | `prisma.tag.update({ where: { id }, data: input })` |
| `deleteTag(id: number)` | `prisma.tag.delete({ where: { id } })` |

标签 Repository 的创建、更新把 `P2002` 转成 409 `TAG_SLUG_CONFLICT`；更新、删除把 `P2025` 转成 404 `TAG_NOT_FOUND`。原错误中间件会把这两个 Prisma 错误码解释成文章错误，因此这里先转换为标签的 `AppError`，再由中间件生成响应。

以 `tag-repository.ts` 中的 `updateTag()` 为例。`Prisma` 从 `../../generated/prisma/client` 导入，`AppError` 从 `../../errors/app-error` 导入；保留已有的 `prisma` 实例和输入类型导入：

```ts
export function updateTag(id: number, input: UpdateTagInput) {
  return prisma.tag.update({ where: { id }, data: input })
    .catch((error: unknown) => {
      if (error instanceof Prisma.PrismaClientKnownRequestError) {
        if (error.code === "P2002") {
          throw new AppError(409, "TAG_SLUG_CONFLICT", "标签 slug 已经存在");
        }
        if (error.code === "P2025") {
          throw new AppError(404, "TAG_NOT_FOUND", "标签不存在");
        }
      }
      throw error;
    });
}
```

**这里只操作 Tag，也要保留末尾的 `throw error`。** 操作一个模型仍可能遇到数据库连接失败等错误，`P2002`、`P2025` 并没有覆盖所有失败。两个分支中的 `throw new AppError(...)` 会立即退出当前 `catch`，已转换的错误不会再执行末尾的 `throw error`；末尾只负责把未匹配的错误原样交给中间件。

如果删掉末尾的 `throw error`，未匹配的错误会让 `catch` 正常结束并返回 `undefined`。这样 `updateTag()` 返回的 Promise 会变成成功，Router 中的 `await updateTag(...)` 得到 `undefined`，随后仍执行成功响应，原来的失败就被吞掉了。

第 15 章的文章更新也是同一个原则：原中间件已经能解释文章错误，所以局部只转换新增的关系错误，其余继续抛出。标签更新需要把已知错误改成标签文案，但仍有未处理的失败需要交给中间件兜底。局部 `catch` 负责转换错误含义，最终的 HTTP 错误响应都由中间件返回。

在 `tag-router.ts` 中用 `Router()` 创建并导出 `tagRouter`，导入四个 Repository 函数和三个 Schema。以更新路由为例，下面是这个文件中的局部代码：

```ts
tagRouter.patch("/:id", async (request, response) => {
  const { id } = tagIdParamsSchema.parse(request.params);
  const input = updateTagSchema.parse(request.body);
  const tag = await updateTag(id, input);
  response.json({ data: tag });
});
```

其余路由按同一流程完成：GET `/` 调用 `getTags()`；POST `/` 用 `createTagSchema.parse(request.body)` 后创建，返回 201；DELETE `/:id` 校验路径参数后删除。列表返回 `{ data: tags }`，创建、更新、删除返回 `{ data: tag }`，其余成功状态码为 200。传给 Repository 的是 `.parse()` 的返回值。

最后在 `src/app.ts` 中导入并注册，放在 404 和错误中间件之前：

```ts
import { tagRouter } from "./modules/tags/tag-router";

app.use("/api/tags", tagRouter);
```

运行 `npx tsc --noEmit`，再用 Apifox 创建一个标签，例如 `{"name":"联调标签","slug":"integration-tag"}`，记录返回的 id。依次查询列表、修改名称、删除并再次查询，确认四个接口的正常流程都能完成，再检查失败请求。

## 2. 验证标签接口的错误响应

先按 CRUD 操作看，哪些已知错误需要转换成标签提示：

| 操作 | 需要转换的已知错误 |
|---|---|
| 查询列表 `getTags()` | 没有标签时返回 `[]`，不报“标签不存在” |
| 创建标签 `createTag()` | `P2002`：slug 重复 |
| 更新标签 `updateTag()` | `P2002`：slug 重复；`P2025`：标签不存在 |
| 删除标签 `deleteTag()` | `P2025`：标签不存在 |

**在这两个已知错误码中，只有更新标签需要同时处理两个。** 这不代表每个操作只可能发生表中的错误；四种操作都可能遇到数据库连接失败等问题。没有写 `catch` 时，错误自然向上传播；写了 `catch`，就要继续抛出未处理的错误。

标签 Repository 把 slug 重复、标签不存在转换成对应的 `AppError`，已有错误中间件负责返回状态码和错误 JSON。具体对应关系如下：

| 场景 | 原始错误 | 映射位置 | 对外响应 |
|---|---|---|---|
| 名称为空或全为空格、slug 格式错误 | `ZodError` | 原错误中间件 | 422 `VALIDATION_ERROR` |
| PATCH 提交 `{}`，或提交未声明的字段 | `ZodError` | 原错误中间件 | 422 `VALIDATION_ERROR` |
| 路径 id 为 `abc`、`0` 或 `1.5` | `ZodError` | 原错误中间件 | 422 `VALIDATION_ERROR` |
| 标签 slug 重复 | `P2002` | 标签 repository 的创建、更新函数 | 409 `TAG_SLUG_CONFLICT` |
| 更新或删除的标签不存在 | `P2025` | 标签 repository 的更新、删除函数 | 404 `TAG_NOT_FOUND` |
| 数据库连接失败等未匹配的错误 | 未被局部分支转换的错误 | Repository 原样抛出，原错误中间件兜底 | 500 `INTERNAL_ERROR` |

## 3. 管理页面

下面沿用第 14 章的 Table、Drawer、Form 和页面反馈。每完成一小节，先验证对应操作，再继续下一项。

### 3.1 先完成标签管理页

新建 `features/tags/types.ts`，统一保存标签类型，文章页面也从这里导入：

```ts
export type Tag = { id: number; name: string; slug: string };
export type CreateTagInput = { name: string; slug: string };
export type UpdateTagInput = { name?: string; slug?: string };
```

在 `features/tags/api.ts` 中参照第 14 章第 10 节，独立完成四个请求函数：

| 函数 | 请求 | 传给 `apiRequest` 的类型 | 请求体 |
|---|---|---|---|
| `getTags()` | GET `/api/tags` | `Tag[]` | 不传 body，也不需要 JSON 请求头 |
| `createTag(input)` | POST `/api/tags` | `Tag` | `JSON.stringify(input)`，设置 JSON 请求头 |
| `updateTag(id, input)` | PATCH `/api/tags/:id` | `Tag` | `JSON.stringify(input)`，设置 JSON 请求头 |
| `deleteTag(id)` | DELETE `/api/tags/:id` | `Tag` | 不传 body，也不需要 JSON 请求头 |

例如列表直接写 `return apiRequest<Tag[]>("/api/tags")`。`<Tag[]>` 描述成功后拿到的数据类型，和请求是否带 body 无关。创建、更新才需要在请求配置中填写 `headers: { "Content-Type": "application/json" }` 和 `body`。

再创建 `app/admin/tags/page.tsx`，负责标签列表、Drawer 的打开与关闭，以及调用标签 API。在 `app/admin/layout.tsx` 的公共导航中增加 `/admin/tags` 入口。

**新建和编辑共用一个 `TagForm` 组件。** 新建 `app/admin/tags/_components/tag-form.tsx`，参照第 14 章的 `ArticleForm`，只保留名称和 slug 两个输入框。它负责收集、校验表单值，以及提交中的状态和失败提示；父页面决定调用创建还是更新接口。

在 `features/tags/types.ts` 中增加表单值类型：

```ts
export type TagFormValues = {
  name: string;
  slug: string;
};
```

`TagFormValues` 按表单实际收集的字段定义：名称和 slug 都必填，所以两个字段都是必填字符串。编辑时先回填两个旧值，即使只改名称，提交时仍带上 slug 的原值。

组件的属性沿用文章表单的写法。下面是 `tag-form.tsx` 中的局部类型定义：

```tsx
import type { TagFormValues } from "@/features/tags/types";

type TagFormProps = {
  initialValues?: TagFormValues;
  submitText: string;
  onCancel: () => void;
  onSubmit: (values: TagFormValues) => Promise<void>;
};
```

`initialValues?` 表示新建时可以不传初始值；传了就要包含两个字段。表单值的结构同时满足 `CreateTagInput` 和 `UpdateTagInput`，可以直接传给创建、更新函数；API 请求函数仍使用各自的输入类型。

父页面按两种操作给 `TagForm` 传值：

- 新建：不传 `initialValues`，显示空表单；`onSubmit` 接收表单值后调用 `createTag(values)`。
- 编辑：把点击行保存为 `editingTag`，传入 `initialValues={{ name: editingTag.name, slug: editingTag.slug }}`；`onSubmit` 接收表单值后调用 `updateTag(editingTag.id, values)`。id 用来确定更新哪条记录，不放进表单请求体。

**标签编辑不需要先请求详情。** `GET /api/tags` 已返回每个标签完整的 `id、name、slug`，父页面直接用当前行回填即可。当前没有 `GET /api/tags/:id`。

`TagForm` 把 `initialValues` 交给内部的 Form，`onFinish` 中等待 `onSubmit(values)`。新建、编辑两处组件分别使用 `key="create"` 和 ``key={`edit-${editingTag.id}`}``，并沿用第 14 章 Drawer 关闭后销毁内容的设置，让再次打开时使用本次的初始值。

表单校验与第 1.1 节对齐，失败时保留输入并显示提示；成功后关闭 Drawer 并重新请求标签列表。删除继续使用 `Popconfirm`，加载、空列表和请求错误沿用第 14 章的反馈方式。

验证：从导航进入标签页，创建、修改、删除一个标签，再试一次重复 slug。正常操作会更新列表，失败时 Drawer 保留输入并显示标签错误提示。

### 3.2 让文章表单能选择、保存和回填标签

上一节已经能新建“后端”“数据库”等标签，但打开文章的新建或编辑抽屉，仍然只有标题、正文等原来的字段。**标签已经存在，页面还没有让你把标签选给一篇文章。**

后端在第 15 章已经支持接收 `tagIds`，例如 `tagIds: [3, 7]` 表示这篇文章使用标签 3、7。本节要把页面接上：新建时能选择标签，编辑时能看到原来选了哪些，并保存修改。

#### 3.2.1 新建文章时，怎样选标签并一起提交

首先要解决“有哪些标签可选”。文章页面需要调用上一节的 `getTags()`，拿到全部标签，再把它们交给表单里的多选框。

在父页面 `app/admin/articles/page.tsx` 中，从 `@/features/tags/api` 导入 `getTags`，从 `@/features/tags/types` 导入 `Tag`，增加 `const [tags, setTags] = useState<Tag[]>([])`。进入页面时，在独立的 Effect 中调用 `getTags()`，把结果交给 `setTags()`。请求的加载和失败处理沿用第 14 章：标签请求完成前显示加载状态，成功后再显示表单，失败时显示错误提示。

假设返回的一个标签是 `{ id: 3, name: "后端", slug: "backend" }`，多选框需要把它转换成 `{ label: "后端", value: 3 }`。在父页面中增加：

```tsx
const tagOptions = tags.map((tag) => ({
  label: tag.name,
  value: tag.id,
}));
```

`label` 是显示给用户的名称，`value` 是选中后保存的数字 id。给新建、编辑两处 `<ArticleForm>` 都传入 `tagOptions={tagOptions}`；在 `article-form.tsx` 的 `ArticleFormProps` 中增加 `tagOptions: { label: string; value: number }[]`，并在组件参数解构中接收 `tagOptions`。

有了选项，还要让 Form 收集已选 id。在 Form 内增加：

```tsx
<Form.Item name="tagIds" label="标签">
  <Select mode="multiple" allowClear options={tagOptions} />
</Form.Item>
```

`mode="multiple"` 允许选多个标签；`name="tagIds"` 让 Form 把已选值放进 `values.tagIds`。例如选中“后端”和“数据库”，提交值中就会有 `tagIds: [3, 7]`。

表单现在多收集了一个字段，因此在 `features/articles/types.ts` 的 `ArticleFormValues` 中增加 `tagIds: number[]`。标签可以不选，未选择时用空数组，所以把 Form 原来的初始值改为：

```tsx
initialValues={{ status: "draft", tagIds: [], ...initialValues }}
```

创建和更新请求也要允许这个字段：在同一文件的 `CreateArticleInput`、`UpdateArticleInput` 中分别增加 `tagIds?: number[]`。表单总会提供数组，API 则允许其他调用方省略它，这就是两处是否可选的区别。前端类型需要自己同步，不会随着后端 Schema 自动改变。

第 14 章的 `handleCreate(values)` 已经把整份表单值交给 `createArticle(values)`，请求函数再用 `JSON.stringify(input)` 发送。因此无需再写一个“保存文章标签”的请求，标签 id 会和标题、正文一起提交。

此时新建流程已经接上，但共用 `ArticleFormValues` 的编辑初始值还缺少 `tagIds`，下一步一起补齐，再运行页面验证。

#### 3.2.2 编辑文章时，怎样显示原来选中的标签

多选框有了全部选项，但打开已有文章时，还需要知道“这篇文章选中了哪些”。`getTags()` 返回的是全部可选标签，不能用它判断一篇文章的选择；已选标签要从文章详情里取。

文章继续沿用第 14 章的详情请求。第 15 章已经让后端在详情中返回 `articleTags`，其中每项的 `tagId` 就是已选标签 id。先在 `features/articles/types.ts` 中导入 `Tag`：

```ts
import type { Tag } from "@/features/tags/types";
```

在原 `Article` 类型中增加下面两个字段，其他字段保留：

```ts
articleTags: { articleId: number; tagId: number; tag: Tag }[];
publishedAt: string | null;
```

`articleTags` 描述文章关联的标签，供回填和展示使用；`publishedAt` 是第 15 章同时新增的发布时间，这里一起对齐响应类型。

然后在父页面传给编辑 `<ArticleForm>` 的 `initialValues` 对象中，保留标题、正文等原字段，增加：

```tsx
tagIds: editingArticle.articleTags.map((item) => item.tagId),
```

例如文章详情包含标签 3、7，`map()` 得到 `[3, 7]`。Form 用它设置 `tagIds` 的初始值，多选框就会选中 value 为 3、7 的选项。没有标签的文章得到 `[]`。

`Article` 现在包含标签关系，但删除接口没有查询并返回关系。因此同时把 `features/articles/api.ts` 中删除请求的 `apiRequest<Article>` 改为 `apiRequest<Pick<Article, "id">>`，只描述页面需要的删除结果。

验证：选择两个标签并新建文章，在 Network 中确认 POST 请求体包含数字数组 `tagIds`，响应中的 `articleTags` 包含对应关系。再打开这篇文章编辑，确认两个标签都已选中；打开没有标签的文章，多选框应为空。

#### 3.2.3 只改标签，为什么会提示“内容没有变化”

第 14 章的 `handleUpdate()` 用 `isUnchanged` 比较标题、slug、摘要、正文和状态。它还没有比较标签，所以只修改标签时，原来的五个字段都没变，函数就会提前返回，不发送更新请求。

在父页面 `handleUpdate()` 确认 `editingArticle` 存在之后、计算 `isUnchanged` 之前增加：

```tsx
const originalTagIds = editingArticle.articleTags.map((item) => item.tagId);
const sameTags = values.tagIds.length === originalTagIds.length &&
  values.tagIds.every((id) => originalTagIds.includes(id));
```

`originalTagIds` 是这篇文章原来的标签，`values.tagIds` 是本次表单的选择。数量相同且每个 id 都在原数组中，才认为没变化；标签顺序不同不算修改。

把原 `isUnchanged` 表达式最后的状态比较改为 `values.status === editingArticle.status && sameTags`。这样只有原来的字段和标签都没变，才会阻止提交。

验证：只修改标签后保存，应发送 PATCH 请求；重新打开，看到修改后的选择。再清空全部标签保存，请求体应包含 `tagIds: []`，重新打开时仍为空。`[]` 表示清空关系，省略 `tagIds` 则表示不修改关系。

#### 3.2.4 列表怎样显示文章的标签

保存和回填已经完成，但文章列表还看不到标签。列表接口也返回了 `articleTags`，可以从每条关系的 `tag.name` 取出名称。

先让 `ArticleListItem` 原来的 `Pick` 字段再包含 `articleTags` 和 `publishedAt`，与第 15 章的列表响应保持一致。然后增加标签列，在该列的 `render` 中使用：

```tsx
render: (_, article) =>
  article.articleTags.map((item) => item.tag.name).join("、") || "—",
```

验证：刷新列表，有标签的文章显示名称，没有标签的文章显示“—”。本节完成了标签选择与展示；下一步再让列表接上后端已经提供的筛选和分页。

### 3.3 让列表请求保留分页信息

文章列表已经能显示数据，但分页器还需要知道当前页、每页条数和总数。这些信息后端在第 15 章就已经返回了，例如：

```json
{
  "data": [],
  "pagination": { "page": 1, "pageSize": 20, "total": 0 }
}
```

本小节先让前端请求函数把分页信息返回给页面，并能发送页码和筛选条件；下一小节再把它们接到 Table 和筛选控件上。

#### 3.3.1 响应里有分页信息，页面为什么拿不到

看第 14 章 `apiRequest()` 最后的两行：

```ts
const successBody: ApiSuccess<T> = await response.json();
return successBody.data;
```

`response.json()` 解析出的对象包含 `data` 和 `pagination`，但 `return successBody.data` 只把文章数组返回给调用方。因此 Network 或 Apifox 能看到完整响应，页面执行 `const result = await getArticles()` 时，拿到的 `result` 却只有数组。

这里不是类型把 `pagination` 过滤掉了。**类型描述数据的形状，`return` 决定实际返回什么。** 即使给 `ApiSuccess` 补上 `pagination`，只要仍然 `return successBody.data`，页面就拿不到分页信息。

#### 3.3.2 提取公共请求过程，为分页列表保留完整结果

原来的详情、新建、更新等调用只需要 `data`，文章分页列表还需要 `pagination`。把发送请求和处理错误的代码提取出来，外面提供两种取结果的方式：

```text
requestJson()：发送请求、处理错误，返回完整响应
    ├─ apiRequest()：只返回 data，原来的调用不用改
    └─ apiListRequest()：返回 data + pagination，给分页列表用
```

在 `lib/api-client.ts` 中保留原来的 `ApiFailure`、`API_BASE_URL` 及环境变量检查，把原来的 `ApiSuccess` 类型和 `apiRequest()` 替换为下面代码：

```ts
export type Pagination = {
  page: number;
  pageSize: number;
  total: number;
};

export type ApiListSuccess<T> = {
  data: T[];
  pagination: Pagination;
};

// S 描述整个成功响应，解析后原样返回。
async function requestJson<S>(path: string, options?: RequestInit): Promise<S> {
  const response = await fetch(`${API_BASE_URL}${path}`, options);
  if (!response.ok) {
    const errorBody: ApiFailure = await response.json();
    throw new Error(errorBody.error.message);
  }
  const body: S = await response.json();
  return body;
}

// 普通请求：继续只取 data。
export async function apiRequest<T>(path: string, options?: RequestInit): Promise<T> {
  const body = await requestJson<{ data: T }>(path, options);
  return body.data;
}

// 分页列表：保留 data 和 pagination。
export function apiListRequest<T>(path: string): Promise<ApiListSuccess<T>> {
  return requestJson<ApiListSuccess<T>>(path);
}
```

普通请求仍用 `apiRequest<Article>()`、`apiRequest<Tag[]>()` 等原来的写法。只有文章列表改用 `apiListRequest<ArticleListItem>()`，页面拿到的结果才同时包含 `data` 和 `pagination`。

这里 `ApiListSuccess<T>` 已经把 `data` 定义成 `T[]`，所以传入的 `ArticleListItem` 表示一篇文章，不再加 `[]`。下一小节修改文章列表请求，3.4 再接到页面。

#### 3.3.3 能接收分页结果后，怎样指定要查哪一页

上面解决了“后端返回什么”，接下来解决“前端发送什么条件”。页面翻页时要传 `page`、`pageSize`，筛选时还可能传标题、状态和标签 id。

在 `features/articles/types.ts` 中增加 `ArticleListQuery`，描述发送给文章列表接口的查询条件：

```ts
export type ArticleListQuery = {
  title?: string;
  status?: ArticleStatus;
  tagId?: number;
  page: number;
  pageSize: number;
};
```

在 `features/articles/api.ts` 中从 `@/lib/api-client` 增加导入 `apiListRequest`，从 `./types` 用 `import type` 导入 `ArticleListQuery`。原来的 `apiRequest` 和 `ArticleListItem` 导入保留，替换 `getArticles()`：

```ts
export function getArticles(query: ArticleListQuery) {
  const params = new URLSearchParams({
    page: String(query.page),
    pageSize: String(query.pageSize),
  });
  const title = query.title?.trim();
  if (title) params.set("title", title);
  if (query.status) params.set("status", query.status);
  if (query.tagId !== undefined) params.set("tagId", String(query.tagId));

  return apiListRequest<ArticleListItem>(`/api/articles?${params.toString()}`);
}
```

`URLSearchParams` 把条件编码成查询字符串。空标题和清空的筛选项不发送，页码和每页条数始终带上。后端第 15 章的 Schema 再把数字字符串转换成数字。

例如调用 `getArticles({ page: 2, pageSize: 10, status: "draft" })`，会请求 `/api/articles?page=2&pageSize=10&status=draft`。它返回的 Promise 成功后，得到的是 `{ data, pagination }`，不再只是文章数组。

此时页面原来的 `getArticles()` 调用需要同步修改：传入查询条件，再把结果中的 `data` 交给文章列表、`pagination.total` 交给分页器。下一小节完成这部分后，统一做类型检查，并在页面打印结果，确认同时拿到了 `data` 和 `pagination`。

### 3.4 接入分页、筛选和操作后的刷新

`getArticles(query)` 已经能接收查询条件，但页面还需要让用户选择这些条件，并在条件变化后重新请求。本节把这条流程接起来：

```text
操作搜索框、下拉框或分页器
→ 更新 query
→ getArticles(query) 请求后端
→ 用 data 更新列表，用 pagination.total 更新总数
```

下面的代码都修改文章父页面 `app/admin/articles/page.tsx`，保留已有的文章表单、标签选项请求和页面反馈。

#### 3.4.1 用状态保存条件，让控件修改它

用户输入了标题、选择了标签，页面需要记住这些值，才能把它们传给 `getArticles()`。从 `@/features/articles/types` 用 `import type` 导入 `ArticleListQuery`、`ArticleStatus`，增加查询状态：

```tsx
const [query, setQuery] = useState<ArticleListQuery>({ page: 1, pageSize: 10 });
```

初始状态表示“不筛选，查询第 1 页，每页 10 条”。用户操作控件后，再向 `query` 中写入对应条件：

| 控件 | 修改的字段 |
|---|---|
| 标题搜索框 | `title` |
| 状态下拉框 | `status` |
| 标签下拉框 | `tagId` |
| 分页器 | `page`、`pageSize` |

从 `antd` 导入 `Input`、`Select`、`Space`，在 Table 上方增加三个筛选控件。`tagOptions` 复用第 3.2 节的标签选项：

```tsx
<Space wrap>
  <Input.Search
    placeholder="按标题搜索"
    allowClear
    onSearch={(value) => setQuery((current) => ({
      ...current,
      title: value.trim() || undefined,
      page: 1,
    }))}
  />
  <Select
    allowClear
    placeholder="全部状态"
    style={{ width: 140 }}
    value={query.status}
    options={[
      { label: "草稿", value: "draft" },
      { label: "已发布", value: "published" },
    ]}
    onChange={(status: ArticleStatus | undefined) =>
      setQuery((current) => ({ ...current, status, page: 1 }))
    }
  />
  <Select
    allowClear
    placeholder="全部标签"
    style={{ width: 180 }}
    value={query.tagId}
    options={tagOptions}
    onChange={(tagId: number | undefined) =>
      setQuery((current) => ({ ...current, tagId, page: 1 }))
    }
  />
</Space>
```

`value={query.tagId}` 表示当 `query.tagId` 变化时，让 Select 跟着改变选中项；`onChange` 则在用户选择时更新 `query.tagId`。

搜索框在按回车或点击搜索时，才把文字写入 `query.title`，不是每输入一个字就请求。清空按钮也会触发搜索，`value.trim() || undefined` 会把空文字变成 `undefined`；下拉框清空时同样保存 `undefined`。第 3.3 节的请求函数不会发送这些空条件。

`current` 是更新前的查询状态，`...current` 保留其他条件。例如选标签时保留已有的标题和状态，所以三个条件可以组合。你原来在第 5 页，筛选后的结果只有 2 页，第 5 页就不存在了。所以改变筛选条件时，把 `page` 重置为 1，从筛选结果的第一页开始看。

现在控件能修改 `query` 了，继续把它接到请求上，再验证页面结果。

#### 3.4.2 条件变化后，重新请求并更新列表

原来的列表 Effect 依赖数组是 `[]`，只在页面挂载时请求。现在需要让它跟随 `query` 变化，并把新状态传给 `getArticles(query)`。

保留原来的 `articles`、`listLoading`、`listError` 状态，再增加总数：

```tsx
const [total, setTotal] = useState(0);
```

用下面代码替换原来的文章列表 Effect，标签选项的 Effect 保留：

```tsx
useEffect(() => {
  async function loadArticles() {
    setListLoading(true);
    setListError(null);
    try {
      const result = await getArticles(query);
      setArticles(result.data);
      setTotal(result.pagination.total);
    } catch (error) {
      setListError(error instanceof Error ? error.message : "文章列表加载失败");
    } finally {
      setListLoading(false);
    }
  }

  void loadArticles();
}, [query]);
```

这里的 `[query]` 表示查询状态变化后重新执行 Effect。`result.data` 是当前页的文章，`result.pagination.total` 是全部符合筛选条件的文章数量，两者分别保存。

接着让分页器显示并修改同一份查询状态。保留 Table 的 `columns`、`dataSource`、`rowKey` 和加载反馈，只替换 `pagination` 属性：

```tsx
pagination={{
  current: query.page,
  pageSize: query.pageSize,
  total,
  showSizeChanger: true,
  pageSizeOptions: [10, 20, 50, 100],
  onChange: (page, pageSize) => setQuery((current) => ({
    ...current,
    page: pageSize !== current.pageSize ? 1 : page,
    pageSize,
  })),
}}
```

分页器的 `current` 对应 `query.page`。点击第 2 页会更新 `query.page`，触发 Effect 请求第 2 页；改变每页条数时则回到第 1 页。后端已经完成分页，页面直接显示 `result.data`，不用再手动切分数组。

运行前端 `npx tsc --noEmit`，再用 Network 验证：搜索标题、选择状态或标签后，URL 带上对应条件且 `page=1`；清空后不再带该条件。翻页会改变 `page`，Table 总数应等于响应里的 `pagination.total`。数据不足以翻页时，可以用第 4 节的测试数据再检查。

#### 3.4.3 条件没变，保存或删除后怎样刷新

现在只有 `query` 改变才会重新请求。但更新文章、删除文章之后，查询条件可能完全没变，列表仍然需要刷新。

第 14 章直接向本地数组插入、替换或删除行，现在有了筛选和分页，这样做还不够。例如筛选草稿时把一篇文章发布，它应该从列表消失，总数也应减少。让后端按当前条件重新查一次，才能同时得到正确的行和总数。

增加一个刷新计数状态：

```tsx
const [refreshVersion, setRefreshVersion] = useState(0);
```

把上面文章列表 Effect 的依赖数组从 `[query]` 改为 `[query, refreshVersion]`。这个数字不传给后端，只用来触发 Effect；每次加 1，就重新请求当前条件。

新建、更新和删除成功后，移除原来直接插入、替换或删除行的 `setArticles(...)`，改为增加刷新计数。以新建为例，替换原 `handleCreate()`：

```tsx
async function handleCreate(values: ArticleFormValues) {
  await createArticle(values);
  setDrawerOpen(false);
  messageApi.success("文章已创建");
  setRefreshVersion((version) => version + 1);
}
```

更新保留第 3.2 节的 `isUnchanged` 判断，成功后关闭 Drawer、提示成功并刷新；删除保留原来的确认、错误处理和 `deletingId` 状态，只替换成功后的数组处理。重新请求失败由列表的 `listError` 显示，不会把已经保存成功的操作提示成保存失败。

验证：新建、更新、删除成功后，Network 都应出现新的文章列表 GET 请求。再筛选草稿，通过编辑表单把一篇文章改为已发布，保存后它应从当前列表消失，总数减 1。发布时间继续由后端维护。

#### 3.4.4 最后处理旧请求覆盖和页码越界

先处理快速切换条件的问题：先选草稿，再选已发布，两个请求可能先后发出、倒序返回。需要让旧请求的结果不再更新页面。

在现有文章列表 Effect 内、`loadArticles()` 定义之前增加 `let active = true`；在 `void loadArticles()` 后增加清理函数：

```tsx
return () => { active = false; };
```

再在 `await getArticles(query)` 后立即增加 `if (!active) return`，并给 `catch`、`finally` 中的状态更新加上判断：

```tsx
} catch (error) {
  if (active) {
    setListError(error instanceof Error ? error.message : "文章列表加载失败");
  }
} finally {
  if (active) setListLoading(false);
}
```

每次 Effect 都有自己的 `active`。条件变化或页面卸载时，清理函数把旧的那次设为 `false`，所以它之后返回的结果、错误和加载状态都不会覆盖新请求。这不会取消网络请求，只是不再使用旧结果。

再处理最后一页被删空的问题。例如共 11 篇、每页 10 篇，删除第 2 页唯一的一篇后，只剩 1 页，页面应该退回第 1 页。发布文章使它不再符合筛选条件时，也可能发生同样的情况。

在 `if (!active) return` 之后、`setArticles(result.data)` 之前增加：

```tsx
const lastPage = Math.max(1, Math.ceil(result.pagination.total / query.pageSize));
if (query.page > lastPage) {
  setQuery((current) => ({ ...current, page: lastPage }));
  return;
}
```

`Math.ceil` 向上取整计算总页数，`Math.max(1, ...)` 让零条结果也停在第 1 页。当前页超出范围时，更新 `query.page`，Effect 就会重新请求有效的一页。

最后再运行类型检查。用浏览器慢速网络快速切换状态，确认最终显示最后一次选择的结果；删除最后一页唯一的文章，确认页码和列表一起回到有效页。

## 4. 一次生成 100 篇测试文章

种子数据就是提前准备的一批测试记录。有了它，不用在页面上手动新建 100 次，就能测试翻页、筛选和标签显示。

先完成第 15 章第 2 节的模型迁移，再把种子脚本保存在 `mini-cms/server` 中，以后运行命令即可重建数据。脚本用 SQL 清空 `articles`、`tags`、`article_tags` 三张表并重置自增 id，再用 Prisma 创建标签、文章和关系。

**先配置执行命令。** 在 `server/prisma.config.ts` 已有的 `migrations` 中增加 `seed`，其他配置保留：

```ts
migrations: {
  path: "prisma/migrations",
  // 运行 npx prisma db seed 时，通过 tsx 执行这个 TypeScript 文件。
  seed: "tsx prisma/seed.ts",
},
```

**再新建 `server/prisma/seed.ts`。** 复用项目现有的 `prisma` 实例。下面按 `src/db/client.ts` 导入；如果保留的是第 09 章的 `src/data/client.ts`，只需把导入路径改为 `../src/data/client`。

```ts
import { prisma } from "../src/db/client";

async function main() {
  // 先准备 5 个标签，后面的文章从中选择标签。
  const tags = [
    { name: "后端", slug: "backend" },
    { name: "数据库", slug: "database" },
    { name: "Prisma", slug: "prisma" },
    { name: "Express", slug: "express" },
    { name: "TypeScript", slug: "typescript" },
  ];
  // 用同一个当前时间作为基准，安排 100 篇文章的创建时间。
  const now = Date.now();

  // 清空和重新生成属于同一个事务；中途抛错时，全部回滚。
  // 事务内统一通过 tx 操作数据库。
  const counts = await prisma.$transaction(async (tx) => {
    // 执行 SQL：清空这三张表的数据，保留表结构。
    // RESTART IDENTITY 重置自增序列，文章和标签的新 id 都从 1 开始。
    await tx.$executeRaw`
      TRUNCATE TABLE article_tags, articles, tags RESTART IDENTITY
    `;

    // 先创建标签，收集数据库实际生成的 id，供文章建立关系时使用。
    const tagIds: number[] = [];
    for (const input of tags) {
      const tag = await tx.tag.create({ data: input });
      tagIds.push(tag.id);
    }

    for (let n = 1; n <= 100; n++) {
      // 把编号补成 001～100，用于标题和唯一的 slug。
      const number = String(n).padStart(3, "0");
      // % 表示取余数：每 5 篇中有 2 篇草稿，共 40 篇草稿、60 篇已发布。
      const isDraft = n % 5 === 0 || n % 5 === 1;
      // 时间单位是毫秒；每篇比前一篇晚 1 小时，方便验证列表倒序排列。
      const createdAt = new Date(now - (101 - n) * 60 * 60 * 1000);
      const selectedTagIds: number[] = [];

      // 每 5 篇中，第 5 篇不选标签，其余 4 篇先选一个标签。
      // 数组下标 0～4 分别对应前面创建的 5 个标签。
      if (n % 5 !== 0) {
        selectedTagIds.push(tagIds[(n - 1) % 5]);
      }
      // 第 3、4 篇再选一个不同的标签，形成无标签、单标签、多标签三种情况。
      if (n % 5 === 3 || n % 5 === 4) {
        selectedTagIds.push(tagIds[n % 5]);
      }

      await tx.article.create({
        data: {
          title: `分页测试文章 ${number}`,
          slug: `seed-article-${number}`,
          summary: `这是第 ${n} 篇文章的摘要`,
          content: `这是第 ${n} 篇文章的测试正文，用于练习列表、编辑和发布。`,
          status: isDraft ? "draft" : "published",
          createdAt,
          // 草稿没有发布时间；已发布文章设为创建后 30 分钟发布。
          publishedAt: isDraft
            ? null
            : new Date(createdAt.getTime() + 30 * 60 * 1000),
          articleTags: {
            // 嵌套写入：每个选中的标签生成一条 ArticleTag 关系记录。
            // articleId 由当前创建的文章提供，tagId 来自下面 connect 的 id。
            // selectedTagIds 为空数组时，不创建关系记录。
            create: selectedTagIds.map((tagId) => ({
              tag: { connect: { id: tagId } },
            })),
          },
        },
      });
    }

    // 查询实际写入的数量，返回后在终端打印，方便核对生成结果。
    return {
      articles: await tx.article.count(),
      drafts: await tx.article.count({ where: { status: "draft" } }),
      published: await tx.article.count({ where: { status: "published" } }),
      tags: await tx.tag.count(),
      relations: await tx.articleTag.count(),
    };
  }, { timeout: 30_000 }); // 整个事务最多执行 30 秒。

  console.log("种子数据生成完成：", counts);
}

try {
  await main();
} catch (error) {
  console.error("种子数据生成失败：", error);
  // 用非零退出码告诉终端：本次脚本执行失败。
  process.exitCode = 1;
} finally {
  // 无论成功还是失败，都关闭这个种子进程的数据库连接。
  await prisma.$disconnect();
}
```

脚本已经包含清空数据的 SQL，不用另外在 TablePro 中清空。

种子脚本直接用 `tx.article.create()` 写入数据库，不会调用第 15 章第 8 节的 `createArticle()`，其中计算发布时间的代码也就不会执行。因此，脚本自己填写 `status` 和 `publishedAt`：草稿的发布时间为 `null`，已发布文章填一个测试时间。`updatedAt` 不用手动填写，Prisma 会根据模型中的 `@updatedAt` 自动设置。

**最后执行种子。** 在 `mini-cms/server` 目录运行：

```bash
# 先检查 TypeScript 类型，不生成编译文件；检查通过后再执行下一条。
npx tsc --noEmit
# 执行种子脚本：先清空三张表并重置 id，再生成测试数据。
npx prisma db seed
```

`prisma db seed` 会按配置执行 `tsx prisma/seed.ts`。Prisma 7 不会在迁移后自动运行种子，需要主动执行这条命令。成功后终端会打印数量统计；本次文章 id 为 1～100、标签 id 为 1～5，下一篇新文章的 id 为 101。文章创建时间逐篇递增，所以倒序列表从 id 100 开始。

执行后应有 **100 篇文章、40 篇草稿、60 篇已发布文章、5 个标签、120 条关系**。其中 20 篇没有标签、40 篇有一个标签、40 篇有两个标签。草稿没有发布时间，已发布文章有发布时间。

刷新管理页面，在刚生成、尚未修改的数据上按顺序检查。下表会明确指出何时清空上一项筛选：

| 操作 | 预期 |
|---|---|
| 不筛选，每页 10 条 | 共 100 条、10 页；第一页 id 为 100～91 |
| 翻到第 2 页 | id 为 90～81，总数仍是 100 |
| 每页改成 20 条 | 共 5 页，每页最多 20 条 |
| 状态选择草稿，每页 10 条 | 回到第 1 页，共 40 条、4 页 |
| 保留草稿筛选，再选择“数据库”（id 2） | 共 0 篇；这批数据中“数据库”标签只关联已发布文章 |
| 清空状态，保留“数据库”标签 | 共 20 篇文章 |
| 清空标签，再搜索标题 `001` | 只返回“分页测试文章 001” |
| 清空标题搜索，回到第 1 页，再打开 id 100、99 的编辑抽屉 | id 100 没选标签；id 99 选中 Express、TypeScript |

再次运行 `npx prisma db seed`，会清掉你在这三张表中新建或修改的数据，重新生成同一批测试记录，不会累计成 200 篇。重置后刷新页面，重新加载列表和标签选项；第 15 章第 3 节记录过的旧 id 不再代表原来的练习数据。

## 5. 完成阶段 5 前的检查

- 标签可以新建、编辑和删除；非法字段、空更新和非法 id 返回 422；重复 slug 返回 409，操作不存在的标签返回 404，提示指向标签。
- 新建文章选择两个标签，重新打开编辑抽屉仍选中这两个；只改标签可以保存，清空后再次打开显示为空。
- 标题、状态、标签筛选能组合使用；翻页后总数仍是符合筛选条件的总数；清空筛选恢复列表。
- 发布、重复发布、撤回的时间符合第 15 章第 6 节规则；包含无效标签的更新返回 422，旧标题和关系都保留。
- 删除带关系的文章后，标签仍在；删除仍被文章使用的标签后，文章仍在，详情里少了这个标签。

如果执行了本章第 4 节，第 15 章第 3 节的旧数据已经清空，不必再执行下面的清理。若没有生成种子数据，可以在练习结束后按原来的 slug 清理：

```sql
DELETE FROM articles
WHERE slug IN ('ch15-prisma-intro', 'ch15-express-middleware');

DELETE FROM tags
WHERE slug IN ('ch15-backend', 'ch15-database');
```

在 TablePro 中按记录过的文章、标签 id 查询 `article_tags`，对应关系应已消失。第 15 章第 8 节通过 API 新建的练习文章按你记录的 id 单独删除；若练习中改过 slug，也按实际 id 清理。
