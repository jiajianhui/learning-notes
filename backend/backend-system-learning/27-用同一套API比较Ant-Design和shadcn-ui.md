# 27. 用同一套 API 比较 Ant Design 和 shadcn/ui

## 这一章要完成什么

前面已经按顺序完成两个并列项目：

```text
Ant Design 管理后台
-> 第一套前端实现

shadcn/ui 管理后台
-> 第二套前端实现
```

先做 Ant Design、再做 shadcn/ui 是学习顺序，不是项目主次。本章不再提供一份标签页面完整代码。你要把文章模块练过的请求、表格、表单和错误处理迁移到标签模块，再用实际代码比较两种方案。

完成后，`mini-cms` 中有三个可以独立安装和运行的工程：

```text
mini-cms/
├── server/              Express API
├── admin-web-antd/      Ant Design 后台项目
└── admin-web-shadcn/    shadcn/ui 后台项目
```

两个后台共用同一个 `server` 和 PostgreSQL，不复制数据库，也不创建第二套接口。

---

## 1. 开始条件

进入本章前先确认：

- Ant Design 后台已经完成文章、标签、登录和主要状态。
- 已完成第 23～26A 章。
- `server` 的文章和标签 contract 已经稳定。
- `admin-web-shadcn` 能登录、查看文章列表、新建和编辑文章。

如果 Ant Design 后台还没有完成，先回到 Mini CMS 阶段 4～6。这只是实现顺序；shadcn/ui 后台同样属于 Mini CMS 的必做前端项目。

---

## 2. 独立完成标签管理

新增页面：

```text
/admin/tags
```

至少完成：

- 查看标签列表。
- 新建标签。
- 编辑标签名称和 slug。
- 删除未被文章使用的标签。
- 正确处理重复 slug。
- 删除前要求确认。
- 操作成功后刷新列表或更新本地数据。

页面需要覆盖：

```text
loading
empty
error
success
```

不要直接复制文章页面再批量改名。先写出标签功能需要的数据：

```text
TagListItem
TagFormValues
标签列表响应
创建和更新请求
后端错误 code
```

再决定哪些部分值得复用。

---

## 3. 把前面知识迁移到新功能

### 列表

标签列表继续使用第 25 章的数据流：

```text
页面请求标签
-> 得到 data
-> columns 描述每列
-> useReactTable 生成表格实例
-> DataTable 渲染
```

如果标签数量很少，可以暂时不做分页。是否分页由 API contract 和真实数据量决定，不是因为文章表格用了分页，所有表格就必须分页。

### 表单

标签表单继续使用第 26 章的职责划分：

```text
Field
-> 组织字段结构

React Hook Form
-> 管理值、错误和提交状态

前端 Zod
-> 提交前快速反馈

Express Zod
-> 保护真实 API 边界
```

标签字段少，可以用 Dialog 承载表单。不要为了复用而把文章表单和标签表单合成一个充满条件分支的“大表单”。

### 错误

继续使用同一套 `ApiError`：

| 返回结果 | 页面处理 |
|---|---|
| 401 | 回到登录页 |
| 422 | 显示到对应字段 |
| 409 | 显示 slug 冲突 |
| 标签仍被文章使用 | 说明为什么不能删除 |
| 网络或 500 | 保留页面内容并显示整体错误 |

错误 code 以 `server` 的真实响应为准。两个后台不能为同一个失败创造不同 contract。

## 4. 跑通完整产品链路

在 shadcn/ui 后台完成一次连续操作：

```text
管理员登录
-> 新建标签
-> 新建一篇草稿并选择标签
-> 编辑标题和正文
-> 发布文章
-> 在列表中筛选到它
-> 撤回或删除
-> 退出登录
```

这一步检查的不是某个按钮，而是页面、API、认证和数据库能否连成闭环。

同时打开 Ant Design 后台，确认：

```text
在 shadcn/ui 后台创建的数据
-> Ant Design 后台能看到

在 Ant Design 后台修改的数据
-> shadcn/ui 后台刷新后能看到
```

如果两边数据不一致，先检查是否真的请求了同一个 `NEXT_PUBLIC_API_BASE_URL` 和同一个数据库，不要先怀疑 UI 组件。

## 5. 用同一组条件做比较

不要只比较页面截图。两套后台视觉不同，但真正有价值的是比较“完成同一件事需要自己负责什么”。

选取四个相同功能：

1. 后台布局。
2. 文章分页表格。
3. 文章编辑表单。
4. 删除确认和结果反馈。

逐项填写：

| 比较项 | Ant Design | shadcn/ui |
|---|---|---|
| 第一版完成速度 |  |  |
| 需要自己维护的代码 |  |  |
| 默认交互是否完整 |  |  |
| 自定义样式是否直接 |  |  |
| 表格状态由谁管理 |  |  |
| 表单状态由谁管理 |  |  |
| 更新组件的方式 |  |  |
| 排错时先看哪里 |  |  |

记录具体证据，例如：

```text
文章表格涉及哪些文件？
分页状态写在哪里？
校验规则写在哪里？
为了调整一处样式改了什么？
升级组件时修改 package 还是比较本地源码？
```

不要先写“哪个更先进”。先记录代码，再形成结论。

## 6. 两套方案的核心差别

做到这里，应该能够用自己的代码验证下面的差别。

### Ant Design

```text
安装组件库
-> 直接使用功能较完整的 Table、Form、Modal
-> 主要通过 props 和主题配置调整
```

它更像一套已经组装好的管理后台工具箱。常见业务组件齐全，第一版通常更快。

### shadcn/ui

```text
把组件源码加入项目
-> 用 Tailwind 和底层 primitive 组成界面
-> 表格和表单状态由专门工具管理
```

它给出可修改的页面基础，但文章 DataTable、React Hook Form 连接和业务状态仍由项目负责。

因此，两种方案不是简单的“组件数量比较”：

```text
Ant Design
-> 更快获得统一、完整的后台能力

shadcn/ui
-> 更直接拥有组件代码和视觉控制权
```

两套方案各自承担完整项目目标：Ant Design 重点掌握高层后台组件的组合，shadcn/ui 重点掌握源码组件、headless 表格和表单状态的组合。

## 7. 整理项目说明

在 `mini-cms/README.md` 中补充三个工程：

```text
server
admin-web-antd
admin-web-shadcn
```

至少说明：

- 每个目录解决什么问题。
- 安装依赖的命令。
- 开发启动命令。
- 默认端口。
- 需要复制哪些 `.env.example`。
- 两个后台怎样连接同一个 API。
- 启动顺序。

开发端口保持：

```text
admin-web-antd     http://localhost:3000
server             http://localhost:3001
admin-web-shadcn   http://localhost:3002
```

`server` 的允许来源应同时包含两个后台。不要使用 `*` 配合 Cookie。

## 8. 最后验证

分别在三个工程运行已有检查：

```bash
# server
npm run build
npm test

# admin-web-antd
npm run lint
npm run build

# admin-web-shadcn
npm run lint
npm run build
```

如果某个工程还没有 `test` script，就不要照抄不存在的命令。以各自 `package.json` 为准，并在 README 中记录真实可用的命令。

再检查：

- 两个后台都能在刷新后保持登录。
- 401 会回到登录页。
- 列表筛选和分页由服务器执行。
- 提交失败不会清空长正文。
- 删除前有确认，失败时不会假装成功。
- 两个后台看到同一份数据库内容。
- 两个前端都没有数据库密码和服务端密钥。

## 9. 完成标准

双前端项目完成，不等于“页面长得一样”。完成标准是：

```text
能运行
-> 三个工程都有明确启动方式

能操作
-> 两个后台都能完成核心管理链路

能解释
-> 能说清 Ant Design 和 shadcn/ui 的职责差别

能比较
-> 结论来自同一功能的真实代码
```

最终保留边界：

- `admin-web-antd` 和 `admin-web-shadcn` 是两个并列项目，都要能完成核心管理功能。
- 项目可以根据具体上线条件选择其中一套部署，但学习完成标准不偏向任何一套。
- 两个后台共享 API contract，但不共享 UI 组件源码。
- 不为了维持两套页面而复制后端和数据库。
