# 20. 从本地到服务器：上线前需要改什么

部署可以先理解为：**把项目放到另一台电脑上运行，让别人也能通过网络访问。** 那台长期运行、对外提供服务的电脑就是服务器。给真实用户使用的环境，通常叫“生产环境”。

第 19 章完成的后台、API 和数据库仍然是同一套。上线增加的问题是：新机器怎样装依赖、连接自己的数据库、启动程序，以及让别人通过域名访问。

本章先讲清这些差别，并在本地试一次上线时的启动方式。[20A](./20A-用1Panel和Docker-Compose部署MiniCMS.md)再带你把它们放到服务器，用 Docker 和 1Panel 管理运行、域名、HTTPS 与备份。

## 1. 换一台电脑，为什么不能只复制代码

你现在的电脑上已经有 Node.js、安装好的依赖、`.env` 和数据库。新机器只有代码时，这些条件还不齐：

| 新机器缺什么 | 怎样补齐 |
|---|---|
| 运行程序的工具和依赖 | 准备 Node.js，在前后端目录各自按锁文件安装依赖 |
| 数据库地址、后台地址等配置 | 为新环境填写配置，程序继续读取相同的变量名 |
| 数据库里的表 | 执行项目已有的迁移文件，建立表结构 |
| 持续运行和外部访问的安排 | 由 20A 的容器负责启动与重启，再接域名和 HTTPS |

因此，“上线准备”主要是在整理已有项目怎样运行。文章管理、登录、编辑器这些业务不需要重写。本章涉及的修改都在已有 `mini-cms` 中，下面会直接写明文件位置。

## 2. 前后端上线时分别怎样启动

后端 Express 和前端 Next.js 的启动方式分别如下。

### Express：开发用 dev，线上用 start

在 `server/package.json` 的现有 `scripts` 中增加 `start`，保留 `dev` 和其余命令：

```json
{
  "dev": "tsx watch src/server.ts",
  "start": "tsx src/server.ts"
}
```

- 开发时用 `npm run dev`，`watch` 会在修改代码后自动重启。
- 线上用 `npm run start`，运行同一个后端，不监听代码变化。

本地验证时，先停止原来的 `dev`，再在 `mini-cms/server` 中执行 `npm run start`。继续使用已有配置和数据库，接口地址仍是 `http://localhost:3001`。

检查 `server/.env` 是否已按第 09、10 章配置 `NODE_ENV=development`；漏配就补上这一行并重启后端。第 17A 章的 Cookie 配置会读取它。20A 部署时由 Compose 设置 `NODE_ENV=production`，`start` 这个脚本名不会自动设置它。

### Next.js：开发用 dev，线上先 build 再 start

之前用 `npm run dev` 开发后台，Next.js 会编译页面；修改代码后，也会自动更新页面，方便边写边看。

上线时使用提前编译、打包好的版本。**把页面和相关代码编译、打包成运行所需的文件，这一步就叫“构建”，对应 `build`。** 构建完成后，再用 `start` 启动 Next.js 服务，让浏览器访问这些页面。

项目的 `package.json` 已有 `build` 和 `start`，不用新增脚本。现在可以在本地试一次：停止原来的前端 `dev`，在 `mini-cms/admin-web-antd` 中依次执行：

```bash
# 1. 构建，结果保存到 .next/，完成后命令结束
npm run build

# 2. 构建成功后启动服务，持续接收浏览器请求
npm run start
```

保持后端运行，打开 `http://localhost:3000`，登录并查看文章。此时访问的是刚才构建好的后台，仍然连接本地 API 和数据库。

`start` 不会自动构建，也不会在修改代码后更新页面。发布新版前端时，需要重新 `build`，再重启 `start`；平时写代码仍用 `dev`。

## 3. 换了地址，为什么不用到处修改代码

例如，本地后台请求的是 `http://localhost:3001`；上线后，访问者浏览器里的 `localhost` 指向访问者自己的电脑，不能再用它找你的 API。

所以前文才把地址放进环境变量：代码读取变量，新环境给它填写新的值。

| 配置位置与变量 | 本地使用什么 | 20A 部署时使用什么 |
|---|---|---|
| 后端 `DATABASE_URL` | 本地 PostgreSQL 地址 | 服务器中 PostgreSQL 的地址；Compose 内用服务名 `postgres` 连接 |
| 后端 `ADMIN_WEB_ORIGIN` | `http://localhost:3000` | 正式后台来源，如 `https://admin.example.com` |
| 前端 `NEXT_PUBLIC_API_BASE_URL` | `http://localhost:3001` | 正式 API 地址，如 `https://api.example.com` |

现在不用提前填写正式域名。先检查两处：

- 后端 `src/app.ts` 的 CORS 和写请求来源检查，都读取第 17A 章的 `ADMIN_WEB_ORIGIN`，没有单独写死地址。如果还没改齐，按[17A 第 2.3 节](./17A-管理员登录实操-用Session和Cookie保护写接口.md)补齐。
- 前端请求使用 `NEXT_PUBLIC_API_BASE_URL`。这个值会在 `next build` 时写入浏览器代码，所以以后换 API 地址，要重新构建前端。

本地后端通过 `dotenv/config` 读取 `server/.env`，前端由 Next.js 读取 `admin-web-antd/.env.local`。保留这些真实配置在本机，再各准备一份 `.env.example`，只记录变量名和示例值，供新环境照着填写。真实密码不提交到 Git；示例文件要保存在 Git 中。

例如，前端的 `.env.example` 只需记录：

```dotenv
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

`.env.example` 是配置说明，不会代替实际的 `.env` 或 `.env.local`。20A 会用 Compose 给后端容器传入正式配置，不需要把本机 `.env` 原样搬上去。

## 4. 新数据库怎样得到项目需要的表

服务器新建的 PostgreSQL 里还没有文章、标签和管理员这些表。代码里的 `schema.prisma` 描述了模型，但文件放过去，数据库不会自己照着建表。

前面每次修改模型并运行 `db:migrate`，Prisma 已把建表或修改表的 SQL 保存在 `server/prisma/migrations/` 中。打开这个目录，你会看到创建文章表、增加标签、增加登录相关表、把正文改为 JSON 等记录。

首次部署时，只要对新数据库执行这些已有文件，就能从空库建立当前项目所需的结构：

```text
已有的迁移文件
-> 在新数据库中依次执行
-> 得到文章、标签、管理员等表
-> 后端可以读写这些表
```

在 `server/package.json` 的现有 `scripts` 中再增加一项：

```json
{
  "db:migrate:deploy": "prisma migrate deploy"
}
```

**现在只添加命令，不需要为了本章重建本地数据库。** 20A 会在服务器的 API 容器启动前运行它，使用容器的 `DATABASE_URL` 连接新数据库。迁移文件随代码一起保存到 Git。

以后再次部署，Prisma 会根据数据库里的迁移记录，只执行尚未成功应用的文件；没有新迁移就跳过。它不会每次把表删掉重建。生成新迁移仍在本地开发时使用 `migrate dev`，线上只应用已经准备好的文件。

这里建立的是表结构。**本地写过的文章、管理员账号不会自动复制过去。** 20A 会单独创建线上管理员；如果需要保留本地文章，需要另做数据导出和导入。不要在正式库运行前文会清空文章和标签的演示种子。

### db:generate 已经执行过，为什么部署时还会出现

`db:generate` 生成的是后端要导入的 Prisma Client 代码，保存在 `server/src/generated/prisma/`；它不负责建表，也不搬运文章。

**当前电脑上的 Client 已与模型一致、项目也能运行，就不必因为读到第 20 章再执行一次。**

但这个生成目录按前文约定不提交 Git。新机器从 Git 获取代码，或 Docker 重新制作镜像时，可能还没有这份代码，因此要生成一次。20A 的 Dockerfile 会自动执行它。

可以用这两个结果区分：

```text
新环境缺少 Prisma Client 代码 -> db:generate
新数据库缺少项目的表结构    -> db:migrate:deploy
```

模型在开发中再次变化时，也要重新生成 Client，让程序使用的类型和模型一致。

## 5. 本章完成后，直接进入实际部署

到这里，实际增加的是后端的 `start`、`db:migrate:deploy` 两条脚本；前端沿用已有的 `build` 和 `start`。配置没有改齐时补齐配置，已有的登录、文章和数据库逻辑继续保留。

把刚才验证过的启动命令记到 `mini-cms/README.md`，说明命令分别在哪个目录执行、配置文件放在哪里。这样换机器或过一段时间再启动时，不用重新回忆。新环境安装依赖、生成 Client、执行迁移的顺序，会在 20A 的 Dockerfile 和 Compose 中落实，完成后再把部署入口补进 README。

离开本章前只确认：

1. Express 能用 `npm run start` 启动，Next.js 能先 `build` 再 `start`。
2. 当前 Ant Design 后台能登录、保存和重新打开文章；已有的测试继续通过。
3. 地址从环境变量读取，迁移文件和示例配置已保存在项目中。

健康接口沿用第 17A 章的 `/api/health`；已有请求日志和错误日志继续保留，用来判断服务是否启动、请求是否失败。无需在本章另做一轮日志系统或备份练习。

接着进入 [20A：用 1Panel 和 Docker Compose 部署 Mini CMS](./20A-用1Panel和Docker-Compose部署MiniCMS.md)。在那里完成真正的换机运行：安装依赖、生成 Client、建立新库、启动前后端、配置域名和 HTTPS，最后验证公开阅读和备份恢复。
