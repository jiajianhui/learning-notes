# 20. 从开发环境到线上运行：准备生产发布

> Mini CMS 阶段 8：先完成[第 19 章的文章写作、预览与内容排版](./19-文章写作预览与内容排版.md)，再用本章检查生产构建和运行条件。

若已完成 [19A-提升写作体验](./19A-提升写作体验.md)，使用改进后的写作页执行本章检查；19A 是交互增强，不影响直接从第 19 章进入生产准备。

## 这一章完成什么

第 19 章已经跑通富文本编辑、JSON 保存、公开文章 API、个人网站详情页和统一预览。但在自己的电脑上用 `npm run dev` 能运行，还不能说明换一台机器也能启动。

本章继续修改真实 `mini-cms`，把启动条件写进代码、配置和 README，并在本地验证：

```text
复查已有的发布与撤回
-> 生成并运行生产构建
-> 明确前后端分别读取哪些环境变量
-> 用已有迁移在空数据库建立表结构
-> 检查健康接口和日志，整理启动说明
-> 交给 20A 完成真实服务器部署
```

本章先完成本地准备；服务器、域名、HTTPS、Docker 容器和自动备份在 [20A-用 1Panel 和 Docker Compose 部署 Mini CMS](./20A-用1Panel和Docker-Compose部署MiniCMS.md) 中配置。当前只要求已有的 `admin-web-antd`，不用先完成 shadcn/ui 后台。

## 1. 上线前复查发布与撤回

先用现有开发环境走一遍真实操作，确认第 19 章的功能已经完成。第 2 节补齐构建后，再用构建产物重复这条流程：

```text
在管理后台新建草稿
```

如果已经使用页面缓存，发布、修改和撤回后的列表与详情都要及时更新；第一版可以继续使用第 19 章的 `cache: "no-store"`。内容编辑和排版问题回到第 19 章修复，本章不重新选择正文格式。

## 2. 准备交给部署的项目

线上仍然运行同一套管理后台、Express 和 PostgreSQL。变化在于：程序运行事先构建好的文件，配置使用正式地址，数据库需要建立相同的表结构。

个人网站保留在自己的项目中，通过正式 API 域名读取内容。本节的前后端命令分别在 `mini-cms/server`、`mini-cms/admin-web-antd` 中执行。

### 构建和启动命令

**先让 Express 脱离开发命令运行。**

前文的 `dev` 使用 `tsx watch src/server.ts`：读取 TypeScript 源码，修改文件后自动重启。现在补一条发布流程：

```text
src/server.ts 和它导入的模块
-> 检查类型并构建
-> dist/server.js
-> Node.js 运行这个 JavaScript 文件
```

当前项目使用 ES module，相对导入通常写成 `./app`。只用 `tsc` 输出 JavaScript，不会自动把这些路径补成 Node.js ESM 所需的文件扩展名。本章使用 esbuild 把项目内的模块合并为一个入口文件，继续保留前文的导入写法。

在 `server` 中安装构建工具：

```bash
npm install -D esbuild
```

在 `server/package.json` 的现有 `scripts` 中增加下面两项，保留 `dev`、数据库命令和第 18A 章的测试命令。下面是局部片段，不是整个文件：

```json
{
  "build": "tsc --noEmit && esbuild src/server.ts --bundle --platform=node --format=esm --target=node22 --packages=external --outfile=dist/server.js",
  "start": "node dist/server.js"
}
```

这条 `build` 先用 `tsc --noEmit` 检查类型，通过后才运行 esbuild。后半条命令将项目代码构建为 Node.js 22 可用的 ESM 文件；`--packages=external` 让 Express、Prisma runtime、`pg` 等 npm 包继续从 `node_modules` 加载。因此发布时仍然需要安装依赖。

在 `.gitignore` 中忽略 `dist/`，把安装更新后的 `package.json` 和锁文件一起保存在项目中。然后在 `server` 中执行：

```bash
npm run db:generate
npm run build
```

先生成 Prisma Client，是因为构建时会导入它的代码和类型。成功后应能找到 `server/dist/server.js`。停止占用 3001 端口的 `npm run dev`，再执行：

```bash
NODE_ENV=development npm run start
```

这里运行的是构建产物；暂时保留开发环境配置，以便继续用本地 HTTP 联调登录。完整的生产 Cookie 和 HTTPS 验证放到 20A。

**再运行管理后台的构建产物。**

Next.js 项目通常已经有 `build: next build` 和 `start: next start`。确认 `admin-web-antd/.env.local` 中的 `NEXT_PUBLIC_API_BASE_URL` 仍指向 `http://localhost:3001`，在 `admin-web-antd` 中执行：

```bash
npm run build
```

成功后停止占用 3000 端口的 `npm run dev`，再运行：

```bash
npm run start
```

打开 `http://localhost:3000`，检查页面能加载、请求仍发给本地 API。构建报错就先修复报错；只有开发模式可用，还没有完成这一步。

### 环境变量：同一份代码怎样切换地址

本地 API 连接你电脑上的 PostgreSQL；线上 API 连接服务器里的 PostgreSQL。代码仍然读取 `process.env.DATABASE_URL`，部署时传入不同的值即可。

先在 `server/.env.example` 中记录本地示例，真实的 `server/.env` 使用你已有的配置：

```dotenv
NODE_ENV=development
PORT=3001
DATABASE_URL=postgresql://mini_cms:mini_cms_password@localhost:5432/mini_cms?schema=public
ADMIN_WEB_ORIGIN=http://localhost:3000
```

前端的 `admin-web-antd/.env.example` 则记录：

```dotenv
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

这些示例值来自前面的本地练习，不要把正式密码填进示例文件。`.env.example` 供别人照着配置；后端实际读取 `.env`，前端本地配置使用 `.env.local`。确认 Git 忽略真实配置，同时没有把 `.env.example` 也忽略掉。

| 变量 | 谁读取、什么时候读取 | 到线上怎样变化 |
|---|---|---|
| `DATABASE_URL` | Prisma CLI 执行命令时；Express 创建 Prisma Client 时 | 指向线上 PostgreSQL；20A 容器间使用 `postgres:5432` |
| `PORT` | `src/server.ts` 启动时 | API 容器继续监听 3001 |
| `NODE_ENV` | 后端启动时，第 17A 章的 Cookie 配置会读取 | 改为 `production`，登录 Cookie 启用 `Secure` |
| `ADMIN_WEB_ORIGIN` | Express 的 CORS 和写请求来源检查 | 改为正式后台来源，如 `https://admin.example.com` |
| `NEXT_PUBLIC_API_BASE_URL` | Next.js 构建浏览器代码时 | 构建前改为正式 API 地址，如 `https://api.example.com` |

后端沿用 `dotenv/config` 加载 `.env`。如果 `src/app.ts` 会直接读取环境变量，在文件顶部保留 `import "dotenv/config";`，确保这些读取发生前配置已经加载。到了 20A，Compose 会向容器直接传入环境变量，不需要把本机 `.env` 复制进镜像。

回看 `src/app.ts`：第 17A 章已让 CORS 和写请求来源检查共用 `adminWebOrigin`。如果 CORS 还写死了 `http://localhost:3000`，按[第 17A 章](./17A-管理员登录实操-用Session和Cookie保护写接口.md)第 2.3 节改成读取 `ADMIN_WEB_ORIGIN`，保留现有 JSON 解析、Cookie、认证和路由。修改后重建并重启 API，再验证登录和保存文章。

本章和 20A 的首次部署都使用单数 `ADMIN_WEB_ORIGIN`。完成第 26 章、接入第二套后台时，再一起改为复数 `ADMIN_WEB_ORIGINS` 及对应的来源集合判断。

`NEXT_PUBLIC_` 变量会写入浏览器构建结果，不能存密码；改变 API 地址后必须重新构建前端。HTTPS 是加密传输的 HTTP，正式登录通过它传输密码和 Cookie。20A 会配置证书，再验证 `NODE_ENV=production` 下的登录。

### 可重复的数据库迁移

**本地已经有表，服务器上的空数据库怎样获得相同的表结构？**

把代码放到服务器上，不会把本地 PostgreSQL 的表和文章一起带过去。但从第 09 章开始，你修改模型并执行 `npm run db:migrate` 时，Prisma 已把结构变化保存成了 `prisma/migrations/` 下的 SQL 文件。

打开自己项目中的这个目录。沿着前面的练习，你会看到创建文章表、增加标签、增加管理员和 Session、修改正文类型等迁移。下面省略了中间部分目录，日期以自己的项目为准：

```text
server/prisma/
├── schema.prisma
└── migrations/
    ├── 20260812141916_init_articles/
    │   └── migration.sql
    ├── …其他迁移目录…
    ├── 20261021092016_article_content_json/
    │   └── migration.sql
    └── migration_lock.toml
```

`schema.prisma` 描述当前模型；`migration.sql` 记录从旧结构走到新结构的具体 SQL。例如，初始迁移中有 `CREATE TABLE "articles"`，第 19 章生成的迁移则修改 `articles.content`。

**首次部署时，执行已有迁移就能建立结构。**

在 `server/package.json` 的 `scripts` 中增加：

```json
{
  "db:migrate:deploy": "prisma migrate deploy"
}
```

20A 会在 API 容器中运行 `npm run db:migrate:deploy`。它通过 `prisma.config.ts` 读取容器的 `DATABASE_URL`，连接线上数据库，再执行随代码带来的迁移：

```text
线上空数据库
-> 按迁移目录的顺序建文章表
-> 增加标签、关系、登录等结构
-> 将正文列改为 JSON
-> 得到当前 API 需要的表结构
```

这里无需重新生成一份“线上迁移”。应把 `schema.prisma`、整个 `prisma/migrations/` 和 `prisma.config.ts` 随项目保存到 Git；迁移目录的名称包含顺序信息，不用另写一份手工执行清单。

**再次部署时，只执行数据库还没应用的新迁移。**

Prisma 用数据库中的 `_prisma_migrations` 表记录迁移状态。正常情况下，已成功执行的迁移会跳过；没有新迁移时，再执行 `migrate deploy` 不会重新建表。

所以“可重复”包含两件事：换一个空数据库，同一套文件能建立相同结构；对同一个数据库再次部署，只补上新迁移。不要理解成把每条 SQL 手工执行很多遍，也不要修改或删除已经应用的迁移来“重新执行”。

三个命令分别负责：

| 命令 | 何时使用 | 做什么 |
|---|---|---|
| `npm run db:migrate -- --name 变更名` | 本地修改模型后 | 用 `migrate dev` 生成迁移并应用到开发库 |
| `npm run db:generate` | 模型变化后、构建前 | 生成代码使用的 Prisma Client，不给数据库建表 |
| `npm run db:migrate:deploy` | 部署时 | 用 `migrate deploy` 应用已有迁移，不生成新迁移或 Prisma Client |

开发流程可能检查结构差异并要求重置数据库，所以生产环境不用 `migrate dev`。`migrate deploy` 也不会根据最新 Schema 自动补写遗漏的 SQL；模型变化必须先在开发阶段形成迁移。

**现在就在本地验证一次，不用连接生产数据库。**

第 18A 章的 `db:test:migrate` 已经使用同一个 `migrate deploy`，只是通过测试配置连接 `localhost:5433/mini_cms_test`。复用它即可验证“把已有迁移交给另一个数据库”。若尚未完成 18A，先完成[第 18A 章](./18A-接口测试实操-用Vitest和Supertest验证API.md)第 1～2 节的测试库、环境检查和命令配置。

以下操作只针对第 18A 章使用 `tmpfs` 的 `postgres-test`，停止它会丢弃测试数据和表结构。先确认自己的配置与该章一致，再在 `mini-cms` 根目录执行：

```bash
docker compose stop postgres-test
docker compose up -d postgres-test
docker compose exec postgres-test pg_isready -U mini_cms_test -d mini_cms_test
```

最后一条显示 `accepting connections` 后，在 `server` 中执行两次：

```bash
npm run db:test:migrate
npm run db:test:migrate
```

第一次应应用完整迁移历史；第二次应提示没有待执行的迁移。也可以用 TablePro 连接测试库，检查 `articles.content` 已是 `jsonb`，文章、标签、登录相关表以及 `_prisma_migrations` 都已建立。然后运行 `npm test`，验证现有接口仍能使用迁移后的结构；测试用例沿用第 18A、19 章，不能把默认的占位 `test` 命令当成已经验证。

**建表成功，不代表本地文章已经搬到线上。**

当前这些迁移负责建立和修改结构，不会复制本地文章。首次上线后，20A 会单独创建生产管理员，文章可以从后台录入；如果要保留本地正式内容，需要另做数据导出和导入。第 16、19 章的演示种子会清空文章和标签，不能拿它初始化已有正式内容的数据库。

第 19 章是一个具体例子：当时生成的正文迁移删除旧 `content` 列，再创建 JSON 列，所以先清空了本地测试文章。空库从头执行这段历史时尚无文章；以后线上已有内容，再做类似改动，就必须先设计数据转换并备份，不能照搬“先清空”的练习方式。

迁移文件保存结构变化，数据库备份保存可恢复的结构和数据，两者不能互相代替。本章先验证空库迁移；20A 第 10 步再配置正式备份并演练恢复。

### 公开健康检查

服务器启动后，需要一个不登录也能请求的地址，快速判断 Express 是否在响应。

第 17A 章已在 `src/app.ts` 中保留下面的路由。如果缺失，把它放在认证保护的业务路由和 404 中间件之前；已有则不用重复添加：

```ts
app.get("/api/health", (_request, response) => {
  response.json({ server: "server is running" });
});
```

修改代码后重新构建、重启 API，在另一个终端验证：

```bash
curl -i http://localhost:3001/api/health
```

应返回 200 和上面的 JSON。这个接口没有查询数据库，只证明 Express 能响应；数据库与业务是否可用，还要靠迁移检查、接口测试和真实文章操作验证。

### 请求与错误日志

页面提示失败时，后端日志需要告诉你请求到没到、返回了什么状态、花了多久。

在 `src/app.ts` 创建 `app` 后、CORS 和业务路由前检查请求日志中间件。没有时增加下面这段；已有同类中间件就复用，只补缺少的字段：

```ts
app.use((request, response, next) => {
  const startedAt = Date.now();

  response.on("finish", () => {
    console.log(JSON.stringify({
      method: request.method,
      path: request.path,
      status: response.statusCode,
      durationMs: Date.now() - startedAt,
    }));
  });

  next();
});
```

中间件先记下开始时间，`next()` 让请求继续；响应发送完成后，`finish` 回调才读取最终状态码并计算耗时。这里只记录路径，不输出查询参数、请求体或 Cookie。

第 11 章的 `errorHandler` 已用 `console.error(error)` 记录未知错误，并向客户端返回统一的 500 响应。保留这条排错路径，检查错误输出没有密码或密钥，不把请求对象和环境配置整体打印出来。

重新构建、重启后，分别请求 `/api/health` 和 `/api/not-a-route`，终端应出现 200、404 以及对应耗时。20A 中同样的标准输出会进入容器日志，不需要先增加日志文件系统。

## 3. 进入 20A 前的交付检查

先用构建后的 API 和 Ant Design 后台重复第 1 节的发布、阅读和撤回流程。个人网站仍在自己的项目中运行，读取本地公开 API。正文保存、重新打开和预览应保持第 19 章的结果。

再在 `mini-cms/README.md` 记录新环境的实际启动顺序：

```text
准备 Node.js 22 和 Docker
-> 在 server、admin-web-antd 各自执行 npm ci
-> 参考 .env.example 填写各自的本地配置
-> 在根目录启动开发 PostgreSQL，确认可连接
-> 在 server 执行 db:migrate:deploy，应用已有迁移
-> 在 server 执行 db:generate、build

-> 启动 API，再构建和启动后台
-> 检查健康接口、登录和文章操作
```

这是“拿到已有项目，在新环境运行”的顺序，所以应用已有迁移；以后自己修改模型时仍使用开发命令。README 中写出各条命令的工作目录、端口，以及第 18A 章独立测试库和测试命令的用法。`npm ci` 按锁文件安装依赖，前后端都要保留各自的 `package-lock.json`。

进入 20A 前，用下面这些结果验收：

| 检查项 | 怎样判断完成 |
|---|---|
| 生产构建 | API 和 Ant Design 后台都能 `build`，停止 `dev` 后能用 `start` 运行 |
| 配置 | 示例文件说明必需变量，真实配置不进入 Git，后台来源没有写死在代码里 |
| 迁移 | 空测试库能应用完整历史，再执行一次没有待执行迁移 |

| 排错 | 不登录可访问健康接口，请求日志包含方法、路径、状态和耗时 |

Dockerfile、Compose、域名、HTTPS 和正式备份不要求在这里提前完成，它们是 20A 的实操内容。shadcn/ui 的回显验收等第二套后台接入后再做。
