# 20. 从本地到服务器：上线前需要改什么

部署可以先理解为：**把项目放到另一台电脑上运行，让别人也能通过网络访问。** 那台长期运行、对外提供服务的电脑就是服务器。给真实用户使用的环境，通常叫“生产环境”。

第 19 章完成的后台、API 和数据库仍然是同一套。上线增加的问题是：新机器怎样装依赖、连接自己的数据库、启动程序，以及让别人通过域名访问。

本章先讲清这些差别，并在本地试一次上线时的启动方式。[20A](./20A-用1Panel和Docker-Compose部署MiniCMS.md)再带你把它们放到服务器，用 Docker 和 1Panel 管理运行、域名、HTTPS 与备份。

## 1. 换一台电脑，为什么不能只复制代码

你现在的电脑上已经有 Node.js、安装好的依赖、`.env` 和数据库。新机器只有代码时，这些条件还不齐：

| 新机器缺什么 | 怎样补齐 |
|---|---|
| 运行程序的工具和依赖 | 准备 Node.js，在前后端目录各自按锁文件安装依赖 |
| 数据库地址、后台地址等配置 | 为新环境填写配置，程序继续读取相同的变量名 |
| 数据库里的表 | 执行项目已有的迁移文件，建立表结构 |
| 持续运行和外部访问的安排 | 由 20A 的容器负责启动与重启，再接域名和 HTTPS |

因此，“上线准备”主要是在整理已有项目怎样运行。文章管理、登录、编辑器这些业务不需要重写。本章涉及的修改都在已有 `mini-cms` 中，下面会直接写明文件位置。

## 2. 前后端上线时分别怎样启动

后端 Express 和前端 Next.js 的启动方式分别如下。

### Express：开发用 dev，线上用 start

在 `server/package.json` 的现有 `scripts` 中增加 `start`，保留 `dev` 和其余命令：

```json
{
  "dev": "tsx watch src/server.ts",
  "start": "tsx src/server.ts"
}
```

- 开发时用 `npm run dev`，`watch` 会在修改代码后自动重启。
- 线上用 `npm run start`，运行同一个后端，不监听代码变化。

本地验证时，先停止原来的 `dev`，再在 `mini-cms/server` 中执行 `npm run start`。继续使用已有配置和数据库，接口地址仍是 `http://localhost:3001`。

检查 `server/.env` 是否已按第 09、10 章配置 `NODE_ENV=development`；漏配就补上这一行并重启后端。第 17A 章的 Cookie 配置会读取它。20A 部署时由 Compose 设置 `NODE_ENV=production`，`start` 这个脚本名不会自动设置它。

### Next.js：开发用 dev，线上先 build 再 start

之前用 `npm run dev` 开发后台，Next.js 会编译页面；修改代码后，也会自动更新页面，方便边写边看。

上线时使用提前编译、打包好的版本。**把页面和相关代码编译、打包成运行所需的文件，这一步就叫“构建”，对应 `build`。** 构建完成后，再用 `start` 启动 Next.js 服务，让浏览器访问这些页面。

项目的 `package.json` 已有 `build` 和 `start`，不用新增脚本。现在可以在本地试一次：停止原来的前端 `dev`，在 `mini-cms/admin-web-antd` 中依次执行：

```bash
# 1. 构建，结果保存到 .next/，完成后命令结束
npm run build

# 2. 构建成功后启动服务，持续接收浏览器请求
npm run start
```

保持后端运行，打开 `http://localhost:3000`，登录并查看文章。此时访问的是刚才构建好的管理页面，页面通过本地 Express API 读写数据库。

`start` 不会自动构建，也不会在修改代码后更新页面。发布新版前端时，需要重新 `build`，再重启 `start`；平时写代码仍用 `dev`。

## 3. 本地和线上分别配置哪些地址

本地开发时，你在浏览器打开 `http://localhost:3000`，看到的是 `admin-web-antd` 提供的管理页面。查看文章列表时，**页面中的前端代码向 Express 后端发送请求**：

```text
浏览器中的管理页面（localhost:3000）
-> 请求 http://localhost:3001/api/articles
-> Express 查询 PostgreSQL，返回文章数据
```

部署后，浏览器要请求服务器上的 API，例如 `https://api.example.com/api/articles`。不能继续写 `localhost:3001`，因为浏览器里的 `localhost` 指向正在使用浏览器的那台电脑。

前端要知道 API 地址，后端也要知道允许哪个管理页面访问、连接哪个数据库。这三个地址分别通过下面的环境变量配置：

| 变量与配置位置 | 作用 | 本地值 | 20A 的线上示例 |
|---|---|---|---|
| 前端 `NEXT_PUBLIC_API_BASE_URL` | 告诉管理页面向哪个 API 发请求 | `http://localhost:3001` | `https://api.example.com` |
| 后端 `ADMIN_WEB_ORIGIN` | 告诉 Express 允许的管理页面来源 | `http://localhost:3000` | `https://admin.example.com` |
| 后端 `DATABASE_URL` | 告诉 Express 和 Prisma 连接哪个数据库 | 数据库连接串中的主机为 `localhost:5432` | Compose 中改为数据库服务名 `postgres:5432`，并使用线上账号和库名 |

代码继续读取这些变量，部署时为它们填写对应环境的值。

现在不用提前填写正式域名。先检查两处：

- 后端 `src/app.ts` 的 CORS 和写请求来源检查，都读取第 17A 章的 `ADMIN_WEB_ORIGIN`，没有单独写死地址。如果还没改齐，按[17A 第 2.3 节](./17A-管理员登录实操-用Session和Cookie保护写接口.md)补齐。
- 前端请求使用 `NEXT_PUBLIC_API_BASE_URL`。这个值会在 `next build` 时写入浏览器代码，所以以后换 API 地址，要重新构建前端。

本地后端通过 `dotenv/config` 读取 `server/.env`，前端由 Next.js 读取 `admin-web-antd/.env.local`。保留这些真实配置在本机，再各准备一份 `.env.example`，只记录变量名和示例值，供新环境照着填写。真实密码不提交到 Git；示例文件要保存在 Git 中。

例如，前端的 `.env.example` 只需记录：

```dotenv
NEXT_PUBLIC_API_BASE_URL=http://localhost:3001
```

`.env.example` 是配置说明，不会代替实际的 `.env` 或 `.env.local`。20A 会用 Compose 给后端容器传入正式配置，不需要把本机 `.env` 原样搬上去。

## 4. 部署时生成 Client，并执行数据库迁移

新环境需要准备两样东西：后端代码要导入的 Prisma Client，以及数据库中的表结构。它们分别由两个命令完成：

| 在 `server` 中执行的命令 | 读取什么 | 得到什么 |
|---|---|---|
| `npm run db:generate` | `prisma/schema.prisma` | 生成 `src/generated/prisma/` 中的 Client 代码 |
| `npm run db:migrate:deploy` | `prisma/migrations/` 中的 SQL 文件 | 在目标数据库中建立或更新表结构 |

`db:generate` 已在前文配置。已有的 `db:migrate` 用于开发时生成迁移；现在在 `server/package.json` 的现有 `scripts` 中增加**部署时应用已有迁移的命令**：

```json
{
  "db:migrate:deploy": "prisma migrate deploy"
}
```

本节先把命令加好。20A 部署时会生成 Client、更新线上数据库，再启动后端。迁移命令连接哪个数据库，由 `DATABASE_URL` 决定。

### migrate deploy 怎样判断哪些 SQL 需要执行

Prisma 将项目中 `prisma/migrations/` 的 SQL 文件，与目标数据库 `_prisma_migrations` 表中的执行记录对照：成功执行过的跳过，没执行过的按顺序执行，并记下结果；有未处理的失败记录则停止执行并报错。

例如，项目有三份迁移，数据库已成功执行前两份，这次只执行第三份。

后续修改模型时：

- **本地开发**：用 `db:migrate` 生成并执行新迁移，再用 `db:generate` 更新本地 Client。
- **部署更新**：用 `db:generate` 生成新版本的 Client，用 `db:migrate:deploy` 更新线上数据库，再启动后端。

生成 Client 和执行迁移都不会把本地文章或管理员账号复制到线上。20A 会单独创建线上管理员；需要保留本地文章时，要另外导出、导入数据。

## 5. 把启动方式记到 README

把下面这份简短说明放到 `mini-cms/README.md`。

这里的 `npm ci` 用于按 `package-lock.json` 中锁定的版本安装依赖，适合在新电脑或服务器上安装已有项目。

```markdown
# Mini CMS

Express + Prisma + PostgreSQL 提供 API，Next.js + Ant Design 提供管理页面。

## 本地准备

- 安装 Node.js 24 和 Docker，在 `server`、`admin-web-antd` 中分别执行 `npm ci`。
- 后端参考 `server/.env.example` 创建 `server/.env`。
- 前端参考 `admin-web-antd/.env.example` 创建 `admin-web-antd/.env.local`。
- 在项目根目录执行 `docker compose up -d postgres`，启动数据库。
- 首次运行时，确认数据库可连接，在 `server` 中依次执行 `npm run db:generate`、`npm run db:migrate:deploy`。
- 新数据库还需创建管理员：在后端 `.env` 临时填写 `ADMIN_USERNAME` 和 `ADMIN_PASSWORD`，执行 `npm run admin:create`，成功后删除 `.env` 中的 `ADMIN_PASSWORD`。

## 启动命令

前后端分别在两个终端中运行：

| 执行目录 | 开发时 | 上线时 |
|---|---|---|
| `server` | `npm run dev` | `npm run start` |
| `admin-web-antd` | `npm run dev` | 先 `npm run build`，再 `npm run start` |

本地管理页面是 `http://localhost:3000`，API 地址是 `http://localhost:3001`。

## 数据库命令

以下命令在 `server` 中执行：

- `npm run db:migrate -- --name 变更名`：开发时生成迁移并更新开发库。
- `npm run db:generate`：生成 Prisma Client。
- `npm run db:migrate:deploy`：把已有迁移应用到配置指定的数据库。
```

接着进入 [20A：用 1Panel 和 Docker Compose 部署 Mini CMS](./20A-用1Panel和Docker-Compose部署MiniCMS.md)。部署完成后，把部署命令补进 README。
