# 16B. 页面变大后怎样拆组件：职责、状态与数据流

第 16 章把标签、筛选和分页接入了后台，16A 讲清数据怎样变化。现在回头看 `admin-web-antd/app/admin/articles/page.tsx`：功能已经能串起来，下一步是理解哪些内容应该放在一起，哪些可以分开。

本章以当前 Mini CMS 工程为例，分析组件封装和状态归属，不提供逐文件搬代码的跟练。下面的新组件和 Hook 是建议的整理方向，不表示项目已经实现。理解原则后可继续 16C 的 UI 完善与 16D 的 ProComponents 改造，不必先把所有拆分方案实现一遍。

## 1. 先看职责，不按行数拆文件

当前文章页面约 430 行，其中也包含学习注释。需要关注的是它同时承担了哪些工作：

| 当前内容 | 负责什么 |
|---|---|
| `query`、文章列表 Effect、`total` | 根据条件获取文章，处理旧请求和页码回退 |
| 标签请求、`tagOptions` | 为筛选栏和文章表单提供标签选项 |
| 新建、编辑、删除函数 | 调用 API，处理操作结果 |
| Drawer 状态、文章详情请求 | 决定打开哪个表单、回填什么数据 |
| `columns`、Table | 显示文章和操作按钮 |
| Input、Select | 收集搜索与筛选条件 |

例如，只想调整标签列的显示，却需要在列表请求和删除函数之间寻找 `columns`，说明表格展示已经可以独立组织。反过来，一个逻辑连贯的表单即使有一百多行，也不必为了变短而拆开。

**拆分的目标是：修改一种行为时，容易找到它负责的文件，并能看清它与其他部分怎样协作。**

## 2. 已有的 ArticleForm 为什么适合独立

项目已经把表单放进 `_components/article-form.tsx`。它有清楚的输入和输出：

```text
父页面传入 initialValues、tagOptions 和 onSubmit
→ ArticleForm 显示字段、校验输入
→ 调用 onSubmit(values)，等待结果
→ 保存失败时显示 submitError
```

`ArticleForm` 知道怎样收集一篇文章的表单值，但不决定发送 POST 还是 PATCH。父页面分别提供 `handleCreate`、`handleUpdate`，成功后关闭抽屉并重新获取文章列表。

这让新建和编辑共用一套字段，也让表单内部的改动集中在一个地方。**组件即使只在一个页面使用，只要职责完整，也可以独立。**

一个重要约定要保留：`onSubmit` 返回 `Promise<void>`，表单需要等待它。父页面若把保存错误捕获后吞掉，表单就无法通过自己的 `catch` 显示失败提示。拆文件不能改变这条错误传递关系。

## 3. 优先拆筛选栏和表格

### 3.1 筛选栏负责收集条件

可以把标题搜索、状态选择和标签选择放进 `ArticleFilters`。它接收当前条件和标签选项，用户操作后通过回调通知父页面。

以选择标签为例，建议的分工是：

```text
ArticleFilters：用户选择标签 3，调用 onTagChange(3)
→ 父页面：更新 query.tagId，并把 query.page 设为 1
→ 列表 Effect：发现 query 变化，重新获取文章列表
```

“选择了哪个标签”来自筛选控件；“筛选变化后回到第一页”与列表查询有关，由管理 `query` 的地方统一处理。筛选栏不用自己调用 `getArticles()`。

### 3.2 表格负责展示数据和报告操作

可以把 `columns`、Table、行内按钮和删除确认放进 `ArticleTable`。下面只是建议的组件接口，类型沿用现有的 `ArticleListItem`：

```ts
type ArticleTableProps = {
  articles: ArticleListItem[];
  loading: boolean;
  deletingId: number | null;
  page: number;
  pageSize: number;
  total: number;
  onPageChange: (page: number) => void;
  onEdit: (id: number) => void;
  onDelete: (id: number) => Promise<void>;
};
```

`ArticleTable` 用 `articles` 显示行，用 `loading` 显示列表加载，用 `deletingId` 判断哪个删除按钮正在加载。点击编辑时只调用 `onEdit(article.id)`，确认删除时调用 `onDelete(article.id)`，不在表格里另写一套 API 请求。

拆分前，行内编辑按钮直接调用页面的 `openEditDrawer(id)`；拆分后，父页面通过 `onEdit` 把这个操作交给表格。**增加的是组件之间的连接，原来的业务流程没有变。**

暂时可以把 Drawer 和新建、编辑、删除函数留在 `page.tsx`。先拆出两个明确的界面区域，再判断剩余代码是否仍难以阅读。

## 4. 状态放在哪里，看谁需要它

组件拆开后，不需要把页面状态平均分配到每个文件。按当前分工，可以这样判断：

| 状态或数据 | 建议归属 | 原因 |
|---|---|---|
| 表单值、`submitting`、`submitError` | `ArticleForm` | 只服务当前表单的输入和提交反馈 |
| `query`、`articles`、`total`、`listLoading`、`listError` | 页面；以后可整体放入列表 Hook | 条件、请求结果和加载过程属于同一条列表流程 |
| `drawerOpen`、`drawerMode`、`editingArticle`、详情状态 | 页面 | 点击表格操作后，页面决定打开和回填哪个表单 |
| `deletingId` | 执行删除操作的页面 | 页面控制请求，表格读取它显示按钮加载状态 |
| 标签数据及其请求状态 | 页面 | 筛选栏和表单都需要标签选项 |

**状态由一处保存，其他组件通过属性读取，通过回调请求修改。** 例如页面已经保存 `query.page`，表格就不必再保存另一份当前页码，否则两边可能不同步。

当前工程的标签选项请求失败时，也会写入文章列表的 `listError`。整理职责时，应分清这是两次请求：文章列表错误给表格区域，标签选项错误给需要标签的区域，分别管理加载和错误状态。仅把 JSX 移出文件，不会自动解决这种状态混用。

`tagOptions` 可以继续由 `tags.map(...)` 计算，不需要再增加一份状态保存同样的数据。

## 5. 请求逻辑长了，可以封装为 Hook

拆组件解决“界面由谁展示”。当前列表 Effect 还负责请求、加载、错误、旧请求失效和页码回退，这组逻辑若继续占据页面，可以考虑封装成 `useArticleList`。

Hook 在这里就是一个组织相关 React 状态和逻辑的函数，它本身不输出界面。建议让这一组内容一起归入它：

```text
useArticleList
├─ 保存 query、articles、total 和列表加载、错误状态
├─ 条件变化时调用 getArticles(query)
├─ 忽略旧请求的结果，处理最后一页被删空
└─ 提供修改查询条件、重新获取文章列表的方法
```

页面拿到结果后交给筛选栏和表格；保存或删除成功后，调用它提供的重新获取方法。`refreshVersion` 可以成为 Hook 内部实现，页面不必再关心计数怎样变化。

如果走到这一步，就把原来的列表状态和 Effect 一起移入，页面不再保留第二份。`getArticles()` 仍留在 `features/articles/api.ts`：它负责发出一次请求；Hook 负责何时请求，以及怎样把结果存成页面状态。

先能说明列表逻辑的职责，再考虑抽 Hook。无需把所有创建、编辑、删除、Drawer 和提示都装进一个大 Hook，否则只是把原来的长文件换了位置。

## 6. 按业务整理文件，不急着做通用后台

当前工程把标签请求和类型也放在 `features/articles/api.ts`、`types.ts`，标签页因此从文章模块导入标签功能。第 16 章建议的 `features/tags` 更符合它们的归属：文章使用标签，但标签本身是一个独立的业务对象。

下面是可参考的整理方向，新增项按需要选择，不是必须一次完成的目录清单：

```text
app/admin/articles/
├─ page.tsx                      页面组合与操作协调
└─ _components/
   ├─ article-form.tsx           已有：字段、校验、提交反馈
   ├─ article-filters.tsx        建议：搜索与筛选控件
   └─ article-table.tsx          建议：列配置、分页和行操作

features/
├─ articles/
│  ├─ api.ts                     文章请求
│  ├─ types.ts                   文章类型
│  └─ use-article-list.ts        可选：列表状态与请求逻辑
└─ tags/
   ├─ api.ts                     标签请求，文章页和标签页都可使用
   └─ types.ts                   标签类型
```

页面专用组件先放在自己的 `_components`，有其他页面真正需要时再考虑共享。文章表单有状态、正文和标签，标签表单只有名称和 slug；两者都用了 Form，并不意味着现在就需要一个可配置的“通用 CRUD 表单”。

## 7. 怎样判断整理确实有帮助

读完后，用当前工程回答四个问题：

1. 修改文章标签列的显示，应该去哪里？——表格组件。
2. 保存失败的提示，谁负责显示？——表单接住 `onSubmit` 的错误。
3. 筛选变化为什么会重新请求？——统一管理的 `query` 变化，触发列表请求逻辑。
4. 删除最后一页唯一一条文章，谁决定退页？——列表逻辑；表格只显示得到的页码和数据。

如果实际进行整理，先移动一个职责清楚的部分，再验证原有操作：筛选和翻页、编辑回填、保存错误、删除确认，以及操作后重新获取文章列表。文件数量增加了，但请求次数、错误传递和页面行为不应无意改变。

能够沿着“表格报告操作 → 页面执行业务 → 请求返回 → 状态更新 → 组件显示结果”追踪一遍，就继续阅读 [16C-用 Ant Design 完善后台 UI](./16C-用AntDesign完善后台UI.md)，自主还原目标页面；再用 [16D-用 ProComponents 简化管理后台](./16D-用ProComponents简化管理后台.md) 理解业务组件怎样接管重复工作，回到[第 10 章](./10-MiniCMS项目总览.md)验收阶段 5。
