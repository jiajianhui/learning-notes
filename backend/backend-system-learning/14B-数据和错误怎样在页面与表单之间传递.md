# 14B. 数据和错误怎样在页面与表单之间传递

> 完成第 14 章并用第 14A 章看清完整 CRUD 主线后，本章只放大其中的页面内部。它不增加新功能，只用已经写过的代码讲清 `ArticlesPage`、`ArticleForm` 和 API 请求之间的数据、状态与错误。读完应该能说清：函数从哪里传入、谁调用它、成功数据去哪里、失败错误最后显示在哪里。

## 先看要放大的这一段

第 14A 章已经从页面一路追到 PostgreSQL。本章不再重复 Express、Schema、repository 和 Prisma，只观察用户点击保存后，数据怎样离开表单，以及成功或失败怎样回到页面：

```text
用户输入
-> ArticleForm 收集 values
-> handleFinish(values)
-> onSubmit(values) 执行外层页面传入的箭头函数
-> handleCreate(values) 或 handleUpdate(editingArticle.id, values)
-> 页面操作函数调用文章 API

成功
-> 页面操作函数得到 API 返回的文章
-> handleCreate() / handleUpdate() 更新 articles
-> Table 重新渲染
-> 关闭 Drawer 并显示成功提示

失败
-> API 请求抛出 Error
-> handleCreate() / handleUpdate() 返回失败的 Promise
-> ArticleForm 中的 await onSubmit(values) 收到错误
-> catch 写入 submitError
-> ArticleForm 重新渲染
-> Alert 显示错误
```

编辑操作还多一个不需要进入 API 的分支：

```text
handleUpdate(id, values) 比较 values 和 editingArticle
-> 最终内容没有变化
-> 显示“内容没有变化”
-> 直接 return，不调用 updateArticle()
-> Drawer 保持打开，提交按钮恢复可用
```

这里最重要的不是背函数名，而是分清三件事：

```text
谁发现或产生错误
-> apiRequest()

错误怎样继续传递
-> async 函数返回失败的 Promise，外层 await 把失败变成可被 catch 接住的错误

谁接住并显示错误
-> ArticleForm 的 catch、submitError 和 Alert
```

---

## 1. 先分清页面和表单的职责

第 14 章的新建和编辑由两个组件配合完成：

| 组件 | 负责什么 | 不负责什么 |
|---|---|---|
| `ArticlesPage` | 保存文章列表、请求 API、更新 Table、打开或关闭 Drawer | 不保存表单的提交错误 |
| `ArticleForm` | 收集和校验字段、维持提交状态、显示保存错误 | 不决定调用 POST 还是 PATCH，也不直接修改文章列表 |

新建和编辑的表单字段、校验和错误展示都相同，所以放在共用的 `ArticleForm` 中。两个操作发送的 API 不同，对列表的更新方式也不同，所以由 `ArticlesPage` 定义 `handleCreate(values)` 和 `handleUpdate(id, values)`。

---

## 2. `onSubmit={(values) => ...}` 把参数来源显式写出来

新建 Drawer 有下面两种写法，它们都能正常工作：

```tsx
// 写法一：直接传入已有函数
onSubmit={handleCreate}

// 写法二：创建一个箭头函数再传入
onSubmit={(values) => handleCreate(values)}
```

先看第一种：

```tsx
<ArticleForm
  submitText="创建文章"
  onCancel={() => setDrawerOpen(false)}
  onSubmit={handleCreate}
/>
```

JSX 花括号中的 `handleCreate` 会得到这个函数本身，再把它作为 `onSubmit` 属性的值交给 `ArticleForm`。可以把它理解为：

```ts
const submitFunction = handleCreate;
```

这里没有小括号，所以渲染 `<ArticleForm>` 时不会执行 `handleCreate`。等用户提交表单后，`ArticleForm` 内部会执行 `onSubmit(values)`；因为此时 `onSubmit` 保存的就是 `handleCreate` 函数，所以实际执行的是 `handleCreate(values)`：

```text
onSubmit={handleCreate}
-> 传入 handleCreate 函数本身
-> ArticleForm 提交时调用 onSubmit(values)
-> 实际执行 handleCreate(values)
```

第二种写法传入的不是原来的 `handleCreate`，而是现场创建的一个箭头函数：

```tsx
<ArticleForm
  submitText="创建文章"
  onCancel={() => setDrawerOpen(false)}
  onSubmit={(values) => handleCreate(values)}
/>
```

可以把它理解为先创建下面这个函数，再把新函数交给 `ArticleForm`：

```ts
const submitFunction = (values: ArticleFormValues) =>
  handleCreate(values);
```

渲染时同样不会执行 `handleCreate()`。等 `ArticleForm` 调用 `onSubmit(values)` 后，箭头函数先收到 `values`，再把它转交给 `handleCreate(values)`：

```text
onSubmit={(values) => handleCreate(values)}
-> 传入一个箭头函数
-> ArticleForm 提交时把 values 交给它
-> 箭头函数再调用 handleCreate(values)
```

因此，对于新建操作，两种写法的运行结果相同，因为 `onSubmit` 和 `handleCreate` 都只接收一个 `ArticleFormValues` 参数。第一种更简短；本章采用第二种，是为了把 `values` 的来源和去向显式写在 JSX 中，并与下面需要补充 `id` 的编辑写法保持一致。

要注意，`onSubmit={handleCreate()}` 是另一回事：它会在渲染时立即执行函数，并把执行结果传给 `onSubmit`，不符合这里“等用户提交后再调用”的需要。

`ArticleFormProps` 用函数类型说明 `onSubmit` 接收什么：

```ts
onSubmit: (values: ArticleFormValues) => Promise<void>;
```

它表示：

```text
输入：ArticleFormValues
输出：Promise<void>
```

`ArticleForm` 不知道这个函数的具体实现。它只知道：校验通过后，把 `values` 交给 `onSubmit()` 并等待它完成。

编辑时，箭头函数除了接收表单 `values`，还会把外层已经拿到的 `editingArticle.id` 一起交给 `handleUpdate()`：

```tsx
<ArticleForm
  onSubmit={(values) =>
    handleUpdate(editingArticle.id, values)
  }
  // 其他属性保持不变
/>
```

两个参数的来源现在都能在 JSX 中直接看到：

```text
editingArticle.id
-> 来自 ArticlesPage 已经保存的详情数据

values
-> 来自 ArticleForm 当前收集的字段值
```

这个改动没有改变 `ArticleForm` 的组件接口：`onSubmit` 仍然是一个只接收 `values` 的函数。变化的是外层页面的适配方式：新建箭头函数只转交 `values`，编辑箭头函数再补上 `id`。

## 3. `ArticleForm` 决定何时调用，`ArticlesPage` 决定具体做什么

Ant Design Form 校验通过后，调用 `handleFinish(values)`：

```tsx
async function handleFinish(values: ArticleFormValues) {
  setSubmitting(true);
  setSubmitError(null);

  try {
    await onSubmit(values);
  } catch (requestError) {
    setSubmitError(
      requestError instanceof Error
        ? requestError.message
        : "保存失败",
    );
  } finally {
    setSubmitting(false);
  }
}
```

在新建模式中，`onSubmit` 接收的是 `(values) => handleCreate(values)`，所以：

```tsx
await onSubmit(values);
```

运行时可以理解为：

```tsx
await handleCreate(values);
```

箭头函数没有写大括号，会直接返回 `handleCreate(values)` 产生的 Promise，因此外层 `await onSubmit(values)` 仍然可以等待请求成功或失败。

这不表示 `handleCreate()` 被搬进了 `ArticleForm`。它仍然定义在 `ArticlesPage` 中，因此仍然可以访问 `setArticles()`、`setDrawerOpen()` 和 `messageApi`。`ArticleForm` 只负责在用户提交后调用 `ArticlesPage` 传入的箭头函数。

编辑时，`handleUpdate()` 收到 `values` 后会先和 `editingArticle` 比较。没有变化时直接 `return`，因此传回 `ArticleForm` 的 Promise 仍然会正常结束，只是不会发送 PATCH、更新列表或关闭 Drawer。这个分支的逐字段判断和 `summary ?? ""` 的数据转换见第 14 章第 12.3 节。

## 4. 创建成功时，数据怎样回到页面

`handleCreate()` 的完整成功流程是：

```tsx
async function handleCreate(values: ArticleFormValues) {
  const newArticle = await createArticle(values);

  setArticles((current) => [
    newArticle,
    ...current,
  ]);
  setDrawerOpen(false);
  messageApi.success("文章已创建");
}
```

数据按照下面的方向传递：

```text
ArticleForm 收集 values
-> handleCreate(values)
-> await createArticle(values)
-> 请求成功后，newArticle 得到返回的新文章
-> setArticles() 把新文章放到列表最前面
-> Table 使用新的 articles 重新渲染
```

`createArticle()` 怎样经过 `apiRequest()`、Express 和 PostgreSQL，已经由第 14A 章说明。这里的重点是：`ArticleForm` 不直接调用 `setArticles()`，因为表单只负责收集和提交数据；文章列表属于外层 `ArticlesPage`，因此由外层函数处理成功后的列表更新。

## 5. 创建失败时，错误怎样回到表单

### 5.1 `apiRequest()` 先把失败响应转成 Error

`fetch()` 只有在网络层无法完成请求时才会直接失败。Express 返回 409、422 或 500 时，仍然要由 `apiRequest()` 检查 `response.ok`：

```ts
if (!response.ok) {
  const errorBody: ApiFailure = await response.json();
  throw new Error(errorBody.error.message);
}
```

这一步的输入和输出是：

```text
输入：Express 返回的失败 HTTP 响应
-> 读取 error.message
-> new Error(错误文案)
输出：抛出 Error，让当前 Promise 变成失败状态
```

### 5.2 `handleCreate()` 没有 `catch`，错误才会继续向外传

第 4 节的 `handleCreate()` 没有自己的 `try...catch`。如果第一步 `createArticle(values)` 失败，后面的成功操作都不会执行：

```text
await createArticle(values) 收到错误
-> handleCreate() 立即停止
-> setArticles() 不执行
-> Drawer 不关闭
-> 成功提示不显示
-> handleCreate() 返回失败的 Promise
```

`try...catch` 不必写在调用 API 的同一个函数中。只要外层使用 `await` 等待这个函数，就可以捕获它没有自行处理的错误。

### 5.3 外层 `await onSubmit(values)` 接住错误

新建时 `onSubmit` 接收的箭头函数会返回 `handleCreate(values)` 的 Promise，所以 `handleFinish()` 中的这段代码：

```tsx
try {
  await onSubmit(values);
} catch (requestError) {
  setSubmitError(
    requestError instanceof Error
      ? requestError.message
      : "保存失败",
  );
}
```

在新建流程中等价于：

```tsx
try {
  await handleCreate(values);
} catch (requestError) {
  setSubmitError(
    requestError instanceof Error
      ? requestError.message
      : "保存失败",
  );
}
```

这就是 `handleCreate()` 中没有 `try...catch`，创建失败仍然能被处理的原因。

> 如果忘记写 `await onSubmit(values)`，`try...catch` 不会等待这个异步函数完成，也就不能按当前流程捕获后续的请求错误。

## 6. `submitError` 怎样变成页面提示

`ArticleForm` 使用自己的状态保存表单提交错误：

```tsx
const [submitError, setSubmitError] = useState<string | null>(null);
```

这组状态中的两个名字分别用在不同步骤：

```text
setSubmitError(错误文案)
-> 写入错误

submitError
-> 重新渲染时读取错误
```

每次重新提交前先清除上一次错误：

```tsx
setSubmitError(null);
```

请求失败后写入这次错误：

```tsx
setSubmitError(
  requestError instanceof Error
    ? requestError.message
    : "保存失败",
);
```

React 在状态更新后重新渲染 `ArticleForm`，下面的条件就会读取新的 `submitError`：

```tsx
{submitError ? (
  <div className="mb-6">
    <Alert
      type="error"
      showIcon
      title="保存失败"
      description={submitError}
    />
  </div>
) : null}
```

实际表单把这段 `Alert` 放在所有字段之后、提交按钮之前。外层 `div` 使用 Tailwind 提供下间距，避免 `Alert` 自带的 `margin: 0` 覆盖间距工具类。这样即使 Drawer 很长，用户在底部点击保存后，也能立即看到 API 返回的错误。

因此一次完整的错误流程可以分成五步：

| 步骤 | 当前代码由谁负责 |
|---|---|
| 发现并产生错误 | `apiRequest()` 检查 `response.ok` 并 `throw new Error()` |
| 传递错误 | `createArticle()` 和 `handleCreate()` 都不吃掉错误，失败 Promise 继续向外传 |
| 接住错误 | `handleFinish()` 的 `catch` |
| 保存错误 | `setSubmitError()` |
| 展示错误 | `submitError` 存在时渲染 `Alert` |

## 7. 为什么状态没有全部放在最外层页面

状态不是默认全部放在页面顶层。先看哪个组件需要更新和读取它，再把它放在最近的合适组件中。

| 状态 | 存放位置 | 原因 |
|---|---|---|
| `articles` | `ArticlesPage` | Table 读取文章列表，新建、编辑和删除都要更新它 |
| `listLoading` / `listError` | `ArticlesPage` | 列表请求影响 Table 区域 |
| `detailLoading` / `detailError` | `ArticlesPage` | 详情请求决定编辑 Drawer 显示加载、错误还是表单 |
| `drawerOpen` / `drawerMode` | `ArticlesPage` | 外层页面同时控制新建和编辑入口 |
| `submitting` / `submitError` | `ArticleForm` | 只有表单提交按钮和表单错误提示需要它们 |
| `deletingId` | `ArticlesPage` | 保存正在删除的文章 id，供 Table 中对应行的按钮显示 loading；删除请求和列表过滤仍使用函数参数 `id` |

可以记住这条原则：

> 只有一个组件使用的状态，优先留在这个组件中；多个组件需要共用时，再提升到它们共同的父组件。

## 8. 列表、详情、保存和删除怎样展示错误

请求都可能失败，但错误不需要全部用同一种方式展示。当前页面按错误影响的区域处理：

| 请求 | 在哪里捕获 | 保存或展示方式 | 为什么 |
|---|---|---|---|
| 文章列表 | `ArticlesPage.loadArticles()` | `listError` -> Table 上方的 `Alert` | 失败影响整个列表区域 |
| 文章详情 | `ArticlesPage.openEditDrawer()` | `detailError` -> Drawer 内的 `Alert` | 失败只影响当前编辑抽屉 |
| 新建和编辑 | `ArticleForm.handleFinish()` | `submitError` -> 提交按钮上方的 `Alert` | 需要保留输入，让用户根据错误继续修改 |
| 删除 | `ArticlesPage.handleDelete()` | `messageApi.error()` | 删除没有需要长期保留的表单区域 |

请求状态的处理模式可以复用，但不同请求的状态不能混用；错误显示也应靠近它真正影响的操作和页面区域。

## 9. 用重复 slug 串起一次真实失败

假设表单提交了已经存在的 slug，后端返回 409：

```text
Express 返回 409 和 { error: { message: "slug 已存在" } }
-> fetch() 得到 response
-> apiRequest() 发现 response.ok 是 false
-> apiRequest() 抛出 Error("slug 已存在")
-> createArticle() 返回失败的 Promise
-> handleCreate() 也返回失败的 Promise
-> ArticleForm 的 await onSubmit(values) 收到错误
-> catch 调用 setSubmitError("slug 已存在")
-> React 重新渲染 ArticleForm
-> Alert 显示“保存失败”和“slug 已存在”
```

这个过程中，没有一个统一对象主动到处“收集错误”。每一层只完成当前职责：API 请求层产生可理解的 `Error`，中间函数不吃掉错误，最后由需要展示错误的组件接住它。
