# 18. 后端测试：手动检查、产品流程和自动化测试怎样配合

> Mini CMS 阶段 7：把已经跑通的核心接口变成可以重复执行的检查。

自动化测试解决一个实际问题：**修改代码后，怎样快速知道原来的功能有没有被改坏？** 这种检查叫回归测试。

对独立开发者，先为登录和文章管理保留少量核心测试，就能减少反复手动检查的时间。当前不追求覆盖率数字，也不展开完整的测试体系。

## 三种验证方式分别解决什么问题

| 方式 | 当前怎么用 |
|---|---|
| Apifox | 手动发送请求，查看状态码、JSON 和错误信息 |
| 管理后台 | 亲自走一遍登录、创建、编辑、退出，确认页面能用 |
| 自动化测试 | 用代码发送请求、检查结果，每次改动后重复运行 |

它们互相配合。接口测试通过后，页面交互和浏览器里的 Cookie 往返仍需要实际操作确认。

## 测试层级

知道三种测试各管什么即可：

| 类型 | 检查范围 |
|---|---|
| 单元测试 | 一个函数或一条业务规则 |
| 接口集成测试 | 一次 API 请求经过路由、中间件和数据库后的结果 |
| 端到端测试（E2E） | 浏览器中的完整操作流程 |

本阶段先做**接口集成测试**，复用已有 Express 应用和数据库操作。

## 本项目怎样测试

两个工具各负责一件事：**Supertest 向 Express 发请求，Vitest 运行测试并检查结果。** 检查实际结果是否符合预期，就叫断言，例如“创建文章应返回 201”。

```text
测试代码发送请求
-> Express 执行已有的中间件、路由和 Repository
-> Prisma 读写测试数据库
-> 接口返回响应
-> 测试检查状态码、JSON 和必要的数据库结果
```

第 12 章已将 `app.ts` 和 `server.ts` 分开。测试直接导入 `app`，Supertest 使用临时端口，不需要先启动 3001 端口或前端页面。

测试会创建和删除数据，所以要使用**独立测试数据库**。每条测试自行准备数据，不依赖开发库里已有的管理员和文章。

## 先测哪些场景

先覆盖健康检查、登录后创建和发布文章、未登录访问、参数错误、slug 冲突和文章不存在。以后修复某个容易复发的 bug，再为它补测试。

进入 [18A-接口测试实操](./18A-接口测试实操-用Vitest和Supertest验证API.md)，先跑通一个成功用例，再照着补其他场景。17A 的 5.6 是前端请求代码整理，不影响这里的后端测试。
