## 十、答案线索：答不出来时从这里重新出发

先独立回答，再展开这一节。这里给的是判断方向，不是要求背诵的标准句子。

### 1. 技术分层

```text
Node.js
-> 运行服务器端 JavaScript / TypeScript 编译后的代码

Express
-> 在 Node.js 上匹配 HTTP 路由、执行中间件并组织响应

PostgreSQL
-> 长期保存数据、执行 SQL 并落实约束

npm
-> 管理项目依赖和 scripts，不负责运行 HTTP 服务器
```

继续回看：[01-后端大图景](./01-后端大图景-页面背后的系统.md)、[02-Node.js](./02-Nodejs-让JavaScript运行在服务器.md)。

### 2. HTTP 和文章接口

合理答案示例：

| 场景 | method 和 path | 常见成功或失败状态码 |
|---|---|---|
| 第一页草稿 | `GET /api/articles?status=draft&page=1` | 200 |
| 查询 42 号文章 | `GET /api/articles/42` | 200 / 404 |
| 新建文章 | `POST /api/articles` | 201 / 422 / 409 |
| 修改标题 | `PATCH /api/articles/42` | 200 / 404 / 422 |
| 删除文章 | `DELETE /api/articles/42` | 204 / 404 |
| 管理员登录 | `POST /api/auth/login` | 200 / 401 |
| 当前管理员 | `GET /api/auth/me` | 200 / 401 |

未知服务器或数据库故障通常对外返回 500；不要把数据库内部错误和堆栈直接返回给客户端。

继续回看：[03-HTTP](./03-HTTP-一次请求到底带了什么.md)、[06-API 设计和校验](./06-API设计和参数校验.md)。

### 3. 一次创建请求的职责链

```text
route
-> 匹配 POST /api/articles，并组合需要的中间件

validate middleware
-> 检查 params、query 和 body 的运行时合法性

controller
-> 读取 HTTP 输入，调用 service，决定响应状态码和 JSON

service
-> 执行业务规则和流程

repository
-> 调用 Prisma Client 读写数据库

error middleware
-> 把已知错误统一翻译成 API 响应
```

TypeScript 只能检查开发时能看到的代码类型，不能保证网络上刚收到的 JSON 合法；数据库约束负责最终数据完整性，也不能代替友好的 422 响应。因此前端、后端请求边界和数据库约束各自解决不同问题。

继续回看：[10-请求校验和统一错误处理](./10-请求校验和统一错误处理.md)、[11-项目结构](./11-后端项目怎么拆文件.md)。

### 4. 数据库和 Prisma

- `findUnique()` 没查到数据时返回 `null`，不是自动返回 404。
- `WHERE` 限制要查询、修改或删除哪些行；更新和删除漏掉它可能影响整张表。
- `UNIQUE`、外键和 `CHECK` 是数据库最后一道完整性边界。
- Prisma Schema 描述模型；Prisma Migrate 记录并执行表结构变化；Prisma Client 提供 TypeScript 数据访问 API。
- nested write 适合一次 Prisma 调用能清楚表达的关联写入；自定义多步流程用 `$transaction()`，回调内统一使用 `tx`。
- SQL 参数和用户输入分开传递，是为了不让输入被当作 SQL 结构执行。

继续回看：[07-表结构和约束](./07-关系型数据库-表结构和约束.md)、[08-SQL CRUD](./08-SQL-用CRUD查询和修改数据.md)、[13-关系和事务](./13-数据关系JOIN和事务.md)。

### 5. 登录和测试

```text
隐藏前端按钮
-> 只改变界面，不能阻止别人直接请求 API

后端认证中间件
-> 真正决定请求能否进入敏感业务

HttpOnly
-> 阻止前端脚本直接读取 Cookie，但不能单独解决 CSRF 或全部 XSS 风险
```

`POST /api/articles` 的六个优先测试可以是：创建成功、缺少标题、字段格式错误、slug 冲突、未登录、登录后创建；再补不存在资源和发布规则。

继续回看：[14A-登录实操](./14A-管理员登录实操-用Session和Cookie保护写接口.md)、[15A-测试实操](./15A-接口测试实操-用Vitest和Supertest验证API.md)。

### 6. Next.js 方案判断

- 当前 Next.js 页面服务器渲染数据：优先 Server Component 直接调用同层数据能力。
- 当前应用内的表单提交：可以使用 Server Action。
- 给外部系统的 webhook 或 HTTP 入口：使用 Route Handler。
- 多客户端共用、独立部署和维护的长期 API：更适合独立 Express。

Server Component、Server Action 和 Route Handler 都运行在服务器，不代表它们自动拥有认证、校验和错误处理。

继续回看：[12A-Next.js 也能写后端](./12A-Nextjs也能写后端-具体什么时候用.md)。
