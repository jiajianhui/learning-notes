# 13. 后端测试：Apifox、管理后台和自动化测试各管一层

## 问题背景

只在 Apifox 中调用成功一次，不能证明接口以后一直可靠。

只在管理后台点击，也很难覆盖缺少字段、重复 slug、未登录等错误条件。

后端验证应该分层：

```text
接口手动检查
产品流程检查
自动化回归测试
```

---

## 核心解释

### 1. Apifox：主动构造请求

适合：

- 快速查看请求和响应。
- 修改 headers、body 和 query。
- 检查错误参数和状态码。
- 在前端还没完成时验证 API。

不足：需要人工操作，修改代码后容易漏掉旧场景。

### 2. Next.js 管理后台：验证真实工作流

适合：

- 用户能否完成新建、编辑、发布和删除。
- 表单和 API 是否正确配合。
- loading、empty、error、success 是否完整。
- Cookie 登录是否能在浏览器里工作。

它是产品界面，不是专门的接口边界测试工具。

### 3. 自动化测试：稳定重复验证

```text
Vitest
-> 组织测试、断言结果

Supertest
-> 向 Express app 发送测试请求
```

每次修改代码都可以重新运行，不依赖人工点击。

---

## 测试层级

| 类型 | 主要验证什么 | Mini CMS 示例 |
|---|---|---|
| 单元测试 | 一个纯函数或业务规则 | slug 生成、状态转换 |
| 接口集成测试 | 路由、中间件、业务和数据库配合 | `POST /api/articles` |
| 端到端测试 | 浏览器中的完整流程 | 登录后创建并发布文章 |

第一轮优先接口集成测试，不急着搭完整浏览器 E2E。

---

## 为什么要把 `app` 和 `server` 分开

`app.ts` 导出 Express app：

```ts
export { app };
```

`server.ts` 才监听端口：

```ts
app.listen(port);
```

测试可以直接使用 app：

```ts
import request from "supertest";
import { app } from "../src/app.js";

it("returns health status", async () => {
  await request(app)
    .get("/api/health")
    .expect(200)
    .expect({ status: "ok" });
});
```

不需要手动先运行端口 3001。

---

## 数据库测试要隔离

测试不能随意删除开发数据库的数据。

可以使用：

```text
独立测试数据库
-> 每个测试前准备数据
-> 每个测试后清理或回滚
```

测试必须可重复，不能依赖“数据库里刚好已经有一篇文章”。

---

## Mini CMS 优先测试什么

- 创建文章成功并返回 201。
- 缺少标题时返回校验错误。
- slug 重复时返回 409。
- 查询不存在文章时返回 404。
- 未登录时不能修改文章。
- 登录后能创建和发布文章。
- 删除标签不会误删文章。

不要为了覆盖率数字测试每一行。先覆盖最重要的业务边界。

---

## 常见误区

- 把 Apifox、产品界面和自动化测试看成三选一。
- 测试直接使用开发数据库。
- 测试之间共享不稳定数据，导致执行顺序一变就失败。
- 只测试成功，不测试无权限和错误参数。
- 为了测试强行暴露内部实现，而不是从接口行为验证。

---

## 小结

```text
Apifox 方便探索接口
管理后台验证真实产品流程
Supertest 重复验证 HTTP 行为
测试数据库保证自动化过程可隔离
```

三层一起使用，后端才既能开发、能操作，也能放心修改。
