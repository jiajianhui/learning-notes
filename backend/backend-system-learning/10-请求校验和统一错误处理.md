# 10. 接口收口：先校验请求，再统一返回错误

## 问题背景

第 09 章 demo 已经第一次跑通文章 CRUD；读完 09A 后，又在独立 `mini-cms` 仓库中复现了这条正常流程：

```text
HTTP 请求
-> Express 路由
-> article-repository
-> Prisma Client
-> PostgreSQL
-> JSON 响应
```

但客户端不会永远提交正确数据，数据库操作也不会永远成功。例如：

```text
标题为空
slug 格式错误
请求体带有不允许修改的字段
创建文章时 slug 重复
修改或删除的文章不存在
数据库暂时无法连接
```

如果不处理这些情况，客户端可能只得到一段 Prisma 堆栈或笼统的 500。第 09 章 demo 到此已经冻结，本章开始直接修改真实 `mini-cms/server`，补齐两件事：

```text
进入数据库前
-> 校验外部请求

数据库操作失败后
-> 把已知错误转换成稳定的 HTTP 响应
```

本章不阻塞 Mini CMS 的阶段 1～2。等真实项目已经能连接 PostgreSQL，并具备文章 CRUD 初版后，再进入阶段 3，用本章把失败流程补完整。

这一章代码较多，不要把它当成一次必须记住的大改造。按三个里程碑推进：

```text
里程碑 1：Zod 只让合法输入进入 repository
-> 里程碑 2：AppError 和错误中间件统一失败响应
-> 里程碑 3：Prisma 已知错误变成 409 和 404
```

每完成一个里程碑就运行类型检查，并用一组请求观察结果，再继续下一部分。

---

## 1. 三层检查分别负责什么

一条写请求可以经过三层检查：

| 层级 | 主要职责 | 例子 |
|---|---|---|
| 前端表单 | 尽快提示正常用户 | 标题没填时立即显示提示 |
| Express 后端 | 不信任客户端，检查真实请求 | 判断字段类型、长度和格式 |
| PostgreSQL | 保证最终数据不能破坏核心约束 | `slug` 唯一、字段不能为 `NULL` |

后端不能依赖前端校验。Apifox、`curl` 和其他程序都可以绕过页面直接请求 API。

数据库约束也不能代替后端校验。数据库知道 `slug` 不能重复，但不负责给客户端组织清楚的 HTTP 状态码和错误 JSON。

这三层不是重复劳动：

```text
前端负责体验
后端负责请求边界
数据库负责最终数据完整性
```

## 2. 使用 Zod 检查运行时收到的数据

TypeScript 类型只能检查开发时写下的代码，不能约束客户端真正发来的 JSON。本章使用 Zod 把文章输入规则写成可以在运行时执行的 Schema。

进入真实 Mini CMS 的后端目录。本章后面出现的文件路径都相对于这个 `server/` 目录：

```bash
cd mini-cms/server
npm install zod
```

安装后，`zod` 是服务器运行时需要的依赖，应放在 `dependencies` 中。

### 2.1 创建文章 Schema

新增文件：

```text
src/modules/articles/article-schema.ts
```

写入：

```ts
import { z } from "zod";

const titleSchema = z
  .string()
  .trim()
  .min(1, "标题不能为空")
  .max(200, "标题不能超过 200 个字符");

const slugSchema = z
  .string()
  .trim()
  .toLowerCase()
  .min(1, "slug 不能为空")
  .max(200, "slug 不能超过 200 个字符")
  .regex(
    /^[a-z0-9]+(?:-[a-z0-9]+)*$/,
    "slug 只能包含小写字母、数字和连字符",
  );

const summarySchema = z
  .string()
  .trim()
  .max(500, "摘要不能超过 500 个字符");

const contentSchema = z
  .string()
  .trim()
  .min(1, "正文不能为空")
  .max(100_000, "正文内容过长");

const statusSchema = z.enum(["draft", "published"]);

export const createArticleSchema = z.strictObject({
  title: titleSchema,
  slug: slugSchema,
  summary: summarySchema.optional(),
  content: contentSchema,
  status: statusSchema.optional(),
});

export type CreateArticleInput = z.infer<
  typeof createArticleSchema
>;
```

这段代码同时完成两件事：

```text
createArticleSchema
-> 运行时检查真实 JSON

CreateArticleInput
-> 给 TypeScript 提供输入类型
```

`z.strictObject()` 只允许 Schema 中声明的字段。如果客户端额外提交 `id`、`createdAt` 或其他字段，校验会失败，而不是把它们继续交给 Prisma。

`trim()` 返回去掉首尾空格后的字符串，`toLowerCase()` 把 slug 转成小写，所以通过校验的数据也完成了最小规范化。

### 2.2 修改文章 Schema

修改接口允许只提交部分字段，但不能提交空对象。继续在同一文件中增加：

```ts
export const updateArticleSchema = z
  .strictObject({
    title: titleSchema.optional(),
    slug: slugSchema.optional(),
    summary: summarySchema.nullable().optional(),
    content: contentSchema.optional(),
    status: statusSchema.optional(),
  })
  .refine((input) => Object.keys(input).length > 0, {
    message: "至少提交一个可修改字段",
  });

export type UpdateArticleInput = z.infer<
  typeof updateArticleSchema
>;
```

这里的 `summary` 允许传入 `null`，表示清空已有摘要。

### 2.3 路由参数也属于外部输入

`request.params.id` 进入 Express 时是字符串，同样需要运行时校验：

```ts
export const articleIdParamsSchema = z.strictObject({
  id: z.coerce
    .number()
    .int("文章 ID 必须是整数")
    .positive("文章 ID 必须大于 0"),
});
```

`z.coerce.number()` 先尝试把路由里的字符串转换成数字，后面的 `int()` 和 `positive()` 再检查它是不是正整数。

## 3. Repository 复用 Schema 推导出的类型

当前 `article-repository.ts` 手写了创建和修改输入类型。Schema 增加后，不需要继续维护第二份相同规则。

在文件顶部导入类型：

```ts
import type {
  CreateArticleInput,
  UpdateArticleInput,
} from "./article-schema";
```

创建和修改函数改成：

```ts
export function createArticle(input: CreateArticleInput) {
  return prisma.article.create({
    data: input,
  });
}

export function updateArticle(
  articleId: number,
  input: UpdateArticleInput,
) {
  return prisma.article.update({
    where: {
      id: articleId,
    },
    data: input,
  });
}
```

职责关系变成：

```text
article-schema
-> 决定什么输入可以进入业务代码

article-repository
-> 接收已经校验的数据并调用 Prisma
```

Repository 不读取 `request.body`，也不负责返回 HTTP 状态码。

先运行一次类型检查，确认 Schema 推导出的类型能正确交给 Prisma：

```bash
npx tsc --noEmit
```

如果这里报错，先修正 Schema、repository 类型或 import，不要带着类型错误继续搭错误中间件。

## 4. 用一种格式返回 API 错误

成功响应继续使用：

```json
{
  "data": {}
}
```

失败响应统一使用：

```json
{
  "error": {
    "code": "ARTICLE_NOT_FOUND",
    "message": "文章不存在"
  }
}
```

其中：

- HTTP 状态码方便客户端先判断成功还是失败。
- `code` 是程序可以稳定判断的错误标识。
- `message` 是给开发者或用户看的说明。
- 字段校验失败时可以额外返回 `details`。

不要让前端通过比较完整中文文案判断错误类型。文案以后可能改变，稳定的 `code` 更适合程序判断。

## 5. 定义应用自己认识的错误

查询单篇文章时，Prisma 的 `findUnique()` 找不到数据会返回 `null`，不会自动抛出错误。应用需要主动把它变成 404。

新增：

```text
src/errors/app-error.ts
```

写入：

```ts
export class AppError extends Error {
  constructor(
    public statusCode: number,
    public code: string,
    message: string,
  ) {
    super(message);
    this.name = "AppError";
  }
}
```

使用时：

```ts
if (!article) {
  throw new AppError(
    404,
    "ARTICLE_NOT_FOUND",
    "文章不存在",
  );
}
```

业务代码只说明发生了什么错误，不在每个路由里重复组织错误 JSON。

## 6. 把所有已知错误集中转换成 HTTP 响应

新增：

```text
src/middleware/error-handler.ts
```

写入：

```ts
import type { ErrorRequestHandler } from "express";
import { z } from "zod";

import { Prisma } from "../generated/prisma/client";
import { AppError } from "../errors/app-error";

function isInvalidJsonError(error: unknown) {
  return (
    error instanceof SyntaxError &&
    "status" in error &&
    error.status === 400 &&
    "body" in error
  );
}

export const errorHandler: ErrorRequestHandler = (
  error,
  _request,
  response,
  next,
) => {
  if (response.headersSent) {
    next(error);
    return;
  }

  if (isInvalidJsonError(error)) {
    response.status(400).json({
      error: {
        code: "INVALID_JSON",
        message: "请求体不是合法的 JSON",
      },
    });
    return;
  }

  if (error instanceof z.ZodError) {
    response.status(422).json({
      error: {
        code: "VALIDATION_ERROR",
        message: "请求参数不正确",
        details: error.issues.map((issue) => ({
          field: issue.path.join("."),
          message: issue.message,
        })),
      },
    });
    return;
  }

  if (error instanceof AppError) {
    response.status(error.statusCode).json({
      error: {
        code: error.code,
        message: error.message,
      },
    });
    return;
  }

  if (error instanceof Prisma.PrismaClientKnownRequestError) {
    if (error.code === "P2002") {
      response.status(409).json({
        error: {
          code: "SLUG_CONFLICT",
          message: "文章 slug 已经存在",
        },
      });
      return;
    }

    if (error.code === "P2025") {
      response.status(404).json({
        error: {
          code: "ARTICLE_NOT_FOUND",
          message: "文章不存在",
        },
      });
      return;
    }
  }

  console.error(error);

  response.status(500).json({
    error: {
      code: "INTERNAL_ERROR",
      message: "服务器内部错误",
    },
  });
};
```

这段中间件完成下面的转换：

| 原始错误 | HTTP 状态码 | API 错误 code |
|---|---:|---|
| JSON 语法错误 | 400 | `INVALID_JSON` |
| Zod 校验失败 | 422 | `VALIDATION_ERROR` |
| `AppError` | 使用错误自身的状态码 | 使用错误自身的 code |
| Prisma `P2002` | 409 | `SLUG_CONFLICT` |
| Prisma `P2025` | 404 | `ARTICLE_NOT_FOUND` |
| 其他未知错误 | 500 | `INTERNAL_ERROR` |

本章约定：JSON 本身无法解析时返回 400；JSON 可以解析，但字段不符合规则时返回 422。项目也可以统一使用 400，真正重要的是前后端约定一致。

未知错误的详细信息只记录在服务器，不直接返回给客户端。客户端不需要知道数据库连接地址、内部文件路径和 Prisma 堆栈。

错误处理中间件必须保留四个参数，并注册在所有路由之后，Express 才会把它识别成错误处理函数。

## 7. 在路由入口解析参数

`parse()` 校验成功时返回经过转换的数据，失败时抛出 `ZodError`。Express 5 会把异步路由中抛出的错误或被拒绝的 Promise 交给后面的错误处理中间件。

`app.ts` 的核心代码可以整理为：

```ts
import express from "express";

import { AppError } from "./errors/app-error";
import { errorHandler } from "./middleware/error-handler";
import {
  articleIdParamsSchema,
  createArticleSchema,
  updateArticleSchema,
} from "./modules/articles/article-schema";
import {
  createArticle,
  deleteArticle,
  getArticleById,
  getArticles,
  updateArticle,
} from "./modules/articles/article-repository";

const app = express();

app.use(express.json());

app.get("/api/health", (_request, response) => {
  response.json({ server: "server is running" });
});

app.get("/api/articles", async (_request, response) => {
  const articles = await getArticles();
  response.json({ data: articles });
});

app.get("/api/articles/:id", async (request, response) => {
  const { id } = articleIdParamsSchema.parse(request.params);
  const article = await getArticleById(id);

  if (!article) {
    throw new AppError(
      404,
      "ARTICLE_NOT_FOUND",
      "文章不存在",
    );
  }

  response.json({ data: article });
});

app.post("/api/articles", async (request, response) => {
  const input = createArticleSchema.parse(request.body);
  const article = await createArticle(input);

  response.status(201).json({ data: article });
});

app.patch("/api/articles/:id", async (request, response) => {
  const { id } = articleIdParamsSchema.parse(request.params);
  const input = updateArticleSchema.parse(request.body);
  const article = await updateArticle(id, input);

  response.json({ data: article });
});

app.delete("/api/articles/:id", async (request, response) => {
  const { id } = articleIdParamsSchema.parse(request.params);
  const article = await deleteArticle(id);

  response.json({ data: article });
});

app.use((_request, response) => {
  response.status(404).json({
    error: {
      code: "ROUTE_NOT_FOUND",
      message: "接口不存在",
    },
  });
});

app.use(errorHandler);

app.listen(3001, () => {
  console.log("Server is running at http://localhost:3001");
});
```

路由现在只做四件事：

```text
读取外部输入
-> 使用 Schema 解析
-> 调用数据库操作函数
-> 返回成功结果
```

失败结果统一交给 `errorHandler`。

## 8. 为什么不在每个路由里写一套 try/catch

如果每个路由都这样处理：

```ts
try {
  // 数据库操作
} catch (error) {
  // 判断 P2002、P2025 和未知错误
}
```

创建、修改和删除接口会重复相同代码，也容易返回不同的错误格式。

当前使用 Express 5。异步路由里的下面两种失败都会自动进入错误处理中间件：

```text
Schema 的 parse() 主动抛出错误
Prisma Promise 被拒绝
```

只有当前函数能够补充必要信息、把底层错误转换成业务错误或真正恢复流程时，才在局部使用 `catch`。不要为了“看起来处理过”而捕获错误后原样再次抛出。

## 9. 五个接口的失败路径现在是什么

| 接口 | 失败情况 | 返回 |
|---|---|---|
| 查询列表 | 未查询到文章 | `200` 和空数组，不是错误 |
| 查询单篇 | ID 不合法 | `422 VALIDATION_ERROR` |
| 查询单篇 | 文章不存在 | `404 ARTICLE_NOT_FOUND` |
| 创建文章 | 请求体不合法 | `422 VALIDATION_ERROR` |
| 创建文章 | slug 重复 | `409 SLUG_CONFLICT` |
| 修改文章 | ID 或请求体不合法 | `422 VALIDATION_ERROR` |
| 修改文章 | 文章不存在 | `404 ARTICLE_NOT_FOUND` |
| 修改文章 | slug 重复 | `409 SLUG_CONFLICT` |
| 删除文章 | ID 不合法 | `422 VALIDATION_ERROR` |
| 删除文章 | 文章不存在 | `404 ARTICLE_NOT_FOUND` |
| 所有接口 | 未知服务器或数据库故障 | `500 INTERNAL_ERROR` |

特别注意三个不同结果：

```text
findMany() 没有记录
-> 返回 []

findUnique() 没有记录
-> 返回 null，由应用抛出 AppError

update() / delete() 的目标不存在
-> Prisma 抛出 P2025
```

## 10. 用三个检查点验证失败流程

自动化测试放到后面的测试章节。本章先不要一次测试所有情况，按下面三个检查点使用 Apifox。

### 检查点 1：请求边界

| 测试 | 预期结果 |
|---|---|
| 创建合法文章 | `201` |
| 标题为空 | `422 VALIDATION_ERROR` |
| slug 含空格或其他非法字符 | `422 VALIDATION_ERROR` |
| 请求体额外提交 `id` | `422 VALIDATION_ERROR` |

这一步确认原始 `request.body` 不会直接进入 repository。

### 检查点 2：数据库已知错误

| 测试 | 预期结果 |
|---|---|
| 连续创建相同 slug | 第二次返回 `409 SLUG_CONFLICT` |
| 查询不存在的正整数 ID | `404 ARTICLE_NOT_FOUND` |
| 修改不存在的文章 | `404 ARTICLE_NOT_FOUND` |
| 删除不存在的文章 | `404 ARTICLE_NOT_FOUND` |

这一步确认数据库约束和 Prisma 错误已经被转换成 API 能理解的结果。

### 检查点 3：统一出口

| 测试 | 预期结果 |
|---|---|
| 提交不完整 JSON | `400 INVALID_JSON` |
| 请求一个不存在的接口 | `404 ROUTE_NOT_FOUND` |

最后再次运行：

```bash
npx tsc --noEmit
```

检查失败响应时，不只看状态码，还要确认 `error.code` 和 JSON 结构稳定。三个检查点都通过后，本章才算完成。

## 11. 现在还没有处理什么

本章完成的是请求边界和错误响应，不包含下面内容：

- 谁可以创建、修改和删除文章：登录和授权章节处理。
- 发布文章需要满足哪些产品规则：Mini CMS 增加状态流程时处理。
- HTML 或 Markdown 怎样安全展示：真正允许富文本或原始 HTML 时再处理。
- 接口自动化测试：后端测试章节处理。
- route、controller、service 和 repository 怎样拆分：项目结构章节处理。

不要把“输入通过 Zod”理解成“这次业务操作一定允许”。字段格式正确和业务规则成立是两件事。

## 学习建议

这一章不需要背错误码和 Zod 的全部 API。先记住请求失败时从哪里走：

```text
外部输入
-> Zod 校验
-> route 调用 repository
-> Prisma / PostgreSQL
-> Express 错误处理中间件
-> 稳定的 HTTP 状态码和 JSON
```

三个检查点全部通过后，继续阅读第 11 章，在不改变当前 API 行为的前提下整理 Mini CMS 的后端项目结构。第 10、11 章都验收后，才算完成 Mini CMS 阶段 3。

## 小结

本章给真实 Mini CMS 的 CRUD 初版补上失败流程：

```text
Zod
-> 检查请求参数并生成可靠类型

AppError
-> 表达应用自己认识的错误

Prisma 错误码
-> 识别数据库已经说明的失败原因

Express 错误处理中间件
-> 统一决定状态码和错误 JSON
```

到这里，单表 CRUD 不只会在正确输入下工作，也能对常见失败给出稳定结果。
