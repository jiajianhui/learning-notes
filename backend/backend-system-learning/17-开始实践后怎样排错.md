# 17. 开始实践后怎样排错：先判断问题发生在哪一层

## 问题背景

后端报错经常看起来相似：

```text
页面没有数据
请求失败
服务器报错
数据库连不上
```

不要一次乱改前端、Express 和 SQL。先根据现象定位层级。

这一章不是第一次阅读时要记住的概念。等接口已经开始运行，遇到具体故障时再回来查。

---

## 常见问题速查

| 现象 | 优先检查 |
|---|---|
| 端口打不开 | Node 进程是否启动、端口是否正确 |
| 返回 404 | 方法、完整路径、路由前缀、注册顺序 |
| `request.body` 是空 | `express.json()`、`Content-Type`、请求 body |
| 浏览器提示 CORS | 后端允许来源、端口、credentials |
| Apifox 正常但页面失败 | 浏览器 CORS、Cookie、前端 API 地址和状态处理 |
| 数据库连接拒绝 | PostgreSQL 是否启动、端口、用户名、密码、database |
| SQL 报错 | SQL 语法、列名、参数顺序、迁移是否执行 |
| 查询结果为空 | WHERE 条件、参数类型、实际连接的数据库 |
| slug 重复却返回 500 | 后端是否把数据库的重复错误识别出来并返回 409 |
| 登录成功但后续仍 401 | Cookie 是否设置和携带、credentials、域和 SameSite |
| 测试一直不结束 | 服务器端口、数据库连接池、未释放 client |
| 修改代码后旧行为坏了 | 是否有核心接口自动化测试 |

---

## 按层排查

### 1. 浏览器层

- Network 中有没有发出请求？
- 请求 URL 和 method 对不对？
- body、headers 和 Cookie 有没有带上？
- 响应状态码和 body 是什么？

### 2. Express 层

- 请求有没有进入 route？
- 中间件顺序是否正确？
- 参数在哪里校验？
- 错误有没有进入统一错误处理？

### 3. 数据库层

- 使用的是哪个 `DATABASE_URL`？
- 数据库和表是否存在？
- SQL 能否单独执行？
- 参数顺序和类型是否正确？
- 事务是否回滚？

### 4. 前端状态层

- 是否检查 `response.ok`？
- loading 是否在 `finally` 结束？
- 错误有没有被吞掉？
- 操作成功后列表有没有重新请求或更新？

---

## 几个需要实践后再理解的问题

### TypeScript 通过，不代表请求安全

TypeScript 只检查开发时能看到的代码类型。

浏览器、Apifox 和第三方客户端仍然可以发送任意 JSON，所以后端必须做运行时校验。

### 前端校验通过，不代表后端可以跳过校验

用户可以绕过页面直接请求 API。

### 数据库约束报错，不应该全部返回 500

像 slug 重复这种预期内的情况，应该返回明确状态码和提示；只有数据库断开、代码异常等未知问题才返回 500。

### CORS 不是服务器拒绝所有外部请求

CORS 是浏览器安全机制。Apifox、curl 和服务器程序不按浏览器的同一套限制执行。

### 能查到数据，不代表事务正确

要主动测试中间步骤失败时，前面的修改有没有回滚。

---

## 按实现阶段检查

### Express 和 API

- 路由由 HTTP 方法和完整路径共同决定，只对一个通常仍然匹配不到。
- `request.body` 是空时，检查 `express.json()` 是否注册在路由之前，以及请求是否声明 JSON。
- `response.json()` 或 `sendStatus()` 已经发送结果后，不要再次响应。
- 认证中间件放在受保护路由之前，404 和错误处理中间件放在路由之后。
- 同一种错误应返回相同状态码、错误 code 和 JSON 结构。

### SQL 和 PostgreSQL

- 执行 `UPDATE`、`DELETE` 前确认 `WHERE`，避免影响所有行。
- SQL 和用户输入分别传递，不把输入拼进 SQL 字符串。
- pg 查询返回的行在 `result.rows` 中，单条查询仍然先得到数组。
- 整个应用复用一个 Pool，不在每个请求中重新创建。
- 事务中的 SQL 使用同一个 client，并在 `finally` 中释放连接。
- 表结构变化保存成有顺序的 migration，不只在图形工具中手动修改。

### 前端、Cookie 和认证

- `fetch()` 返回 Response 不代表业务成功，还要检查 `response.ok`。
- 跨来源 Cookie 请求需要前端设置 credentials，后端 CORS 也要允许准确来源和凭证。
- 前端的 `isLoggedIn` 只控制页面显示，后端仍要验证每次敏感请求。
- 管理页面不能读取数据库密码，只能调用后端 API。

### 测试和部署

- 自动化测试使用独立测试数据库，不直接清空开发数据。
- 每条测试自行准备和清理数据，不依赖上一条测试留下的内容。
- 真实 `.env` 不提交，只提交 `.env.example`。
- 线上运行生产构建，不把开发服务器直接当成生产服务。
- 删除表、列或大量数据前先确认迁移、备份和恢复方式。

---

## 建议排错顺序

```text
1. 看浏览器 Network 或 Apifox 的真实请求
2. 看状态码和响应 body
3. 看 Express 请求日志
4. 确认进入了哪个路由和中间件
5. 单独检查 SQL 和数据库数据
6. 最后才修改代码
```

不要只根据页面上的一句“请求失败”猜原因。

---

## 小结

排错的核心是缩小范围：

```text
请求有没有发出？
Express 有没有接到？
校验和权限有没有通过？
SQL 有没有执行？
响应有没有正确处理？
```

只盯当前层，后端问题会比同时乱改整个项目容易得多。
