# 12. 后端项目结构：按职责拆开，不要为了分层而分层

> Mini CMS 阶段 3（第二部分）：第 11 章已经补齐校验和错误处理，第 11A 章已经拆解错误中间件的执行流程。本章只整理文件职责，不改变接口契约。

## 问题背景

Mini CMS 的第一版可以把健康检查、文章路由和端口监听集中在 `app.ts`，先证明整条请求链能运行。

当文章接口和数据库代码逐渐增加后，一个文件会同时出现：

```text
路由
参数校验
业务规则
SQL
错误处理
服务器启动
```

这时需要拆分，但拆分的目标是让请求链路更容易追踪，不是让目录看起来复杂。

---

## 项目先按哪些职责拆开

### 1. 先把启动和应用分开

```text
server.ts
-> 监听端口，真正启动服务

app.ts
-> 创建 Express app，注册中间件和路由
```

这样自动化测试可以直接使用 `app`，不需要真的占用固定端口。

### 2. 先知道每种文件名负责什么

这里的“层”不是额外框架，而是按职责给文件分组。每层只处理一类问题，再把结果交给下一层。

| 层 | 主要职责 |
|---|---|
| routes | 声明 HTTP 方法、路径和中间件顺序 |
| controller | 读取 request，调用业务函数，返回 response |
| service | 执行业务规则，调用需要的数据访问函数 |
| repository | 使用 Prisma Client 查询数据库，把结果交给上层 |
| schema 文件 | 校验请求输入；这里指项目代码，不是 PostgreSQL 中组织表的 schema |
| middleware | 日志、404、错误等公共流程 |
| config | 环境变量和应用配置 |

完整项目的依赖方向可以逐步发展成：

```text
route
-> controller
-> service
-> repository
-> Prisma Client 生成 SQL
-> PostgreSQL 执行 SQL
```

响应结果再反方向返回。不过阶段 3 还没有复杂业务规则，可以先不创建 service：

```text
route
-> controller
-> schema / repository
```

### 3. 按业务模块组织

```text
src/
├── app.ts
├── server.ts
├── generated/
│   └── prisma/        Prisma 自动生成，不手动修改
├── db/
│   └── client.ts
├── errors/
│   └── app-error.ts
├── middleware/
│   ├── not-found.ts
│   └── error-handler.ts
└── modules/
    └── articles/
        ├── article-routes.ts
        ├── article-controller.ts
        ├── article-repository.ts
        └── article-schema.ts
```

项目根目录另外有 `prisma/schema.prisma` 和 `prisma/migrations/`，分别保存数据模型和迁移历史。文章相关业务代码仍然放在一起，寻找一条文章请求时不用在全项目来回跳。

`not-found.ts` 负责处理没有任何路由匹配的请求并返回 404，因此会注册在业务路由之后。

### 4. 把当前 Mini CMS 整理成正式结构

完成第 11 章后，真实 `mini-cms/server` 已经有 Prisma Client、article repository、Zod Schema、`AppError` 和错误中间件。现在不重写功能，只把 `app.ts` 中已经跑通的职责移到更清楚的位置：

| 当前位置 | 整理后的位置 | 为什么移动 |
|---|---|---|
| `app.ts` 中的 `app.listen()` | `server.ts` | 让 `app.ts` 可以被后续测试直接导入 |
| `app.ts` 中的文章路由 | `modules/articles/article-routes.ts` | 文章模块自己管理路径 |
| route 中读取参数和返回响应的代码 | `article-controller.ts` | 把 HTTP 处理从路由声明中分开 |
| `app.ts` 中的未匹配路由处理 | `middleware/not-found.ts` | 让公共 404 流程单独管理 |

整理顺序保持从小到大：

```text
1. 新建 server.ts，移动 app.listen()
2. 让 app.ts 导出 app，修改 dev 命令入口
3. 新建 article-controller.ts，移动文章请求和成功响应
4. 新建 article-routes.ts，只保留方法、路径和 controller 对应关系
5. 新建 not-found.ts，再在 app.ts 中按顺序注册路由和中间件
```

第 2 步完成后，`package.json` 的开发入口要指向真正负责启动的文件：

```json
{
  "scripts": {
    "dev": "tsx watch src/server.ts"
  }
}
```

`app.ts` 中的注册顺序保持：

```text
express.json()
-> article routes
-> not-found middleware
-> error-handler middleware
-> 导出 app
```

整理不是重写功能。每移动一步都保持 API 行为不变，并立即用类型检查和 Apifox 重新请求：

```text
移动前能创建文章
-> 移动文件并修正 import
-> 类型检查通过
-> 同一请求仍返回相同状态码和 JSON
```

当前 `src/db/client.ts`、`src/errors/app-error.ts`、`src/middleware/error-handler.ts`、`article-schema.ts` 和 `article-repository.ts` 已经在正确位置，不需要为了整齐再移动。只有阶段 5 真正出现发布和标签规则时，才增加 `article-service.ts`。

## 不要一开始机械拆五层

健康检查可以直接写在 route：

```ts
app.get("/api/health", (_request, response) => {
  response.json({ server: "server is running" });
});
```

简单查询也可以先只有：

```text
route + repository
```

出现真实业务规则后，再增加 service。

判断是否需要拆文件，可以问：

```text
这个函数是否同时处理了 HTTP、业务和数据库访问？
它是否已经很难单独测试？
同一逻辑是否被多个路由重复使用？
```

---

## 一次创建文章怎样经过文件

```text
article-routes.ts
-> 匹配 POST /api/articles

article-controller.ts
-> 读取请求并调用 Zod Schema 校验输入

article-schema.ts
-> 定义 body 和 params 的校验规则

article-repository.ts
-> 调用 `prisma.article.create()`

error-handler.ts
-> 统一处理失败
```

阶段 5 出现发布状态和标签关联规则后，再在 controller 与 repository 之间加入 `article-service.ts`。如果无法沿请求链找到代码，说明结构可能拆得不够清楚，或者拆得过度。

---

## 小结

```text
server.ts
-> 监听端口，启动服务

app.ts
-> 创建 Express app，注册中间件和路由

routes / controller
-> 匹配请求，读取输入并返回响应

service
-> 检查和执行文章规则

repository
-> 调用 Prisma Client，由其生成 SQL，并把结果交给上一层
```

不需要一开始就拆出所有文件。当一个函数同时处理 HTTP、业务规则和数据库访问时，再按上面的作用拆开。

类型检查通过，五个文章接口的正常和常见失败响应都没有变化后，回到[第 10 章项目总览](./10-MiniCMS项目总览.md)完成阶段 3 验收。下一步再阅读第 13 章，创建管理页面。
