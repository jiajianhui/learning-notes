# 14. 登录和安全：服务器怎样确认管理员身份

> Mini CMS 阶段 6：先完成标签、发布规则和管理页面，再用本章理解登录闭环；具体代码放到第 14A 章实践。

## 问题背景

有一个登录页面，不代表后端已经有登录能力。

真正的登录要解决：

```text
密码怎样保存？
登录成功后怎样记住身份？
下一次请求怎样证明自己已经登录？
哪些接口必须拦截未登录用户？
```

---

## 登录链路包含哪些部分

### 1. 认证和授权不同

```text
认证 Authentication
-> 你是谁？

授权 Authorization
-> 你能做什么？
```

单管理员文章系统先完成认证即可，不急着增加角色和复杂权限。

### 2. 密码不能明文保存

数据库只保存密码哈希：

```text
用户输入密码
-> 使用密码哈希算法验证
-> 比较结果
```

哈希不是加密后再解密。验证时比较哈希结果，不取回原始密码。

### 3. Cookie 可以携带登录凭证

登录成功后，服务器通过响应设置 Cookie：

```text
Set-Cookie: session=...; HttpOnly; SameSite=Lax
```

以后浏览器在符合规则的请求中自动携带 Cookie。

Cookie 后面的属性用于限制它怎样被使用：

| 属性 | 当前先理解成 |
|---|---|
| `HttpOnly` | 浏览器 JavaScript 不能直接读取这条 Cookie |
| `SameSite` | 限制跨站请求何时可以自动携带 Cookie |
| `Secure` | 只通过 HTTPS 发送 Cookie |

这些限制可以降低登录凭证被误用或窃取的风险。

### 4. 认证中间件保护接口

```text
请求创建文章
-> 认证中间件读取 Cookie
-> 验证登录凭证
-> 成功则继续
-> 失败返回 401
```

401 表示这次请求没有有效的登录凭证。

不是只隐藏前端按钮，而是后端必须拦截未授权请求。

---

## 单管理员系统的最小认证范围

```text
POST /api/auth/login
POST /api/auth/logout
GET  /api/auth/me
```

公开接口：

- 健康检查。
- 读取已发布文章的公开接口。

受保护接口：

- 创建、修改、删除文章。
- 管理后台使用的草稿内容。

第一轮不做公开注册、多角色和找回密码。

---

## CORS 和 Cookie 为什么会一起出现

开发环境中：

```text
Next.js：http://localhost:3000
Express：http://localhost:3001
```

来源（origin）由协议、主机和端口共同决定。这里端口不同，所以属于不同来源。

如果已按第 12 章配置 Express 允许管理后台的来源，登录改用 Cookie 后，还需要让后端 CORS 允许凭证：

```ts
app.use(cors({
  origin: "http://localhost:3000",
  credentials: true,
}));
```

前端请求也要声明携带凭证：

```ts
fetch(`${API_URL}/api/auth/me`, {
  credentials: "include",
});
```

CORS 不是认证。它主要限制浏览器中的跨来源请求，不能代替后端身份验证。

浏览器会自动携带 Cookie，也带来一种风险：恶意网站可能诱导已登录用户发出修改数据的请求。这类攻击叫 CSRF。`SameSite` 可以降低风险，正式上线时还需要根据部署方式增加相应的服务器防护。

---

## 基本安全边界

第一轮至少做到：

- 密码只保存哈希。
- 数据库查询使用参数。
- 密钥和数据库地址放环境变量。
- 不向客户端返回堆栈和数据库内部错误。
- CORS 只允许明确来源，不随意开放全部来源和凭证。
- Cookie 根据环境设置 `HttpOnly`、`SameSite` 和 `Secure`。
- Cookie 认证上线前补齐 CSRF 防护。
- 后端始终重新校验输入和权限。

---

## 小结

```text
密码哈希
-> 数据库不保存原始密码，登录时通过哈希结果验证

Cookie
-> 登录成功后保存凭证，并在符合规则的后续请求中自动携带

认证中间件
-> 验证凭证；成功才继续，失败返回 401

CORS
-> 决定浏览器是否允许跨来源请求，不能代替登录验证
```

登录的核心不是页面，而是每次敏感请求都能被服务器验证。
