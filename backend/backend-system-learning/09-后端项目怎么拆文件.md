# 09. 后端项目结构：按职责拆开，不要为了分层而分层

## 问题背景

最开始可以把健康检查和内存数组写在一个文件里。

当文章、标签、登录和数据库都加入后，一个文件会同时出现：

```text
路由
参数校验
业务规则
SQL
错误处理
服务器启动
```

这时需要拆分，但拆分的目标是让请求链路更容易追踪，不是让目录看起来复杂。

---

## 核心解释

### 1. 先把启动和应用分开

```text
server.ts
-> 监听端口，真正启动服务

app.ts
-> 创建 Express app，注册中间件和路由
```

这样自动化测试可以直接使用 `app`，不需要真的占用固定端口。

### 2. 按业务模块组织

```text
src/
├── app.ts
├── server.ts
├── config/
│   └── env.ts
├── db/
│   └── pool.ts
├── middleware/
│   ├── auth.ts
│   ├── not-found.ts
│   └── error-handler.ts
└── modules/
    ├── articles/
    │   ├── article.routes.ts
    │   ├── article.controller.ts
    │   ├── article.service.ts
    │   ├── article.repository.ts
    │   └── article.schema.ts
    └── tags/
        └── ...
```

文章相关代码放在一起，寻找一条文章请求时不用在全项目来回跳。

---

## 每层负责什么

| 层 | 主要职责 |
|---|---|
| routes | 声明 HTTP 方法、路径和中间件顺序 |
| controller | 读取 request，调用业务函数，返回 response |
| service | 执行业务规则，决定哪些数据库操作需要放进同一事务 |
| repository | 执行 SQL，把数据库结果交给上层 |
| schema | 校验请求输入 |
| middleware | 认证、日志、404、错误等公共流程 |
| config | 环境变量和应用配置 |

依赖方向可以先保持：

```text
route
-> controller
-> service
-> repository
-> PostgreSQL
```

响应结果再反方向返回。

---

## 不要一开始机械拆五层

健康检查可以直接写在 route：

```ts
app.get("/api/health", (_request, response) => {
  response.json({ status: "ok" });
});
```

简单查询也可以先只有：

```text
route + repository
```

出现真实业务规则后，再增加 service。

判断是否需要拆文件，可以问：

```text
这个函数是否同时处理了 HTTP、业务和 SQL？
它是否已经很难单独测试？
同一逻辑是否被多个路由重复使用？
```

---

## 一次创建文章怎样经过文件

```text
article.routes.ts
-> 匹配 POST /api/articles

article.schema.ts
-> 校验 body

article.controller.ts
-> 读取校验后的输入

article.service.ts
-> 检查规则，组织事务

article.repository.ts
-> 执行 INSERT

error-handler.ts
-> 统一处理失败
```

如果无法沿这条线找到代码，说明结构可能拆得不够清楚，或者拆得过度。

---

## 常见误区

- route handler 同时写校验、业务规则和 SQL，代码会难读也难单独测试；职责变多后再逐层拆开。
- controller 如果只把参数原样传给 service，而 service 又原样传给 repository，拆文件没有带来清晰职责；简单流程可以先合并。
- 每张表都复制 routes、controller、service、repository，会产生大量只负责转发的空层；根据真实复杂度拆分。
- 不相关函数全部扔进 `utils`，以后很难判断由谁使用；优先放回所属业务模块并用具体名称描述用途。
- A 模块依赖 B、B 又依赖 A，会形成循环引用；保持 route 到 repository 的单向依赖。
- 如果导入 `server.ts` 就立刻监听端口，测试也会启动真实服务器；让 `app.ts` 导出 app，只有 `server.ts` 负责监听。

---

## 小结

```text
先让功能跑通
-> 发现职责混在一起
-> 按请求、业务、数据访问拆开
-> 保持请求链路可以追踪
```

好的结构不是文件多，而是你知道修改某类问题应该去哪里。
