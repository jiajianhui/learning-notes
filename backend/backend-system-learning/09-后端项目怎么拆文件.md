# 09. 后端项目结构：按职责拆开，不要为了分层而分层

## 问题背景

最开始可以把健康检查和内存数组写在一个文件里。

当文章、标签、登录和数据库都加入后，一个文件会同时出现：

```text
路由
参数校验
业务规则
SQL
错误处理
服务器启动
```

这时需要拆分，但拆分的目标是让请求链路更容易追踪，不是让目录看起来复杂。

---

## 核心解释

### 1. 先把启动和应用分开

```text
server.ts
-> 监听端口，真正启动服务

app.ts
-> 创建 Express app，注册中间件和路由
```

这样自动化测试可以直接使用 `app`，不需要真的占用固定端口。

### 2. 按业务模块组织

```text
src/
├── app.ts
├── server.ts
├── config/
│   └── env.ts
├── db/
│   └── pool.ts
├── middleware/
│   ├── auth.ts
│   ├── not-found.ts
│   └── error-handler.ts
└── modules/
    ├── articles/
    │   ├── article.routes.ts
    │   ├── article.controller.ts
    │   ├── article.service.ts
    │   ├── article.repository.ts
    │   └── article.schema.ts
    └── tags/
        └── ...
```

文章相关代码放在一起，寻找一条文章请求时不用在全项目来回跳。

---

## 每层负责什么

| 层 | 主要职责 |
|---|---|
| routes | 声明 HTTP 方法、路径和中间件顺序 |
| controller | 读取 request，调用业务函数，返回 response |
| service | 业务规则和事务边界 |
| repository | 执行 SQL，把数据库结果交给上层 |
| schema | 校验请求输入 |
| middleware | 认证、日志、404、错误等公共流程 |
| config | 环境变量和应用配置 |

依赖方向可以先保持：

```text
route
-> controller
-> service
-> repository
-> PostgreSQL
```

响应结果再反方向返回。

---

## 不要一开始机械拆五层

健康检查可以直接写在 route：

```ts
app.get("/api/health", (_request, response) => {
  response.json({ status: "ok" });
});
```

简单查询也可以先只有：

```text
route + repository
```

出现真实业务规则后，再增加 service。

判断是否需要拆文件，可以问：

```text
这个函数是否同时处理了 HTTP、业务和 SQL？
它是否已经很难单独测试？
同一逻辑是否被多个路由重复使用？
```

---

## 一次创建文章怎样经过文件

```text
article.routes.ts
-> 匹配 POST /api/articles

article.schema.ts
-> 校验 body

article.controller.ts
-> 读取校验后的输入

article.service.ts
-> 检查规则，组织事务

article.repository.ts
-> 执行 INSERT

error-handler.ts
-> 统一处理失败
```

如果无法沿这条线找到代码，说明结构可能拆得不够清楚，或者拆得过度。

---

## 常见误区

- 所有逻辑都放在 route handler。
- controller 和 service 只是互相转发，没有任何职责差异。
- 每张表都机械复制完整分层，即使只有一条简单查询。
- 工具函数目录变成不知道放哪里的垃圾桶。
- 模块之间随意循环引用。
- `server.ts` 启动时立刻监听端口，导致测试难以复用 app。

---

## 小结

```text
先让功能跑通
-> 发现职责混在一起
-> 按请求、业务、数据访问拆开
-> 保持请求链路可以追踪
```

好的结构不是文件多，而是你知道修改某类问题应该去哪里。
