# 16A. 从表单到数据库再回到页面：看懂前后端数据流

这是第 16 章的配套巩固章。完成标签管理与页面联调后，用这一篇复习数据怎样在 `admin-web-antd`、Express 和 PostgreSQL 之间流动。不增加新功能，代码片段用于对照已有实现。

[第 06 章](./06-API设计和参数校验.md)已经从顶层说明 API contract 怎样规定数据进出后端的边界。第 14A 章按文件追踪 CRUD，第 15A 章解释关系维护；这里结合阶段 5 的真实数据，继续关注同一份数据经过各层时，**类型、字段和含义怎样变化**。

## 1. 点击保存后，数据经过哪里

以编辑文章 42 为例：用户修改表单后点击保存，页面把表单值交给前端的 `updateArticle(id, values)`。

```text
表单中的 values：JavaScript 对象
→ features/articles/api.ts：JSON.stringify(values)，生成请求体
→ lib/api-client.ts：fetch 发送 PATCH /api/articles/42
→ Express 的 express.json()：解析请求体，得到 req.body
→ article-router.ts：Schema.parse() 校验参数和请求体，得到 id、input
→ article-repository.ts：计算发布时间，更新文章和标签关系
→ PostgreSQL：保存数据
→ router：response.json({ data: article }) 返回结果
→ 前端 requestJson() 解析响应，apiRequest() 取出 data
→ 页面等待保存成功，关闭抽屉、提示成功
→ 重新获取当前筛选条件和页码下的文章列表
→ 用 data 更新 articles，用 pagination.total 更新总数
```

前后端都有名为 `updateArticle()` 的函数，但它们不是同一个函数：前端函数发送 HTTP 请求，后端函数通过 Prisma 操作数据库。HTTP 传递的是数据，不会把前端的函数或变量直接交给后端。

看具体问题时，沿这条线找“数据在哪一步变了”，比只看最终页面更容易定位。

## 2. 同一个 id，为什么有时是数字，有时是字符串

请求中的数据可以放在不同位置。Express 读取的位置不同，得到的值也可能不同：

| 请求内容 | 后端从哪里取 | 校验前 | 校验后 |
|---|---|---|---|
| `PATCH /api/articles/42`，路由为 `/:id` | `req.params.id` | `"42"` | 路径 Schema 用 `z.coerce.number()` 转成 `42` |
| `GET /api/articles?tagId=3&page=2` | `req.query` | `tagId` 为 `"3"`，`page` 为 `"2"` | 查询 Schema 转成数字 `3`、`2` |
| JSON 请求体 `{"tagIds":[3,7]}` | `req.body.tagIds` | 数字数组 `[3, 7]` | 仍是数字数组 |
| JSON 请求体 `{"tagIds":["3","7"]}` | `req.body.tagIds` | 字符串数组 | 本项目的 `z.number()` 拒绝它 |

**URL 中的数字，通过 `req.params` 或 `req.query` 读取时是字符串。** 本项目的 id、页码等参数后续要作为数字使用，因此在 Schema 校验时转成数字。

**JSON 请求体则保留数字和字符串各自的类型。** `express.json()` 解析后，`req.body` 中的 `3` 仍是数字，`"3"` 仍是字符串。因此，后端要求数字数组时，前端应提交 `[3, 7]`，而不是 `["3", "7"]`。

## 3. Schema 是规则，parse 才执行检查和转换

定义 Schema 时还没有处理任何请求。router 调用 `.parse()`，才把这次请求的数据交给规则检查：

```ts
const input = updateArticleSchema.parse(req.body);
const article = await updateArticle(id, input);
```

第一行失败会抛出 `ZodError`，当前请求进入错误处理，不会执行第二行。通过后得到的 `input`，也不一定和原来的 `req.body` 完全一样：

| 规则 | 输入 | 校验结果 |
|---|---|---|
| 标题的 `.trim()` | `"  新标题  "` | `"新标题"` |
| 查询参数的 `z.coerce.number()` | `"2"` | 数字 `2` |
| `page` 的 `.default(1)` | 没提交 `page` | 数字 `1` |
| `tagIds` 的 `.refine()` | `[3, 3, 7]` | 校验失败，不会自动改成 `[3, 7]` |

前面三项会转换或补上值；最后一项只判断是否符合规则。repository 接收校验后的 `input`。

**TypeScript 类型在开发时检查代码；Zod Schema 在程序运行时通过 `.parse()` 检查实际收到的数据，并按规则转换。** 给 `req.body` 标注类型，并不能保证请求内容合法，也不会转换其中的值。

## 4. 不传、null、空字符串和空数组分别意味着什么

以修改标题和摘要为例，表中省略标题字段，只展示摘要在各阶段的变化：

| 原始请求数据（JS 对象） | `JSON.stringify()` 后的 JSON 请求体 | `express.json()` 解析后的 `req.body.summary` | Schema 校验后的 `input.summary` | Prisma 更新结果 | 再次回填表单的值 |
|---|---|---|---|---|---|
| `{ summary: undefined }`，或不写该字段 | 不包含 `summary` 字段 | `undefined`（字段不存在） | `undefined` | 不改原摘要 | 原摘要（为 `null` 时转成 `""`） |
| `{ summary: null }` | `"summary": null` | `null` | `null` | 保存为 SQL `NULL` | `""` |
| `{ summary: "" }` | `"summary": ""` | `""` | `""` | 保存为空字符串 | `""` |
| `{ summary: "新摘要" }` | `"summary": "新摘要"` | `"新摘要"` | `"新摘要"` | 保存为“新摘要” | `"新摘要"` |

**JSON 没有 `undefined`，对象中值为 `undefined` 的字段会在序列化时被省略；`null` 和空字符串则会保留。** 后端再按本项目的更新规则处理这些值。

**`null` 不是空字符串。** 输入框看起来一样，是因为第 14 章回填时做了转换：

```ts
summary: editingArticle.summary ?? ""
```

这里的 `??` 表示：左边为 `null` 或 `undefined` 时使用 `""`，其他值保留。当前输入框清空后提交的是空字符串，不会自动变成 `null`。页面展示时的转换，也不会自行改变数据库。

如果请求整个变成 `{}`，`updateArticleSchema` 中的 `.refine()` 会拒绝空更新。上表的“不改摘要”可以与修改标题等其他字段一起使用。

更新文章时，各字段按下面的规则处理：

- **摘要 `summary`**：不传就保留数据库中的原摘要；传 `null` 保存为 SQL `NULL`；传 `""` 保存为空字符串。
- **标签 `tagIds`**：不传就保留文章原有的标签关联；传 `[]` 移除全部标签关联。Schema 要求数字数组，`.optional()` 允许不传，但没有 `.nullable()`，所以传 `null` 会校验失败。
- **状态 `status`**：不传就保留数据库中的原状态；传 `"draft"` 或 `"published"` 更新为指定状态。Schema 只允许这两个枚举值，没有允许 `null`，所以传 `null` 会校验失败。

**创建文章时，不传 `status`，默认设为 `"draft"`；更新文章时，不传 `status`，保留原状态。** 两种情况下传 `null` 都会校验失败。

## 5. 更新时，提交完整表单还是只提交改动字段

假设用户只修改了标题，前端可以用两种方式提交，**两种都可以使用 PATCH**：

| 提交方式 | 请求中包含什么 | 前端需要做什么 |
|---|---|---|
| 提交完整表单（当前项目） | 标题、slug、摘要、正文、状态和标签，即使部分值没有变化 | 将完整 `values` 交给更新接口 |
| 只提交改动字段 | 例如 `{ "title": "新标题" }` | 比较修改前后的值，只收集发生变化的字段 |

**当前项目即使只修改了 `title`，更新时也会提交整个表单。**

## 6. 标签从选择、保存到再次显示

以文章 42 选择 React（id 为 3）和 TypeScript（id 为 7）为例，看标签数据怎样经过前端、数据库，再回到页面。

### 6.1 选择标签，提交 id

页面通过 `GET /api/tags` 获取全部可选标签，为 Select 生成选项：

```ts
// 选项示意
[
  { label: "React", value: 3 },
  { label: "TypeScript", value: 7 },
]
```

选中这两个选项后，多选框将它们的 `value` 收集成 `tagIds: [3, 7]`。保存时，请求体携带这些 id，不需要提交标签名称。

### 6.2 后端把 id 保存为关联记录

`tagIds` 不是 Article 表的列。repository 从校验后的 `input` 中拆出 `tagIds`，其余字段用于更新文章；`tagIds` 用于更新这篇文章的标签关联。

本次提交了 `[3, 7]`，后端在同一事务中删除文章 42 的旧关联，再写入两条 ArticleTag 记录：

| articleId | tagId |
|---|---|
| 42 | 3 |
| 42 | 7 |

这里删除的是文章与标签的关联，不会删除 Tag 表中的标签。

### 6.3 查询关联，供页面展示和回填

查询文章时，Prisma 通过 `include` 带上 `articleTags` 关联记录，以及每条记录对应的 `tag`。响应中的标签部分如下，省略其他字段：

```json
{
  "articleTags": [
    { "tag": { "id": 3, "name": "React" } },
    { "tag": { "id": 7, "name": "TypeScript" } }
  ]
}
```

页面从同一份数据中取出不同内容：

```ts
// 列表展示：取名称，得到 ["React", "TypeScript"]
article.articleTags.map((item) => item.tag.name);

// 编辑回填：取 id，作为表单的 tagIds，得到 [3, 7]
article.articleTags.map((item) => item.tag.id);
```

再次打开编辑表单时，**全部标签列表决定“可以选什么”，文章详情中的标签 id 决定“已经选了什么”**。

本例中，同一组标签在三个位置的形态分别是（只展示标签相关数据）：

```ts
// 请求体：提交选中的标签 id
{ tagIds: [3, 7] }

// ArticleTag 中间表：保存两条关联记录
{ articleId: 42, tagId: 3 }
{ articleId: 42, tagId: 7 }

// 响应中的文章数据：带回关联的标签信息，省略其他字段
{
  articleTags: [
    { tag: { id: 3, name: "React" } },
    { tag: { id: 7, name: "TypeScript" } },
  ]
}
```

## 7. 时间从数据库返回后，为什么变成了字符串

前端提交 `status`，后端根据状态生成或清空 `publishedAt`，再将它随文章返回。这个字段不需要前端提交，但会出现在响应中。它经过各层时的形式是：

| 位置 | 数据形式 |
|---|---|
| PostgreSQL | `published_at` 时间列，类型为 `timestamptz`；草稿为 `NULL` |
| Prisma 查询结果 | JavaScript `Date` 对象，或 `null` |
| `response.json()` 发出的 JSON | ISO 时间字符串，例如 `"2026-09-10T02:00:00.000Z"`，或 `null` |
| 前端 `response.json()` 解析后 | 仍是字符串，或 `null`，不会自动变回 `Date` |

所以前端的 `Article` 类型写 `publishedAt: string | null`。需要格式化时，再转换成 `Date`：

```ts
// 显示逻辑示例：null 显示“未发布”，有值时格式化为本地时间。
const text = article.publishedAt === null
  ? "未发布"
  : new Date(article.publishedAt).toLocaleString();
```

示例中的 `Z` 表示 UTC。浏览器时区为上海时，UTC 的 `02:00` 对应本地 `10:00`；这是同一时刻的不同显示方式，不是数据库多存了 8 小时。

创建草稿时没有发布时间；发布时由后端生成当前时间；撤回时清空；更新时未提交状态就保留原时间。完整规则在[第 15 章第 6 节](./15-数据关系JOIN和事务.md)，前端不另算一份发布时间。

## 8. 数据库保存成功，为什么页面还需要更新

数据库中的文章和 React 状态中的文章是两份数据。接口保存成功，不会自动修改浏览器里的 `articles` 数组。

第 14 章的做法是：保存成功后，取得接口返回的文章，在 React 的 `articles` 数组中找到相同 id 的文章并替换，再通过 `setArticles()` 更新状态，表格随之更新。

第 16 章接入筛选分页后，保存成功会重新获取当前条件下的文章列表。例如当前筛选草稿，文章发布后应从列表中消失，总数也应减少，只替换原来那一行就不够了。

获取列表后，`data` 用来更新表格数据，`pagination.total` 用来更新分页器的总条数：

| 响应数据 | 后端怎样得到 | 页面怎样使用 |
|---|---|---|
| `data` | `findMany({ where, skip, take })` | Table 显示当前页的文章 |
| `pagination.total` | `count({ where })` | 分页器显示全部符合条件的数量 |

例如符合条件的文章共 23 篇，每页 10 条，第 2 页的 `data.length` 是 10，`total` 仍是 23。**当前页条数不等于总数。**

为让页面同时拿到文章和分页信息，当前请求封装分为：

```text
requestJson()：发送请求、处理 HTTP 错误、解析并返回完整响应
├─ apiRequest()：取出 data，用于详情、保存和标签列表等请求
└─ apiListRequest()：保留 data 和 pagination，用于文章分页列表
```

因此 `getArticles(query)` 使用 `apiListRequest()`。如果使用只返回 `data` 的 `apiRequest()`，分页信息会被丢掉，页面就拿不到总数。

## 9. 后端抛出的错误，怎样变成页面上的提示

后端的 `AppError` 或 `ZodError` 不会作为 JavaScript 错误对象跨网络传到浏览器。中间件先把它变成 HTTP 状态码和 JSON，前端再决定如何处理：

```text
Router 校验失败，或 repository 操作失败（按需转换为 AppError）
→ Express 5 交给 errorHandler
→ 返回 422、404 或 409 等状态码和错误 JSON
→ 前端 fetch 得到 Response
→ requestJson() 检查 response.ok，失败时读取错误 JSON 并 throw new Error(...)
→ 错误沿请求函数向上传播，由发起操作的表单或页面捕获
```

`fetch` 收到 422 或 500 响应时，不会仅因状态码而自动抛错，所以 `requestJson()` 需要检查 `response.ok`。后端错误和前端重新抛出的 `Error` 是两次不同的抛错。

保存失败时，错误沿 `onSubmit` 传回表单，由 `handleFinish()` 的 `catch` 写入 `submitError`，在表单内显示；获取列表失败时，列表 Effect 的 `catch` 写入 `listError`，在表格上方显示。

例如标签 id 重复，后端响应里有：

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "请求参数不正确",
    "details": [{ "field": "tagIds", "message": "标签不能重复" }]
  }
}
```

当前请求封装只读取 `error.message`，所以页面显示“请求参数不正确”。`details` 中虽然有“标签不能重复”，也不会自动出现在表单字段下面；若要展示，需要前端读取它并交给对应的 Form 字段。这里先分清已有行为，不新增字段错误展示功能。

后端四类错误的来源与错误码对照，回看[第 15 章第 10 节](./15-数据关系JOIN和事务.md)。

## 10. 在 Network 中对照 req 和 res

打开浏览器开发者工具的 **网络（Network）** 面板，选择 **Fetch/XHR** 筛选，在页面修改并保存一次文章，再点击对应的 `PATCH /api/articles/:id` 请求。

后端通过 `req` 读取请求，通过 `res` 返回响应；这些数据在 Network 中的位置如下：

| 后端代码 | Network 中的查看位置（中英对照） |
|---|---|
| `req.params`：路径参数 | 标头（Headers）→ 常规（General）→ 请求网址（Request URL），例如 `/api/articles/98` 中的 `98` |
| `req.query`：查询参数 | 载荷（Payload）→ 查询字符串参数（Query String Parameters），例如 `page=1` |
| `req.body`：请求体 | 载荷（Payload）→ 请求载荷（Request Payload），查看提交的 JSON |
| `req.headers`：请求头 | 标头 → 请求标头（Request Headers） |
| `res.status(...)`：响应状态码 | 标头 → 常规 → 状态代码（Status Code） |
| `res.json(...)`：返回的 JSON | 预览（Preview）中展开查看，响应（Response）中查看正文 |

**预览和响应展示的是同一份响应。** 没有查询参数和请求体时，例如 `GET /api/articles/98`，不会出现 Payload 面板，路径参数仍在请求网址中。

**Apifox 用来主动构造请求测试接口，Network 用来观察页面实际发出的请求。** 两边结果不同时，可以对比 URL、标头和请求体。

面板说明可查 [Chrome DevTools 网络功能参考](https://developer.chrome.com/docs/devtools/network/reference?hl=zh-cn)。

能沿着“表单值 → 请求 → 校验结果 → 数据库 → 响应 → 页面”说清每一步，就按 [16B-用 Ant Design 完善后台 UI](./16B-用AntDesign完善后台UI.md) 自主还原页面、[16C-用 ProComponents 简化管理后台](./16C-用ProComponents简化管理后台.md) 完成组件改造，回到[第 10 章](./10-MiniCMS项目总览.md)验收阶段 5。
