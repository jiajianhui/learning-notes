# 11A. 错误处理中间件：一段代码怎样接住不同错误

> 这是第 11 章第 5～6 节的配套概念章。它不增加新功能，专门解释 `app-error.ts` 和 `error-handler.ts` 为什么要这样设计。读完应该能说清“错误从哪里产生、Express 怎样传递、最后变成什么响应”，不需要背下整份 `errorHandler`。

## 从一张错误处理地图开始

正常请求只需要把查询结果返回给客户端。失败请求更复杂，因为错误可能来自请求流程的不同位置：

```text
express.json() 解析请求体 JSON 失败
Zod 发现请求数据不符合 Schema
路由发现文章不存在
Prisma 发现 slug 重复
数据库断开或程序出现未知异常
```

这些错误的形状不一样，但客户端需要稳定的 HTTP 状态码和 JSON。因此 Mini CMS 使用这条主线：

```text
请求流程的某一步产生错误对象
-> Express 把错误传递给 errorHandler
-> errorHandler 识别错误类型
-> 把内部错误翻译成统一 HTTP 响应
```

这不是 `errorHandler` 主动去各个文件“收集”错误。Zod、路由和 Prisma 先发现或产生错误，Express 再负责传递，`errorHandler` 只在最后分类并返回响应。

当前实现中的三个核心文件各有一个职责：

| 文件 | 职责 | 不负责什么 |
|---|---|---|
| `app-error.ts` | 定义一种能携带状态码和 code 的业务错误 | 不返回 HTTP 响应 |
| `error-handler.ts` | 识别不同错误，转成统一响应 | 不执行文章 CRUD |
| `app.ts` | 注册路由和错误中间件，让整条流程连起来 | 不重复定义错误分类规则 |

## 1. 路由里不写 `try/catch`，是不是漏了

`try/catch` 没有被废弃。在当前 Express 5 项目中，如果 `catch` 只为了把错误交给 Express，就不需要在每个异步路由里重复编写。

可以手动写成：

```ts
app.post("/api/articles", async (request, response, next) => {
  try {
    const input = createArticleSchema.parse(request.body);
    const article = await createArticle(input);

    response.status(201).json({ data: article });
  } catch (error) {
    next(error);
  }
});
```

这里的 `catch` 没有处理错误，只做了一件事：

```text
接住 error
-> next(error) 把它交给 Express
```

Express 5 已经会自动传递 `async` 路由里抛出的错误和被拒绝的 Promise。因此当前路由可以保持为：

```ts
app.post("/api/articles", async (request, response) => {
  const input = createArticleSchema.parse(request.body);
  const article = await createArticle(input);

  response.status(201).json({ data: article });
});
```

这段代码中：

```text
Schema.parse() 抛出 ZodError
或 createArticle() 返回的 Promise 失败
-> Express 5 内部按 next(error) 处理
-> errorHandler 收到错误
```

如果每个路由都在 `catch` 里直接返回 JSON，不同路由就容易出现不同的状态码、code 和文案。这正是当前项目要避免的重复。

`try/catch` 仍然有用，例如错误发生后需要恢复、补充上下文或把它转成另一种错误。当前 Mini CMS 的路由只需要把错误继续向后传，所以先交给 Express 5 和统一错误中间件。

## 2. 先认识错误对象：它也有类型和属性

### 2.1 Error 也是一个对象

代码出错时，传递的不只是一句错误文案，而是一个描述错误的对象。

```ts
const error = new Error("文章不存在");
```

可以先认识三个常见属性：

```text
error.name
-> 错误名称，默认是 Error

error.message
-> 创建错误时传入的文案

error.stack
-> 错误堆栈，用来定位错误发生在哪里
```

`Error` 只提供通用信息。不同库会定义自己的错误类，再增加当前场景需要的属性：

| 错误对象 | 额外的关键信息 |
|---|---|
| `ZodError` | `issues` 保存请求数据未通过校验的详情 |
| `PrismaClientKnownRequestError` | `code` 保存 `P2002` 等 Prisma 错误码 |
| `AppError` | `statusCode` 和 `code` 保存项目自己定义的响应信息 |

因此 `errorHandler` 收到错误后，不是只读取 `message`，而是先判断它是哪一种错误对象。

### 2.2 instanceof 在检查“它是哪种错误”

```ts
if (error instanceof AppError) {
  // 这个分支里才按 AppError 使用 error
}
```

`instanceof AppError` 可以先理解成：

```text
这个 error 是不是通过 AppError 创建的，
或者它是不是 AppError 的子类对象？
```

答案为真时，TypeScript 也知道它是 `AppError`，于是允许代码读取 `error.statusCode` 和 `error.code`。

### 2.3 in 在检查“它有没有这个属性”

```ts
"status" in error
```

这句不检查 `status` 的具体值，只是询问：“`error` 对象上有没有 `status` 属性？”

所以下面两步的职责不同：

```ts
"status" in error
// 先确认属性存在

error.status === 400
// 再检查它的值
```

### 2.4 为什么还会出现 unknown

JavaScript 甚至允许抛出字符串或其他值。第三方库传来的错误形状也不一定相同。

当前 `@types/express` 中，`ErrorRequestHandler` 的 `error` 参数是宽松的 `any`。但 `isInvalidJsonError()` 把参数明确改成更安全的 `unknown`，表示：

```text
现在还不知道 error 的具体形状
-> 不能一上来就随意读取属性
-> 必须先用 instanceof 或 in 进行检查
```

把参数标注为 `unknown`，会强制代码先识别错误，再按确定的错误类型读取属性。

## 3. 为什么要单独设计 `app-error.ts`

先看 JavaScript 原生错误的写法：

```ts
throw new Error("文章不存在");
```

`new Error(...)` 创建的错误对象已经包含 `name`、`message` 和 `stack`。`errorHandler` 收到它后，可以知道错误信息是“文章不存在”，却无法从中判断：

```text
应该返回哪个 HTTP 状态码？
应该返回哪个稳定 code？
```

因为 HTTP 状态码和项目错误码属于 Mini CMS 自己的 API 规则，不是 JavaScript 原生错误自带的信息。

所以 `AppError` 的本质很简单：在 JavaScript 原生 `Error` 上，再增加 Mini CMS 需要的两个字段：

- `statusCode`：这次错误应该返回哪个 HTTP 状态码。
- `code`：前端可以稳定识别的项目错误码。

项目不需要重新设计一套错误对象，只需要继承原生 `Error` 并补上这两个字段：

```ts
export class AppError extends Error {
  constructor(
    public statusCode: number,
    public code: string,
    message: string,
  ) {
    super(message);
    this.name = "AppError";
  }
}
```

`constructor` 是类的构造函数。每次使用 `new AppError(...)` 创建错误对象时，它都会自动执行，并按顺序接收传入的参数。

例如路由中这样创建 `AppError`：

```ts
throw new AppError(
  404,
  "ARTICLE_NOT_FOUND",
  "文章不存在",
);
```

三个值会依次进入 `constructor`：

| 传入的值 | 对应的参数 | 最后保存到 |
|---|---|---|
| `404` | `statusCode` | `error.statusCode` |
| `"ARTICLE_NOT_FOUND"` | `code` | `error.code` |
| `"文章不存在"` | `message` | `error.message` |

`extends Error` 表示 `AppError` 继承内置 `Error`。`message` 是普通的构造函数参数，暂时只是传进来的一个值。

`super(message)` 表示把这个值交给原生 `Error` 进行初始化。执行后，新创建的 `AppError` 对象就有了 `this.message`，它的值是 `"文章不存在"`。错误堆栈也由原生 `Error` 负责生成。完成这一步后，下面的代码才能继续使用 `this` 设置其他属性。

`public statusCode: number` 和 `public code: string` 是 TypeScript 的“参数属性”简写。它们既是 `constructor` 的参数，也会自动成为对象属性。下面两种写法作用相同：

```ts
// 参数属性简写
constructor(
  public statusCode: number,
  public code: string,
  message: string,
) {
  super(message);
}
```

```ts
// 展开后的写法
public statusCode: number;
public code: string;

constructor(statusCode: number, code: string, message: string) {
  super(message);
  this.statusCode = statusCode;
  this.code = code;
}
```

因此，`public statusCode` 不只是声明“这里会收到一个状态码”，还相当于执行了 `this.statusCode = statusCode`。`public code` 也是同样的道理。`this.name = "AppError"` 则把错误对象的名称改成 `AppError`。

可以把抛出的对象简化理解为：

```ts
{
  name: "AppError",
  statusCode: 404,
  code: "ARTICLE_NOT_FOUND",
  message: "文章不存在",
  // 还有供服务器排错的 stack
}
```

`AppError` 的设计重点是“携带信息”，它自己不发送响应。路由只需要说明发生了什么，至于错误 JSON 怎样返回，由 `errorHandler` 统一决定。

## 4. `error-handler.ts` 怎样把不同错误翻译成统一响应

### 4.1 `ErrorRequestHandler` 的作用

最小错误中间件可以写成：

```ts
import type { ErrorRequestHandler } from "express";

export const errorHandler: ErrorRequestHandler = (
  error,
  _request,
  response,
  _next,
) => {
  console.error(error);

  response.status(500).json({
    error: {
      code: "INTERNAL_ERROR",
      message: "服务器内部错误",
    },
  });
};
```

`ErrorRequestHandler` 的作用是告诉 TypeScript：

```text
这个函数要按 Express 错误中间件的形状使用
-> 第 1 个参数是 error
-> 后面是 request、response、next
-> response 和 next 获得 Express 的类型提示
```

它不会主动运行函数，也不会主动抓取错误。真正让这个函数进入 Express 流程的是：

```ts
app.use(errorHandler);
```

Express 错误中间件必须保留四个参数：

```text
(error, request, response, next)
```

即使暂时没有使用 `request` 或 `next`，也要保留它们。`_request` 和 `_next` 的下划线只表示“当前没有使用这个参数”。

### 4.2 为什么 `errorHandler` 里面有很多 if

只返回 500 虽然已经能结束失败请求，但会把标题为空、slug 重复和数据库断开都当成同一种错误。

`errorHandler` 中的多个 `if` 实际上是一个翻译器：

| 识别到的错误 | 翻译后的响应 |
|---|---|
| JSON 解析错误 | `400 INVALID_JSON` |
| `ZodError` | `422 VALIDATION_ERROR` |
| `AppError` | 使用它自己携带的状态码和 code |
| Prisma `P2002` | `409 SLUG_CONFLICT` |
| Prisma `P2025` | `404 ARTICLE_NOT_FOUND` |
| 以上都不是 | `500 INTERNAL_ERROR` |

例如 `AppError` 分支：

```ts
if (error instanceof AppError) {
  response.status(error.statusCode).json({
    error: {
      code: error.code,
      message: error.message,
    },
  });
  return;
}
```

这段代码做了三件事：

```text
确认这是 AppError
-> 读取它携带的信息
-> 结束这次失败请求
```

返回 JSON 后立即 `return`，是为了结束 `errorHandler`，避免同一个错误继续走到后面的 500 分支。

## 5. 四类错误分别从哪里来，又变成什么响应

本节先看 Zod、`AppError`、Prisma 和未识别错误。JSON 解析错误需要额外检查错误对象的形状，放到第 6 节单独拆解。

`errorHandler` 不关心错误是在哪个路由产生的。它只根据错误对象的类型和属性决定响应。

### 5.1 请求数据未通过 Schema 校验：ZodError

```ts
const input = createArticleSchema.parse(request.body);
```

标题为空时，`.parse()` 抛出 `ZodError`。JSON 此时已经被 `express.json()` 解析成 `request.body`，失败的是请求数据没有满足 Schema 规则，而不是 JSON 文本无法解析。

`articleIdParamsSchema.parse(request.params)` 校验文章 ID 失败时，也会抛出 `ZodError` 并进入同一分支。因此这里统一使用“请求数据未通过 Schema 校验”，不只指某个字段。

`errorHandler` 中的完整分支如下：

```ts
if (error instanceof z.ZodError) {
  response.status(422).json({
    error: {
      code: "VALIDATION_ERROR",
      message: "请求参数不正确",
      details: error.issues.map((issue) => ({
        field: issue.path.join("."),
        message: issue.message,
      })),
    },
  });
  return;
}
```

`error.issues` 是 Zod 生成的问题数组。例如标题为空时，其中一项可以简化理解为：

```ts
{
  path: ["title"],
  message: "标题不能为空",
}
```

`map()` 遍历每一项，把 Zod 的问题对象改成前端更容易使用的结构：

```ts
{
  field: "title",
  message: "标题不能为空",
}
```

`issue.path.join(".")` 会把 `["title"]` 变成 `"title"`；`issue.message` 保留 Schema 中定义的错误文案。最后整个分支返回 `422 VALIDATION_ERROR`。

### 5.2 查询不到文章：AppError

`findUnique()` 查询不到数据时返回 `null`，没有错误对象可以传递。因此路由主动创建 `AppError`：

```text
findUnique() 返回 null
-> 路由 throw new AppError(...)
-> Express 传递错误
-> errorHandler 识别 AppError
-> 404 ARTICLE_NOT_FOUND
```

### 5.3 数据库约束失败：Prisma 错误

```text
create() 发现 slug 违反唯一约束
-> Promise 被拒绝，错误 code 为 P2002
-> Express 传递错误
-> errorHandler 识别 Prisma 错误和 P2002
-> 409 SLUG_CONFLICT
```

`update()` 或 `delete()` 找不到目标记录时，当前项目用 `P2025` 分支返回 404。

### 5.4 无法识别的错误：500 兜底

如果错误不属于当前已知分类，服务器记录完整错误，客户端只收到固定的 500：

```ts
console.error(error); // 输出到运行后端的终端，不会发给客户端

response.status(500).json({
  error: {
    code: "INTERNAL_ERROR",
    message: "服务器内部错误",
  },
});
```

`console.error(error)` 和 `response.json(...)` 去往两个不同地方：

- 运行后端的开发者可以在服务器终端中查看原始错误和堆栈，用来排查问题。
- 前端只收到固定的 `500 INTERNAL_ERROR`，不会收到 `console.error()` 打印的内容。

这样做是为了分开“服务器排错信息”和“对外 API 响应”。数据库连接信息、内部文件路径和错误堆栈对开发者有用，但不是前端处理请求失败所需要的 API 数据。

## 6. `isInvalidJsonError()` 为什么不只检查 `SyntaxError`

这一节只解决一个困惑：`isInvalidJsonError()` 为什么要连续检查 `SyntaxError`、`status` 和 `body`。Express 传来的错误是一个带有属性的对象，这些条件会共同判断它是不是“HTTP 请求体 JSON 解析失败”。

### 6.1 为什么非法 JSON 进不了 Zod

请求体要先经过：

```text
JSON 文本
-> express.json() 解析
-> 生成 request.body
-> Schema.parse(request.body) 检查请求体数据
```

如果客户端发送了少引号或大括号的 JSON，`express.json()` 在文章路由执行前就会失败。这时还没有可供 Zod 检查的 `request.body`。

```text
JSON 文本无法解析
-> 400 INVALID_JSON

JSON 可以解析，但请求数据不符合 Schema
-> 422 VALIDATION_ERROR
```

### 6.2 请求体解析错误长什么样

`express.json()` 使用的请求体解析器会为解析失败的错误增加信息。可以先把它的形状简化理解为：

```ts
{
  name: "SyntaxError",
  message: "...",
  status: 400,
  body: "原始请求体",
}
```

`name` 和 `message` 来自语法错误。`status` 和 `body` 不是所有 `SyntaxError` 都有的标准属性，它们是请求体解析错误携带的信息。

### 6.3 四个条件合起来在判断什么

```ts
function isInvalidJsonError(error: unknown) {
  return (
    error instanceof SyntaxError &&
    "status" in error &&
    error.status === 400 &&
    "body" in error
  );
}
```

整个条件可以读成：

```text
如果它是 SyntaxError，
并且有 status 属性，
并且 status 等于 400，
并且还携带 body，
就把它当成非法 JSON 错误。
```

`&&` 会从左到右检查。前一项不成立时，后面不再执行。所以代码先确认它是错误对象，再检查属性，不会一开始就读取未知值的 `status`。

`SyntaxError` 是一个比较宽泛的错误类型。项目在其他地方调用 `JSON.parse()` 等解析函数时，也可能产生 `SyntaxError`，但它们不一定与 HTTP 请求体有关。

继续检查 `status === 400` 和 `body` 不是判断另一种错误类型，而是把宽泛的 `SyntaxError` 缩小到“Express 解析 HTTP 请求体 JSON 失败”这个具体场景。

识别后，`errorHandler` 返回：

```ts
if (isInvalidJsonError(error)) {
  response.status(400).json({
    error: {
      code: "INVALID_JSON",
      message: "请求体不是合法的 JSON",
    },
  });
  return;
}
```

## 7. `app.ts` 中的 404 和 `errorHandler` 为什么走两条路

这段中间件注册顺序对应两种失败情况：

```ts
app.use(express.json());

// 在这里注册健康检查和文章路由

app.use((_request, response) => {
  response.status(404).json({
    error: {
      code: "ROUTE_NOT_FOUND",
      message: "接口不存在",
    },
  });
});

app.use(errorHandler);
```

### 情况 1：根本没有匹配到路由

例如请求了项目中不存在的地址：

```text
GET /api/abc
-> 前面没有路由匹配
-> 没有代码抛出 error
-> 继续走到 404 普通中间件
-> 404 ROUTE_NOT_FOUND
```

这个 404 只是“没找到对应接口”，不是某段代码运行失败，所以它是普通中间件。

### 情况 2：前面的步骤抛出了错误

```text
POST /api/articles
-> 文章路由已经匹配
-> Zod 或 Prisma 抛出错误
-> Express 进入错误流程
-> 跳过普通的 404 中间件
-> 寻找四参数 errorHandler
```

两者最关键的区别是：

| 情况 | 有没有 error | 谁返回响应 |
|---|---|---|
| 没有路由匹配 | 没有 | 404 普通中间件 |
| 请求处理过程抛错 | 有 | 四参数 `errorHandler` |

`errorHandler` 放在路由之后，是因为它要处理前面步骤产生的错误。

## 8. `headersSent`：响应已经开始后怎样处理错误

这段是个"安全阀"，专门处理一种情况：错误发生时，响应其实已经开始往外发了。

`response.headersSent` 是 Express/Node 自动维护的一个布尔值——只要你调用过 `response.status().json()`、`response.send()`，或者哪怕只是开始往响应流里写过字节，它就会变成 `true`。

问题在于：为什么"已经发送了"还会报错？举个例子，假设以后加了个流式接口，要把一个大文件慢慢传给客户端——先发出 200 状态码和响应头，开始一点点往外写数据，写到一半，读文件本身失败了（磁盘出错、网络中断之类）。这个错误照样会被传到 `errorHandler`，但这时候麻烦来了：状态码和头信息已经发给客户端了，没法"反悔"重发一个 500，也没法再塞一份新 JSON——硬要调用 `response.status(500).json(...)`，Node 会直接甩你一个新错误：`Cannot set headers after they are sent to the client`。

所以这里不是自己处理，而是交出去：

```ts
if (response.headersSent) {
  next(error);
  return;
}
```

- `next(error)`：不是交给你自己的 `errorHandler`（因为你已经在里面了），而是交给 **Express 内置的默认错误处理器**。它知道怎么安全地结束一个"已经开始、但半路出错"的连接——比如直接关闭它，而不会再尝试写一份完整的新响应。
- `return`：让函数在这里立刻结束，不要继续往下走到 JSON 解析错误、ZodError 那些判断。反正这个分支已经把权力交出去了，后面判断了也没意义。

对 Mini CMS 现在这种"只返回小 JSON"的接口来说，这个分支基本碰不到——响应要么完整发出去，要么在真正开始发送前就已经出错了。放着它，是为了万一以后加了流式或大文件接口，不至于在那种边界情况下让服务器崩掉，或者报出更难看的二次错误。

## 9. 现在把完整 `errorHandler` 放回一棵判断树

```text
errorHandler 收到 error
|
|-- response.headersSent 是否为 true？
|   |-- 是：响应头已发送，但响应可能尚未完成
|   |        因此不能再返回错误 JSON，只能调用 next(error)，
|   |        由 Express 内置错误处理器结束本次请求
|   `-- 否：响应头还没发送，继续判断错误类型
|
|-- 是不是 JSON 解析错误？
|   `-- 是：400 INVALID_JSON
|
|-- 是不是 ZodError？
|   `-- 是：422 VALIDATION_ERROR
|
|-- 是不是 AppError？
|   `-- 是：使用 AppError 携带的状态码和 code
|
|-- 是不是 Prisma 已知请求错误？
|   |-- P2002：409 SLUG_CONFLICT
|   `-- P2025：404 ARTICLE_NOT_FOUND
|
`-- 以上都不是：记录详细错误，返回 500 INTERNAL_ERROR
```

这棵树的主体只是“识别 -> 翻译 -> 结束请求”。`headersSent` 是最前面的安全保护，最后的 500 是没有识别成功时的兜底。

## 10. 用一次查询不存在文章的请求重建主线

Mini CMS 真实的文章详情路由使用 `:id`：

```ts
app.get("/api/articles/:id", async (request, response) => {
  const { id } = articleIdParamsSchema.parse(request.params);
  const article = await getArticleById(id);

  if (!article) {
    throw new AppError(
      404,
      "ARTICLE_NOT_FOUND",
      "文章不存在",
    );
  }

  response.json({ data: article });
});
```

现在请求一个不存在的正整数 ID：

```text
客户端请求 GET /api/articles/999999
-> Express 匹配文章详情路由
-> articleIdParamsSchema 把 id 转成数字并校验通过
-> getArticleById() 调用 Prisma findUnique()
-> findUnique() 查不到记录，返回 null
-> 路由判断 article 为空，主动 throw new AppError(...)
-> Express 5 把 AppError 传给 errorHandler
-> errorHandler 识别 AppError，读取它携带的状态码和 code
-> 客户端收到 404 ARTICLE_NOT_FOUND
```

`findUnique()` 返回 `null` 只表示“没有数据”，它没有抛出错误。路由需要把这个查询结果转成 API 的 `404`，`AppError` 就是“查不到数据”和“返回稳定错误响应”之间的桥。

在这一次请求中，每个对象的职责已经可以分开：

| 对象 | 这次做了什么 |
|---|---|
| Zod | 校验并转换路径参数 `id` |
| Prisma | 查询数据库并返回 `null`，没有产生 Prisma 错误 |
| 路由 | 把 `null` 判断为“文章不存在”，抛出 `AppError` |
| Express | 把异步路由抛出的 `AppError` 传给错误中间件 |
| `errorHandler` | 把 `AppError` 翻译成 `404 ARTICLE_NOT_FOUND` |

现在回到第 11 章，再完成三步：

```text
创建 app-error.ts
-> 创建完整 error-handler.ts
-> 在 app.ts 的路由和 404 之后注册 errorHandler
```
