# 11A. 错误处理中间件：一段代码怎样接住不同错误

> 这是第 11 章第 5～6 节的配套概念章。它不增加新功能，专门解释 `app-error.ts` 和 `error-handler.ts` 为什么要这样设计。

## 先建立错误处理的整体概念

正常请求只需要把查询结果返回给客户端。失败请求更复杂，因为错误可能来自请求流程的不同位置：

```text
express.json() 解析 JSON 失败
Zod 发现字段不合法
路由发现文章不存在
Prisma 发现 slug 重复
数据库断开或程序出现未知异常
```

这些错误的形状不一样，但客户端需要稳定的 HTTP 状态码和 JSON。因此 Mini CMS 使用这条主线：

```text
请求流程的某一步产生错误对象
-> Express 把错误传递给 errorHandler
-> errorHandler 识别错误类型
-> 把内部错误翻译成统一 HTTP 响应
```

所以，错误处理不是 `errorHandler` 主动去各个文件“收集”错误。更准确的理解是：

- Zod、路由和 Prisma 负责发现或产生错误。
- Express 负责把这些错误送到错误中间件。
- `errorHandler` 负责分类和返回响应。

当前实现中的三个核心文件各有一个职责：

| 文件 | 职责 | 不负责什么 |
|---|---|---|
| `app-error.ts` | 定义一种能携带状态码和 code 的业务错误 | 不返回 HTTP 响应 |
| `error-handler.ts` | 识别不同错误，转成统一响应 | 不执行文章 CRUD |
| `app.ts` | 注册路由和错误中间件，让整条流程连起来 | 不重复定义错误分类规则 |

读完这篇，不要求背下完整 `errorHandler`。只要能顺着“产生错误 -> 传递错误 -> 翻译错误”说清两个文件的分工，就建立了主线。

## 1. 为什么路由里没有写 try/catch

先说结论：`try/catch` 没有被废弃。只是在当前 Express 5 项目中，如果 `catch` 只为了把错误交给 Express，就不需要在每个异步路由里重复编写。

可以手动写成：

```ts
app.post("/api/articles", async (request, response, next) => {
  try {
    const input = createArticleSchema.parse(request.body);
    const article = await createArticle(input);

    response.status(201).json({ data: article });
  } catch (error) {
    next(error);
  }
});
```

这里的 `catch` 没有处理错误，只做了一件事：

```text
接住 error
-> next(error) 把它交给 Express
```

Express 5 已经会自动传递 `async` 路由里抛出的错误和被拒绝的 Promise。因此当前路由可以保持为：

```ts
app.post("/api/articles", async (request, response) => {
  const input = createArticleSchema.parse(request.body);
  const article = await createArticle(input);

  response.status(201).json({ data: article });
});
```

这段代码中：

```text
Schema.parse() 抛出 ZodError
或 createArticle() 返回的 Promise 失败
-> Express 5 内部按 next(error) 处理
-> errorHandler 收到错误
```

如果每个路由都在 `catch` 里直接返回 JSON，不同路由就容易出现不同的状态码、code 和文案。这正是当前项目要避免的重复。

`try/catch` 仍然有用，例如错误发生后需要恢复、补充上下文或把它转成另一种错误。当前 Mini CMS 的路由只需要把错误继续向后传，所以先交给 Express 5 和统一错误中间件。

## 2. 先认识 JavaScript 的错误对象

### 2.1 Error 也是一个对象

代码出错时，传递的不只是一句错误文案，而是一个描述错误的对象。

```ts
const error = new Error("文章不存在");
```

可以先认识三个常见属性：

```text
error.name
-> 错误名称，默认是 Error

error.message
-> 创建错误时传入的文案

error.stack
-> 错误堆栈，用来定位错误发生在哪里
```

`Error` 只提供通用信息。不同库会定义自己的错误类，再增加当前场景需要的属性：

| 错误对象 | 额外的关键信息 |
|---|---|
| `ZodError` | `issues` 保存字段错误 |
| `PrismaClientKnownRequestError` | `code` 保存 `P2002` 等 Prisma 错误码 |
| `AppError` | `statusCode` 和 `code` 保存项目自己定义的响应信息 |

因此 `errorHandler` 收到错误后，不是只读取 `message`，而是先判断它是哪一种错误对象。

### 2.2 instanceof 在检查“它是哪种错误”

```ts
if (error instanceof AppError) {
  // 这个分支里才按 AppError 使用 error
}
```

`instanceof AppError` 可以先理解成：

```text
这个 error 是不是通过 AppError 创建的，
或者它是不是 AppError 的子类对象？
```

答案为真时，TypeScript 也知道它是 `AppError`，于是允许代码读取 `error.statusCode` 和 `error.code`。

### 2.3 in 在检查“它有没有这个属性”

```ts
"status" in error
```

这句不检查 `status` 的具体值，只是询问：“`error` 对象上有没有 `status` 属性？”

所以下面两步的职责不同：

```ts
"status" in error
// 先确认属性存在

error.status === 400
// 再检查它的值
```

### 2.4 为什么还会出现 unknown

JavaScript 甚至允许抛出字符串或其他值。第三方库传来的错误形状也不一定相同。

当前 `@types/express` 中，`ErrorRequestHandler` 的 `error` 参数是宽松的 `any`。但 `isInvalidJsonError()` 把参数明确改成更安全的 `unknown`，表示：

```text
现在还不知道 error 的具体形状
-> 不能一上来就随意读取属性
-> 必须先用 instanceof 或 in 进行检查
```

这不是多余的代码，而是在提醒我们：别把一个还没识别的值当成某种确定错误来用。

## 3. app-error.ts 的设计：描述项目自己的业务错误

内置 `Error` 可以表达“文章不存在”，但它不知道 Mini CMS 的 HTTP 约定：

```text
应该返回哪个 HTTP 状态码？
应该返回哪个稳定 code？
```

因此项目定义 `AppError`：

```ts
export class AppError extends Error {
  constructor(
    public statusCode: number,
    public code: string,
    message: string,
  ) {
    super(message);
    this.name = "AppError";
  }
}
```

这段代码可以分成两层理解。

第一层，它仍然是错误：

```text
extends Error
-> AppError 继承内置 Error

super(message)
-> 让 Error 保存 message 和错误堆栈
```

第二层，它增加了 Mini CMS 需要的信息：

```text
public statusCode
-> TypeScript 同时创建属性，并保存传入的状态码

public code
-> 同时创建属性，并保存传入的稳定错误 code
```

路由中创建它：

```ts
throw new AppError(
  404,
  "ARTICLE_NOT_FOUND",
  "文章不存在",
);
```

可以把抛出的对象简化理解为：

```ts
{
  name: "AppError",
  statusCode: 404,
  code: "ARTICLE_NOT_FOUND",
  message: "文章不存在",
  // 还有供服务器排错的 stack
}
```

`AppError` 的设计重点是“携带信息”，它自己不发送响应。路由只需要说明发生了什么，至于错误 JSON 怎样返回，由 `errorHandler` 统一决定。

## 4. error-handler.ts 的设计：把错误翻译成 HTTP 响应

### 4.1 ErrorRequestHandler 只是 Express 提供的 TypeScript 类型

最小错误中间件可以写成：

```ts
import type { ErrorRequestHandler } from "express";

export const errorHandler: ErrorRequestHandler = (
  error,
  _request,
  response,
  _next,
) => {
  console.error(error);

  response.status(500).json({
    error: {
      code: "INTERNAL_ERROR",
      message: "服务器内部错误",
    },
  });
};
```

`ErrorRequestHandler` 的作用是告诉 TypeScript：

```text
这个函数要按 Express 错误中间件的形状使用
-> 第 1 个参数是 error
-> 后面是 request、response、next
-> response 和 next 获得 Express 的类型提示
```

它不会主动运行函数，也不会主动抓取错误。真正让这个函数进入 Express 流程的是：

```ts
app.use(errorHandler);
```

Express 错误中间件必须保留四个参数：

```text
(error, request, response, next)
```

即使暂时没有使用 `request` 或 `next`，也要保留它们。`_request` 和 `_next` 的下划线只表示“当前没有使用这个参数”。

### 4.2 为什么 errorHandler 里面有很多 if

只返回 500 虽然已经能结束失败请求，但会把标题为空、slug 重复和数据库断开都当成同一种错误。

`errorHandler` 中的多个 `if` 实际上是一个翻译器：

| 识别到的错误 | 翻译后的响应 |
|---|---|
| JSON 解析错误 | `400 INVALID_JSON` |
| `ZodError` | `422 VALIDATION_ERROR` |
| `AppError` | 使用它自己携带的状态码和 code |
| Prisma `P2002` | `409 SLUG_CONFLICT` |
| Prisma `P2025` | `404 ARTICLE_NOT_FOUND` |
| 以上都不是 | `500 INTERNAL_ERROR` |

例如 `AppError` 分支：

```ts
if (error instanceof AppError) {
  response.status(error.statusCode).json({
    error: {
      code: error.code,
      message: error.message,
    },
  });
  return;
}
```

这段代码做了三件事：

```text
确认这是 AppError
-> 读取它携带的信息
-> 结束这次失败请求
```

返回 JSON 后立即 `return`，是为了结束 `errorHandler`，避免同一个错误继续走到后面的 500 分支。

### 4.3 每种错误从哪里来

```text
createArticleSchema.parse(request.body)
-> 字段错误时抛出 ZodError

throw new AppError(...)
-> 路由主动创建项目业务错误

Prisma create() / update() / delete()
-> 数据库操作失败时拒绝 Promise，并可能携带 Prisma 错误码
```

`errorHandler` 不关心这些错误是在哪个路由产生的。它只根据错误对象的类型和属性决定响应。

## 5. 四种主要错误怎样进入各自分支

### 5.1 字段错误进入 ZodError 分支

```ts
const input = createArticleSchema.parse(request.body);
```

标题为空时，`.parse()` 抛出 `ZodError`。`error.issues` 保存字段位置和错误文案，`errorHandler` 再把它转成 `details`。

```text
ZodError.issues
-> 取出每项的 path 和 message
-> 生成给前端使用的 details
-> 422 VALIDATION_ERROR
```

### 5.2 查询不到文章进入 AppError 分支

`findUnique()` 查询不到数据时返回 `null`，没有错误对象可以传递。因此路由主动创建 `AppError`：

```text
findUnique() 返回 null
-> 路由 throw new AppError(...)
-> Express 传递错误
-> errorHandler 识别 AppError
-> 404 ARTICLE_NOT_FOUND
```

### 5.3 数据库约束错误进入 Prisma 分支

```text
create() 发现 slug 违反唯一约束
-> Promise 被拒绝，错误 code 为 P2002
-> Express 传递错误
-> errorHandler 识别 Prisma 错误和 P2002
-> 409 SLUG_CONFLICT
```

`update()` 或 `delete()` 找不到目标记录时，当前项目用 `P2025` 分支返回 404。

### 5.4 未识别错误进入 500 兜底

如果错误不属于当前已知分类，服务器记录完整错误，客户端只收到固定的 500：

```ts
console.error(error);

response.status(500).json({
  error: {
    code: "INTERNAL_ERROR",
    message: "服务器内部错误",
  },
});
```

这样既能在服务器排查原因，又不会把数据库地址、文件路径和错误堆栈直接暴露给客户端。

## 6. isInvalidJsonError() 到底在检查什么

这一节的难点不是 Zod，而是“错误也是对象”。

### 6.1 非法 JSON 甚至进不了文章路由

请求体要先经过：

```text
JSON 文本
-> express.json() 解析
-> 生成 request.body
-> Schema.parse(request.body) 检查字段
```

如果客户端发送了少引号或大括号的 JSON，`express.json()` 在文章路由执行前就会失败。这时还没有可供 Zod 检查的 `request.body`。

```text
JSON 文本无法解析
-> 400 INVALID_JSON

JSON 可以解析，但字段不符合 Schema
-> 422 VALIDATION_ERROR
```

### 6.2 JSON 解析错误对象有哪些信息

`express.json()` 使用的请求体解析器会为解析失败的错误增加信息。可以先把它的形状简化理解为：

```ts
{
  name: "SyntaxError",
  message: "...",
  status: 400,
  body: "原始请求体",
}
```

`name` 和 `message` 来自语法错误。`status` 和 `body` 不是所有 `SyntaxError` 都有的标准属性，它们是请求体解析错误携带的信息。

### 6.3 把辅助函数读成一句话

```ts
function isInvalidJsonError(error: unknown) {
  return (
    error instanceof SyntaxError &&
    "status" in error &&
    error.status === 400 &&
    "body" in error
  );
}
```

先不逐行读语法，把整个条件读成：

```text
如果它是 SyntaxError，
并且有 status 属性，
并且 status 等于 400，
并且还携带 body，
就把它当成非法 JSON 错误。
```

`&&` 会从左到右检查。前一项不成立时，后面不再执行。所以代码先确认它是错误对象，再检查属性，不会一开始就读取未知值的 `status`。

之所以不只检查 `error instanceof SyntaxError`，是因为项目在其他地方调用 `JSON.parse()` 等解析函数时，也可能产生 `SyntaxError`。继续检查 `status` 和 `body`，才更像“请求体无法解析”这个具体场景。

识别后，`errorHandler` 返回：

```ts
if (isInvalidJsonError(error)) {
  response.status(400).json({
    error: {
      code: "INVALID_JSON",
      message: "请求体不是合法的 JSON",
    },
  });
  return;
}
```

## 7. app.ts 中的 404 和 errorHandler 是两条不同流程

不再用“两个出口”来理解这段代码。只需区分两种失败情况：

```ts
app.use(express.json());

// 在这里注册健康检查和文章路由

app.use((_request, response) => {
  response.status(404).json({
    error: {
      code: "ROUTE_NOT_FOUND",
      message: "接口不存在",
    },
  });
});

app.use(errorHandler);
```

### 情况 1：根本没有匹配到路由

例如请求了项目中不存在的地址：

```text
GET /api/abc
-> 前面没有路由匹配
-> 没有代码抛出 error
-> 继续走到 404 普通中间件
-> 404 ROUTE_NOT_FOUND
```

这个 404 只是“没找到对应接口”，不是某段代码运行失败，所以它是普通中间件。

### 情况 2：前面的步骤抛出了错误

```text
POST /api/articles
-> 文章路由已经匹配
-> Zod 或 Prisma 抛出错误
-> Express 进入错误流程
-> 跳过普通的 404 中间件
-> 寻找四参数 errorHandler
```

两者最关键的区别是：

| 情况 | 有没有 error | 谁返回响应 |
|---|---|---|
| 没有路由匹配 | 没有 | 404 普通中间件 |
| 请求处理过程抛错 | 有 | 四参数 `errorHandler` |

`errorHandler` 放在路由之后，是因为它要处理前面步骤产生的错误。

## 8. headersSent 是一个少见的保护分支

这不是当前 Mini CMS 错误处理的主线。第一次只要先记住结论：

```text
响应已经开始发送
-> 不能再改状态码或发送另一份错误 JSON
-> 把错误继续交给 Express 默认错误处理
```

### 8.1 为什么响应开始发送后还可能出错

一次响应不一定总是一次性写完。例如以后输出大文件或流式数据时，可能已经发送了前面一部分，后面的读取又失败了：

```text
开始发送状态码、响应头和部分数据
-> 后续读取或输出过程失败
-> 错误仍然会进入 errorHandler
```

此时 `response.headersSent` 为 `true`。状态码和响应头已经发给客户端，自定义错误中间件不能再执行：

```ts
response.status(500).json({ /* ... */ });
```

否则相当于尝试为同一次请求再发一份新响应。

### 8.2 next(error) 不是又发送一份错误 JSON

```ts
if (response.headersSent) {
  next(error);
  return;
}
```

这里的 `next(error)` 表示：

```text
当前自定义 errorHandler 已经无法安全返回 JSON
-> 把错误继续传给 Express 默认错误处理
-> 由 Express 结束或关闭这次已经失败的响应
```

所以“已经发送了，为什么还有 error”的答案是：发送可能只是已经开始，后续过程仍可能失败。`next(error)` 不是再次响应，而是在自定义中间件无法处理时交还给 Express。

当前 Mini CMS 返回的主要是小型 JSON，很少遇到这种情况。保留这个分支，是为了避免未来响应已经开始后又重复发送错误响应。

## 9. 现在再读完整 errorHandler 判断树

```text
errorHandler 收到 error
|
|-- 响应是否已经开始发送？
|   |-- 是：不再返回 JSON，next(error) 交给 Express 默认错误处理
|   `-- 否：继续判断
|
|-- 是不是 JSON 解析错误？
|   `-- 是：400 INVALID_JSON
|
|-- 是不是 ZodError？
|   `-- 是：422 VALIDATION_ERROR
|
|-- 是不是 AppError？
|   `-- 是：使用 AppError 携带的状态码和 code
|
|-- 是不是 Prisma 已知请求错误？
|   |-- P2002：409 SLUG_CONFLICT
|   `-- P2025：404 ARTICLE_NOT_FOUND
|
`-- 以上都不是：记录详细错误，返回 500 INTERNAL_ERROR
```

这棵树的主体只是“识别 -> 翻译 -> 结束请求”。`headersSent` 是最前面的安全保护，最后的 500 是没有识别成功时的兜底。

## 10. 用一次 slug 重复请求重建全文主线

```text
客户端提交创建文章请求
-> express.json() 把 JSON 文本解析成 request.body
-> Zod 校验通过
-> Prisma create() 发现 slug 重复，产生 P2002 错误
-> async 路由返回的 Promise 失败
-> Express 5 把错误传给 errorHandler
-> errorHandler 识别 Prisma 错误和 P2002
-> 客户端收到 409 SLUG_CONFLICT
```

在这条流程中：

- Prisma 产生错误对象。
- Express 传递错误。
- `errorHandler` 翻译错误。
- `AppError` 没有参与这次请求，它专门表达路由主动发现的业务错误。

最后再记住五个结论：

```text
AppError
-> 一种能携带项目错误信息的 Error

errorHandler
-> 把不同错误翻译成统一 HTTP 响应

ErrorRequestHandler
-> 描述 Express 错误中间件形状的 TypeScript 类型

404 普通中间件
-> 处理“没有路由匹配”，它没有收到 error

headersSent 分支
-> 响应已经开始后不再重复返回 JSON
```

现在回到第 11 章，再完成三步：

```text
创建 app-error.ts
-> 创建完整 error-handler.ts
-> 在 app.ts 的路由和 404 之后注册 errorHandler
```
