# 05. 异步和错误：失败怎样沿请求流程传下去

## 问题背景

读取变量通常立刻完成，但网络请求、文件读取和数据库查询都需要等待。

后端的大量代码都是：

```text
等待某个外部结果
-> 成功后继续
-> 失败时交给统一错误处理
```

本章只建立异步和错误传播的基本模型：先看懂 `await`、`throw` 和错误中间件怎样连起来。接口应该返回什么错误结构由第 06 章约定；`AppError`、Prisma 错误码和完整错误中间件放到第 10 章实现。

---

## 异步结果和错误怎样进入同一条流程

### 1. 为什么后端操作经常是异步的

Express 和 PostgreSQL 是两个不同进程。执行 SQL 时，Node.js 要等待数据库返回结果。

Promise 可以先理解成“稍后才会得到的结果”：操作成功时得到数据，操作失败时得到错误。

```ts
const article = await findArticle(articleId);
```

`await` 不是让整个服务器停止，而是让当前异步函数等待 Promise 的结果。

这里先把 `findArticle()` 理解成“需要等待的查询函数”。它怎样真正查询数据库，会在第 09 章展开。

### 2. `async` 函数会返回 Promise

```ts
async function getArticleTitle(id: number) {
  const article = await findArticle(id);
  return article.title;
}
```

调用方也需要等待：

```ts
const title = await getArticleTitle(1);
```

### 3. 业务错误和系统错误不同

```text
业务错误
-> 文章不存在、slug 重复、操作不符合规则

系统错误
-> 数据库断开、代码异常、配置缺失
```

同一种业务错误应该始终返回相同状态码和可理解信息；未知系统错误通常返回 500，并在服务器记录细节。

## 错误为什么要汇到一个出口

业务代码发现问题时，可以先停止当前流程并抛出错误：

```ts
if (!article) {
  throw new Error("文章不存在");
}
```

这里的 `Error` 只用来演示“抛出后停止当前流程”，还不是最终项目里的错误设计。如果每个 route 都自己决定状态码和 JSON，相同错误很容易返回不同结果。因此，错误通常会汇到同一个出口：

```text
文章 route 抛错 ─┐
标签 route 抛错 ─┴-> 同一个错误处理中间件 -> 统一 HTTP 响应
```

现阶段先记住职责关系：

```text
业务代码
-> 发现问题并抛出错误

Express
-> 把错误继续传递

错误处理中间件
-> 决定怎样结束这次 HTTP 请求
```

具体怎样给错误添加状态码、稳定的 code 和安全的 message，第 10 章再完整实现。

## Express 5 中的异步错误

Express 5 可以把异步 route handler 中抛出的错误或被拒绝的 Promise 交给错误处理中间件：

```ts
articleRouter.get("/:id", async (request, response) => {
  const article = await findArticle(Number(request.params.id));

  if (!article) {
    throw new Error("文章不存在");
  }

  response.json({ data: article });
});
```

这里仍然只是演示错误传播，不代表最终接口应该直接返回 `Error` 的文案。正式项目会在第 10 章把这类错误转换成稳定的 HTTP 状态码和 JSON。

如果维护旧 Express 项目，需要先确认它使用的版本和异步错误写法。

## 放进文章接口中理解

- 查询文章时等待 PostgreSQL。
- 创建文章时，slug 已经存在属于可以预期的失败。
- 查询不到文章属于可以预期的失败。
- 数据库断开属于系统错误。
- 不同 route 抛出的错误最终进入同一个处理出口。

本章先识别这些失败类型。它们分别应该返回什么状态码和 JSON，由第 06 章建立约定；怎样识别 Prisma 错误并真正返回这些结果，由第 10 章实现。

## 小结

后端不只处理成功流程。

```text
await
-> 等 Promise 得到结果后，再继续执行后面的代码

throw
-> 停止当前处理，把错误交给错误中间件

业务错误
-> 可以预期的失败，例如文章不存在或 slug 重复

未知错误
-> 程序没有预料到的失败，对客户端统一返回 500

错误中间件
-> 统一结束失败请求；具体响应设计在第 06、10 章继续展开
```

错误路径清楚，接口才算真正可用。
