# 05. 异步和错误：数据库不会立刻返回结果

## 问题背景

读取变量通常立刻完成，但网络请求、文件读取和数据库查询都需要等待。

后端的大量代码都是：

```text
等待某个外部结果
-> 成功后继续
-> 失败时交给统一错误处理
```

---

## 异步结果和错误怎样进入同一条流程

### 1. 为什么后端操作经常是异步的

Express 和 PostgreSQL 是两个不同进程。执行 SQL 时，Node.js 要等待数据库返回结果。

```ts
const article = await findArticle(articleId);
```

`await` 不是让整个服务器停止，而是让当前异步函数等待 Promise 的结果。

这里先把 `findArticle()` 理解成“需要等待的查询函数”。它怎样通过 `pg` 执行 SQL，会在第 10 章再展开。

### 2. `async` 函数会返回 Promise

```ts
async function getArticleTitle(id: number) {
  const article = await findArticle(id);
  return article.title;
}
```

调用方也需要等待：

```ts
const title = await getArticleTitle(1);
```

### 3. 业务错误和系统错误不同

```text
业务错误
-> 文章不存在、slug 重复、没有登录

系统错误
-> 数据库断开、代码异常、配置缺失
```

同一种业务错误应该始终返回相同状态码和可理解信息；未知系统错误通常返回 500，并在服务器记录细节。

---

## 统一错误处理

可以先定义一个带状态码的错误：

```ts
class AppError extends Error {
  constructor(
    public statusCode: number,
    public code: string,
    message: string,
  ) {
    super(message);
  }
}
```

业务代码抛出错误：

```ts
if (!article) {
  throw new AppError(404, "ARTICLE_NOT_FOUND", "文章不存在");
}
```

最后由错误处理中间件统一返回：

```ts
app.use((error, _request, response, _next) => {
  const statusCode = error.statusCode ?? 500;

  response.status(statusCode).json({
    error: {
      code: error.code ?? "INTERNAL_ERROR",
      message: statusCode === 500 ? "服务器内部错误" : error.message,
    },
  });
});
```

错误处理中间件必须保留 `error、request、response、next` 四个参数，Express 才会把它识别成错误处理函数。示例中的 `_request` 和 `_next` 仍然是 request 和 next，只是下划线表示当前函数没有使用它们；这不是新的 Express 语法。

错误处理中间件通常注册在所有路由之后。

“统一处理”是指各个 route 只负责抛出或传递错误，最后都由同一个错误中间件决定状态码和 JSON 格式：

```text
文章 route 抛错 ─┐
标签 route 抛错 ─┼-> 同一个错误处理中间件 -> 统一 HTTP 响应
登录 route 抛错 ─┘
```

如果每个 route 都自己写一套 `try/catch` 和 `response.status(...).json(...)`，代码会大量重复，而且很容易出现同一种错误在不同接口中返回不同格式。只有当当前函数能补充信息、把错误转换成已知情况或真正恢复流程时，才需要在这里单独 `catch`。

---

## Express 5 中的异步错误

当前 Express 5 可以把异步 route handler 中抛出的错误或被拒绝的 Promise 交给错误处理中间件：

```ts
articleRouter.get("/:id", async (request, response) => {
  const article = await findArticle(Number(request.params.id));

  if (!article) {
    throw new AppError(404, "ARTICLE_NOT_FOUND", "文章不存在");
  }

  response.json({ data: article });
});
```

如果维护旧 Express 项目，需要先确认它使用的版本和异步错误写法。

---

## 放进文章接口中理解

- 查询文章时等待 PostgreSQL。
- 创建文章时，如果 slug 已经存在，数据库会拒绝保存；后端收到这个错误后，向前端返回 409 和明确提示。
- 未找到文章时返回 404。
- 数据库故障时记录错误并返回 500。
- 所有模块共用一种错误结构。

---

## 小结

后端不只处理成功流程。

```text
await
-> 等 Promise 得到结果后，再继续执行后面的代码

throw
-> 停止当前处理，把错误交给错误中间件

业务错误
-> 可以预期的失败，例如文章不存在或 slug 重复

未知错误
-> 程序没有预料到的失败，对客户端统一返回 500

错误中间件
-> 统一决定状态码和 JSON，不向客户端暴露服务器内部细节
```

错误路径清楚，接口才算真正可用。
