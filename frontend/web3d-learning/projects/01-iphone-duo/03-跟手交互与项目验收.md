# 03. 让拖动跟手，让切换顺滑

“顺滑”至少有两件事：每帧都按时画出来，以及动作本身连续。“跟手”还要求输入到画面的延迟小。高帧率并不能抵消过大的拖尾，增加阻尼也不能修复渲染掉帧。

## 第一步：从浏览器事件读到运动状态

先读 [use-product-drag.ts](./components/use-product-drag.ts)。它负责浏览器事件与指针捕获；计算放在 [drag-motion.ts](./lib/drag-motion.ts)。这让代码的输入和输出容易追踪，也能在不启动浏览器时检查运动边界。

```text
pointerdown → beginDrag：从当前显示角度接管，取消残余惯性
pointermove → moveDrag：像素增量换成目标角度，估计速度
useFrame    → stepDrag：计算这一帧的角度 → turn.rotation
pointerup   → endDrag：预测停点 → 水平惯性 → 角度吸附；俯仰回正
cancel / lost capture → endDrag：清除速度，结束手势
```

`useProductDrag()` 返回 `input`、`handlers`、`reset`。product-demo 把 handlers 交给画布容器，把 input 交给场景；姿态按钮调用 reset。hook 不需要知道模型名称，运动函数也不依赖 DOM。

捕获指针后，用户按住拖出画布仍可继续收到本次事件；释放和取消都要结束状态。`pointerId` 用于确认事件属于当前手势。普通松手后主动释放捕获，此后到达的 lost capture 因指针已结束而被忽略，避免把刚建立的惯性误取消。[Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)

核心换算来自 moveDrag：

```ts
const dyaw = (x - state.x) / width * config.radiansPerWidth;
state.targetYaw += dyaw;
```

x、y 是当前指针像素位置，width、height 是画布的 CSS 尺寸。先把移动距离换成画布比例，再换成弧度。之后记录当前 x、y，下一次只累计新的增量。它不乘 DPR，因为 DOM 指针坐标与 CSS 尺寸本来就是同一单位。

DragState 中最重要的三组量：

| 字段 | 表示什么 | 谁写入 |
|---|---|---|
| targetYaw / targetPitch | 手势希望到达的角度 | moveDrag、惯性积分、resetDrag |
| yaw / pitch | 当前显示的角度 | stepDrag |
| velocityYaw | 最近输入的水平角速度，单位弧度/秒 | moveDrag 估计，stepDrag 衰减或交给吸附弹簧 |
| velocityPitch | 俯仰回正时的弹簧速度 | 松手清零，stepDrag 更新 |
| snapTarget / snapping | 本次停靠目标、是否进入吸附 | endDrag 选择，stepDrag 执行 |

**动手**：在 viewer-config.ts 把 radiansPerWidth 从 `Math.PI * 1.6` 改成 `Math.PI`。相同相对位移旋转更少。恢复后再修改 followRate，区分“灵敏度”和“追随速度”。

## 第二步：跟手、缓停、限位如何共同工作

所有参数都在 [viewer-config.ts](./lib/viewer-config.ts) 的 motionConfig 中：

| 参数 | 当前值 | 增大后会怎样 |
|---|---:|---|
| followRate | 32 | 更快追上指针目标，拖尾更短 |
| inertiaDecay | 4.2 | 松手后更快停下 |
| maxVelocity | 8 | 允许更快甩动；一般先保持限制 |
| pitchLimit | π/12 | 上下可转范围扩大；当前各 15° |
| pitchReturnRate | 12 | 松手后更快回正 |
| snapStep / snapThreshold | 45° / 25° | 分别控制停靠间隔、捕获范围 |
| snapRate | 10 | 更快收敛到停靠角度 |
| resetRate | 14 | 更快复位 |
| poseRate | 12 | 更快切换骨骼姿态、中心和展示朝向 |

当前 yaw 允许水平整圈旋转；按住时 pitch 在目标值和实际值两处限位；松手后由弹簧回到 0，不保留上下倾斜。限位作用于**相对预设的用户微调**，不禁止“纵向展开”配置本身的整机旋转。

到达俯仰边界后不继续积累看不见的距离，因此反向一点就能离开边界。上下回正独立于水平旋转，既不会把水平角度强行拉回正面，也不会翻转手机。

### 按住时快速追随

stepDrag 用以下指数追随计算当前值：

```ts
target + (value - target) * Math.exp(-rate * dt)
```

rate 是每秒的追随速率，dt 是本帧秒数。比每帧固定 `lerp(..., 0.1)` 更不依赖刷新率。基线保留很短的追随过程，用于缓和输入采样跳动；它不是“阻尼越大越好”。拖动觉得迟钝，优先提高 followRate、检查帧耗时，不要无限加惯性。

### 松手后短距离缓停

moveDrag 根据角度增量除以事件间隔估计速度，并做过滤和速度上限。松手时把速度逐渐衰减：

```ts
const decay = Math.exp(-config.inertiaDecay * dt);
const distance = (1 - decay) / config.inertiaDecay;
state.targetYaw += state.velocityYaw * distance;
state.velocityYaw *= decay;
```

distance 是衰减速度在本帧内的积分系数。这样相同的松手速度在 30、60、120 Hz 下会有接近的总位移。若按住停稳超过 120 ms 再松手，则清除水平速度，不应该突然甩一下。重复的零位移事件不覆盖最后一次真实移动速度。浏览器取消手势时不继续惯性，也不启动吸附。

### 从惯性过渡到固定角度

endDrag 先用 `targetYaw + velocityYaw / inertiaDecay` 预测自然停点，再选 25° 范围内最近的 45° 停靠点。这个目标只在松手时选一次，避免运动中左右抢目标。水平速度低于 snapStartVelocity 后，stepDrag 把当前角度和速度交给临界阻尼弹簧，缓慢落到准确角度。

“先惯性，再吸附”和“一松手立即拉到最近角度”的手感不同。再次按住时 beginDrag 清空停靠目标，从当前画面接管。上下回正使用同一种弹簧，目标固定为 0。

官网公开的角度配置包含正背面、四个斜角和两侧视角，阈值为 25°。本项目将侧视角的小幅俯仰简化为水平，并使用自己的按秒积分参数；这部分是根据参考行为重建，不是移植原站控制器。[参考配置](https://www.apple.com/v/iphone-duo/f/static//uploads/dIFKSKvliUSYOBw/dOKLAkGZzJBEnNO/gVFBvbhWgzeMQqC/nlwxXusRyVVeHtf/zvCJxGMnsidyZFI.lsd)

### 自动运动被手势接管

按姿态按钮时 resetDrag 把目标偏移归零，preset 朝向重新开始过渡。复位选最近的一圈正面，不会因之前转过几圈而倒转很久。

开始拖动时，beginDrag 从**当前显示角度**继续，并将 allowPoseTurn 设为 false。预设朝向停止自动转动，内部折叠动画可以继续完成；两者分别写不同 group。再按姿态或复位按钮，恢复预设控制。

这里不同时启用 OrbitControls。当前是固定相机、旋转产品；OrbitControls 通常让相机绕目标运动。需要改成交互相机时，应重新确定控制权，避免两套输入同时改变视图。

这些连续量放在 ref，useFrame 更新 Three.js 对象；React state 只表示选中的业务状态。[R3F Performance pitfalls](https://r3f.docs.pmnd.rs/advanced/pitfalls)

**检查点**：反复向下拖不会翻到背面；到边界反向拖立刻响应；甩动后继续旋转再吸附；上下松手回正；停稳再松手不甩动，但可以缓慢靠向附近停靠点；复位中重新拖动不跳变。

## 第三步：保留手机的页面滚动

基线给展示容器设 `touch-action: pan-y`。手机横向拖动旋转，纵向手势交给页面；触摸输入不再控制俯仰。桌面鼠标可以横向旋转，纵向只在各 15° 内微调。

这是此练习明确选择的手势规则。不要在整个页面设置 `touch-action: none`，否则用户可能被困在一大片画布上无法滚动。全方向触摸旋转更适合用户主动进入的全屏展示，再在那里处理退出与缩放。

这一项必须真机验证，桌面拖动与调整浏览器窗口不能证明触摸冲突已经解决。至少测试：横向转动、纵向滚动、斜向起手、拖到边界、系统打断后返回。

## 第四步：用对照把画面拉近参考

已有基线证明开发流程可运行。继续达到参考方向时，按下面顺序推进，每次保留前后截图。

1. **构图**：固定横向展开视角，对照轮廓大小、留白和透视；只改相机或取景配置。
2. **反射**：固定相机，调 Lightformer 的面积、方向和明暗，让边框亮条连续；先不加 Bloom。
3. **材质**：逐个确认主要材质的颜色、metalness、roughness、normal 和 clearcoat。需要单独修改时复制该材质，保留其已有贴图。
4. **屏幕**：分别替换 `screen-inner.png` 与 `screen-outer.png`，保持各自图片比例和 UV 方向。当前是公开图层的静态合成，不含官网动态壁纸的 Shader、LUT 与视差。
5. **运动**：记录按钮过渡和拖动灵敏度，对比快切、短拖、长拖与逆向操作。

不必同时复刻全部官网效果。先让这四个姿态在相同环境里稳定成立，再增加 Standing。Durability 如果需要独立展示结构或动画，必须先确认资产中是否存在对应数据，不能给一个新按钮随便绑定 `Slider` 就算完成。

材质差异较大时回 [材质与色彩校准](../../04-材质灯光与色彩校准.md)。由于源站专用材质扩展和场景配置未移植，这份基线不承诺逐像素一致；对差异要能指出原因，并选择重建或替代方案。

## 第五步：找到实际的性能瓶颈

先保留当前连续渲染，确认功能，再做性能实验。模型文件小，既不代表纹理显存小，也不代表每帧便宜。

| 症状 | 先看什么 | 有意义的实验 |
|---|---|---|
| 第一次很慢，之后流畅 | 网络、解析、纹理解码、Shader 编译 | 关闭缓存重载，与第二次加载分开记录 |
| 动画期间持续卡顿 | 帧耗时、主线程工作、GPU 负载 | 把 DPR 上限从 2 改为 1，看帧耗时是否明显下降 |
| 切换时卡一下 | 是否重复加载模型、创建材质、重新挂载 Canvas | 维持同一场景实例，只改目标状态 |
| 静止也持续消耗 | 渲染循环 | 最后再做 demand 练习 |

记录目标设备、浏览器、屏幕刷新率、DPR、画布尺寸、网络条件；再记录帧耗时。60 Hz 的帧预算约 16.7 ms，120 Hz 约 8.3 ms；不能只看平均 FPS，忽略最慢的一批帧。当前没有真机性能实测，不把上述预算写成“已经达标”。

### 进阶练习：静止时停帧

当前项目尚未实现按需停帧。完成前面的行为检查后再改 `frameloop="demand"`，并补齐：

1. 姿态或环境变化时请求第一帧。
2. 指针输入改变 ref 时调用 `invalidate()`，因为 ref 变化不会自动通知 React。
3. 动画时间、中心、朝向、复位偏移或惯性尚未收敛时继续请求下一帧。
4. 接近阈值后吸附到准确目标并停止请求；手势中断也要重新判断是否还需渲染。

`invalidate()` 请求的是将来的渲染，不是立即把画面画出来。只改 Canvas 的参数会让动画停住。按需渲染的完整原理见 [R3F Scaling performance](https://r3f.docs.pmnd.rs/advanced/scaling-performance)。先把此项作为独立练习，避免把加载、动画、事件和优化一次混改。

已有的运动检查可运行 `npm run check:interaction`，覆盖限位与反向、30/60/120 Hz 惯性与吸附、上下回正、零位移事件、停稳释放、取消和复位中接管。它不替代浏览器与真机测试。

最后执行：

```bash
npm run check:interaction
npm run typecheck
npm run build
```

生产构建通过不代表视觉或手感通过。发布成自己的公开作品前，换成自制或已获授权的资产，并补静态预览、资源失败回退、减少动态效果偏好及目标托管环境检查。
