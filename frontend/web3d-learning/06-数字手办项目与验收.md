# 06. 完成一台数字手办，再做展示网站

毕业项目做一台自己的设备，不从整个手机博物馆开始。先把单件的视觉和操作完成度拉高，再复制成熟流程制作第二件。

## 项目范围

第一版做这些：

- 一个设备详情页，包含名称、简短介绍和操作说明。
- 一台可以旋转、缩放和重置视角的模型。
- 至少三种清楚可辨的表面：塑料、金属、屏幕。
- 一个能改变屏幕状态的模型按键，并有等价的 HTML 按钮。
- 一个与设备结构相符的机械动作；直板设备可先练独立小盖子。
- 加载提示、失败反馈与静态预览。
- 桌面与手机的实际测试记录。

相机拍照、音频播放器、多款手机、复杂系统菜单和物理碰撞先作为后续扩展。第一版不靠功能数量证明完成度。

下面是计划中的目录，跟练时逐步创建，不表示仓库已经附带这些文件：

```text
projects/phone-lab/
├── app/                     Next.js 页面
├── components/              3D 场景与普通 UI
├── public/
│   ├── models/phone.glb
│   ├── textures/screen-home.png
│   ├── hdri/studio.hdr      采用 HDRI 方案时才需要
│   └── images/phone-poster.webp
└── docs/
    ├── asset-notes.md        模型、贴图、环境与导出记录
    ├── visual-check.md       四个角度的视觉对照
    ├── performance.md        设备、网络与性能记录
    └── screenshots/          网页截图
```

`.blend` 源文件与原始贴图放在自己管理的源资产目录，不放进 `public/`。`public/` 只保留网站实际要提供的交付文件。

## 里程碑一：只做静态视觉

先完成第 02–04 章，不加动画。

1. 用真实产品照片或自己的实物确定比例和三种主要材质。
2. 导出未压缩基线 GLB，保留源文件。
3. 在网页建立一个固定主视角和三组检查视角。
4. 按轮廓、材质、反射、色彩、贴图细节的顺序修正。
5. 在相同尺寸下保存 Blender 与网页对照图，写清仍然存在的差异。

验收看具体结果：金属不会一直灰暗；塑料有合理的柔和高光；关机屏幕有反射；图标近看清楚；模型转向后仍成立。

判断每项时使用三个状态：未成立、局部成立、稳定成立。例如只有主视角看起来像金属，就记“局部成立”。主要材质在四个视角都稳定成立后再扩展特效。

## 里程碑二：完成最小可玩链路

沿第 05 章完成：

```text
按键 → 状态切换 → 屏幕改变
开合按钮 → 目标变化 → 部件沿轴心运动
```

实际执行以下动作，而不只是检查有没有相关代码：

| 动作 | 预期结果 |
|---|---|
| 连续开关机十次 | 状态一致，没有重复材质、重复事件或闪烁 |
| 在模型上拖动后松手 | 正常旋转，不频繁误触按键 |
| 从背面点击外壳 | 不穿透触发正面的按钮 |
| 动画未结束时反向操作 | 向新目标运动，轴心和范围不变 |
| 使用 Tab 与 Enter 操作网页按钮 | 能完成等价的开关机和开合 |
| 重置视角 | 相机和 OrbitControls 的 target 同步恢复 |

第一版只使用一种相机控制器。以后增加镜头演出时，要明确动画期间由谁控制相机，避免 OrbitControls 和另一段动画同时写位置。

## 里程碑三：控制成本

先测再优化。以下是本项目的**初始预算建议**，不是行业标准，也不是参考站的实测数据。

| 项目 | 第一轮目标 | 记录方式 |
|---|---|---|
| 初次需要下载的 3D 资产 | 模型、贴图和环境合计先争取约 5–10 MB | 浏览器 Network，禁用缓存后记录；另记 JS 体积 |
| 贴图 | 多数先用 1K–2K，近景确实需要时再提高 | 记录每张图的尺寸与用途 |
| 桌面交互 | 常用设备争取稳定在约 60 fps | 记录设备、窗口尺寸与持续旋转表现 |
| 手机交互 | 自己选定的测试机争取稳定在 30 fps 以上 | 真机连续操作，并观察发热和卡顿 |
| 画布 DPR | 从 `[1, 1.5]` 开始 | 对比轮廓清晰度、帧率与耗电 |

FPS 不只由三角面数量决定。分辨率、透明层、阴影、材质数量、纹理与后处理都会影响性能。

压缩后的文件大小也不等于显存开销。例如未压缩的 2048 × 2048 RGBA 纹理基础像素约占 16 MiB，带完整 mipmaps 大致再增加三分之一；一张下载很小的 JPEG 仍可能解码成大纹理。

按症状优化：

| 症状 | 优先动作 |
|---|---|
| 下载慢，但转动顺滑 | 去掉未使用资产，降低不必要的图片尺寸，检查请求与缓存 |
| 桌面顺滑，手机卡 | 先降低 DPR，关闭昂贵透明与后处理，降低阴影成本 |
| 静止也持续发热 | 改成按需渲染，检查隐藏页面是否仍更新 |
| 近看纹理模糊 | 核对 UV 与纹理像素分配，再判断是否需要提高分辨率 |
| 文件小但首屏仍慢 | 分开记录下载、解码、着色器编译和首帧，不只看体积 |

### 分清几何压缩与纹理压缩

Draco / Meshopt 主要处理几何等数据，不能解决所有纹理成本。KTX2 / Basis 面向 GPU 纹理压缩，需要匹配的加载器支持和转码资源。先保留未压缩基线，再逐项引入，别让“变小”与“变坏”同时发生而无法定位。

可以先用 [glTF Transform CLI](https://gltf-transform.dev/cli) 只读检查模型：

```bash
npx @gltf-transform/cli inspect public/models/phone.glb
```

优化时输出新文件，不覆盖唯一原件。不要盲目合并带交互的按键或删掉铰链 group。每次优化都要重新检查外观、节点名称、动画、加载器与手机表现。

### 静止时停止反复渲染

第 03 章的样片使用 `frameloop="demand"`；第 05 章为了先跑通每帧动画切到 `always`。最终可以回到 demand，但必须主动请求动画期间的帧。

对 `hinge.tsx` 做两处修改：导入增加 React 的 `useEffect` 与 R3F 的 `useThree`；在 `useFrame` 前添加：

```tsx
const invalidate = useThree((state) => state.invalidate);

useEffect(() => {
  invalidate();
}, [opened, invalidate]);
```

然后在原 `useFrame` 的阻尼赋值后添加：

```tsx
if (Math.abs(hinge.current.rotation.x - target) > 0.001) {
  invalidate();
} else {
  hinge.current.rotation.x = target;
}
```

状态变化请求第一帧，动画没到终点就继续请求，结束后停止。Drei 的 OrbitControls 会为自己的交互触发更新；直接修改对象时则需要你处理失效通知。[R3F 按需渲染](https://r3f.docs.pmnd.rs/advanced/scaling-performance)

**检查点**：静止时不持续刷帧；开合完整播放；旋转仍然顺滑。不要只加上 demand 就以为动画也会自动持续。

## 里程碑四：把场景交付成网站

1. 保留设备介绍和 HTML 操作区，让它们不依赖 3D 成功加载。
2. 用自己作品的截图制作静态预览，先显示预览，再加载 3D 模块。
3. 区分“准备 3D 代码”“加载模型资源”“失败”三种状态。按请求数量统计的进度不等于按字节统计的下载进度，先用文字提示也可以。
4. WebGL 不可用或资源失败时保留静态预览与介绍。失败重试不能无限循环。
5. 调整手机布局：画布高度合理，按钮好点，不拦截整页所有触摸滚动。
6. 对偏好减少动态效果的用户关闭自动旋转和装饰动画；仍保留主动操作。
7. 在目标托管环境构建并检查 GLB、HDRI、纹理路径，尤其是路径大小写和资源响应。

发布前运行项目的类型检查、lint 与 build。再执行三种访问：正常首次访问、限速访问、故意缺失模型资源。最后在真机上关闭再打开页面，测试屏幕方向切换与多次进入。

## 什么时候扩展成博物馆

第一件设备完成后再做第二件。第二件重点验证流程是否可复用：更换资产、配置主视角和操作项即可，不必复制一整套渲染代码。

先用静态图片做列表卡片，进入详情再加载对应模型。不要给每张卡片都创建一个持续运行的 Canvas。

最后留下三份能复用的东西：资产交付清单、棚拍场景配置、交互组件。做到这里，才有了继续制作同类高完成度作品的稳定方法。
