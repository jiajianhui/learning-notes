# 13. 未来网站开发展望：从前端地图走向完整网站

## 问题背景

这套文档的最终目标，不是让你背前端名词。

你的长期目标是：

```text
独立完成一个网站开发。
```

后端方向已经确定：

```text
Node.js + Express
```

你又长期写 Swift，所以自然会问：

```text
前端是不是应该默认用 TypeScript？
```

本文属于第七层：学习方法层。它不讲后端教程，只把前端地图和未来网站目标接起来。

主线先记这一条：

```text
先建立前端地图
-> 再做纯前端小项目
-> 再接 Express API
-> 最后按真实网站需求选型
```

---

## 核心解释

### 1. 当前阶段和未来阶段不同：现在先建立判断力

当前阶段：

```text
建立前端技术地图
知道每层解决什么问题
能看项目文件判断技术栈
用 minimal-frontend-demo 练小功能
```

未来阶段：

```text
明确网站需求
做前端技术选型
搭建前端项目
调用 Express API
完成真实网站
```

所以现在先别急着定最终技术栈。先建立判断力。

---

### 2. 前后端边界先这样理解：前端管界面，Express 管 API

在你的方向里，最清楚的边界是：

```text
前端：页面、组件、交互、路由、状态
后端 Express：API、业务请求处理
前后端通信：HTTP
```

关系图：

```text
浏览器
  ↓
前端应用
  ↓ fetch / axios
Express API
```

---

### 3. TypeScript 对你很值得默认使用：做项目时更稳

不是绝对“一定”，但对你来说，TypeScript 很适合作为默认项目选择。

| Swift 经验 | TypeScript 里的对应价值 |
|---|---|
| 明确类型 | 函数参数、接口数据、组件 props 更清楚 |
| 编译期提示 | 提前发现字段和参数错误 |
| 结构化建模 | 用 `type` / `interface` 描述数据 |
| 重构依赖 IDE | 类型系统帮助发现影响范围 |

但顺序仍然是：

```text
学习时先懂 JavaScript
做项目时默认 TypeScript
```

TypeScript 不是跳过 JavaScript 的捷径。

---

### 4. Next / Nuxt 不要现在默认选：看网站类型再决定

如果未来网站是：

```text
后台管理
强交互工具
前后端分离清楚
主要调用 Express API
```

可以先考虑：

```text
Vite + TypeScript + React/Vue + Express
```

如果网站非常重视：

```text
SEO
内容页面
首屏 HTML
静态生成
页面级结构
```

再讨论：

```text
Next.js + React
Nuxt.js + Vue
```

别为了“高级”上应用框架。

---

## 技术关系

### 一个可能的长期组合

```text
前端：Vite + TypeScript + React 或 Vue
后端：Node.js + Express
通信：HTTP API
```

各自负责：

| 部分 | 负责什么 |
|---|---|
| 前端 | 页面、组件、交互、路由、状态 |
| Express | API、请求处理、业务接口 |
| TypeScript | 降低前端维护成本，也可用于后端 |
| Vite | 前端开发服务器和打包 |

后面项目变大，再考虑前后端类型约束是否要更系统。

---

## 学习建议

未来路线可以分四步：

```text
1. 建立前端地图
2. 做纯前端小项目
3. 接入 Express API
4. 根据真实网站需求再选型
```

现在最该避免的问题：

```text
我现在必须选 React 还是 Vue？
我现在必须上 Next 吗？
我是不是必须全栈 TypeScript？
```

更好的问题：

```text
我要做的网站是什么类型？
页面和交互复杂到什么程度？
前端怎样调用 Express API？
哪些技术现在必须学，哪些可以以后学？
```

---

## 小结

你的最终目标可以这样表述：

```text
以 Node.js + Express 为后端基础，
逐步掌握现代前端体系，
最终独立完成一个网站开发。
```

结合 Swift 背景，TypeScript 很适合作为默认选择；但学习上仍然要先理解 JavaScript。
